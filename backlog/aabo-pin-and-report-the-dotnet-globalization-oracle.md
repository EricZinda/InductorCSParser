# Pin and report the .NET globalization oracle

The differential Unicode tests currently describe `.NET 8` as a single stable oracle, but `string.Normalize` can run against system ICU, app-local ICU, Windows NLS, or invariant globalization depending on the host and runtime configuration. System ICU and NLS data can move independently of the target framework, so an otherwise unrelated CI image or operating-system update can silently change the normalization behavior being used to define “matches .NET.” `StringInfo` segmentation uses the runtime's own implementation and data, so record it separately rather than assuming its provenance is identical to normalization's.

Define the compatibility rules precisely. Keep the bundled Unicode 15.0 implementation plus the official UAX #15 and UAX #29 corpora as the standards oracle. For the .NET-compatibility oracle, pin the exact .NET 8 runtime used by CI and choose one canonical normalization backend, preferably a specific app-local ICU package/version with NLS and invariant globalization explicitly disabled. If Windows NLS is a supported deployment, run it as a named additional matrix job instead of allowing the host to select it silently.

At test startup, fail with an actionable diagnostic when the canonical job is using the wrong backend or runtime, and print the exact framework, operating system, globalization mode, and ICU/NLS version information available. Keep the full-scalar and randomized bundled-versus-runtime differential tests, but label their result with that environment so a failure says which oracle changed. Include a deliberate test of the U+FFFE runtime quirk without using it as evidence that U+FFFE is ill-formed Unicode.

Done when CI reproducibly selects and verifies its canonical .NET 8 globalization configuration, any additionally supported backend has an explicit matrix job, test output identifies the active oracle, and documentation distinguishes standards conformance from compatibility with that pinned .NET environment.
