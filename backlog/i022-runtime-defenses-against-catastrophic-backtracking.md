- Runtime defenses against catastrophic backtracking
    - Current state: None. A pathological grammar/input combination will spin forever. The library has no MaxRuleInvocations, no MaxDepth, no Timeout, no CancellationToken support. For any use case that touches untrusted input (editor plugins parsing user files, server-side parsing, anything exposed to the web) this is a ReDoS-shaped hole.
    - Design from docs/ProgrammingModel.md (the "Catastrophic Backtracking Design" section spends real effort on this):
        - `ParseOptions.MaxRuleInvocations` (default 10_000_000): deterministic work limit. Every rule invocation increments a counter; when it trips, the parse aborts.
        - `ParseOptions.MaxDepth` (default 1000): recursion-depth limit to prevent stack overflow on inputs like `((((...))))`. Tracked via a depth counter on ParseContext or the lexer.
        - `ParseOptions.Timeout` (no default): wall-clock limit, polled from inside the parse loop using Stopwatch (NOT via CancellationTokenSource.CancelAfter, which needs a timer thread that WebGL doesn't have).
        - `ParseOptions.CancellationToken`: standard .NET cancellation; polled alongside the timeout.
    - When any budget trips, a single internal `ParseBudgetExceeded` exception unwinds through the rule stack (every transaction's `using` rolls back the lexer on the way up) and `Parse()` catches it at the boundary, converting to a `ParseResult` with Outcome set to `Timeout`, `WorkLimitExceeded`, `DepthLimitExceeded`, or `Canceled` as appropriate. These outcomes already need to exist in the ParseOutcome enum.
    - The budget check runs every N invocations (not every one) so the overhead stays invisible on well-formed input.
    - WebGL constraint: the time-polling has to use `Stopwatch.Elapsed`, not Timer-backed mechanisms, because WebGL has no timer thread. The rationale is in the doc.
    - Priority: Ship before anyone parses untrusted input through this library.
    - Done when: the three budgets are enforced, ParseOutcome distinguishes the four abort reasons, a test demonstrates a pathological `OneOrMore(OneOrMore(A))` grammar aborting under the work limit instead of hanging.
