# IL2CPP: string.Normalize on Unity's Mono diverges from .NET, ~93 tests fail

- Where this came up: the first IL2CPP run after the bundled UAX #29 segmenter landed (2026-07-11). Vendoring segmentation took the pass from all 2,426 discovered tests failing on one TypeInitializationException to 7,187 discovered with about 93 failures, and every remaining failure traces to the next runtime dependency: `string.Normalize`. The parser normalizes grammar text at Compile and input at Parse with the runtime's `Normalize`, and Unity's Mono implementation doesn't behave like .NET 8's.

- The two flavors, with the failing tests as the inventory:
    - **Compatibility forms don't convert.** Mono's `Normalize(FormKC/FormKD)` leaves at least ligatures unexpanded: U+FB01 stays one grapheme instead of becoming "fi", so Compile never reports the normalization offender the tests expect, and FormKC-matching grammars don't match. About 44 failures: the `CompatibilityMultiGraphemeExpansion` matrix rows across the five leaf-rule fixtures (32), the ligature one-offs in `NormalizationTests` (`Nfkc_collapses_*`, `FormKC_converts_ligature_*`, `FormKD_converts_ligature_*`, `SourceRange_under_FormKC_*`), the compatibility compile-error tests in `GraphemeRuleTests` / `OneOfRuleTests` / `NoneOfRuleTests` / `WithErrorTests`, and the `Identifier_rejects_body_extra_*` cases in `XidIdentifierTests` (two of which fail under FormD too, so at least one canonical decomposition also differs).

- Verified evidence (not inference). The failure messages in `test-results/il2cpp-playmode-results.xml` from the 2026-07-11 player run contain the actual `Normalize` output on the player:
    - `"ﬀoo".Normalize(FormKC)` returned `"ﬀoo"` unchanged (U+FB00, BMP), expected `"ffoo"` (`Nfkc_collapses_latin_ff_ligature_to_two_letters`).
    - The mathematical-bold string `"𝐟𝐨𝐨"` (supplementary plane) came back unchanged under FormKC, expected `"foo"` (`Nfkc_collapses_mathematical_bold_to_ascii`).
    - `"≠".Normalize(FormD)` didn't decompose to `= + U+0338` even though that mapping is canonical, not compatibility (`Identifier_rejects_body_extra_that_decomposes_under_the_form(FormD)`).
    - Meanwhile Latin-1 canonical mappings (the é rows) and Hangul decomposition (algorithmic, not table-driven) passed, so `Normalize` is partially working, not a wholesale no-op. That's what makes it dangerous: simple spot checks look fine.
    - The same six `XidIdentifierTests` failures reproduce in the Unity *editor* on Mono JIT (no IL2CPP involved), with byte-identical messages, so this is Unity's Mono class library, not an IL2CPP conversion artifact. Repro: `Unity.exe -batchmode -nographics -projectPath src/InductorParser.Tests/Unity -runTests -testPlatform PlayMode -testFilter "InductorParser.Tests.XidIdentifierTests" -testResults <path>` (about a minute, no player build).

- How a .NET API can behave this way (citations):
    - `string.Normalize` has never been one implementation. Windows .NET Framework calls the OS NLS functions, .NET Core calls ICU, Mono ships its own managed implementation with its own tables, and data-less .NET flavors degrade to identity. Microsoft's own tracker acknowledges the divergence: "string.Normalize(NormalizationForm.FormKD) behaves differently on different platforms" (https://github.com/dotnet/runtime/issues/12452), and browser WASM lacks the compatibility forms entirely (https://github.com/dotnet/runtime/issues/117116).
    - .NET's globalization-invariant mode documents the degraded behavior we observed as a designed-in possibility for the whole family: "If the app requested to normalize any string, the original string is returned without modification", and `IsNormalized` always answers true (https://github.com/dotnet/runtime/blob/main/docs/design/features/globalization-invariant-mode.md).
    - Unity's player class libraries come from Unity's Mono fork, where `string.Normalize` is `Mono.Globalization.Unicode.Normalization`, a managed implementation whose data arrives through the `load_normalization_resource` internal call (https://github.com/Unity-Technologies/mono/blob/unity-main/mcs/class/corlib/Mono.Globalization.Unicode/Normalization.cs). Two structural facts in that source explain two of the observations directly: its `QuickCheck(char c, ...)` classifies one UTF-16 code unit at a time, so supplementary-plane characters (each two code units) can never match a mapping and always pass through, and the file contains no throw statements at all, so the ArgumentException that .NET documents for "invalid Unicode characters" (https://learn.microsoft.com/en-us/dotnet/api/system.string.normalize) can't happen on any input.
    - Under IL2CPP the same managed code runs against tables baked into libil2cpp (`load_normalization_resource` hands back static arrays from `il2cpp-normalization-tables.h`, see the mirror at https://github.com/dreamanlan/il2cpp_ref/blob/master/libil2cpp/icalls/mscorlib/Mono.Globalization.Unicode/Normalization.cpp). Which layer drops the BMP mappings that .NET applies (the shipped tables or the managed lookup path) is still an open question. The observed behavior above is the ground truth either way, and it's identical in editor Mono and the IL2CPP player.
    - **Ill-formed input doesn't throw.** The parser's MalformedInput detection relies on `string.Normalize` throwing ArgumentException on unpaired surrogates (and on U+FFFE): `Rule.Parse` catches the throw and reports `MalformedInput` with a position from `FindFirstUnnormalizableIndex`. Mono's `Normalize` doesn't throw on this input, so on Unity the ill-formed input flows on into the lexer instead of being reported. About 50 failures: the `LoneSurrogateNotNormalizable` matrix rows (24), every `FormX + lone surrogate` / `FormX + reversed surrogate pair` case in `UnexpectedUnicodeTests` (12), the `MalformedInput` tests in `SecurityByDefaultTests` and `Core` (`Ill_formed_UTF16_reported_as_MalformedInput_before_any_grammar_runs`, `Malformed_input_position_*`, `Lone_high/low_surrogate_handling`, `Noncharacter_FFFE_handling`), and the compile-side stray-literal validation tests (`Token/Literal_with_stray_surrogate_under_default_Compile_throws_clear_error`, `Multiple_surrogate_literals_*`, `Failed_compile_invalidates_touched_rules_and_refuses_recompile`).

- Why it matters beyond red tests: the ill-formed flavor is a behavior difference users hit. On .NET a default `Compile(FormC)` grammar reports `MalformedInput` for a lone surrogate in the input. On Unity the same grammar silently parses or mismatches instead. That's the security-by-default story not holding on one of the library's headline platforms.

- Fix directions, smallest first:
    1. **Own the ill-formed detection (small, fixes the ~50).** Stop relying on `Normalize` to throw: scan the input for unpaired surrogates and U+FFFE directly (the logic already exists in `Rule.FindFirstUnnormalizableIndex`) before calling `Normalize`, and report `MalformedInput` from that scan uniformly on every runtime. Needs a decision about the extra pass on the hot path, but the scan is a tight char loop and only the pre-normalization path pays it.
    2. **Vendor or verify normalization (large, fixes the ~44).** The compatibility-form tables are the bigger dependency. Options: vendor an NFC/NFD/NFKC/NFKD implementation the way the segmenter was vendored (much bigger tables, decomposition + composition + reordering logic), or document that FormKC/FormKD grammars require a UAX #15-conformant runtime and skip those tests on Unity with a runtime-capability check. The segmenter vendoring (GraphemeSegmentation.cs) is the template if vendoring wins.

- The wider picture (parked here for now, split into its own item if it grows): the library's policy is that each build's Unicode environment stays internally consistent. The net8.0 build takes segmentation from the runtime's `StringInfo`, so token boundaries, `string.Normalize`, and category data all move together at the runtime's Unicode version, and cross-machine agreement is the caller's job (run the same runtime on both ends). The netstandard2.1 build can't do that, because Unity's runtime Unicode machinery is both old and wrong, and that's where the seams live.
    - **The Unity build's normalize-then-segment seam**: on netstandard2.1 the bundled 15.0 segmenter pairs with Mono's `Normalize`, which is exactly this item's subject. Fixing normalization per the directions below is what closes it.
    - **`UnicodeCategory` data**: `TokenSet.Category(...)` and the General_Category half of the XID sets read the BCL's tables, documented in `TokenSet.Xid.cs` to track whatever Unicode version the runtime ships. On the Unity build that means Mono-era category data next to 15.0 segmentation. The hand-typed Xid spec constants are pinned at Unicode 17.0 on every build, a third version in the mix.
    - **`char.IsWhiteSpace`**: `TokenSet.InlineWhitespace` is built from it at static init, so whitespace membership tracks the runtime's White_Space property. Real precedent: U+180E MONGOLIAN VOWEL SEPARATOR left White_Space in Unicode 6.3, and the corpus comment on `MongolianVowelSeparatorText` already documents the per-runtime shift.
    - Existing tripwires: the differential tests in `GraphemeSegmentationTests` fail the moment the test TFM moves to a runtime whose `StringInfo` diverges from the bundled segmenter (GB9c will be the first), which is the prompt to regenerate the bundled table so the Unity build keeps matching contemporary .NET. `NormalizationExamplesSelfCheck` asserts the row data against the runtime's `Normalize`, and the `[Explicit]` Xid UCD tests re-derive the pinned constants.

- Repro: `./src/InductorParser.Tests/runil2cpptest.sh`, then read `test-results/il2cpp-playmode-results.xml`. The failure list should match the inventory above, and anything outside it is a new finding.

- Done when: either fix direction lands for each flavor, the IL2CPP pass runs green (or the skipped set is an explicit runtime-capability skip, not a failure), and `docs/TestArchitecture.md`'s IL2CPP section stops naming this item as the known-red set.
