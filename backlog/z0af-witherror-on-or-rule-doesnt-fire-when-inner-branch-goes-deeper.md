# WithError on Or rule doesn't fire when an inner branch consumed deeper

    - Where this came up: the Newsboat sample's `ComparisonOperator` rule wraps 12 alternatives in an Or with `.WithError("expected one of: =~, ==, =, !~, !=, <=, >=, <, >, between, #, !#")`. On input `a !! "b"` the user's intent was that the parser report something like "position 2: expected one of: =~, ==, ..." (the upstream Rust port does this via `nom`'s `expect` combinator). Instead the rewrite reports `Parse failed at offset 3: unexpected '!'.` at position 3.
    - What's happening: the branches `Literal("!~")` and `Literal("!=")` both consume the leading `!` (position 2 to 3) before failing on the trailing char (a second `!`). Each of those branch failures records a deepest-failure at position 3 with its own internal "unexpected" message. The outer Or's WithError fires at position 2 (before any branch matched). The deepest-failure tracker picks position 3 (deeper) over position 2 (shallower), and the message that got recorded at position 3 is the inner-branch one, not the outer Or's WithError.
    - Why this is friction: WithError is the mechanism for "name the rule for the user's error." Users put it on the OUTER rule because that's where they have a name (`expected an operator`, `expected a value`, `expected a semicolon`). The current behavior is "WithError fires only if no inner branch consumed further than the outer rule's start." That's almost never true for Or-of-Literals where the alternatives share a prefix. The WithError ends up dead code for the case it was added for.
    - The compounding issue is that the position reported (3) is a half-consumed-`!~`-or-`!=` position that's hard to explain to a human. The user types `a !! "b"`, sees `column 4: unexpected '!'` (Inductor uses 1-based for line/column), and has to count back one to figure out the bad token actually starts at column 3.
    - Options, in order of preference:
        - When an Or rule has a WithError, prefer that error message over inner-branch deepest-failures even when the inner branch went deeper. The position can still be the deepest one (informational) but the message should be the user-named one. Probably the right fix; the user clearly stated their preferred error string by attaching WithError, the library should respect it.
        - Add a "sticky deepest-failure mode" where WithError on a parent rule overrides any descendant failure messages whose position falls within the parent's match attempt. Same idea, slightly more general.
        - Document on WithError that it only fires when no inner rule consumed further, and that operator-list grammars should put WithError on each branch instead. Cheap, doesn't fix anything, makes the workaround verbose.
    - Done when: setting `.WithError("...")` on an Or rule whose branches share a prefix produces the `WithError` message on failures inside the Or, regardless of which branch consumed deepest before failing. A test covers the operator-list shape from this sample (`a !! "b"` should report something with "expected" and "operator" in it, not "unexpected '!'").
