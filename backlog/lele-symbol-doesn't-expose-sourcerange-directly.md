# Symbol doesn't expose SourceRange directly

    - Where this came up: the SemVer sample's consumer wanted to attach line/column positions to its post-parse validation errors (a positioned error pointing at the offending major-version span when "01.2.3" is rejected). The position info already lives on the Symbol's leaves (`Symbol.TryGetCharSpan` walks them and reports parseInput-relative bounds), but `TryGetCharSpan` is `internal`, so the only way to get a position out of a Symbol from a consumer is to keep the `ParseResult` around and call `result.SourceRangeOf(symbol)`.
    - Why that's friction: a typed-AST projection (the JsonParserTyped pattern, which the SemVer Rewrite mirrors) walks the parse tree once and produces an immutable record hierarchy. The natural shape is "discard the ParseResult after projection." But if any error from the post-parse validator should carry a position, the projector has to thread the ParseResult through every recursion just to call `SourceRangeOf`. That's an extra parameter on every helper method, plus a dependency the AST itself doesn't otherwise have.
    - What other consumers want positions for: error reporting (where this came up), syntax highlighting (each AST node carries the source span it covers), refactoring tools (rename this identifier, the AST node knows its span), incremental reparse (find the smallest AST node that overlaps the edit), source-mapped code generation. Every one of them already has a Symbol in hand and wants its source range without going back to the ParseResult.
    - Why it's not already on Symbol: looks like deliberate scoping. The Symbol holds `ReadOnlyMemory<char>` leaves that point into parseInput, and `ParseResult.SourceRangeOf` does the parseInput-to-original-input translation when normalization rewrote the input. Symbol on its own doesn't know whether the input was normalized or what the normalization form was, so it can't produce original-input coordinates without the ParseResult's `_grammar.NormalizationForm` and `_input` reference.
    - Options:
        - Add `Symbol.SourceRange` that returns parseInput-relative coordinates only. Documented as "matches the original input when no normalization happened, otherwise these are coordinates into the normalized form." Cheap to add (TryGetCharSpan is the implementation already), and for the common case of grammars that don't normalize, the answer is exactly right. Consumers that DO normalize keep using `result.SourceRangeOf`. Probably the right tradeoff: the simple case gets simple, the hard case stays explicit.
        - Add `Symbol.SourceRange` that needs the original input passed in, like `symbol.SourceRange(originalInput, normalizationForm)`. Forces callers to remember the form they normalized with. Verbose at the call.
        - Make `TryGetCharSpan` public. Lowest-effort. Callers do their own translation. Loses the encapsulation `SourceRangeOf` provides. Worst form.
        - Threading the ParseResult through projection code is what the SemVer sample does today. Works, but it's friction every consumer hits.
    - Recommend the first option (parseInput-relative `Symbol.SourceRange` with a clear doc note about normalization). It covers the common case, the docs explain the harder case, and a power user can always go back to `result.SourceRangeOf` for the translated coordinates.
    - Done when: `Symbol.SourceRange` returns a `SourceRange` for any leaf-anchored Symbol, with the parseInput-relative semantics documented in the property's `<summary>`. Tests cover an unnormalized grammar (parseInput == input, ranges match) and a normalized grammar (parseInput != input, the property gives parseInput coordinates and the doc says so). The SemVer sample's consumer drops its ParseResult-threading and uses `Symbol.SourceRange` directly, since it doesn't normalize.
