- SM Step_ScanUntilFast still rune-scoped after the recursive engine moved to grapheme-scoped checks
    - Backlog 7scu fixed the recursive engine's `ScanUntilRule` so its stopper and escape-start checks operate on whole grapheme clusters, the same unit every other rule uses. The state-machine engine's equivalent in `ExperimentalSrc/InductorParser/StateMachine/Stepper.cs:Step_ScanUntilFast` (around line 805) is still rune-scoped. It calls `stopperSet.Contains(runeValue)` against the first rune of the cluster and matches the escape start with `runeValue == spec.EscapeStartRune` without checking that the cluster is exactly one rune long. So the SM and recursive engines diverge on inputs where the cluster's first rune is a stopper or escape but the cluster as a whole isn't (a `'"'<U+0301>` cluster, a `\<U+0301>` cluster, a CRLF cluster against a single-rune `\r` stopper).
    - Fix shape, mirroring `ScanUntilRule.TryParseRule`: pull the cluster length once per iteration via `Lexer.PeekTokenLength(pos)` (or do the surrogate-pair plus extending-character walk inline if the SM wants to avoid the StringInfo call); test the stopper with `stopperSet.ContainsToken(input.AsSpan(pos, tokenLen))`; gate the single-rune escape-start fast path on `tokenLen == runeLen && runeValue == spec.EscapeStartRune`; advance the body fall-through by `tokenLen` instead of `runeLen`. The cross-engine compare tests in `ExperimentalSrc/InductorParser.Tests/StateMachineE2ECompareTests.cs` and `StateMachineGrammarCompareTests.cs` will fail on the divergent inputs once both ends produce ParseResults; those failures are the fix's verification.
