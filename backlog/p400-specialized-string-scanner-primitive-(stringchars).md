- Specialized string-scanner primitive (StringChars), closes the gap to Parlot
    - Current state: InductorJsonParser.cs:50-58 expresses JSON string content as `ZeroOrMore(Or(literalChar, escapeSequence))`. Per character, that runs through one Or, one BetweenInclusive iteration, one RuneIn, plus a transaction, a Lexer.Read, and a leaf Symbol allocation. Parlot's Terms.String(Double) is one hand-written method that scans the entire string body in a tight loop, decodes escapes inline, and returns one value. The benchmark gap is concentrated here: Parlot at 2.5x SystemTextJson, InductorParser at 29x, on inputs dominated by string content.
    - Why now: Tiers p100-p300 reduce wrapper overhead and allocation but leave the per-character work intact. To compete with Parlot, we need to collapse "loop over chars in a string body, decoding escapes" from N rule invocations to one. This is a new primitive, separate PR, only worth doing once p100-p300 have shipped and we know the remaining gap is genuinely the per-char inner loop.
    - Design: New factory `Rules.StringChars(RuneSet literal, IReadOnlyDictionary<Rune, Rune> simpleEscapes, bool unicodeEscape)` (or similar shape; exact API needs design pass). Produces a leaf rule that scans runes in a loop: if the next rune is in `literal`, advance and continue; if it's the escape lead-in (typically `\`), consume the escape and decode it; else stop matching and return one leaf Symbol covering the matched range. The decoded content needs to live somewhere, either a separate buffer attached to the Symbol, or the leaf Symbol carries both the source slice (for round-trip) and the decoded value (for consumers). This is the design fork: do we materialize decoded text eagerly (Parlot's choice) or lazily?
    - Optional, not replacing: The existing per-char Or pattern stays available. Grammars that want every char as its own leaf in the tree (syntax highlighters, LSPs that want per-token positions) keep using the current shape. Grammars that just want the decoded string opt into StringChars.
    - Edge cases: How does the position metadata work; does the leaf Symbol hold the source span as `ReadOnlyMemory<char>` (consistent with current leaf design at Symbol.cs:34) and decode on demand, or hold the decoded string directly? The current design strongly prefers source slices to avoid copies; following that pattern means callers get the original input bytes back from ToString(), and decoded text comes from a separate Decode() method or property. Round-trip verification in --spot-check still works because the source slice is preserved.
    - Done when: Rules.StringChars exists with a documented API; InductorJsonParser.cs is updated to use it for the JSON string body; benchmark shows Mean for Big/Long/Wide drops significantly toward Parlot's range; round-trip spot-check still passes byte-for-byte; existing per-char Or pattern still works for grammars that want it.
    - Verification: Same harness as the previous tiers, but pay attention to the Mean column for Big/Long/Wide specifically (these are string-heavy shapes). Compare InductorParser's ratio to Parlot's; the question this tier is answering is "how close to Parlot can we get on the string-heavy shapes." Also verify with `dotnet run -c Release --project src/Benchmarks/Benchmarks.csproj -- --spot-check` that round-trip is still byte-perfect, since the new primitive changes how string content is represented in the tree.
