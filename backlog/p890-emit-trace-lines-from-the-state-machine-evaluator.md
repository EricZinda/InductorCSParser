- Emit trace lines from the state-machine evaluator
    - Current state: the recursive engine emits trace lines at rule success / failure (Rule.cs:205-253, via `TraceSuccess` / `TraceFailure`) and at lexer-level events (Lexer.cs:204-220, via `WriteTraceLine`). `TraceSink` and `TraceLevel` on `ParseOptions` gate the output. The Stepper has zero trace hooks: it's pure computation. The lexer-level traces (advance, scanner skip) do fire under the SM because both engines share the same `Lexer` instance, but rule-level enter / exit / outcome are silent. So a TracingTests run against the SM sees lexer noise but none of the rule structure that the recursive trace records.
    - Recommended path: extend the Lowerer (src/InductorParser/StateMachine/Lowerer.cs) to embed a per-call rule reference (or its name + id) into the CompiledProgram (src/InductorParser/StateMachine/CompiledProgram.cs). A parallel array keyed by call instruction index works: at each `Call` opcode the Stepper can index into the array to get the source `Rule` for that call. In the Stepper, on `Call` / `ReturnSuccess` / `ReturnFailure` call `lexer.WriteTraceLine(...)` with the rule name and outcome, gated by `lexer.IsTracing(level)` so the cost stays at one bool check per opcode when tracing is off. The lexer-level traces (advance, scanner skip) already happen unchanged.
    - Open question (settle inside this item, not the plan): TracingTests.cs probably asserts on specific trace-line text. The SM's call structure isn't isomorphic to the recursive call tree because the lowerer collapses several recursive shapes into single opcodes (BetweenInclusive, fused-scan ScanOneOfRune / ScanNoneOfRune, FirstOf first-rune-skip), so the trace output won't be byte-identical even with matching emit points. Two paths: (a) make the SM produce trace text that matches the recursive output line-for-line, which means re-expanding collapsed opcodes back into virtual rule entries solely for trace purposes; (b) loosen TracingTests to assert on the structurally important content (rule names visited, outcomes, level-gating respected) rather than exact strings. Path (b) is cheaper and produces a fixture that's actually meaningful for both engines. Decide after reading the asserts in TracingTests.cs.
