- Skip Symbol.FlattenInto on trees that cannot contain Flatten or Delete wrappers
    - Current state: `Symbol.FlattenInto` is the user-facing helper that applies the flatten pass to a hand-built tree. Inside `Rule.Parse` the pass is no longer invoked (the p800-line lift-up work makes the default `ParseResult.Tree` already flat), so the only callers left are user code operating on trees they constructed themselves. FlattenInto still walks and allocates unconditionally, even on subtrees whose descendants are all None-typed and contain no Delete or Flatten nodes — in that case the pass rebuilds every None composite into an identical new Symbol + new List<Symbol>, for no effect on the output.
    - Recommended path: cache a single bit per Rule at Compile time: "could any rule reachable from me ever emit a Symbol with FlattenType.Flatten or FlattenType.Delete?" For grammars whose composites are all Or (already removed at parse time) and whose leaves are None-typed with Delete Chars stripped at parse time, the answer is no. When the answer is no, Symbol.FlattenInto on a subtree rooted at such a Symbol is a no-op modulo the `result.Add(this)` — no walk, no allocation. When the answer is yes, fall back to the current walk.
    - Interaction with parse-time lift-up: the p800 lift-up work makes the `Rule.Parse` tree already flat, so the short-circuit is most valuable for user code that calls `Symbol.FlattenInto` on a manually built tree (the intended remaining use case). The identity-preservation optimization already added to FlattenInto's None branch covers the common "nothing lifted under me" case at runtime without Compile-time analysis, so this backlog item is the follow-on that avoids the walk entirely rather than just the Symbol allocation.
    - Design sketch: on Rule, add `internal bool CanEmitFlattenOrDelete` populated during the existing Compile ComputeRuleStart pass (it already does a depth-first post-order walk, so children's bits are populated before the parent is consulted). The bit is: `FlattenType == Flatten || FlattenType == Delete || Children.Any(c => c.CanEmitFlattenOrDelete)`. Expose the bit on Symbol via a new static query: callers who built Symbols from a known Rule can pass the rule (or its id) to a FlattenInto overload that short-circuits. The `FlattenInto(List<Symbol>)` no-arg-overload stays as-is to preserve the "safe default" behavior when the caller has no Rule in hand.
    - Edge cases: LateBoundRule has to propagate the bit from its target (set after Bind runs, checked during Compile validation). User-defined Rule subclasses default to true (pessimistic; we don't know what they'll emit). Recursive grammars need the Compile cycle-detection path that ComputeRuleStart already uses — leave cycle-cut nodes at true (safe fallback).
    - Impact estimate: Low, because the target population (user code calling Flatten on a manually built tree) is small and the identity-preservation optimization already covers most of the saved work. Would shine on a future `ToSyntaxTree(Rule, Symbol)` API that wants to collapse a PreserveFlattenWrappers=true debug tree into the default syntax tree for inspection.
    - Done when: the Compile pass populates the bit, Symbol gains a gated FlattenInto overload (or equivalent), and a test verifies that a grammar whose tree is already-flat walks a post-parse FlattenInto in O(1) rather than O(n). Benchmark-wise there is no JSON number to move because the lift-up work moved it; this item is measured by the walk count on user-constructed trees, which would need a synthetic bench.
    - Note: this item does not replace the identity short-circuit already in Symbol.FlattenInto (which reuses `this` when a None-typed composite's children come back unchanged). The two are complementary: identity short-circuit skips the allocation, this item skips the walk.
