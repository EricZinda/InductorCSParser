- Refactor Step 2: Collapse to one lexer
    - Context: today the parser ships two lexers, `RuneLexer` and `GraphemeLexer`, selected at parse time via `ParseOptions.InputUnit`. They differ in exactly one method (`NextTokenLength`); everything else lives in a shared `Lexer` base. ~95% of grammars use the default (Grapheme). The choice leaks into many user-facing names (`RuneLexer`, `GraphemeLexer`, `InputUnit`, `ErrorRuneIndex`, `{runeIndex}` placeholder) and the docs spend a section explaining "why two lexers" before users have written a grammar. Step 2 collapses to one lexer that always walks `StringInfo` text elements. The Rune-mode use cases that survive are reachable through `WithinGrapheme(rule)` (renamed in Step 4), which already exists today and forces rune-level walking inside one grapheme.
    - The lexer code: inline the grapheme path into `Lexer.cs`, drop the `NextTokenLength` virtual dispatch. Keep the ASCII fast paths in `AdvanceUntilRuneIn` and `AdvanceWhileSingleRuneIn` unconditionally — ASCII chars are tokens-of-themselves under grapheme tokenization, so `IndexOfAny` on an ASCII set is safe. The grapheme-aware path added in Step 1 (`AdvanceWhileIn(RuneSet)` for sets with multi-rune entries) stays as is.
    - Position reporting: drop `ErrorRuneIndex` from `ParseResult`, drop `RuneIndex` from `SourcePosition`, drop `ToRuneIndex` from `SourcePositionConverter`. Drop the `{runeIndex}` placeholder from `ParseOptions`. The grapheme/character index keeps its current name (`ErrorGraphemeIndex`) — it gets renamed in Step 4. Position model after this step has four units: Char (UTF-16), Line, Column, Grapheme.
    - Selection plumbing: delete `InputUnit.cs`. Drop `ParseOptions.InputUnit`. Drop the ternary in `Rule.ParseRecursive` (lines 549-551 of `Rule.cs`). In `StateMachineParser.cs`, drop the dual pooled lexers (lines 568-595) and keep just one pooled lexer.

Decide before starting the step.
