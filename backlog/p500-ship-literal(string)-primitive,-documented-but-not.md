- Ship Literal(string) primitive, documented but not implemented
    - Current state: The docs treat `Literal(string)` as a shipped primitive. docs/ProgrammingModel.md:45 lists it in the primitives table alongside `Char`; docs/ProgrammingModel.md:331-333 gives the pseudocode ("`_tokenizedLiteral` precomputed, foreach expected in loop"); docs/ProgrammingModel.md:356 describes the semantics ("Same pre-tokenize-then-lockstep logic as `Char`; the difference is that `Literal` accepts any length"); docs/Recipes.md:19-21 uses `Literal("**")` in the bold-text recipe; docs/UnicodeGotchas.md:21-24 defines a `LiteralIgnoreCase(s)` helper on top of it; docs/TestArchitecture.md:58 says "Future: `Literal`". But src/InductorParser/ has no `LiteralRule.cs` and Rules.cs has no `Literal` factory. Grammars that want word-matching today write `And(Char('m'), Char('a'), Char('j'))`, which is N rules and N lexer transactions per word. The existing `Char(string grapheme)` factory at Rules.cs:34 validates the string is exactly one grapheme, so it's no substitute.
    - Why now: The UnityTabs chord-grammar POC at src/InductorParser.Tests/E2EExamples/ChordGrammarTests.cs measures the grammar at ~21x slower than a compiled regex. Every Or branch in the chord grammar contains a `CiWord` helper that expands a 3-char literal into 3 `RuneIn` rules, each with its own transaction begin/rollback. The recent p300 Or-wrapper optimization on origin/master moved the chord-grammar ratio from 21.72x to 21.01x, essentially no change, because the per-char transaction overhead dominates, not the wrapper allocation. `Literal` collapses a word match from N transactions to one.
    - Design: New `LiteralRule : Rule` and `Rules.Literal(string value)` factory. At construction, reject empty strings (matches nothing reliably is worse than the alternative of "always succeeds zero-width," and the Char(string) rule already rejects empty). The pre-tokenize step needs the lexer's InputUnit, which isn't known until Parse; options are (a) pre-tokenize both ways at construction and pick at Parse, (b) defer pre-tokenize to first Parse and cache per InputUnit, (c) pre-tokenize to runes always and let the lexer adapt. Pick (a) for simplicity and because literals are typically short; cost is one string-segmentation walk per lexer variant at construction, which is cheap. At parse time: one transaction, lockstep read-and-compare loop, one leaf Symbol on success covering the whole matched range. Position on mismatch is the start of the specific failing token, not the start of the whole attempt (the rule from docs/ProgrammingModel.md:442). `LiteralIgnoreCase(string)` ships alongside as a thin wrapper per docs/UnicodeGotchas.md:21; ASCII-only case folding, matching what regex IgnoreCase does for most real grammars.
    - Edge cases: Multi-rune graphemes in the literal (`Literal("café")` with combining acute, `Literal("👨‍👩‍👧‍👦")`) need to produce the same accept/reject verdict under both lexers, which is what pre-tokenizing both ways at construction gives us. Trace output should render the literal as the original string, not the token sequence, so the trace log stays readable. Default `FlattenType`: match `Char` (Delete by default so literals don't clutter the tree), or Keep so the literal shows up as its own leaf; needs a decision consistent with what the docs already imply. WithError: the default error message should quote the literal string, not the individual failing token.
    - Impact estimate: For PEG grammars with word alternation, roughly 3x-5x per-word speedup because N transactions collapse to one. For the chord grammar specifically, the expected ratio drops from ~21x to somewhere near ~10x vs regex; closing the rest of the gap to 2x would want Or first-set dispatch on top (separate backlog item). For keyword-heavy grammars (HTTP parsers, SQL parsers), similar order-of-magnitude wins on keyword recognition.
    - Done when: `Rules.Literal(string)` exists; `Rules.LiteralIgnoreCase(string)` exists or the docs/UnicodeGotchas.md helper compiles against the public API; the recipes and examples in docs/ that use `Literal(...)` compile as-is; new `src/InductorParser.Tests/Rules/LiteralRuleTests.cs` covers single-rune literal, multi-rune grapheme literal, mismatch on first token, mismatch on Nth token with correct position, empty-input rejection, GraphemeLexer and RuneLexer parity, trace output; the chord grammar in ChordGrammarTests is rewritten to use Literal and the timing test records the improvement.
    - Verification: Run `dotnet test src/InductorParser.sln` — no existing behavior should change. Run ChordGrammarTests timing test before and after to confirm the expected ~2x improvement in the grammar/regex ratio. Run `dotnet run -c Release --project src/Benchmarks/Benchmarks.csproj` — no regression expected since the JSON grammar doesn't use Literal today (it could, for `true`/`false`/`null`, but that's a separate consumer-side change).
