- Enforce RuleCountLimit / MaxDepth / Timeout / Cancellation in the state-machine evaluator
    - Current state: `ParseOptions` declares four budget knobs (RuleCountLimit, MaxDepth, Timeout, Cancellation; see ParseOptions.cs:51-73) and the recursive engine enforces them through the lexer's `EnterRule` / `ExitRule` / `CheckPeriodicBudgets` (Lexer.cs:594-651). On a budget breach the lexer throws `ParseBudgetExceeded`, which `Rule.Parse` catches at Rule.cs:524-536 and turns into a `ParseResult.Aborted(...)`. The state machine already calls `lexer.ConfigureBudgets(options)` at StateMachineParser.cs:96 so the lexer is configured, but the Stepper itself never calls the hooks, so a state-machine parse with a tiny RuleCountLimit will not abort the way the recursive parse would. BudgetTests.cs depends on the abort behavior and fails when run against the SM today.
    - Recommended path: in the Stepper's `Call` opcode dispatch (the SM's "rule entry", at roughly Stepper.cs:854) call `lexer.EnterRule()`. That single call handles `MaxDepth` (immediate throw if depth would exceed the cap) and increments the per-rule counter that powers `RuleCountLimit`. On the matching `ReturnSuccess` / `ReturnFailure` (~Stepper.cs:878-887) call `lexer.ExitRule()` so the depth counter falls back. Periodic checks for `Timeout` and `Cancellation` are already inside `CheckPeriodicBudgets` (which the lexer fires every 1024 invocations from inside its own increment path), so no separate poll loop is needed. In `StateMachineParser.Parse` and the matching counting / matching variants, wrap `Stepper.Run` in `try / catch (ParseBudgetExceeded budget)` and return `ParseResult.Aborted(budget.Outcome, abortPos, BuildBudgetMessage(budget.Outcome), input, rootRule)`, the same shape as Rule.cs:524-536. Lift the private `BuildBudgetMessage` from `Rule` to internal so both engines share one source of truth for the abort message.
    - Edge cases: the recursive engine counts one per `TryParseRule` invocation. The SM's `Call` opcode is the lowered equivalent, so counts should agree exactly and the existing tests that trip "at exactly the same point on every run" (ParseOptions.cs:42-50) keep tripping at the same point under both engines. The `BridgeToRecursive` opcode is the trap: bridged calls trigger their own `EnterRule` inside `Rule.TryParse`, so we'd double-count if the SM also called `EnterRule` for the synthetic frame. Decide at implementation time whether the SM-side `Call` skips the hook on a bridge frame, or the bridge skips it on its own entry; one of the two has to give. The matching counting / matching entry points (TryMatch, CountMatches, EnumerateMatchSpans, CountMatchesAndCaptures, HasAnyMatch) all need the same try/catch wrap, otherwise a budget-exceeded run on those paths will throw rather than return a clean `Aborted` result.
