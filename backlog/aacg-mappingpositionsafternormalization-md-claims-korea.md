# MappingPositionsAfterNormalization.md claims Korean compatibility jamo are the only case where compatibility normalization changes the grapheme count, which is false as written

    - What's wrong: [docs/MappingPositionsAfterNormalization.md](../docs/MappingPositionsAfterNormalization.md) line 110 says "As of Unicode 16, Korean compatibility jamo are still the only case where compatibility normalization changes the grapheme count." Line 44 makes the same claim ("In Unicode 16 the only such case is the Korean compatibility-jamo example above"). The header comment of src/InductorParser/Lexing/NormalizedPositionMap.cs (lines 24-30) repeats it ("Korean compatibility jamo is the known case ... Korean jamo being the only such case in Unicode 16"). Read literally, the claim is contradicted by the doc's own easy case at line 30: FormKC turns the one-grapheme "ﬁ" into the two-grapheme "fi". And it isn't only single characters expanding in isolation. Verified on 2026-07-02 (net8.0): Thai "กำ" (KO KAI + SARA AM) is one grapheme, and both FormKD and FormKC convert it to KO KAI + U+0E4D NIKHAHIT + U+0E32 SARA AA, which is two graphemes. Lao "ກຳ" behaves the same way. U+FDFA converts to an 18-grapheme Arabic phrase. None of these involve Korean.
    - What the doc means, and should say instead: the property that makes the Korean case special isn't "the grapheme count changes", it's that graphemes *merge across an original grapheme boundary*. U+3131 and U+314F are two separate graphemes in the original, and FormKC composes their conversions into one syllable, so normalizing the original one grapheme at a time stops lining up with the normalized string and the walker's per-boundary check fails and absorbs a chunk. The ﬁ and Thai SARA AM cases change the count *without* breaking per-grapheme alignment: the whole original cluster still converts to a matching normalized substring, so the check passes and the walker never notices them. The algorithm is correct either way (its check really does catch any drift). Verified on 2026-07-02 that the walker maps Thai SARA AM positions correctly under FormKD: the boundary after "กำ" maps to original offset 2, and positions inside the expanded region snap back to 0.
    - One more wrinkle for the corrected wording: the merge case isn't limited to the Hangul Compatibility Jamo block the doc names (U+3131, U+314F). Halfwidth jamo merge too. "ﾡￂ" (U+FFA1 HALFWIDTH HANGUL LETTER KIYEOK + U+FFC2 HALFWIDTH HANGUL LETTER A, two graphemes in the original) converts to the single grapheme 가 (U+AC00) under FormKC, verified 2026-07-02. That's still Korean jamo, but it comes from the Halfwidth and Fullwidth Forms block, so "compatibility jamo" undersells the trigger set. Saying "Korean jamo sequences (compatibility and halfwidth forms)" keeps the claim true.
