# .As(name) silently overwrites when the same rule instance is reused

    - Where this came up: the SemVer sample's grammar wanted to give the same digit-run pattern three different tree-node names (major, minor, patch). The first version was `var numericCore = OneOrMore(OneOf(...)); MajorVersion = numericCore.As("major").Preserve(); MinorVersion = numericCore.As("minor").Preserve(); PatchVersion = numericCore.As("patch").Preserve();`. Compiles cleanly, doesn't crash, doesn't print a warning. But because `.As(name)` mutates the rule instance in place and returns it, MajorVersion / MinorVersion / PatchVersion all end up pointing at the same `numericCore` object, all named "patch" (the last call wins). The grammar parses fine but `tree.Find(MajorVersion)` and `tree.Find(MinorVersion)` and `tree.Find(PatchVersion)` all return the same node, and the consumer gets the same digit string for all three.
    - Why this is friction: the fluent API encourages chaining (`.As("foo").Preserve().WithError("...")`), and chaining looks like it's building a new rule each time. The mutation contract isn't visible at the call. A user reusing a sub-pattern across positions is a natural pattern (the same numeric shape, the same identifier shape, the same whitespace shape). The library accepts it silently and the tests pass on valid input because the digits matched in all three positions are the same digits. The bug only shows up when the consumer tries to dispatch on which one matched, by which point the user has built more grammar on top.
    - The current way to do it correctly: a factory function that returns a fresh rule each call. `static Rule NumericCore(string name) => OneOrMore(OneOf(...)).As(name).Preserve();`. That works. It's also not what a user reaching for "I want this pattern three times under different names" tries first.
    - Options, in order of preference:
        - Throw on the second `.As(name)` call. The current behavior is "second call silently wins"; "second call throws InvalidOperationException with a message like 'Rule was already named X. To reuse this pattern under multiple names, build a factory function or call .Clone() first.'" is strictly better. ThrowIfSealed already exists for the post-Compile case; this is the analogous gate for "post-named." Probably the right fix.
        - A non-mutating `.WithName(string)` factory that returns a clone. This is the "do what I meant" form. Cost: a Clone implementation on every Rule subclass, which is a non-trivial new contract. Defer.
        - Document in `Rule.As` that calling it twice on the same instance overwrites and that reuse needs a factory. Cheap, doesn't catch the bug, but at least gives a place to point a confused user.
    - The same gotcha applies to `.WithError`, `.Flatten`, and `.As(SymbolId)`. All of them mutate. The throw-on-second-call rule should apply to whichever of these are documented as "set once."
    - Done when: calling `.As("name")` on a rule that already has a name throws with a message that names the offending rule and explains the factory-function workaround. Tests cover the throw and the override-via-`.As(SymbolId.Custom(...))`-after-`.As(string)` cases (the two paths to "name this thing" should both gate cleanly).
