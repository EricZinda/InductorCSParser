- Reduce per-iteration allocations on the matching path
    - Current state: After p100 (Delete-skip) and p200 (lazy children list), the allocation count on zero-match and all-discarded paths is basically bottomed out. The matching path is still allocation-heavy: every successful BetweenInclusive iteration that produces a non-Discarded child still goes through `Inner.TryParse(lexer)` to build a wrapper Symbol, which in turn builds a Symbol[] (or List<Symbol>) for its own children. Every successful primitive CharRule/RuneInRule match allocates a leaf Symbol via `new Symbol(Id, FlattenType, rune)` (CharRule.cs roughly line 70, RuneInRule.cs ~45). On an N-rune JSON string body, that's N leaf Symbols even when the caller's StringChars primitive is about to concatenate them and drop all but the string value. On a ChordGrammar parse, every successful LiteralIgnoreAsciiCase("maj") still allocates its own wrapper Symbol with a small children array, even though the grammar's flatten pass will splice it away.
    - Why now: The Chord timing comment (ChordGrammarTests.cs:209-216) lists "fewer per-iteration allocations" as one of three levers needed to close the gap to 2x regex. p600 targets transaction overhead on the matching path; this item targets the other half, the Symbol + children-array cost per successful match. BacklogGrammar H1 at 25-42x and Paragraph at 20-45x are mostly single-match, single-regex-style rules; the allocation per match is disproportionately visible because the match itself is cheap.
    - Why this is architecturally different from p100/p200/p300: p100 filtered Delete-typed matches, p200 deferred empty-list allocation, p300 (rolled into p500 shipment) elided the Or wrapper on the default Flatten path. All three targeted wrappers that the caller was going to throw away. This item targets allocations on the "caller wants the value" path — where the Symbol does land in the tree, but the caller doesn't actually need a Symbol object per leaf rune. StringChars (p400) is the existence proof: it produces one Symbol for an N-rune run by specializing the combinator. The lever here is widening that idea to more primitives.
    - Design: Three candidate sub-levers, pick whichever the benchmark says matters most.
      (a) Value-carrying leaf Symbol interning. Primitives like CharRule and RuneInRule allocate a fresh Symbol per match even when the Id, FlattenType, and rune value are all identical to last time. A small cache keyed on (rule id, rune) would let the grammar reuse leaf Symbols across calls. Thread-unsafe by default (the Lexer is already single-threaded); the cache lives on Lexer or on the Rule. Size bound is small (a few hundred entries would cover ASCII + common BMP). Risk: if any consumer relies on reference-unique Symbols across calls (unlikely — Symbol is semantically a value), this breaks silently.
      (b) `SymbolChildren` struct that avoids the List/array dichotomy. AndRule and BetweenInclusiveRule both pay for a List<Symbol> on populated paths; the list grows, then gets boxed into an IReadOnlyList<Symbol> when the wrapper Symbol is built. A struct with a small inline buffer (say 2-4 entries) and a heap fallback would eliminate the List allocation for the common case of few children. Needs Symbol's Children field to become generic over the struct or to accept both; either is invasive.
      (c) Compile-time specialization for "flat" primitive alternatives. Many user grammars have patterns like `Or(Char('a'), Char('b'), Char('c'))` that are equivalent to `RuneIn("abc")` but don't get rewritten. A compile pass that detects `Or(CharRule, CharRule, ...)` and substitutes a single RuneInRule at compile time collapses N+1 Symbols per match down to 1. Same for `ZeroOrMore(RuneIn(...))` which is nearly StringChars — the existing StringCharsRule is the specialization; the missing piece is a compile-time detector that rewrites the user's grammar to use it.
    - Edge cases: (a) needs a cache-invalidation story if Rule objects are mutable post-Compile (they shouldn't be, but confirm). (b) changes Symbol's public surface — breaking change for any external consumer; probably stays internal. (c) is the safest: pure compile-time rewrite, output is observably equivalent. User-defined Rule subclasses (mentioned in backlog item gsss) shouldn't be rewritten — only built-in primitives.
    - Impact estimate: Option (c) feels like the biggest win for the smallest surface change because it promotes StringChars-class wins to grammars that never knew to use StringChars. The p400 commit said StringChars roughly halved JSON parse time; even a partial application to user grammars would be meaningful. Options (a) and (b) are more speculative; worth a quick benchmark spike before committing.
    - Done when: One of the three sub-levers ships with a measurable Mean and Allocated improvement on JSON, ChordGrammar timing, or BacklogGrammar timing (pick the benchmark the approach targets). Test suite passes. If option (c), user grammars that happen to use `Or(Char, Char, ...)` or `ZeroOrMore(RuneIn)` show the improvement without any source change on their end.
