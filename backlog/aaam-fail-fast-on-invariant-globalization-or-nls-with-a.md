# Fail fast on invariant globalization or NLS, with an override

On every non-Unity build the parser's Automatic setting resolves to the runtime implementations, so string.Normalize does the normalizing. Process-wide .NET globalization settings change what that call returns without the parser or its caller doing anything. Invariant globalization (common in trimmed containers) makes string.Normalize return its input unchanged, so a default FormC grammar silently stops unifying decomposed and precomposed input, and FormKC/FormKD grammars stop applying compatibility mappings. Windows NLS normalizes from Windows' own data, which moves with OS servicing and can disagree with ICU on edge cases. Nothing throws today. The parse quietly produces different results, and the person debugging has no signal that the host configuration is the cause. The "Host Globalization Settings" section in docs/UnicodeGotchas.md describes the problem, but a doc only helps after someone already knows to be confused.

Make the parser understandable by default. When the implementation resolves to `Runtime` and the process is running invariant globalization or NLS, throw an actionable exception at the earliest point that always runs (implementation resolve time, or the first normalization through the runtime path). The message names the detected mode and the two ways out: set `UnicodeEnvironment.Implementation` to `Bundled`, or set an explicit override next to it that says the host's globalization is understood and the runtime implementations are wanted anyway. The override is a deliberate opt-in in code, so nobody gets the altered behavior without having asked for it.

Detection has to work on the shipped targets. Invariant mode is detectable with plain behavior: normalize a decomposed e plus combining acute and see whether it composes, the same check GlobalizationOracleFixture uses in the test suite. NLS detection likely needs reflection on System.Globalization.GlobalizationMode, which is fine on the net8.0 target but must degrade to "not detected" instead of throwing if the internals ever move. The netstandard2.1 build resolves Automatic to `Bundled`, so there the check only matters for a caller who explicitly sets `Runtime` on Unity, which the docs already warn against. Segmentation needs no check, since StringInfo's data is compiled into the runtime and ignores these settings.

Done when a net8.0 process under DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1 or DOTNET_SYSTEM_GLOBALIZATION_USENLS=1 gets a clear exception from the first normalizing Compile or Parse instead of quietly different parses, the override restores today's behavior in the same process, tests cover detection, the thrown message, and the override (likely by launching a child process with the environment variable set, since the globalization mode is fixed at process start), and the "Host Globalization Settings" section in docs/UnicodeGotchas.md documents the check and the override.
