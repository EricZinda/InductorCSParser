# NormalizedPositionMap.TranslateToOriginal walks from offset 0 on every call, so extracting positions/text across a parse tree is quadratic on non-NFC input

    - `Symbol.SourceRange` and `Symbol.SourceText` (src/InductorParser/SyntaxTree/Symbol.cs, getters around lines 333 and 371) translate every parse-input offset back to the caller's original-input coordinates via `NormalizedPositionMap.TranslateToOriginal` (src/InductorParser/Lexing/NormalizedPositionMap.cs:39), two calls per node (start and end). For the canonical default forms (FormC/FormD) that lands in `TranslateViaLockstep` (NormalizedPositionMap.cs:59), which re-starts its grapheme-by-grapheme walk from `origPos = 0; normPos = 0` on every call and steps forward until it reaches the requested offset. Each call is O(offset). The compatibility-form walker `TranslateViaPerGraphemeNormalize` (NormalizedPositionMap.cs:111) has the same restart-from-zero shape and additionally re-`Normalize`s a growing chunk per step, so it is the same time bug plus a per-call allocation.
    - This only runs when the translation can't be skipped, i.e. when `ReferenceEquals(original, parseInput)` is false. That fast path (src/InductorParser/SyntaxTree/Symbol.cs:341) fires for ASCII and already-NFC input, so the common case is unaffected. It doesn't fire when the caller's input wasn't already in the grammar's compile form: NFD / decomposed text (macOS file paths, some languages' data, copy-pasted text from sources that emit decomposed sequences) parsed under the default `Compile(FormC)` produces a normalized string that differs from the original, so every `SourceRange` / `SourceText` read on every node walks from zero.
    - User-visible consequence: the exact scenario the atwx item describes (an LSP server emitting diagnostics or semantic tokens, a typed-AST projection recording each production's span, a pretty-printer) reading a `SourceRange` per node, but for the non-NFC-under-normalization input the atwx fast path can't shortcut. A node at offset P costs O(P), and the offsets of N nodes across an L-char document sum to O(N x L), so position/text extraction is quadratic in document size. Measured on a word-per-line grammar over decomposed accented letters (`"é"` typed as `"é"`), parsed under the default FormC with `PreserveAllSymbols`, reading `SourceRange` on every node via `Walk()`: 4000 lines took ~14.7 s and 8000 lines ~56.0 s, a size-doubling ratio of 3.80x (quadratic). The 2026-06-04 allocation fix (`docs/BugSearchLog/2026-06-04-normalizedpositionmap-lockstep-allocates-per-grapheme.md`) removed the per-grapheme substring allocation on this same walker but explicitly left the O(offset) time cost, which is this item. atwx (`backlog/atwx-sourcerange-position-conversion-walks-from-offset.md`) fixes the parallel ASCII-path walks (`ToLineColumn`, `CountClustersUpTo`) and scopes this walker out.
    - Who actually hits this (and who doesn't): narrower than the measurement alone suggests, because four things all have to be true at once. (1) Normalization on, which is the FormC default, so this is free. (2) The input isn't already in that form, so `input.Normalize(FormC)` returns a different string and the `ReferenceEquals(original, parseInput)` fast path can't fire. This is the gate that matters: almost all real text is already NFC (anything from a modern editor, web form, database, JSON, or config file), so most callers never reach this walker at all. The realistic non-NFC sources are macOS filesystem paths (APFS/HFS hand back decomposed forms), some IME output, certain copy-paste sources, and deliberately-decomposed corpora. (3) The consumer reads `SourceRange` / `SourceText` on many nodes, not just the error position (one conversion per parse is unaffected), so it takes an LSP server, a span-recording AST projection, a pretty-printer, or a highlighter. (4) The document is large, since the quadratic is microseconds on a small config file. The intersection is "tooling built on this parser, over large decomposed (e.g. macOS-sourced) documents, reading positions on every node." Real, but a minority of cases. By contrast atwx hits broadly: its two walks aren't behind the `ReferenceEquals` gate, so they go quadratic even on pure-ASCII input, and any tooling consumer over a large ASCII document hits it. The case for fixing abkn is "finish the job while fixing atwx, since they share the index-the-walk idiom and all three legs are cheap to do together," not "this is biting people today." The library's own E2E samples (BibTeX, Cron, TOML, JSON, SemVer, PEP508) are small, mostly-ASCII inputs and wouldn't hit this.

    - Fix: build a per-(original, normalized) mapping once and answer each query with a binary search, using the same `ConditionalWeakTable`-keyed cache idiom `GraphemeClusterIndex` already uses. The key insight is that both walkers compute the same monotonic boundary mapping every call, and the walk-from-zero recomputes the whole thing just to read one point on it. Tracing `TranslateViaLockstep`, its answer for a given `normalizedIndex` is exactly: find the largest normalized cluster boundary `<= normalizedIndex`, return the original cluster boundary aligned with it. The `> normalizedIndex` branch (snap back to region start) and the `== normalizedIndex` branch (land on the next boundary) both fall out of that single rule, and canonical normalization preserves grapheme boundaries 1:1 (the file header says so), so the two boundary lists have equal length and line up index-for-index.
      - New `NormalizedPositionIndex` in src/InductorParser/Lexing/, cached on the normalized string instance (each parse makes a fresh normalized string paired with one original, so the instance identifies the pair, and the `ReferenceEquals` case never reaches here):
        ```csharp
        internal sealed class NormalizedPositionIndex
        {
            private static readonly ConditionalWeakTable<string, NormalizedPositionIndex> _byNormalized = new();
            private readonly int[] _normStarts;   // sorted cluster-start offsets, normalized side
            private readonly int[] _origStarts;   // _origStarts[j] is the original boundary aligned with _normStarts[j]

            public static NormalizedPositionIndex For(string original, string normalized, NormalizationForm form)
                => _byNormalized.GetValue(normalized, _ => Build(original, normalized, form));

            public int TranslateToOriginal(int normalizedIndex)
            {
                // Largest j with _normStarts[j] <= normalizedIndex.
                int low = 0, high = _normStarts.Length - 1, found = 0;
                while (low <= high)
                {
                    int mid = (int)((uint)(low + high) >> 1);
                    if (_normStarts[mid] <= normalizedIndex) { found = mid; low = mid + 1; }
                    else high = mid - 1;
                }
                return _origStarts[found];
            }
        }
        ```
      - `Build` runs each walk once, to the end, recording every aligned boundary instead of stopping at the requested offset: it's the existing loop body with `return` replaced by "append to the two lists." The canonical case is the current `TranslateViaLockstep` loop (still using `GraphemeClusterIndex.LengthAt` on both sides, so it keeps the 2026-06-04 zero-allocation property). The compatibility case (FormKC/FormKD) is the current `TranslateViaPerGraphemeNormalize` loop, recording the `(normPos, lastSafeOrigPos)` checkpoint each time a chunk verifies, so the expensive `chunk.Normalize(form)` runs once during the build rather than on every query. The boundary-shift handling is unchanged because the checkpoint list is still monotonic, which is all the binary search needs.
      - `TranslateToOriginal` collapses to a lookup, keeping the three existing checks (return the index unchanged when `ReferenceEquals(original, normalized)`, return 0 at or below offset 0, return `original.Length` at or past the end), then calls `NormalizedPositionIndex.For(original, normalized, form!.Value).TranslateToOriginal(normalizedIndex)`. Cost drops from O(offset) per call (O(N x L) across a tree) to one O(L) build amortized over the parse plus O(log L) per node, so tree-wide extraction goes from quadratic to roughly linear, the same shape atwx gives the ASCII path.
      - Behavior-preserving: the binary search reproduces the old walk's output at every offset (boundary hits, mid-region snap-back, and the run-off-the-end clamp all map to "largest boundary <= index"). Optional hardening: if relying on the normalized-instance cache key feels fragile, key on the pair or store and assert the `original` reference on a cache hit (a couple of lines, no algorithmic change).
