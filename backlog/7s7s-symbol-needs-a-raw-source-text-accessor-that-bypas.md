# Symbol needs a raw-source-text accessor that bypasses Delete-flatten

- Surfaced by: the TOML 1.0 port (E2ESamples/Toml). Repeatedly. The default `FlattenType.Delete` on `Token`, `Literal`, and `EndOfLine()` factories silently strips the matched chars from `symbol.ToString()` of the containing rule. That's the right default when the consumer only cares about the surviving named children. It's the wrong default when the consumer needs the raw matched text to round-trip through a parser like `double.Parse`, `DateTime.Parse`, or a hand-rolled escape decoder. The TOML port hit this in five distinct places before the test suite stabilized:
    - Date-time: `Token('-')` and `Token(':')` in `fullDate` and `partialTime` are Delete by default. `OffsetDateTime.ToString()` returned `"19790527T073200Z"` instead of `"1979-05-27T07:32:00Z"`. `DateTimeOffset.Parse` choked.
    - Float: `Token('.')` in `frac` is Delete. `pi = 3.14` produced a Symbol whose `ToString` was `"314"`. `double.Parse` returned 314.
    - Special float: `Literal("inf")` and `Literal("nan")` are Delete. `SpecialFloat.ToString()` was empty, so the consumer's "starts-with-minus, ends-with-inf" dispatch failed and every special float decoded as NaN.
    - Basic-string escape: `Token('\\')` inside the `basicEscape` rule is Delete. `"C:\\Users"` produced a body Symbol whose text was `"C:\Users"` (with one backslash). The consumer's escape decoder then read the next char as an escape kickoff (`\U`) and crashed trying to slice 8 hex digits out of `"sers"`.
    - Multi-line string body: `EndOfLine()` is Delete by default. `"""line1\nline2"""` (with an actual newline) produced a body whose text was `"line1line2"`. The newline was consumed but didn't survive into the rendered text.
- The current workaround everywhere: `.Preserve()` on every Token / Literal / EndOfLine that contributes to a downstream `ToString()`. That's verbose, easy to forget, and contagious — every literal in a sub-rule that bleeds into a parent's text-bearing match has to be opted in. Easy to leave one out and have a silent decoding bug land much later.
- Proposed addition: a `Symbol.SourceText` (or `RawSourceText`) accessor that returns the substring of the original input the Symbol's match span covers, bypassing the per-child flatten-then-render walk that `ToString()` does today. Implementation: this is exactly what `ParseResult.SourceRangeOf(symbol)` already produces — a `SourceRange(Start, End)` over the original input. The accessor would just slice `originalInput[Start.CharIndex..End.CharIndex]`. The only complication is that `Symbol` doesn't currently hold a back-reference to the original input. Two ways to fix:
    - Pass the input through to Symbol on construction (changes Symbol's footprint).
    - Provide the accessor on `ParseResult` instead: `result.RawSourceTextOf(symbol)` — has the original input handy and already exposes `SourceRangeOf`. This is the lower-impact option.
- The TOML consumer code would then look like:
    - `var rawDateTime = result.RawSourceTextOf(node);`
    - `return DateTimeOffset.Parse(rawDateTime, ...);`
    - With no need to chase down every Token/Literal/EOL inside the date-time grammar and add `.Preserve()` to it.
- Done when: a grammar can write `Token('-')`, `Token(':')`, `Literal("inf")`, etc. with their default flatten behavior, and the consumer can recover the raw matched text of the containing Symbol via a single accessor. The TomlParser's grammar-side `.Preserve()` calls on punctuation in date-time, float, special-float, basic-escape, and ml-basic-string can all be removed, and the existing tests still pass.
