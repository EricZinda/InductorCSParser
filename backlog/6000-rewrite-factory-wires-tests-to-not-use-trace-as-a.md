# Rewrite factory-wires tests to not use trace as a witness for factory behavior

    - Current state: under `INDUCTOR_DEFAULT_ENGINE=statemachine dotnet test` 7 tests still fail after the trace-only tests were marked `[RecursiveEngineOnly]` in commit 468374a. Each one is a factory-wiring test that uses a byte-for-byte trace-text assertion as the witness for the factory's behavior. The tests are: `AtLeastRuleTests.AtLeast_factory_wires_atLeast_N_and_atMost_int_max_with_AtLeast_trace_name`, `AtMostRuleTests.AtMost_factory_wires_atLeast_0_and_atMost_N_with_AtMost_trace_name`, `ExactlyRuleTests.Exactly_factory_wires_both_bounds_to_N_with_Exactly_trace_name`, `OneOrMoreRuleTests.OneOrMore_factory_wires_atLeast_1_and_atMost_int_max_with_OneOrMore_trace_name`, `OptionalRuleTests.Optional_factory_wires_atLeast_0_and_atMost_1_with_Optional_trace_name`, `ZeroOrMoreRuleTests.ZeroOrMore_factory_wires_atLeast_0_and_atMost_int_max_with_ZeroOrMore_trace_name`, `ZeroOrMoreRuleTests.ZeroOrMore_loops_past_two_matches_proving_atMost_is_int_max`. They all live in `src/InductorParser.Tests/Rules/`.
    - Why these are different from the 5aaa trace tests: the test names tell you the real subject. They verify that named factories (`Optional`, `Exactly(N)`, `OneOrMore`, etc.) wire three things into the underlying `BetweenInclusiveRule`: the `atLeast` bound, the `atMost` bound, and the `traceName` string that becomes the rule's `TraceLabel`. The trace-text comparison was a convenient way to capture all three in one assertion, but it conflates "did the factory wire the bounds" with "does the engine emit per-rule trace lines on every Call". The first holds under both engines. The second holds only under the recursive engine because the SM's lowerer fuses inlined rules.
    - Why marking them `[RecursiveEngineOnly]` would be wrong: it would silently weaken cross-engine coverage of the public factory API. `Optional` is a public surface. Whether `Optional(rule)` wires `atLeast=0, atMost=1` is a property of the factory, not the engine. The state machine should be exercised against this same property. Marking the tests recursive-only would mean the SM build never confirms that `Optional` produces a 0-1 bounded loop, even though that question has a well-defined answer.
    - Recommended path: split each trace-based assertion into one or more behavioral assertions that hold under both engines.
        - `traceName` wiring: assert `rule.TraceLabel` directly. For `Optional` that means `Assert.That(Optional(Grapheme('a')).TraceLabel, Does.StartWith("Optional"))`. For `Exactly(3)` it's `Does.StartWith("Exactly[3]")`. `TraceLabel` is a property on the compiled rule and reads the same under either engine.
        - `atLeast` wiring: parse input that doesn't reach the lower bound and assert `result.Success` is false (or true for the zero-bound factories). Most fixtures already have a sibling test for this (`OneOrMore_fails_with_zero_matches_proving_atLeast_is_1`, `Exactly_fails_when_count_is_below_required_count`, etc.). Where one is missing, add it. Where it exists, the trace test is redundant on this dimension and the assertion can be deleted.
        - `atMost` wiring: parse input that exceeds the upper bound inside an `And` whose tail consumes the remainder, and assert the parse succeeded. The Optional fixture already does this shape: `And(Optional(Grapheme('a')), Grapheme('a')).Parse("aa")` succeeds only if Optional released control after one match. For `atMost = int.MaxValue` factories (`OneOrMore`, `AtLeast`, `ZeroOrMore`), the upper bound has no observable behavioral consequence on finite input; the trace test was the only way to "see" the loop probing past the lower bound on EOF. That probe is an implementation detail of the recursive evaluator's loop body, not a property of the public factory, and should not be in the public test surface at all. Drop those assertions.
    - Done when: under `INDUCTOR_DEFAULT_ENGINE=statemachine dotnet test` no `*_factory_wires_*` test fails. The same tests still pass under the recursive baseline. Each named factory (`Optional`, `OneOrMore`, `ZeroOrMore`, `Exactly`, `AtLeast`, `AtMost`) has at least one assertion verifying its `TraceLabel` and at least one assertion verifying each finite bound it sets. No assertion in any of these fixtures depends on per-rule trace text.
    - Verification: rerun both CI invocations from p900. SM-mode failure count drops from 7 to 0. Recursive-mode count stays at zero.
    - Note: this is the follow-up to 5aaa. 5aaa loosened SM-mode behavior for tests whose entire purpose was trace verification. This item rewrites the remaining tests whose purpose was something else and that just happened to be expressed through trace.
