- Refactor Step 1: Expand RuneSet to hold multi-rune graphemes
    - Context: today RuneSet is a set of single Unicode scalar values, with closed set algebra over the rune universe. Multi-rune graphemes (skin-toned emoji, ZWJ sequences, regional indicator pairs, base+combining-mark clusters) aren't members of any RuneSet — `Runes("...")` actively rejects them with one CRLF-shaped exception. Grammars that want to match a class of grapheme clusters have to fall back to `FirstOf(Grapheme(a), Grapheme(b), ...)`, which doesn't compose with set algebra and can't be intersected with `RuneSet.Letters` or used as a `NoneOf` exclusion. Step 1 broadens the type so a single set can describe "this rune class plus these specific multi-rune graphemes" while staying a real set. This is a pure additive change — name stays `RuneSet`, rune-only callers see no behavior change.
    - Data layout: keep `_ranges` as is; add `private readonly string[] _multiRuneGraphemes` (sorted ordinal, deduped at construction). Single-rune graphemes still go in `_ranges`, only graphemes occupying two or more runes go in the new array. The rune fast path (binary search of intervals) is untouched.
    - Membership: `Contains(int rune)` and `Contains(Rune r)` check `_ranges` only. Add `Contains(string grapheme)` — if the grapheme is one rune (1-2 chars decoding to a single Rune), check `_ranges`; else binary search `_multiRuneGraphemes`.
    - Set operations: `a | b` is ranges-union plus sorted merge of grapheme arrays. `a & b` is ranges-intersection plus sorted merge-intersect of grapheme arrays. `~a` returns the rune-complement of `_ranges` if `_multiRuneGraphemes` is empty; otherwise throws `InvalidOperationException` with a message that explains why (the universe of grapheme clusters is unbounded so complement isn't representable) and points at the workaround (`set & ~runeOnlyMask`).
    - Equality and hashing: extend to compare/hash `_multiRuneGraphemes` ordinal alongside `_ranges`. Use `string.GetHashCode(StringComparison.Ordinal)`.
    - ToString: include multi-rune graphemes in the same bracketed list with no special quoting, e.g. `[a-z,👋🏽,🇺🇸]`. The existing length cap counts multi-rune graphemes as entries on equal footing.
    - Factory: extend `RuneSet.Runes(string)` to walk `StringInfo` text elements. Single-rune element becomes an interval add; multi-rune element becomes a string add. Drop the rejection of multi-rune text elements. Drop the CRLF special case — it folds away as a degenerate version of the general path. Other factories (`Single`, `Range`, `Category`, `Letters`, `Digits`, `Whitespace`, `XidStart`, `XidContinue`, Ascii variants, `SingleRuneLineTerminators`) continue to produce rune-only sets unchanged.
    - Rule integration:
        - `OneOfRule`: when `token.RuneValue == -1` (multi-rune token under GraphemeLexer) and the set has any multi-rune graphemes, binary search `_multiRuneGraphemes` against the token's `Chars` span (ordinal compare). If the set has no multi-rune graphemes, keep the fast fail.
        - `NoneOfRule`: same shape — when `RuneValue` is `-1` and the set has any multi-rune graphemes, check the span against the array and fail on a hit; otherwise pass through unconditionally as today.
        - `ScanWhileRule` and `ScanUntilRule`: pick the rune fast path (`AdvanceWhileSingleRuneIn`-style helpers) when the set is rune-only; pick the slower grapheme-aware path when the set has multi-rune entries. Add a `Lexer.AdvanceWhileIn(RuneSet)` variant that handles both, and let the rules dispatch on `_set.HasMultiRuneGraphemes`.
        - `RuleStartRequirements`: extend the lookahead-fail path to handle multi-rune tokens against `FirstConsumedRunes` (rune fast path plus the multi-rune fallback that walks the multi-rune array via the token's `Chars` span).
    - Touches: `src/InductorParser/RuneSet.cs`, `src/InductorParser/OneOfRule.cs`, `src/InductorParser/NoneOfRule.cs`, `src/InductorParser/ScanWhileRule.cs`, `src/InductorParser/ScanUntilRule.cs`, `src/InductorParser/Lexing/Lexer.cs`, `src/InductorParser/RuleStartRequirements.cs`. New tests under `src/InductorParser.Tests/Core/` for the new RuneSet algebra and under `src/InductorParser.Tests/Rules/` for the new OneOf / NoneOf / ScanWhile paths.
    - Done when: `RuneSet.Runes("a👋🏽é")` produces the expected mix of intervals and multi-rune entries. `(rune-only) | (mixed)` and `(mixed) & (mixed)` produce expected canonical content. `~(rune-only)` works as today; `~(mixed)` throws `InvalidOperationException` with the documented message. The same logical set built two ways compares equal with equal hash. `OneOf(RuneSet.Runes(USFlagGrapheme + WomanShruggingGrapheme))` parses the corresponding inputs under the default GraphemeLexer. `NoneOf(RuneSet.Runes(USFlagGrapheme))` rejects the flag and accepts neighboring graphemes. A mixed set `RuneSet.Letters | RuneSet.Runes(USFlagGrapheme)` matches both letters and the flag in `OneOf`. ScanWhile across a mixed string stops at the first non-member. Under RuneLexer the multi-rune entries are unreachable (each token is one rune) — pin this with a regression test. All existing rune-only RuneSet tests pass unchanged.
    - Notes: this step is a prerequisite for Step 2 (collapse to one lexer) because once RuneLexer goes away, the multi-rune entries become the only path that reaches multi-rune tokens. Doing the expansion first keeps every change additive and the regression surface small.
