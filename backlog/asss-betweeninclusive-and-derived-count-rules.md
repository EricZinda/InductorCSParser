- BetweenInclusive and derived count rules
    - Current state: OneOrMoreRule, ZeroOrMoreRule, and OptionalRule are three separate hand-written classes with nearly identical bodies (begin a transaction, loop while the inner matches, guard against zero-width, stop at a limit, commit). The C++ library expresses the same idea as a single `AtLeastAndAtMostExpression<T, AtLeast, AtMost>` template with the three specializations `<T, 1, INT_MAX>`, `<T, 0, INT_MAX>`, and `<T, 0, 1>`. That collapses three bodies into one and gives grammar authors the "match between M and N times" primitive for free.
    - Design:
        - Add `internal sealed class BetweenInclusiveRule : Rule` that takes an inner rule plus two ints `AtLeast` and `AtMost` (inclusive on both ends, hence the name). The body is the existing OneOrMoreRule loop with the count bounds substituted in: fail if count < AtLeast, stop the loop once count == AtMost, return a success Symbol otherwise.
        - Add `public static Rule BetweenInclusive(Rule inner, int atLeast, int atMost)` on `Rules` as the user-facing factory. Validates `atLeast >= 0`, `atMost >= atLeast`, and optionally `atMost <= int.MaxValue - 1` so the "stop once we hit the cap" branch behaves cleanly.
        - Re-express `OneOrMore(inner)` as `BetweenInclusive(inner, 1, int.MaxValue)`, `ZeroOrMore(inner)` as `BetweenInclusive(inner, 0, int.MaxValue)`, and `Optional(inner)` as `BetweenInclusive(inner, 0, 1)`. Delete `OneOrMoreRule.cs`, `ZeroOrMoreRule.cs`, `OptionalRule.cs`.
        - Trace format: use the existing rule-name style from backlog/i021 but parameterize by the bounds, for example `BetweenInclusive[1..] count= 3` or `BetweenInclusive[0..1] count= 1`. The three derived factories still produce the same underlying rule and thus the same trace, but the trace reads as "what the bounds actually are" rather than "which derived factory was called". Pick a rendering that stays legible when `atMost == int.MaxValue` (probably render the upper bound as empty: `[0..]`).
    - Why name it `BetweenInclusive` rather than `AtLeastAndAtMost` (the C++ name) or `Between` (shorter): `Between` is ambiguous about endpoint inclusivity and `AtLeastAndAtMost` is two concepts in one name. `BetweenInclusive(inner, 0, 3)` reads unambiguously as "0, 1, 2, or 3 matches".
    - Test strategy: keep the existing per-rule test files (`OneOrMoreRuleTests.cs`, etc.) since they exercise the three common shapes and those shapes are how grammar authors will use the library. Add a new `Rules/BetweenInclusiveRuleTests.cs` that covers the bounds logic directly: off-by-one at AtLeast, off-by-one at AtMost, AtLeast == AtMost (exact-count match), AtLeast == 0 with AtMost == 0 (always succeeds, zero matches), argument validation on the factory.
    - Priority: low until someone actually needs a bounded-repetition rule in a real grammar, since the current three classes aren't broken. The win is mostly maintenance (one body to fix bugs in instead of three) plus giving grammar authors the primitive without forcing them to compose it by hand from `And` and `Optional`.
    - Done when: `BetweenInclusiveRule` exists, the three derived factories build through it, the old three rule classes are gone, the trace format handles unbounded and bounded cases cleanly, and the existing OneOrMore/ZeroOrMore/Optional test suites pass unchanged plus the new BetweenInclusive-specific tests.
