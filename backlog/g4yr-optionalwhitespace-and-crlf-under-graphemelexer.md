- OptionalWhitespace and CRLF under GraphemeLexer
    - Current state: `Rules.OptionalWhitespace()` is `ZeroOrMore(OneOf(RuneSet.Whitespace)).Flatten(FlattenType.Delete)`. Under `GraphemeLexer` (the default), CRLF arrives as a single two-rune grapheme, and `OneOf` over a rune set fails on multi-rune tokens. So `OptionalWhitespace()` stops at a CRLF boundary instead of consuming it. `Whitespace()` has the same shape and the same blind spot. This is the exact gotcha `docs/UnicodeGotchas.md` "CRLF Under GraphemeLexer" warns about, and the doc already points at `Rules.EndOfLine()` as the fix for line-terminator matching.
    - Question: should the built-in `OptionalWhitespace()` / `Whitespace()` be CRLF-aware, or kept as "horizontal-ish whitespace that stops at line boundaries"? Two reasonable answers and they target different grammar shapes. Free-form grammars (JSON, expression languages, configs that don't care about lines) want to skip every kind of whitespace, including CRLF, between tokens. Line-based grammars (INI, the primer 2 example, anything that uses `EndOfLine()` as a terminator) deliberately want whitespace to stop at the line break so the terminator isn't consumed by the wrong rule. Today the built-in is implicitly the second one, but the name `OptionalWhitespace` suggests the first.
    - Options:
        - Leave the built-in alone and document the intent. Add a sentence to `Rules.OptionalWhitespace()` and `Rules.Whitespace()` saying they stop at multi-rune line-terminator graphemes (i.e. CRLF) under GraphemeLexer, and point at `EndOfLine()` for newline-aware matching. Cheapest fix, clarifies behavior, breaks no callers.
        - Change the built-in to consume CRLF too: `ZeroOrMore(FirstOf(EndOfLine(), OneOf(RuneSet.Whitespace)))`. Closer to "consume any whitespace" reading of the name, but breaks line-based grammars that depend on the current "stops at CRLF" behavior. Would need a sweep of the test corpus and the example grammars (INI, primer 2, etc.) to see what relies on the current stop-at-line shape.
        - Add a separate factory like `OptionalWhitespaceWithNewlines()` that explicitly includes CRLF, leaving the existing names alone. Preserves existing behavior, adds an opt-in for the free-form-grammar case. Doc table grows by one row.
    - Likely tradeoff: option 1 is conservative and probably right for a first pass. Option 3 is a small additive change if real grammars want the inclusive form. Option 2 is the right "principle of least surprise" answer if and only if no existing grammar depends on the stop-at-line behavior, which we'd need to verify before doing it.
    - Done when: the built-in's behavior is either documented to match its current shape, or changed to match a name that better describes what it does. Any callers that relied on the old behavior are migrated.
