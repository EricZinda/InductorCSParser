- Investigate why Rune.IsValid rejects 0xD800 on CoreCLR but not under IL2CPP
    - Symptom: RuneSetTests.Runes_with_lone_surrogate_throws passes under `dotnet test` (net8.0) but fails under runil2cpptest.sh (netstandard2.1 DLL, IL2CPP runtime). The test asserts that `RuneSet.Runes("\uD800")` throws ArgumentException; under IL2CPP it returns normally. Currently guarded with `#if !UNITY_INCLUDE_TESTS` so the IL2CPP pass stays green.
    - Code path: RuneSet.Runes iterates the input, sees a lone high surrogate (index+1 >= Length so the "high then low" branch fails), falls into the else branch, sets codepoint = characters[0] = 0xD800, then calls Rune.IsValid(codepoint). The polyfill in src/InductorParser/Compatibility/Rune.cs returns false for 0xD800 — verified by reading the source. So on paper the throw should fire.
    - Hypotheses to check:
        - IL2CPP type-unifying our polyfill (namespace System.Text in InductorParser.dll) with a Unity-provided BCL Rune and dispatching to the BCL's IsValid, whose behavior might differ. Check by adding a trace that prints `typeof(Rune).Assembly.FullName` from inside Runes and comparing between runtimes.
        - Managed stripping removing the polyfill's IsValid method when the linker sees a BCL match. Check by building the Unity player with Managed Stripping Level = None and re-running.
        - The string literal "\uD800" being sanitized to U+FFFD somewhere in the Unity asset import or compile pipeline. Check by logging `(int)characters[0]` at the start of Runes and comparing runtimes — if the logged value is 0xFFFD, the source never sees the lone surrogate.
        - A subtle overload resolution issue where the call binds to Rune.IsValid(uint) instead of IsValid(int), with different negative-value handling. Check the IL via ildasm/dnSpy on the built DLL.
