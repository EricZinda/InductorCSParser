# Stress test the concurrent-Parse thread-safety promise

- Where this came up: the 2026-07-10 discussion of where bugs could still hide after 151 recorded hunts.
- The claim under test: Rule's doc comment promises that a compiled grammar is immutable and any number of threads can Parse it at once with no synchronization. That claim broke once already (GraphemeClusterIndex kept shared mutable state across concurrent parses, found 2026-05-20), and the code has grown more shared static state since: the grapheme-cluster index cache, TokenSet's NormalizedFor projection cache, the Unicode category cache, and the lazily built NameOf / IdOf indexes on Rule. Each is reasoned about in its own comment, but nothing exercises them together under contention.
- The plan: compile one grammar, then hammer it from many threads with a mixed input corpus, including inputs that hit the lazy first-call paths (NameOf right after Compile, SourceRange translation on input that normalization rewrote, a first Category(...) resolution). Compare every ParseResult against a single-threaded baseline for the same input. Add a variant where several distinct grammars compile on separate threads first, since compilation is documented single-threaded per grammar but the static caches are cross-grammar.
- Run enough iterations that a torn read or a lost cache write has a real chance to show up, and run on more than one machine profile when possible, since these failures are timing-dependent.
- Done when: the stress harness exists in the test project (an [Explicit] fixture is fine if it's too slow for every CI run), passes repeatedly, and any failure is minimized to a filed bug. A clean pass is also a result: it becomes the evidence behind the thread-safety sentence in the docs.
