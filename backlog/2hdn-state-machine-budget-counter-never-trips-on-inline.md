- State machine budget counter never trips on inlined grammars
    - Current state: under `INDUCTOR_DEFAULT_ENGINE=statemachine dotnet test` eight budget-related fixtures fail because the SM's rule-invocation counter only ticks when the lowered program executes a Call opcode (cyclic rules and ScanUntil sub-programs). Non-cyclic grammars are inlined into a single state machine, no Call fires, and `RuleCountLimit` / `Timeout` / `Cancellation` never trip. Sample: `Default_rule_count_limit_aborts_oversized_workload` (`src/InductorParser.Tests/Core/BudgetTests.cs:224`) hands the parser an oversized input and expects `Outcome == RuleCountLimitExceeded`; under the SM the parse runs to `Success` because the counter sat at zero the whole way through. p880's StateMachineBudgetCompareTests pinned the cyclic-grammar path (`BuildNestedParens`, `BuildManyAs`, `BuildBacktrackingFirstOf` all use LateBoundRule cycles), so the bug only shows up on inlined grammars the rest of the suite uses by default.
    - The full list: `Default_rule_count_limit_aborts_oversized_workload`, `RuleCountLimit_aborts_with_RuleCountLimitExceeded`, `Timeout_aborts_with_Timeout_outcome`, `Cancellation_already_canceled_aborts_with_Canceled`, `Aborted_result_carries_a_position_for_diagnostics`, `Aborted_result_reflects_deepest_progress_when_failures_recorded`, `RuleCountLimit_distinguishes_from_GrammarMismatch` (`src/InductorParser.Tests/DocExamples/InductorParserReferenceExamples.cs:287`), `Abort_via_work_limit_reports_position_into_original_not_normalized` (`src/InductorParser.Tests/Core/NormalizationTests.cs:201`).
    - Recommended path: the periodic budget check has to fire on the SM's hot loop too, not only on Call. Two options. (a) Tick the counter on every backtrack-frame push in the Stepper so any branching grammar drives the counter even when it's all inlined. Backtrack-frame push is the closest analogue to "did real work" on the inlined path. (b) Tick on every primary opcode dispatch (one increment per opcode dispatched). Heavier, but matches the recursive engine's "every TryParseRule invocation counts" semantics most closely. Option (a) is probably right because it kills catastrophic-backtracking shapes (the thing the budget is for) without slowing down well-formed parses. Whichever path is chosen, `Lexer.CheckPeriodicBudgets` still has to be the trip point so `RuleCountLimit / Timeout / Cancellation` share one check.
