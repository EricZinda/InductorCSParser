- Compiled "state machine" emitter for stable grammars
    - Current state: Every parse of every grammar goes through the composite interpretation tree. A ChordGrammar match of "C#maj7" walks through And -> BetweenInclusive -> Or -> Literal -> GraphemeRule virtual calls, each opening a transaction, each recording trace hooks, each doing a virtual dispatch on `TryParseRule`. The grammar itself doesn't change between parses (the user Compiles it once), but the interpreter re-does all the bookkeeping per call. The Chord timing comment (ChordGrammarTests.cs:209-216) calls out "a compiled 'state machine' emitter for stable grammars" as the third of three levers needed to close to 2x regex. Pegasus (the reference Peg parser in src/Benchmarks/Json/PegasusParsers/) already ships a compiled grammar approach. Its `.peg` file generates a `Json.peg.g.cs` at build time, and that's the existence proof for this pattern on .NET.
    - Why now: p600 (lazy transactions) and p700 (fewer allocations) both chip away at the interpreter's per-call cost without removing the interpreter. Past some point, the only way to get within 2x of a hand-rolled compiled regex is to stop being an interpreter on the hot path. A compiled grammar emitter doesn't replace the composite API. It compiles a specific Rule graph into specialized code and swaps that in as the rule's TryParseRule implementation. Grammar authors keep writing composites, and perf-sensitive callers pay a one-time Compile cost to get native-ish speed.
    - Design: Two viable shapes, pick one based on appetite.
      (a) IL emit via Reflection.Emit / DynamicMethod. Rule.Compile() walks the grammar tree and generates an IL method that inlines the And/Or/BetweenInclusive decisions as direct branch/loop instructions and calls leaves directly. Transaction state becomes a local int saved position. Leaves become inlined character comparisons. The returned DynamicMethod replaces the rule's TryParseRule via a delegate. Runtime only: no build-step change. Debuggability is poor (no source to step through) and stack traces become opaque. Net Standard 2.1 supports Reflection.Emit on most runtimes but Unity's IL2CPP doesn't, and this matters because the project ships a Unity DLL (InductorParser.Tests/Unity/Assets/Plugins/InductorParser.dll). So an IL emitter has to be gated to runtimes that support it and fall back to the interpreter on Unity.
      (b) Source generation at build time. A Roslyn source generator that consumes a grammar description (either a separate DSL file, or, ambitiously, a C# attribute on a method that returns a Rule) emits a specialized Parser class at compile time. Output is readable C#, steppable in the debugger, works on Unity (the generated .cs ships as source, not IL). Higher upfront cost: build integration, author ergonomics for declaring "this grammar should be compiled." But once shipped, every perf-sensitive grammar in the repo can opt in with one annotation.
      A third option worth naming but probably ruling out: expression-tree compilation via LINQ Expression.Compile. Simpler than Reflection.Emit but slower in hot loops because Expression.Compile output isn't as tight as raw IL. Not a Unity fit either.
    - Edge cases: User-defined Rule subclasses (see gsss-exercise-the-user-defined-rule-subclass-contract.md) can't be compiled because they're user code the emitter can't introspect. The emitter should leave them as virtual calls and only compile the built-in rules it recognizes. Late-bound rules (LateBoundRule for recursion) need to compile to a recursive call into the emitted code, not an indirection through the interpreter. Tracing, error reporting, and ParseOptions budgets (RuleCountLimit, MaxDepth, Timeout, Cancellation) all currently live in the interpreter, so the emitted code has to preserve them, which probably means periodic inline checks that match Lexer.EnterRule's behavior at Lexer.cs:343. Parse-tree shape has to match the interpreter exactly. Any deviation is a silent regression. A differential test harness that runs both emitter and interpreter on every corpus input and compares trees is essentially required.
    - Impact estimate: Pegasus on the JSON benchmark sits roughly 1.5-2x SystemTextJson (check src/Benchmarks/README.md for the latest numbers); a compiled InductorParser should land in the same zip code. For ChordGrammar the compiled regex is the benchmark to beat, and a reasonably tight emitter should get within 2x. The real question is whether the emitter implementation cost (especially option b) is justified by the grammars that would use it. One small grammar (ChordGrammar) hitting the 2x gate wouldn't justify it alone; MergeableBacklog + the full E2E grammar set + JSON + any future perf-sensitive internal callers probably do.
    - Done when: An emitter exists for at least the built-in rule set, wired into Rule.Compile() behind an opt-in flag (ParseOptions.CompileMode or similar). ChordGrammarTests.Timing passes at the 2x gate with the emitter enabled. JSON benchmark Mean drops measurably, ideally into Pegasus's range. A differential test confirms tree shape matches interpreter output on the full test corpus. Unity build still works, either because option b was chosen or because the IL emitter falls back cleanly.
    - Verification: The differential test is the main acceptance gate. Any tree-shape regression is a bug, not an acceptable tradeoff. Benchmark runs on full JSON suite and both E2E timing tests (un-Ignore for the run, re-Ignore if they still don't pass the 2x gate on unchanged grammars). Unity DLL rebuild confirms the managed library still loads in Unity. Track IL emit vs source gen decision in the implementation plan before coding, not during.
    - Note: This is the biggest item in this tier by a wide margin. Probably wants its own design doc (backlog item 2eee-implementation-plan.md is the right slot) before any code is written. p600 and p700 should ship first so the baseline the emitter is measured against is already optimized interpreter code, not the current state.
