- Or first-set dispatch: skip branches whose first character can't match the lookahead
    - Current state: OrRule.cs:10-52 walks every child in order, wrapping each attempt in `lexer.BeginTransaction()` (OrRule.cs:14) and rolling back on failure. For a grammar with N alternatives and disjoint first-character sets (`Or(RuneIn("ABCDEFG"), Char('/'), LiteralIgnoreAsciiCase("maj"))` and the like in ChordGrammar.cs), the matching branch is almost always not the first one tried, so every match pays (position_of_winner - 1) wasted transaction+rollback cycles. Every losing child runs its whole TryParseRule body before the top-level Or decides to move on.
    - Why now: ChordGrammarTests Timing comment (ChordGrammarTests.cs:198-211) calls this out as the lever left after p500 Literal/LiteralIgnoreAsciiCase ("Next lever: Or first-set dispatch... should close the remaining gap to 2x"). BacklogGrammarTests (E2EExamples/BacklogGrammarTests.cs, the ignored Timing test) measures H1 at 51x, H2 at 26x, Paragraph at 28x; the worst cases are the ones where most attempts are rejections, which is exactly the shape first-set dispatch exists to fix.
    - Design: At Compile time, every Rule computes a FirstSet (RuneSet of legal leading runes, plus a CanBeEmpty flag for rules like Optional/ZeroOrMore that don't require any input). Primitive rules have trivial first sets (CharRule = the single rune, RuneInRule = the set, LiteralRule = its first rune's set, Eof = empty with CanBeEmpty=true). Combinators compose: And's first set is its first child's set, widened by the next child's set if the first child CanBeEmpty; Or's first set is the union of children's; BetweenInclusive's first set is the inner's, with CanBeEmpty true iff atLeast==0. OrRule.TryParseRule then peeks the lexer's next rune (without consuming) and skips any child whose FirstSet doesn't contain it and whose CanBeEmpty is false. Children matching the lookahead still run in their original order so PEG semantics don't shift.
    - Edge cases: Rules with CanBeEmpty=true (Optional, ZeroOrMore, Or with an empty-capable branch) must always be tried; they can match on any lookahead, including EOF. Not and Peek are zero-width — their own FirstSet is empty but they don't advance, so dispatch must treat them as "never skip, always try." User-defined Rule subclasses can't compute first sets automatically; expose a virtual `ComputeFirstSet()` with a pessimistic default (full set, CanBeEmpty=true) so subclasses still work, and let advanced subclasses override to get the speedup. LateBoundRule needs recursion handling — mark the node "in progress" during computation so a self-reference yields the pessimistic default rather than looping forever.
    - Impact estimate: Every Or alternation in every grammar gets proportional speedup. Chord has 6 Ors averaging 5+ branches each on the hot path; expect grammar runtime to drop by roughly 3-5x on the ChordGrammar corpus, landing it near the 2x regex budget. BacklogGrammar's H1 is an `And(Char('#'), Not(Char('#')), ...)` where the Not check runs once per input even when input has no `#`; adding a lookahead-skip on the And as well (not just Or) would collapse the non-H1 corpus entries to one rune read each. Worth scoping whether the dispatch also applies to And's first child, or stays Or-only for this tier.
    - Done when: Rule has a FirstSet/CanBeEmpty pair populated at Compile time; OrRule.TryParseRule peeks the lookahead and skips incompatible children; ChordGrammarTests.Timing passes at the 2x gate (or, if it doesn't, we understand why and decide whether an And extension or a different tier ships next); BacklogGrammarTests.Timing ratios drop across the board; existing test suite passes unchanged (dispatch is a pure optimization — the same children are still tried, just in a pre-filtered order).
