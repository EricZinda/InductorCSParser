- A fast path skips work on the premise that the skipped work emits nothing to the tree, but a Preserve Symbol around that work emits an empty node
    - Shape: an optimization recognizes a loop shape like `ZeroOrMore(Or(real..., AnyToken().Delete()))` and jumps the cursor straight to the next position a real alternative could start, treating the runs in between as "deleted, contributes nothing." The premise holds for what's INSIDE the Or (the AnyToken().Delete() lifts/drops to nothing), but the Or itself can be Preserve. A Preserve composite emits a Symbol for EVERY successful match, including matches that bottomed out in Delete children, so a fallback-only position still produces an empty-children Preserve Symbol. The skip jumps over the position and that Symbol never reaches the tree. The optimized tree has fewer nodes than the unoptimized one, even though the optimization is documented to be tree-transparent.
    - Why it hurts: the optimization is supposed to be invisible (same parse tree, just faster). A grammar that wraps the scan-or-skip Or in Preserve (or names it with `.As(...)`, which auto-flips to Preserve) gets a different tree depending on whether the fast path fired. It's silent. `ToString()` is identical (the dropped Symbols have no text), so the only observable difference is node count / tree shape, which most tests don't assert. The existing scanner-skip tests all checked `ToString()` and missed it for exactly this reason.
    - How to spot it: find an optimization that skips invoking a sub-rule on the argument "the skipped input would have been thrown away anyway." Then ask what the sub-rule's OWN flatten policy is. If the sub-rule (not just its children) is Preserve, each skipped match would have emitted a Symbol, and skipping drops it. The gate belongs on the sub-rule's FlattenType: only skip when a skipped match contributes nothing to the tree (Flatten lifts the deleted children to nothing, Delete emits nothing, Preserve emits an empty Symbol so don't skip).
    - How to surface it generally: a default-parse vs `PreserveAllSymbols`-then-`Symbol.Flatten()` round-trip differential is a strong oracle for "an optimization changed the tree," because `PreserveAllSymbols` disables the parse-time fast paths (scanner-skip and the lookahead shortcut). Any divergence between the parse-time-flattened tree and the post-hoc-flattened PreserveAll tree means a fast path (or the flatten machinery) isn't tree-transparent. The same divergence reproduces in pure default mode by toggling the optimization through tracing (`TraceLevel.Normal` also disables the scanner-skip), which proves it's the optimization and not a PreserveAll artifact. (Note: `Alias` over a Preserve leaf legitimately diverges in this round-trip for an unrelated, design-intended rebadge reason. Filter Alias out when using this oracle to isolate fast-path bugs.)
    - Other places this might apply (worth a sweep next time): any other compile-time-recognized fast path that bypasses a sub-rule's TryParse (the lookahead / LL(1) skip in OrRule and BetweenInclusiveRule already gate on `HasErrorMessageInSubtree` for error messages, but should also be audited for whether a bypassed Preserve sub-rule would have emitted a Symbol). Audit any future "jump past this run" optimization against the FlattenType of the rule whose invocations it skips.
