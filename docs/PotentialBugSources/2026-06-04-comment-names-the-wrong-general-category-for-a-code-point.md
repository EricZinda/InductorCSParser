- Comment names the wrong General_Category for a code point
    - Shape: an explanatory comment justifies why a code point is in some set by stating its Unicode General_Category, and gets the category wrong. The set membership is correct (the table/build is right), but the stated reason is false. Found at the top of TokenSet.Xid.cs, which called U+309B "classified as a letter, so it's in ID_Start" when it's actually a Modifier Symbol (Sk) that reaches ID_Start through Other_ID_Start.
    - Why it happens: the Other_ID_Start / Other_ID_Continue properties exist precisely to pull in identifier characters the letter/Nl categories miss (symbols like U+2118 SCRIPT CAPITAL P (Sm), U+212E ESTIMATED SYMBOL (So), the Katakana voicing marks (Sk)). It's easy to write "it's a letter" as shorthand for "it's an identifier character," but that conflates UAX #31 identifier-eligibility with the General_Category, which are different things. The same file's OtherIdStart table had the correct "(Sk)" annotation right next to the wrong prose, so the comment contradicted itself.
    - How to catch it: any comment that asserts a specific code point's category ("309B is a letter", "200C is whitespace", "FEFF is a space separator") is checkable in one line via `CharUnicodeInfo.GetUnicodeCategory((char)cp)` or `char.IsLetter/IsWhiteSpace/IsDigit`. When a comment explains set membership by category, verify the category, not just the membership. The membership is usually UCD-tested, but the prose reasoning usually isn't.
