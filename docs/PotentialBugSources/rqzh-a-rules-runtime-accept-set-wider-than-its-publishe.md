- A rule's runtime accept-set wider than its published FirstConsumedTokens silently breaks Or / count-rule lookahead
    - Every rule publishes a `FirstConsumedTokens` set via `ComputeRuleStart` (see `RuleStartRequirements`). The Or-lookahead shortcut peeks the next cluster and skips a child rule whose `Advance == Always && MustBeIn && peek not in FirstConsumedTokens` (or the MustNotBeIn dual). The shortcut is sound only if the publish-set is a superset of every cluster the rule's runtime match would accept. When a rule's runtime path accepts variants the publish-set doesn't list (case folding, normalization-equivalent forms, language-script-specific equivalences, locale-sensitive comparisons, etc.), the shortcut silently skips the rule on a peek the rule would have matched, and the surrounding grammar commits to a later alternative that consumes less.
    - User-visible consequence: a grammar like `Or(specializedRule, AnyToken())` parses inputs that should match `specializedRule` as the `AnyToken` fallback, and a single-alternative grammar fails outright. The runtime match logic and the published-set are consistent for the simple case (whatever the rule directly compares against) but diverge for the equivalence class the rule was designed to recognize. The bug surface scales with how much "user-friendly equivalence" the rule's runtime adds on top of the literal data it stores.
    - The worked case for this pattern was `LiteralIgnoreAsciiCaseRule.ComputeRuleStart`: the single-char first-grapheme branch admitted both ASCII letter cases, but the multi-char branch fell through to the literal cluster and the runtime `AsciiCaseEquals` accepted the case-swapped variant the publish-set excluded. Two fix shapes were considered:
        - Widen the publish-set to cover every variant the runtime would accept. For ASCII case-insensitive matching on multi-char clusters, that's the literal cluster plus the case-swapped first-char variant. Since the widened set enumerates exactly what the runtime accepts, the publish-set can't drift out of sync at any site that needs the shortcut.
        - Narrow the runtime accept-set by restricting the rule's input domain at construction. For LiteralIgnoreAsciiCase the runtime accept-set widens only when the pattern contains non-ASCII content the rule was never designed to handle anyway (ASCII case folding doesn't reach non-ASCII code points), so rejecting non-ASCII patterns at construction collapses the runtime / publish-set divergence by removing the wider accept-set entirely.
    - The chosen mitigation for LiteralIgnoreAsciiCase is the narrowing one: the constructor throws `ArgumentException` on any char outside 0x00..0x7F, which makes the multi-char first-cluster case unconstructable. The pattern is still relevant for any future rule that adds equivalence relations on top of stored literal data and can't narrow its input domain. The reviewer mental model is: `ComputeRuleStart` is a contract with the lookahead shortcut, and any runtime relaxation the publish-set doesn't reflect is a soundness bug, not a precision-loss bug. When adding a new accept-path to a rule's runtime, either widen the publish-set to match, or constrain the input domain so the wider accept can't be exercised.
    - The conservative fallback (when neither widening nor narrowing fits) is `AlwaysAdvancesByOneToken` (Universe under MustBeIn), which keeps the shortcut sound by never filtering. The middle ground (when the equivalence is enumerable for one position but not the whole cluster, like first-char-folds-but-rest-doesn't) is to seed the set with just the position-by-position variants the runtime actually checks.
    - Sites in the codebase to recheck when changing accept-semantics: `LiteralIgnoreAsciiCaseRule.ComputeRuleStart` (ASCII case folding, now bounded by the construction-time ASCII restriction), `LiteralRule.ComputeRuleStart` and `GraphemeRule.ComputeRuleStart` (no runtime fold, but Compile-time normalization rewrites `_expected` to the form's canonical version — the publish-set has to reflect post-normalization data, which is the topic of search-log entry `2026-05-06-firstconsumedtokens-vs-normalization-form-pass-ordering.md`), `OneOfRule.ComputeRuleStart` / `NoneOfRule.ComputeRuleStart` (the set is the publish-set directly; no relaxation to worry about), and any future user-defined Rule subclass that adds a custom accept-relation. <!-- style-lint-ok -->
    - State-machine engine: `Lowerer.CanSkipUnreachableAlt` and the per-alt `CheckPeekedRuneInSet` lowering consult the same compiled `Rule.FirstConsumedTokens` / `Rule.Polarity` fields. A widened publish-set or a tightened input domain flow through to both engines uniformly; a runtime-only fix that didn't update the publish-set or the input domain would leave the SM with the same wrong-skip bug.
    - Distinct from the sibling pattern `polarity-drop-preserves-fail-set-as-consume-set.md`. That pattern is about the polarity/set algebra getting out of sync in a wrapping or composing helper (so the published triple doesn't mean what its constituent fields claim). This pattern is about the published set being correctly typed but too narrow because the rule's runtime widened its accept-set. Both share the lesson that the shortcut's filter is only as sound as the publish-set, but the failure modes and the fix sites are different.
