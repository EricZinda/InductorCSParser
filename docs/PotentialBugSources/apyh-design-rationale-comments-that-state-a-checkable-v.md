- Design-rationale comments that state a checkable value or name a specific rule can drift wrong

  - The pattern: a comment explains *why* a design choice was made by citing a concrete behavior ("~~X is Y", "this keeps RuleZ from matching W"). Those citations are checkable against the code, and two failure modes recur:
    1. Off-by-one in the reasoning depth. The `operator ~` comment said "~~Surrogates is the scalar universe", but that's the value of a SINGLE complement. The double complement is `Empty`. Easy to write the intermediate value where the final one belongs.
    2. Naming the wrong code path after a refactor. The same comment (and a test comment) credited the surrogate-free `~` design with keeping `NoneOf(Letters)` from matching a lone surrogate under Compile(null). `NoneOf` is a direct non-membership test, not `OneOf(~set)`, so the `~` design never reaches it. The protected rule is `OneOf(~Letters)`. The claim reads as if it dates from a time when `NoneOf` was implemented as `OneOf(~set)`, and the implementation changed without the rationale following.
  - Why it matters: maintainers trust these comments. A wrong "~~X is the universe" can prompt someone to "fix" the operator and break a real invariant. A wrong "NoneOf excludes surrogates" can be relied on for input validation that doesn't hold. The behavior was correct in both cases. Only the explanation was wrong, so no behavioral test would catch it.
  - How to hunt: for any comment that states an equality (`~~X is Y`, `A & ~B == C`) or names a rule as having or avoiding a property, write the one-line assertion the comment implies and run it. If it passes, the comment is right. If it fails, the comment is the bug. Pay special attention to comments that reason about a *different* rule than the one whose source they live in (a comment in `TokenSet.cs` asserting something about `NoneOfRule`), and to comments that survived a refactor of how a rule is built (NoneOf, ScanUntil, the Identifier expansion).
