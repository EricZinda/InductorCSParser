- Shared mutable state on a per-input cached singleton races under concurrent parses
    - Shape: a `static readonly ConditionalWeakTable<TKey, TValue>` (or a similar singleton cache) is keyed on a value the caller controls (here, the input string instance). Two parses that arrive with the same key share one `TValue` instance. If `TValue` has mutable state that any operation writes during the parse (a lazily-walked `TextElementEnumerator`, a count, a bool[] high-water mark, a `_exhausted` flag), the two parses race on those writes. The race surfaces as a wrong return value or an `InvalidOperationException` from a downstream consumer that relies on the state being in a specific shape.
    - Why this is easy to ship by accident: the cache layer makes "is this state really shared" non-local. Each caller looks single-threaded, the field type doesn't shout that it's mutable (a private `TextElementEnumerator?` field looks like an implementation detail), and the test suite parses one string at a time so the race only fires under real workloads (a web server, a config reloader, a fuzz harness). LateBoundRule's `_resolvedFlattenType` field is the same shape done right: written once during single-threaded Compile, then read-only at parse time, so two parses of the same grammar never race. The trap is the cache populated lazily DURING the parse.
    - How it can surface as a security bug: a server that parses identical request bodies on parallel requests, an application that re-parses the same interned configuration string from multiple threads, or a fuzz harness that runs the same input many times in parallel can all trip the race. The consumer downstream of the cached state may then throw an "internal invariant violated" exception that bubbles past the parser, crashing the host (.NET can't catch a StackOverflowException either, and an unhandled InvalidOperationException in a request handler often crashes the process under the default crash-on-unhandled policy).
    - What to do when reviewing similar code: any field on a cached `TValue` that's NOT `readonly` is suspect. The reviewer should check whether every operation that writes that field is on a single-threaded path (e.g., set once during Compile), or whether two parses can reach it simultaneously. If parse-time writes are possible, the field needs a lock, a `volatile` read with an immutable-update pattern, or the cached `TValue` needs to be split into a "shared computed state" half (immutable after construction) and a "per-parse state" half (held on the Lexer / engine, not the cache).
    - Sibling shapes worth looking at when the next hunt picks this thread back up: `TokenSet._categoryCache` and `TokenSet._normalizedForCache` use `ConcurrentDictionary` and are correct, but the `Lazy<T>` and `ConditionalWeakTable<T1, T2>` patterns elsewhere in the codebase deserve a re-read with this in mind. Any future cache that maps "this input string to some computed value about it" inherits this trap unless it computes the value eagerly in the constructor.
