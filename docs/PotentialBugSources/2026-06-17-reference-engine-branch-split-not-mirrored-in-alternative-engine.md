- A decision the reference engine deliberately split into two branches must be split the same way in the alternative (state-machine) engine
    - Shape: the recursive engine is the reference. The state-machine engine is meant to be a drop-in alternative that produces the same `ParseResult` (same Success, same tree, same error position). When the reference engine *splits* a case that used to be a single branch, the alternative engine has to copy both halves, or it silently reintroduces the exact bug the reference engine already fixed.
    - Concrete instance: `Rule.ParseRecursive` once reported `Math.Max(DeepestFailurePosition, Position)` plus the deepest `WithError` message for *both* genuine grammar mismatch and trailing-input-after-success. On 2026-05-05 it split them: the trailing-input branch now reports `lexer.Position` (the first leftover character) with a generic message, because a rolled-back sibling alternative can have read past where the root stopped consuming. `StateMachineParser.Parse` kept the pre-split single branch (`if (!succeeded || trailingInputForbidden)`), so its trailing-input error pointed at the deepest read instead of the first leftover character. Found 2026-06-17.
    - Second instance: when the MalformedInput outcome landed (commit 9820520), `Rule.ParseRecursive` gained a pre-normalization branch that scans with `FindFirstUnnormalizableIndex` and turns input the normalizers reject (an unpaired surrogate, or U+FFFE) into a `MalformedInput` result at the offending code unit. `StateMachineParser` kept calling `UnicodeNormalization.Normalize` bare, so the same parse threw a raw `ArgumentException` out of `Parse` / `TryMatch` / the counter entry points. `Rule.Parse` dispatches to the engine hook *before* `ParseRecursive`, so the scan never ran on the alternative-engine path. Found and fixed 2026-07-29. The quick check for this instance's family: grep `ExperimentalSrc/` for the new outcome or helper name whenever a branch is added to `Rule.ParseRecursive`, and treat zero hits as the smell.
    - Where to look: any spot in `ExperimentalSrc/InductorParser/StateMachine/` whose comment says "mirrors the recursive engine", "same shape as Rule.Parse", or "matching Rule.ParseRecursive". Verify it mirrors the *current* recursive code, not an older revision. The post-success EOF / trailing-input handling, the budget-abort position math, and the deepest-failure ranking are the high-risk spots because the recursive engine has tuned each of them in separate commits the SM engine may predate.
    - Why it hides: the cross-engine test helper `AssertSameOutcome` (in `StateMachineParserTests.cs`) compares only Success and, on success, tree text. It doesn't compare `ErrorCharIndex` or `ErrorMessage` on failure, so any error-position divergence between the engines passes the existing suite. Differential fuzzing that also compares `ErrorCharIndex` is what surfaces these. A targeted regression test that asserts cross-engine error-position parity is what locks each one down.
