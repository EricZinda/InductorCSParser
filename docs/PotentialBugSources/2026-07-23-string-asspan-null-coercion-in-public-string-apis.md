- string.AsSpan() silently maps null to empty in public string-typed APIs
    - `MemoryExtensions.AsSpan` accepts a null string and returns an empty span. That's the right convenience inside the library, but when a public method takes a `string` parameter and immediately calls `text.AsSpan()` (usually to share a span-based implementation), the conversion quietly turns a null argument into "empty input". The caller who passed an accidental null gets the empty-input answer (0, false, no-op) instead of `ArgumentNullException`, and their bug hides. The trap is specific to `AsSpan` and friends: almost any other member access on the parameter (`text.Length`, `text[0]`) would have thrown something, but `AsSpan` is precisely the one that doesn't.
    - Concrete example: `GraphemeHelpers.Count(string)` opened with `text.AsSpan()`, so `Count(null)` returned 0, indistinguishable from `Count("")`, while its sibling `FloorToClusterStart` and both `NormalizationHelpers` methods threw `ArgumentNullException` for null. Fixed by adding the explicit null check before the `AsSpan` call (2026-07-23).
    - Review checklist: for every public method with a `string` (or array) parameter, if the first use of the parameter is `AsSpan()` / `AsMemory()` or passing it to a span-taking overload via the implicit string-to-span conversion, check for an explicit null check above it. Span-typed parameters themselves are exempt: a null string converting to an empty span at the caller is the BCL's own convention, and there's no null span to reject. The related-but-different case of preflight work before validation is 2026-05-28-public-entrypoint-preflight-before-argument-validation.md.
