- Per-call StringInfo.GetNextTextElement segmentation when a cached grapheme-boundary index already exists
    - `StringInfo.GetNextTextElement(string, index)` allocates a fresh substring for the whole grapheme cluster at `index` every time it's called, even when the caller only wants the cluster's `.Length`. On a path that walks a string cluster-by-cluster, that's one throwaway string allocation per cluster, per walk. The parser keeps `GraphemeClusterIndex` (a per-input `bool[]` of cluster-start positions, cached by string instance via a `ConditionalWeakTable`) precisely so a cluster length is a bool-array read (`LengthAt`) instead of a `GetNextTextElement` call. Its class header says exactly this. Any code that segments a string with `GetNextTextElement` instead of going through `GraphemeClusterIndex.For(s)` is re-paying the allocation the cache was built to remove.
    - The shape that bit `NormalizedPositionMap.TranslateViaLockstep` (the default FormC/FormD position-translation walker): it stepped both the original and the normalized string with `StringInfo.GetNextTextElement(...).Length` on every call. Every `Symbol.SourceRange`, `Symbol.SourceText`, and parse-failure-position read on non-ASCII input routes through this walker (ASCII / already-NFC input takes the `ReferenceEquals(original, normalized)` fast path and skips it). Walking a parse tree reads one position per node, so the per-call substring storm multiplied across the whole tree. Fix: step through `GraphemeClusterIndex.For(original)` / `For(normalized)` with `LengthAt`. The normalized side's index is already built by the lexer during the parse. The original side's builds once and is reused by every later lookup on that input.
    - Symptom is allocation pressure and GC churn, not a wrong answer, so it won't surface in a correctness test or a `RuleCountLimit`/`Timeout` budget. It hides on ASCII grammars (the `ReferenceEquals` fast path skips the walker entirely) and only shows up under non-ASCII input that actually changes under normalization (decomposed accents, compatibility forms, anything where `parseInput != input`). Demonstrate it with `GC.GetAllocatedBytesForCurrentThread()` around a single deep-position translate: pre-fix the bytes scale with the offset being mapped, post-fix they're a small constant.
    - When reviewing any walk over a string in this codebase, ask: is this stepping clusters with `StringInfo.GetNextTextElement` / `StringInfo.GetTextElementEnumerator`? If it only needs boundary positions or cluster lengths (not the cluster text itself), route it through `GraphemeClusterIndex` instead. The one case where the cache doesn't help is when the algorithm genuinely needs the cluster's *text*, not just its length, such as the compatibility-form walker `TranslateViaPerGraphemeNormalize` that substrings each chunk to `.Normalize(form)` it. There the substring is the work, not waste, and the cached index wouldn't remove it.
