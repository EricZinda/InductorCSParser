- Public-default struct with reference-typed fields coalesced only by the constructor
    - A `readonly partial struct` that exposes a public `default`-aliased constant (e.g. `public static readonly TokenSet Empty = default;`) makes the default value first-class user-facing API. Any reference-typed field on the struct that the constructor coalesces null to a non-null value (e.g. `_multiRuneGraphemes ?? Array.Empty<string>()`) reads as null on the public default, because the constructor never ran. Methods that read those fields directly without a null-check work fine for every factory-built instance and crash with NullReferenceException on the public default.
    - The shape: `default(T)` and `T.Empty` are the same value. Every other instance comes from a factory or operator that runs the constructor and gets the coalesced field. So 99.9% of test coverage exercises non-null fields and the unguarded direct-read goes undetected. The crash only appears when a real user composes the public default into an actual parse-time path: `OneOf(TokenSet.Empty)` for a programmatically-built stop list that nothing got added to, an intersection that came out empty, an explicit `Empty` placeholder. See backlog `tsne` for the TokenSet.ContainsToken instance.
    - Watch for: any method on the struct that reads a reference-typed field via `.Length`, `.Count`, `.GetEnumerator()`, `[index]`, or any other member access without first caching to a local and null-checking. The pattern that prevents the bug is the same one already used elsewhere in TokenSet: `var foo = _foo; if (foo == null) return ...; ...`. The pattern that re-introduces the bug is `if (_foo.Length > 0 && ...)` or `foreach (var x in _foo) ...` without a null-check.
    - Reviewer mental model: when adding a method to a struct whose default is a public constant, ask "would `default(T).MyNewMethod()` crash?" If the answer involves any reference-typed field, the method has to either delegate to a method that already null-coalesces (e.g. an internal accessor like `MultiRuneGraphemes => _multiRuneGraphemes ?? Array.Empty<string>()`) or null-check directly. Don't trust that "the constructor sets it" is enough — `default(T)` skips the constructor.
    - The same shape applies to any opt-in / opt-out flag fields, lazy caches, or computed-once arrays that get filled by Compile passes or Build passes after construction. If `default(T)` is a public value AND a reachable code path can read those fields before the fill pass runs, the read needs a null-check or a default-state branch.
    - Cross-reference: `ContainsRune(int codepoint)` (line 124-134 of TokenSet.cs) is the canonical example of doing it right. It caches `_ranges` to a local, null-checks, then walks. `MultiRuneGraphemes` accessor (line 122-123) is the canonical accessor-side pattern, coalescing null to `Array.Empty<string>()` so callers don't have to think about it. The TokenSet.ContainsToken bug (line 172, fixed in `tsne`) is the canonical counter-example.
    - Another fixed instance: `SourcePosition.Input` (2026-07-29). The struct isn't `default`-aliased to a public constant, but it's a public struct consumers store in their own AST nodes, arrays, and dictionaries, so `default(SourcePosition)` reaches real code anyway (an uninitialized field, a TryGetValue miss, FirstOrDefault). The constructor coalesced null input to the empty string, `default` skipped the constructor, and `SourceLine()` / `TokenColumn` / `SourceRange.SubstringOfInput()` all crashed with NullReferenceException. Same accessor-side fix: `Input => _input ?? string.Empty`. The lesson worth keeping: the pattern applies to every public struct with a reference-typed field, not just ones that promote `default` to a named constant.
