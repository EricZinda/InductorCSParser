- Rendering code that walks `char` values has to distinguish valid surrogate pairs from unpaired surrogate halves
    - Shape: a diagnostic or display helper walks a UTF-16 string one `char` at a time and decides whether to render each code unit verbatim. It deliberately lets surrogate halves through so supplementary-plane characters (emoji, historic scripts, math alphanumerics) reassemble as the original character. That is correct only when the high surrogate is immediately followed by a low surrogate inside the displayed range.
    - Why it bites: under `Compile(null)`, the parser intentionally supports malformed UTF-16 round-tripping. A lone high or low surrogate can reach error messages, trace output, and tree rendering. If a renderer treats every surrogate half as "part of a supplementary character" and writes it raw, the output string contains an unpaired UTF-16 code unit. Downstream encoders may replace it with U+FFFD or reject it, and the diagnostic no longer tells the user whether the input held U+D800, U+DBFF, U+DC00, etc.
    - Concrete instance: `DisplayEscape.AppendEscaped` / `Escape` escaped Control, LineSeparator, and ParagraphSeparator chars but not unpaired surrogates. The fix preserves complete high+low pairs verbatim and renders any surrogate half not paired within the displayed span as `U+XXXX`.
    - Audit hook: when reviewing any renderer that walks UTF-16 code units, test three cases together: a valid supplementary-plane character should stay intact, a lone high surrogate should render as its code unit, and a range that starts or ends in the middle of an otherwise-valid pair should render the exposed half as a code unit. A simple `char.IsSurrogate(c) == false` / category-only predicate is not enough because paired and unpaired surrogate halves need opposite behavior.
