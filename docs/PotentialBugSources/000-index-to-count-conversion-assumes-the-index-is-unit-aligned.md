- Index-to-count conversion assumes the index is aligned to the unit boundary
    - A converter that turns a fine-grained index (a char offset) into a coarse-grained count or index (a token / grapheme-cluster index) by counting unit-START markers strictly before the index is correct only when the index itself sits on a unit boundary. For an index that lands INSIDE a unit, counting starts also counts the containing unit, overshooting by one.
    - The instance: GraphemeClusterIndex.CountClustersUpTo counted grapheme-cluster starts in [0, charIndex), so SourcePositionConverter.ToTokenIndex / SourcePosition.From over-reported TokenIndex by one for a char index inside a multi-char cluster (a surrogate-pair emoji, a CRLF cluster, a base+combining sequence). The parser itself never feeds a mid-cluster index, error positions and Symbol ranges are all cluster-aligned, so it stayed invisible until a caller handed an arbitrary offset to the public SourcePosition.From.
    - The sound count is "units whose END boundary is at or before the index" (fully-contained units). It agrees with the start-count whenever the index is boundary-aligned and degrades gracefully, not off-by-one, when it isn't.
    - Reviewer check: any helper that maps a position expressed in unit-A coordinates to a count expressed in unit-B coordinates: does it assume the position is B-aligned? If a public entry point can hand it an unaligned position, the count is wrong by the partial unit. The doc comment is a tell: CountClustersUpTo said "clusters fully contained in [0, charIndex)" while the code counted starts, and the unit test had baked the start-count into its reference model.
