- A dispatch predicate built on top of a display-label accessor inherits the accessor's fallback labels
    - The shape: one accessor returns a human-readable label and is allowed to fall back to a synthesized default when the real thing is absent (`Rule.NameOf` / `Symbol.DisplayName` return the class-derived trace label "And" / "OneOrMore" for an unnamed rule, and the rune's text for an unnamed character rule). A second API is a *predicate* meant to answer "is this the rule the author named X?" and is documented to be true only for user-supplied `.As(...)` names. If the predicate is implemented as `displayLabel == X`, it silently inherits the accessor's fallbacks: `Symbol.Is("And")` returned true for every anonymous `And` node because `Symbol.DisplayName` resolved to the trace label "And". (The accessor was called `Symbol.Name` when the bug was found. It was renamed to `DisplayName` afterward to make the display-label role obvious and discourage exactly this misuse.)
    - Why it slips through: the label accessor is correct on its own terms, since a debug label *should* fall back to something printable. The predicate is also correct for the common case (a real user name). The bug only shows when a caller passes a string that happens to collide with a fallback label, which test suites rarely do because they exercise the predicate with names they themselves chose via `.As(...)`.
    - The tell: two name-lookup APIs documented as "equivalent" that are built on *different* indexes. Here `Rule.IdOf` walks the forward index `CollectIdsByName` builds, which only stores user `.As(...)` names (trace labels are skipped on purpose because they aren't unique). `Symbol.Is(string)` walked the display-label accessor → `Rule.NameOf`, which consults the reverse index that *does* carry trace labels. Same-sounding promise, different data, divergent answers. When you see one API's doc say "equivalent to" another, check they resolve through the same index.
    - The fix pattern: implement the predicate by resolving the *name* through the user-name index and comparing ids (`grammarRoot.IdOf(name) == symbol.Id`), not by comparing against the display label. That keeps the predicate matching exactly the named rules and keeps it genuinely equivalent to the other lookup. Don't reuse a display accessor as the backing store for a predicate documented to answer a narrower question than the accessor returns.
    - Watch for: any `bool IsX(string)` / `Matches(name)` / name-keyed dispatch helper whose body compares against a `.Name` / `.Label` / `.DisplayName` property. Ask whether that property has a fallback (a default name, a type name, an "unknown" string). If it does, and the predicate's doc excludes those, the predicate is wrong for inputs equal to a fallback value.
