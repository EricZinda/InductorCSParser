- Normalized input leaks into user-facing strings
    - The parser normalizes the caller's input before lexing (`Compile(NormalizationForm?)`, default FormC). Internally everything works in `parseInput` (post-normalization) coordinates: the lexer reads it, rules record failures into it, the deepest-failure marker is in it. At the boundary where a position becomes user-facing, `NormalizedPositionMap.TranslateToOriginal` maps the offset back to the original input so editor diagnostics, line/column/token reports, and `Symbol.SourceRange` all index into the string the caller passed to `Parse`.
    - The trap: any user-facing string that quotes CONTENT from the input has to read it from the ORIGINAL string, not from `parseInput`. Under FormC the two strings often look the same (FormC composes "e" + combining acute into precomposed "é", but the user sees the same glyph either way). Under FormKC the difference is loud: fullwidth `'１'` folds to ASCII `'1'`, the `'ﬁ'` ligature folds to "f"+"i", Mathematical Bold letters fold to plain ASCII. A string built from `parseInput` says one thing, the user's source code says another, and the user has no way to reconcile the two.
    - Concrete instance: `BuildErrorMessage`'s `{character}` placeholder used `StringInfo.GetNextTextElement(parseInput, posInParseInput)` while the same template's `{charIndex}` / `{tokenIndex}` / `{line}` / `{column}` were built from `(failurePos, input)`. Fix: read from `(input, failurePos)` to match the rest of the placeholder family.
    - When auditing a new user-facing rendering site, the question is: does this string quote content the user could read off their source? If yes, the bytes have to come from `input`, not `parseInput`. The two safe substitutions are `StringInfo.GetNextTextElement(input, originalOffset)` for one grapheme and `input.Substring(originalOffset, originalLength)` for a span. Trace output is a separate surface (developer-facing, not user-facing) and legitimately renders what the lexer saw, so it can keep reading from `lexer.Input`.
