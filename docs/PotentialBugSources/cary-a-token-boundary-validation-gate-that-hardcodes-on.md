- A token-boundary validation gate that hardcodes one tokenization mode
    - The lexer has two token models: one grapheme cluster per token (the default, every top-level parse) and one rune per token (the WithinTokenRule sub-lexer, so an inner rule can walk the runes inside a cluster). `Lexer.NextTokenLength` already branches on `_oneRunePerToken`, so `Read` / `PeekToken` / the per-token slow loops are mode-correct by construction.
    - The trap is a helper that decides "is this offset a valid token start?" but answers only for the grapheme model. The byte-level scanner fast paths (`AdvanceUntilRuneIn`, `AdvanceUntilLiteralCandidateIn`) search by UTF-16 code unit and re-validate each landing through such a gate. When the gate consults only `GraphemeClusterIndex`, it is correct in grapheme mode and wrong in one-rune mode: a combining mark / ZWJ / cluster continuation is its own token in one-rune mode, but the grapheme index reports it as cluster-interior, so the fast path skips a valid stop and diverges from the slow path that walks `NextTokenLength`.
    - When reviewing any lexer helper that answers a "where can a token start / end" question by hand (consulting `GraphemeClusterIndex`, hardcoding CRLF/surrogate logic, etc.), ask: does this run inside the one-rune sub-lexer, and if so does it use the rune token model there? The fix is to branch on `_oneRunePerToken` the same way `NextTokenLength` does. In one-rune mode the only interior offset is the trailing half of a surrogate pair.
    - Related but distinct from docs/PotentialBugSources/o000-byte-level-fast-paths-that-bypass-grapheme-tokeniz.md, which is about *adding* a boundary gate to a byte-level fast path. This pattern is the gate being present but scoped to the wrong token model.
    - Worth a second look: this hazard is easy to ship undetected because the only one-rune caller (WithinTokenRule) discards the inner tree and its scanner-skip shape consumes to end-of-input either way, so a divergence inside it produces correct public output. A fast/slow differential at the lexer-method level (run the same scan with the vectorized candidate array and with it null, assert the landing matches) catches it where a parse-output differential can't.
