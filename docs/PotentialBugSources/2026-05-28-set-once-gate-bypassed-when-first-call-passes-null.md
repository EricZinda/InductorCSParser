- Set-once gates bypassed when the first call passes null
    - A fluent set-once API typically checks itself with "throw if the backing field is already non-null." That works for normal use, where the first call writes a real value and the second call sees a non-null field. It breaks when the first call passes null: the field stays null, the gate stays open, and a later call writes whatever it likes (including overwriting *sibling* state the first call also wrote).
    - Concrete example: `Rule.As(string name)` checked `if (Name != null) throw ...`, but accepted `name == null` and ran `ApplyIdentificationFlattenPolicy(...)` first (which silently flipped a default-non-Preserve `FlattenType` to Preserve). After `Token('a').As(null!)`, Name was still null, FlattenType was Preserve, and a later `.As("real")` quietly succeeded. `Rule.WithError(string errorMessage, bool forced)` had the same shape: `WithError(null!, forced: true)` wrote `_errorForced = true` without writing `_errorMessage`, and a later `WithError("real")` passed the set-once check and overwrote the forced flag back to its default. Fix in both cases: a single `if (param == null) throw new ArgumentNullException(nameof(param));` at the very top of the method, before any sibling-state mutation, matching the order `Rule.Parse(string, ParseOptions)` adopted in `d52ad58`.
    - Review checklist: for every public fluent setter whose set-once check is "field already set," check that null is rejected before any other side effect runs. Also check for `bool` companion parameters (like `forced`) or `FlattenType` side effects whose writes depend on the main string being non-null. Those are the sibling-state mutations a null-first call leaves in an inconsistent state. The pattern composes with `2026-05-28-public-entrypoint-preflight-before-argument-validation.md`. Both ask for null checks at the top of the method, both for the same reason: preflight that runs before argument validation can put the object in a state the validator can no longer detect.
