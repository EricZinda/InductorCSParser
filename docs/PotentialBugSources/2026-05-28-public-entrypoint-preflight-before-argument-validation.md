- Public entrypoints that do preflight work before argument validation
    - A public API boundary should validate required arguments before doing convenience preflight, normalization, cancellation, tracing, or fast-path checks that dereference those arguments. If the preflight comes first, invalid inputs can surface as misleading implementation exceptions (`NullReferenceException`) or, worse, take a different semantic branch before the caller gets the argument error.
    - Concrete example: `Rule.Parse(string input, ParseOptions options)` had a pre-canceled parse fast path that read `options.Cancellation` before checking `options`, and the recursive path normalized `input` before checking `input`. `Parse("a", null!)` threw a raw null-reference exception, and `Parse(null!, options)` depended on whether the cancellation preflight fired before the normal parsing path. The fix is to put `ArgumentNullException` checks for both arguments at the very top of the public overload.
    - Review checklist: on every public method, scan from the opening brace to the first argument check. Any read of a parameter property (`options.Cancellation`), extension/helper call (`input.Normalize(...)`), template formatting, or fast-path return before null/range validation is suspect. The test should cover any special fast path too, not only the normal path, because fast paths are where validation order most often drifts.
