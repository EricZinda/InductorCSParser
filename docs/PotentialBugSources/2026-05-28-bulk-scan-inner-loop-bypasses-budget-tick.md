- Bulk-scan inner loop consumes work units without ticking the parse budget
    - Shape: a `Rule.TryParseRule` (or a `Lexer` scanning primitive called from one) whose body is `while (!lexer.IsEof) { ... }` or `while (_position < _endPosition) { ... }` and that consumes one token per iteration without going through anything that calls `_budget.TickPeriodic()` (or `EnterRule()` / `ExitRule()`). The loop's iteration body does real work (TokenSet membership check, position advance, maybe an escape sub-rule) but doesn't itself enter a child Rule.
    - Why it bites: the `ParseBudget` periodic check (Timeout, Cancellation, RuleCountLimit) is gated on the 1024-invocation mask inside `EnterRule` / `TickPeriodic`. A Rule whose `TryParseRule` consumes N tokens in a tight inner loop is ONE `EnterRule` from the engine's view (when the rule opens) and one `ExitRule` (when it returns). So the periodic budget check fires at most twice for the whole run: once at scan-open (when the outer caller enters the rule), once at scan-close (when the next outer rule enters). Between those two points the parser is wholly unresponsive to `Timeout` and `Cancellation`, and `RuleCountLimit` undercounts the actual work by N. An attacker who feeds a long matching input to a hot scan rule (a JSON string body, a CSV field, an identifier of all letters) pins the parser through the whole run with no budget observation.
    - Where it has shown up in this codebase:
        - `ScanWhileRule` via `Lexer.AdvanceWhileRuneIn` / `AdvanceWhileTokenIn` (fixed [2026-05-28](../BugSearchLog/2026-05-28-bulk-scan-loops-bypass-budget-tick.md): per-iteration `_budget.TickPeriodic()` inside both AdvanceWhile primitives).
        - `ScanUntilRule`'s body scan loop, both the TokenSet and Rule stopper paths (fixed [2026-05-28](../BugSearchLog/2026-05-28-bulk-scan-loops-bypass-budget-tick.md): per-iteration `lexer.Budget.TickPeriodic()` inside the `while (!lexer.IsEof)` body).
    - How to look for more: search for `while (!lexer.IsEof)`, `while (_position < _endPosition)`, `while (lexer.Position < ...)`, `while (pos < ...)` inside any `Rule.TryParseRule` body or `Lexer` scanning method. For each match, walk the iteration body and ask "does anything here go through `EnterRule` (a `Rule.TryParse` call) or `TickPeriodic` (a direct budget tick)?" If neither, it's a candidate. The `BetweenInclusiveRule` shape (`while (count < AtMost) { ParseChild(Inner, ...); ... }`) is fine because `ParseChild` → `Rule.TryParse` → `EnterRule` ticks per iteration. The bug specifically wants iteration bodies that don't enter a child rule.
    - Why "wait for the next `EnterRule` to catch it" isn't a fix: the engine has no way to interrupt a single rule invocation that's already running. A rule whose `TryParseRule` takes 30 seconds to return is a rule that is wholly unresponsive to the caller's `Timeout` / `Cancellation` for those 30 seconds. The fix has to live in the rule's own inner loop, not outside it.
    - The amortization side: the Budget's own 1024-invocation mask amortizes the actual `Stopwatch.Elapsed` / `cancellation.IsCanceled` read to one in 1024 ticks, so the per-iteration cost of the fix is one int increment plus one mask compare. That's ~2-3 ns on the hot loop, against the ~30-100 ns of useful work each iteration already does (TokenSet binary search, position advance, trace check). Acceptable overhead for the security guarantee.
    - Adjacent: the WithinTokenRule sub-lexer fix ([2026-05-19](../BugSearchLog/2026-05-19-withintoken-sub-lexer-no-budget-propagation.md)) addresses the same "single Rule invocation bypasses the budget" shape from a different angle (a fresh sub-lexer with its own budget counter). The fix there is `Budget.InheritFrom(outer)` so every inner tick forwards to the outer. The fix here is to ensure the ticks happen in the first place. Both fixes together close the gap for any scan-shaped rule that runs through WithinToken.
