- "Is the user pointing at this rule?" gates that only consult one of the rule's user-identification fields
    - A `Rule` has two ways the user can say "find me by reference": `.As(string)` sets `Name`, `.As(SymbolId)` pins `Id`. Some optimizations check only one of those fields and silently misbehave on the other. The pre-fix leaf-Id shortcut in `OneOfRule` / `AnyTokenRule` / `NoneOfRule` / `WithinTokenRule` had the shape `(Name == null && runeValue >= 0) ? new SymbolId(runeValue) : Id`: it skipped the rune-as-leaf-id optimization for `.As(string)`-named rules but kept it for `.As(SymbolId)`-pinned ones, so `Tree.Find(rule)` / `Tree.Is(rule)` returned null / false on a single-rune match against a rule the user pinned an id on without also naming. The `.As(SymbolId)` use case is documented as cross-version stable numbering for serialized parse trees, so the silent loss of the pinned id is a real bug for that workflow. See backlog p1nd. Sibling case fixed earlier in `z002`: the `Name`-only path was the previous half of this same shape.
    - The fix consults the existing `IsUserSymbolIdPinned` accessor on `Rule` (added by the `xpid` fix for the GraphemeRule normalization re-pin shape, which is a sibling consumer of the same flag). The leaf-id gate becomes `(Name == null && !IsUserSymbolIdPinned && runeValue >= 0) ? new SymbolId(runeValue) : Id`. Truly anonymous rules (neither named nor pinned) keep the optimization. Either user signal disables it.
    - Two distinct consumer-side patterns for the same flag. The xpid doc (`xpid-compile-time-auto-pin-overriding-user-supplied-pins.md`) covers the "auto-pin sites that walk over user pins" pattern (the `SetIdInternal` callers in subclass `CollectNormalizationOffenders`). This doc covers the "user-identification gate" pattern (decide whether the user "asked for" the rule by reference, then either honor the user's id or use a default). Both ask "did the user pin?" but for different downstream behavior. Reviewer mental model: any code that branches on whether the user identified a rule needs to consult BOTH `Name` and `IsUserSymbolIdPinned`. `Name == null` alone is half the check.
    - When adding a new "the user identified this rule, so honor their reference" branch, ask: does it consult BOTH `Name` and `IsUserSymbolIdPinned`? `Name == null` alone is half the check. The reference shape post-fix lives in the four leaf-emitting rules above. Watch out for the same shape in any future code that surfaces a leaf id, formats a rule name, or short-circuits a lookup based on whether the user "asked for" the rule by reference; the symmetry between `.As(string)` and `.As(SymbolId)` is part of the public contract.
    - State-machine equivalent in `ExperimentalSrc/InductorParser/StateMachine/Stepper.cs:Step_EmitLeafOneOf` has the same gate shape but reads from `SymbolMetadata`, which doesn't carry `Name` or the pinned-id flag yet. The same fix would require widening the metadata struct. Tracked as the follow-up section in backlog p1nd.
