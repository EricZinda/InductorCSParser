- Mid-cluster failure positions reaching the outer parser
    - Related to "Char-unit rendering in user-facing strings": even when rendering uses the right primitive, the POSITION fed into it can be mid-cluster if a sub-lexer in rune-per-token mode (only `WithinTokenRule` today) hands its inner rune offset straight to `outerLexer.RecordFailure`.
    - The outer parser treats the whole cluster as one token, so the recorded position needs to snap back to the outer cluster's start before it leaves the rule. `WithinTokenRule` had this shape; see backlog p3kt.
    - When reviewing a rule that drives a sub-lexer (or otherwise records a position computed in finer-than-grapheme units), ask: would `StringInfo.GetNextTextElement(input, pos)` return a "defective" cluster fragment at this `pos`? If yes, the outer-view invariant is broken and `ErrorTokenIndex` / `{character}` will lie about what the user typed.
    - The fix is to record at `transaction.StartPosition` (the outer cluster's start) rather than the sub-lexer's rune position. Trace messages can keep the inner offset for debugging since it's inner-token relative.
    - Second trap in the same place: a sub-lexer `Position` / `DeepestFailurePosition` is a 0-based UTF-16 *char* offset into the substring, NOT a rune count, even though the rune-per-token model and these comments talk in runes. For a supplementary-plane rune (an emoji, a CJK-extension character) one rune is two chars, so a trace line that prints `subLexer.Position` straight through as a "rune offset" or a "consumed X/Y runes" count over-reports by one per astral rune (e.g. `consumed only 2/4` for a two-rune 👍🏽 cluster where the inner consumed one rune, when it should read `1/2`). `WithinTokenRule` had this shape in both its failure-branch trace lines. The fix is to convert char offsets to rune counts with the lexer's own rune model (`RuneHelpers.RuneCount` / `RuneHelpers.IsSurrogatePairAt`: a well-formed surrogate pair is one rune, a stray surrogate is one rune) before printing. See also [char-unit-rendering-in-user-facing-strings](char-unit-rendering-in-user-facing-strings.md) and [index-to-count-conversion-assumes-the-index-is-unit-aligned](index-to-count-conversion-assumes-the-index-is-unit-aligned.md): same root cause, a UTF-16 char quantity passed off as a grapheme- or rune-level one.
