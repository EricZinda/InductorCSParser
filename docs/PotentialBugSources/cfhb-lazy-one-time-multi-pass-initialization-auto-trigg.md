- Lazy one-time multi-pass initialization auto-triggered from a hot/shared path, gated only by a non-synchronized flag
    - Shape: an object exposes a "use me" entry point (here `Rule.Parse` / `NameOf` / `IdOf`) that, for convenience, lazily runs an expensive one-time initialization the first time it's called (`Compile`). The trigger is a bare `if (!_done) Initialize();`. The initialization walks a graph and mutates per-node state across several passes, and the passes assume nothing else is mutating concurrently. Nothing serializes the trigger. When the entry point is reached from two threads before the first init finishes, both pass the flag check and both run the mutating passes at once. The shared writes race.
    - Why it's easy to ship by accident: the lazy trigger reads as a harmless convenience ("Parse compiles automatically so you don't have to"), and every test compiles-then-parses on one thread, so the init has always already happened by the time anything concurrent runs. The race only fires on the *first* concurrent batch against a not-yet-initialized instance: a web server whose `static readonly Rule Grammar = ...;` field is parsed from request handlers, a config object parsed in parallel on startup, a fuzz harness that shares one target.
    - How it surfaces: most often as a spurious exception from a *self-consistency check inside the init* (here `CheckNoSealedReachableRules`, which throws when it walks into a node a concurrent init already sealed) rather than as silently wrong output. That's a tell: if the init's passes are otherwise deterministic and idempotent (same ids, same derived fields regardless of which thread wins), concurrent runs converge on the same final state, and the only way to *observe* the race is the brief window where one thread sees another's half-applied work. So "two concurrent first-uses throw an internal-looking error, but a single use never does" is the fingerprint. Torn reads of multi-field struct values written during init (a `TokenSet` is two reference fields) are the rarer, scarier failure that does corrupt output.
    - Two valid resolutions, and picking the wrong one is its own mistake. (A) Make the init thread-safe: a double-checked lock on a per-instance gate, plus a `volatile` flag written *last* so a lock-free reader that sees the flag set is guaranteed (release/acquire) to see every field the init populated. (B) Declare the init a single-threaded build step that the caller must run before sharing, and document that. Choose (A) when the lazy init genuinely belongs on the shared/hot path and callers can't reasonably be expected to pre-initialize. Choose (B) when initialization is conceptually a build/setup step that happens once and the synchronization would tax the hot path forever for what is really caller misuse. This codebase chose (B) for `Compile`: a grammar is built and compiled once, then the immutable compiled graph is shared, so the rule is "compile (or do one warm-up parse) single-threaded, then parse concurrently," documented in docs/InductorParserReference.md "Thread Safety" with a design-note comment on `Rule.Compile` so a future hunter doesn't re-add the lock. The thing you *don't* get to do is leave it undocumented and unsynchronized.
    - What to look for when reviewing: any `if (!_initializedFlag) DoExpensiveOneTimeSetup();` where the entry point is reachable from multiple threads and `DoExpensiveOneTimeSetup` mutates state the later (post-init) reads depend on. Then ask which resolution applies. Grep targets in this codebase: `if (!_sealed)` (the auto-compile sites) and any future `??=` / `if (_x == null) _x = Build()` lazy cache that's reachable from `Parse` or a tree-walk accessor. The benign cousin is a lazy build whose result is computed into a fresh local and only the final reference is published (`_nameIndex ??= BuildNameIndex()` is this done right: double-build wastes work but never publishes a half-built value). The trap is the in-place multi-pass mutator.
    - Related: `[[0-2026-05-20-cross-graph-mutation-from-a-second-compile]]` is the sibling shape (Compile mutating shared sealed sub-nodes reached from a *second root*, single-threaded) and `[[0-2026-05-20-shared-mutable-state-cached-per-input]]` is the GraphemeClusterIndex per-input cache race (resolution (A): it's on the parse hot path, so it got the lock). All three are "Compile / per-parse setup mutates state under the assumption nothing else relies on it". The difference between them is which resolution fits.
