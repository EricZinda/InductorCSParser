- A per-node accessor converts an offset by walking the input from 0, so calling it once per tree node is quadratic in the document size

  - Shape: a conversion from a char offset to some derived coordinate (line/column, token index, a cumulative count) is implemented as a scan from offset 0 to the offset. That's correct and cheap when called once per parse (the error path: one failure position). It turns quadratic the moment the same conversion is called once per parse-tree node, because a node at offset P costs O(P) and the offsets of N nodes spread across an L-char input sum to O(N x L). The per-call cost reads as fine in isolation and is even documented as "O(charIndex)". The quadratic only emerges from the calling pattern, which the unit suite (short inputs, few nodes) never exercises.
  - Who calls it once per node: `Symbol.SourceRange` builds a start and an end `SourcePosition` for the node, and `SourcePosition.From` eagerly computes all four units (char, token, line, column). A consumer that wants positions on many nodes (an LSP server emitting diagnostics or semantic tokens, a typed-AST projection that records each production's span, a pretty-printer) reads SourceRange across the whole tree. That's the real-grammar workload the conversions are quietly quadratic under.
  - Concrete instance (2026-06-04): `SourcePositionConverter.ToLineColumn` walked the input char by char from 0 counting line breaks, and `GraphemeClusterIndex.CountClustersUpTo` scanned its boundary bool[] from 1 to charIndex, both O(charIndex) per call. Reading SourceRange on every node of a 16K-line input under PreserveAllSymbols took ~36,900 ms (size-doubling ratio 3.85x, i.e. quadratic). Fix: cache line starts per input in `LineStartIndex` (sorted offsets + binary search, O(log lines)) and back `CountClustersUpTo` with a build-once cumulative-count array (O(1) per query, with an O(1) identity shortcut for inputs that contain no multi-char cluster, which is the common ASCII/BMP case and pays no extra memory). After: ~186 ms, ratio 1.60x (linear). ~198x at 144K chars.
  - Why it hides: it's not a correctness bug, so no test fails and behavior is byte-for-byte identical before and after. It hides on short inputs (unit grammars), on the error path (one conversion per parse, never a tree walk), and even on the ASCII fast path: the `ReferenceEquals(original, parseInput)` shortcut in SourceRange only skips the normalized-position translation (NormalizedPositionMap), not the line/column/token walks, so this bites pure-ASCII grammars too, unlike the normalization-only position-map cost. A per-call "O(charIndex)" comment reads as a deliberate, bounded cost rather than a quadratic-across-a-tree trap.
  - Where else to look: any accessor that converts or derives from an offset/index by scanning from 0 (or to the end) and is reachable per-node or per-token. Cumulative counts, "which Nth thing is at this offset," line/column, byte-offset-from-char-offset, a "find the enclosing X for this position" scan. The tell is an O(position) loop behind a property that a tree/token walk would naturally call many times, especially when its own comment frames the cost as per-call. The fix is the same each time: build a per-input index once (the codebase already uses a `ConditionalWeakTable`-keyed cache idiom: `GraphemeClusterIndex`, now `LineStartIndex`) and answer each query with a binary search or an O(1) prefix lookup.
  - Test that catches it: an equivalence sweep of the cached conversion against the naive walk it replaced, at every offset, over inputs that exercise the whole space (all the line-terminator kinds for line/column, plus multi-char clusters for token index), which catches an off-by-one in the binary-search/prefix handoff. The size of the win is best shown with a one-off measurement comparing the size-doubling ratio (near 2x = linear, near 4x = quadratic) rather than an absolute timing. Don't assert timings, lean on the equivalence sweep as the permanent regression test.
