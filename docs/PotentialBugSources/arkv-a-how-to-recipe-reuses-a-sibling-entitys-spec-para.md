- A how-to recipe reuses a sibling entity's spec parameter without re-checking the cited spec
    - Shape: a doc presents several near-identical recipes for related targets (the per-language identifier recipes in UnicodeGotchas.md: Python 3, Rust, ECMAScript, C#, Java, Swift). The recipes share most parameters, so it's tempting to copy one wholesale and tweak the obvious difference, leaving a non-obvious parameter wrong for the new target.
    - Concrete instance (2026-06-06): the Rust recipe was copied from the Python 3 recipe and kept `Compile(NormalizationForm.FormKC)`. Python 3 normalizes identifiers with NFKC (PEP 3131), but Rust uses NFC (Rust Reference "Identifiers", RFC 2457). The shared parts (XID sets, `_` in Start) were right, but the form was wrong. It compiled and passed a happy-path ASCII test (`_foo`), so it slipped through.
    - Why it hides: the wrong parameter only changes behavior on inputs that exercise the difference. Here NFKC vs NFC only diverges on compatibility characters (ligatures, fullwidth Latin, circled/superscript digits, math letters). An ASCII smoke test can't tell the two forms apart.
    - How to catch it: for each recipe, pull the cited spec and verify every parameter, not just the headline one. For normalization-form recipes, write at least one assertion on a compatibility character that NFKC converts and NFC doesn't (e.g. a circled digit `①`, the `ﬁ` ligature, or fullwidth `ｆｏｏ`), so the test fails if the form is wrong.
