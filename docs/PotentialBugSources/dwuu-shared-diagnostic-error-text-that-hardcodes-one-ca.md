- Shared diagnostic / error text that hardcodes one caller's semantics
    - A helper that builds a user-facing message (a Compile error, a validation failure, a trace line) is often shared by several callers. When the message asserts a *consequence* about the rule ("so no input can match", "so this rule always succeeds", "use X to fix it"), that consequence is usually true only for the caller the author had in mind when they wrote the string. Other callers inherit a confidently-worded claim that is wrong, and sometimes the exact inverse of the truth.
    - Worked case: `OneOfRule.NormalizeAndValidate` is shared by OneOf, NoneOf, ScanWhile, and ScanUntil to project a TokenSet under the Compile normalization form and report entries that convert to a multi-grapheme sequence. The offender text said "OneOf / NoneOf match exactly one grapheme per token, so no single input token can match" and recommended `Literal(...)` / `And(Token-per-grapheme)`. For OneOf that is accurate. For NoneOf it is inverted: a dropped exclusion entry makes the rule match *every* token, not none, and the recovery advice produces a rule with inverted meaning. ScanWhile/ScanUntil inherited the wrong rule names too.
    - User-visible consequence: the message is a Compile-time `InvalidOperationException`. A NoneOf author reads "no single input token can match", concludes their rule is dead, and restructures the grammar to work around a problem that doesn't exist. Or they follow the `Literal` / `WithCompatibilityEquivalents` advice and silently invert what their rule excludes.
    - The fix shape: keep the message to the *structural fact* that holds for every caller (here: "a TokenSet member must be exactly one grapheme") plus a rule-agnostic remedy, and let the surrounding renderer name the specific rule (`BuildNormalizationErrorMessage` already prints the rule and its type). If a per-caller consequence genuinely adds value, branch on the caller (the helper already has the `Rule` reference) rather than hardcoding one.
    - When reviewing a shared message-building helper, ask: does this string assert what *happens* to the rule, or only what the rule's data looks like? An assertion about behavior is sound only if every caller shares that behavior. The membership-test direction (positive OneOf vs. negative NoneOf) is the classic place this breaks. Related: `z004-normalized-input-leaks-into-user-facing-strings.md` (the other family of "the string says something the caller didn't mean").
