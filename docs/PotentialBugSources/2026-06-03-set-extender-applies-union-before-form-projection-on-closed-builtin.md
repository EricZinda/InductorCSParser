- A public API unions a closure-protected built-in set with caller-supplied extras, then runs a projection step over the union. The projection is only sound on the closed built-in, so caller extras leak their projection components into the set
    - Shape: a public API takes a built-in `TokenSet` (or similar collection) that has a documented closure property and an optional "extras" parameter that the caller unions in. Somewhere in the constructor pipeline a projection / expansion step rewrites every member of the combined set. The projection is correct on the built-in because the built-in's closure property guarantees the projected components stay inside the set's intended domain. The caller-supplied extras carry no such guarantee, but the projection treats them identically. Any extra whose projection escapes the intended domain silently injects out-of-domain members into the rule.
    - Concrete `InductorParser` instances (both `Rules.Identifier` under `FormKC` / `FormKD`):
        - **Start side** (`extraStartRunes`, fixed 2026-06-02): `Rules.Identifier` used to compute `start = (TokenSet.XidStart | extraStartRunes).WithCompatibilityEquivalents(form)`. Caller extras with a multi-grapheme NFKx (e.g. U+0140 LATIN SMALL LETTER L WITH MIDDLE DOT, NFKx = `"l" + U+00B7`) silently promoted their tail piece (U+00B7) into the start set, even though U+00B7 is XidContinue-only. Fix introduced `WithCompatibilityHeadRuneEquivalents` (head-only expansion) and `AllCompatibilityTailRunesIn` (validate the dropped tail lands in body), then threw a named-rune error for extras whose tail didn't.
        - **Body side** (`extraBodyRunes`, fixed 2026-06-03): the 2026-06-02 fix updated the start side but left `body = (TokenSet.XidContinue | extraBodyRunes).WithCompatibilityEquivalents(form)` running over the union. Caller extras with a multi-grapheme NFKx that contained a non-XidContinue piece (e.g. U+FDFA ARABIC LIGATURE SALLALLAHOU ALAYHE WASALLAM, NFKC = an 18-char Arabic phrase with three U+0020 SPACE separators) silently injected those pieces (SPACE here) into the body set. `Identifier(form: FormKC, extraBodyRunes: TokenSet.Single(0xFDFA)).Compile(FormKC).Parse("abc def").Success` returned `True`. Fix mirrored the start side: added `AllCompatibilityPiecesIn(form, allowedRunes, ...)` (every-piece check, not just tail) and called it on `extraBodyRunes` against `TokenSet.XidContinue`.
    - Why it hurts: closure-property thinking is easy to lose at the API boundary. The projection's correctness argument is "the input has property P, so projecting preserves the invariant." Once a caller's data is unioned in without P, the same projection silently breaks the invariant, but the projection code can't tell the difference between "this rune came from the closed built-in" and "this rune came from the caller." The check that would catch it (`OneOfRule.NormalizeAndValidate` reporting a multi-grapheme offender at Compile) is exactly the one the projection was added to bypass, on the assumption the projection only ever runs on closure-safe input.
    - How to spot it: search for public factory methods that take a `TokenSet`-typed `extra*` / `extend*` / `additional*` parameter, then look for a normalization, expansion, projection, or rewrite step on the unioned result. If the rewrite would throw / report on certain inputs and the built-in is documented (or test-asserted) to never trigger that path, the rewrite is implicitly relying on the built-in's closure. Check whether the union happens before or after the rewrite. If before, the caller's extras get the projection too, and any extra that violates the built-in's closure leaks its projection components.
    - Symmetry footnote: when a closure-aware fix adds a side-specific helper (`WithCompatibilityHeadRuneEquivalents`) and a side-specific validator (`AllCompatibilityTailRunesIn`) on one side of a paired-set API, audit the other side for the same pattern in the same pass. The 2026-06-02 start fix added `Identifier_rejects_start_extra_whose_decomposition_tail_is_not_a_body_character` but no mirror for body, so the body-side gap survived until the 2026-06-03 sweep. A "fix one side, audit the mirror" checklist would have closed both holes in one pass.
