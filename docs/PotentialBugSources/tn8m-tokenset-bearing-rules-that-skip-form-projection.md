- TokenSet-bearing rules that skip Compile-time form projection
    - Compile's normalization-form pass (`Rule.CollectNormalizationOffendersAll`) walks the rule graph asking each rule to project its caller-supplied text data onto the chosen form. Literal-bearing rules (Token, Literal, LiteralIgnoreAsciiCase) project their `_expected` string. TokenSet-bearing rules project their `_set` via `OneOfRule.NormalizeAndValidate`, which calls `TokenSet.NormalizedFor(form, ...)`: single-rune entries that decompose to one cluster become multi-rune entries, canonical-singleton substitutions (U+212B → U+00C5, U+2126 → U+03A9, U+212A → K) swap rune values, and multi-grapheme conversions (ﬁ → "fi" under FormKD) get reported as offenders.
    - The trap: a rule that holds a TokenSet but doesn't override `CollectNormalizationOffenders` (the default no-op covers composites and zero-width predicates) silently keeps its set in pre-projection shape. At parse time the lexer hands the rule input that's already been form-projected, so a stopper / matcher entry written in one canonical form is asked to match input in the OTHER canonical form, and the membership test returns the wrong answer. OneOf / NoneOf get this right (they override). The scan-shaped rules (ScanWhile, ScanUntil) didn't, so they silently failed under `Compile(FormC)` / `Compile(FormD)` / `Compile(FormKC)` / `Compile(FormKD)` on entries that aren't form-stable. See backlog tn8m for the canonical example.
    - User-visible consequence: a grammar that compiles cleanly and works under `Compile(null)` quietly mismatches input under any non-null form. Either the rule fails where the user expected a match (ScanWhile shape) or the rule succeeds where the user expected a boundary (ScanUntil shape, body swallows the would-be stopper). No diagnostic, because no offender is reported and the membership test just returns false. Most visible on accented Latin (precomposed vs. decomposed), the canonical-singleton substitutions, and the compatibility-form ligatures and presentation variants.
    - Sibling-rule check during a sweep: list every Rule subclass that holds caller-supplied user text (`_expected` strings, `_set` TokenSets, single-rune ints like `_escapeStartRune`). Cross-reference against the set of rules that override `CollectNormalizationOffenders`. The gap is the bug surface. Today the literal-bearing rules and OneOf / NoneOf / ScanWhile / ScanUntil cover the TokenSet and string cases. The single-rune-int case (`ScanUntilRule._escapeStartRune`, `LiteralIgnoreAsciiCaseRule`'s ASCII-only logic) is not currently form-projected; in practice escape starts and ignore-case letters are ASCII and form-stable, but a future grammar that uses a non-ASCII rune there would hit the same shape.
    - When adding a new Rule subclass that holds caller-supplied text, default to overriding `CollectNormalizationOffenders` and projecting that data the same way OneOf does. The `OneOfRule.NormalizeAndValidate` helper is the shared implementation for set-bearing rules; literal-bearing rules use `TryConvertToForm`. Skipping the override is a "silent miss" failure mode that's only visible under non-null compile forms, and the test matrix that covers `Compile(null)` won't catch it.
