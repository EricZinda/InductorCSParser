- A claim that a format/invisible character is "its own token" ignores its grapheme-break property
    - Shape: a doc or comment groups several zero-width / invisible format characters together and says they all "come through as their own tokens" (or all break, or all glue). But the lexer tokenizes by UAX #29 grapheme cluster, and these characters don't all share one grapheme-break behavior. Found in UnicodeGotchas.md, which said ZWJ and ZWNJ come through as standalone tokens like the soft hyphen does. They don't: ZWJ (U+200D, GCB = ZWJ) and ZWNJ (U+200C, GCB = Extend) glue onto the preceding grapheme under rule GB9, while ZWSP (U+200B) and soft hyphen (U+00AD), both GCB = Other, actually break.
    - Why it happens: "invisible format character" is a rendering category (these all render as nothing), but token boundaries are decided by the Grapheme_Cluster_Break property, which is orthogonal. Characters that look interchangeable to a reader (all zero-width, all Cf-ish) fall into different GCB classes: Extend and ZWJ attach to the preceding character (GB9), Other breaks (GB999), Prepend attaches to the following character (GB9b). Lumping them into one sentence is how a wrong tokenization claim sneaks in.
    - How to catch it: any statement about whether a specific character "is its own token" / "splits" / "attaches" is checkable in one StringInfo.GetTextElementEnumerator call. For "X between two letters," count the clusters of "a" + X + "b": 3 means X breaks, 2 means X glued to the left, 2 with the glue on the right means Prepend. Don't trust a character's General_Category (Cf, Mn) or its visual width to predict its token boundary. Read its Grapheme_Cluster_Break value.
    - The usual confusables and their GCB: U+200B ZWSP = Other (breaks), U+200C ZWNJ = Extend (glues left), U+200D ZWJ = ZWJ (glues left), U+00AD SOFT HYPHEN = Other (breaks), U+FEFF BOM = Other (breaks), combining marks (Mn/Mc) = Extend (glue left), U+0E33 THAI SARA AM = a spacing letter (Lo, breaks). A "these all behave the same" claim across this list is almost always wrong.
    - A stray surrogate is not immune either. A comment that says "an unpaired surrogate is always its own one-char token" is wrong the moment an Extend follows: StringInfo decodes the stray to U+FFFD (GCB = Other), which breaks on its own but, being a base, still anchors a following combining mark under GB9, so "stray + combining mark" is ONE two-char cluster. Found in the Lexer class doc (2026-06-06), which claimed grapheme mode "treats unpaired surrogates as 1-char text elements" full stop. The same `StringInfo.GetNextTextElement` check applies: count the first cluster of "\uD800" + U+0301 and it's length 2, not 1. The tokenLength == 1 check in AdvanceWhileRuneIn already knew this. Only the prose was behind.
    - Related: the CRLF gotcha (a two-char cluster that a rune-only set misses) and the lone-surrogate OneOf(~set)/NoneOf(set) split are the same family, where token boundaries and set membership don't line up with a reader's mental model of "one character."
