- Compile-time auto-pin sites silently overriding user-supplied pins
    - The grammar build process has several places that opportunistically pin per-rule fields (Id, in particular) based on rule content: the constructor's rune-pin in `GraphemeRule` for single-rune tokens, the post-normalization re-pin in `GraphemeRule.CollectNormalizationOffenders` for canonical-singleton characters, the named-hash assignment in `Rule.AssignNamedIds`, the sequential-anon assignment in `Rule.AssignAnonymousIds`. The ctor and the `Assign*Ids` passes are gated on `!_idAssigned`, so they correctly skip rules the user already pinned via `.As(SymbolId)`. The post-normalization re-pin in `GraphemeRule` was NOT gated and silently overwrote user pins.
    - The shape that bit `GraphemeRule`: `Token('Å').As(new SymbolId(0x200100)).Compile()`. The constructor pins Id=0x212B (rune of ANGSTROM SIGN). The user's `.As` overrides Id=0x200100. Compile's normalization pass projects U+212B → U+00C5 under FormC and re-pins Id=0x00C5, dropping the user's pin. The user's `.As(SymbolId)` docstring promises "stable numbering across versions, useful when serializing parse trees"; the re-pin breaks that promise. See backlog `xpid` and search log `xpid`. The fix adds an `_idUserPinned` flag set by `As(SymbolId)` (and only by `As(SymbolId)`, not by the auto-pin path `SetIdInternal`) and gates the re-pin on `!IsUserSymbolIdPinned`.
    - Why the bug surface is narrow: only `GraphemeRule` re-pins Id during Compile. `LiteralRule` and `LiteralIgnoreAsciiCaseRule` update only `_expected` in their `CollectNormalizationOffenders`. `OneOfRule.NormalizeAndValidate` projects only `_set`. So a similar review of every other rule's `CollectNormalizationOffenders` confirmed no second instance.
    - When reviewing any new opportunistic Id-assignment site, ask: does this auto-pin run AFTER the user has had a chance to call `.As(SymbolId)` on the rule? If yes, gate the auto-pin on `!IsUserSymbolIdPinned`. The constructor's auto-pin is fine (runs before any `.As` call), and the `Rule.Assign*Ids` passes are already gated on `!_idAssigned` (which catches both ctor pins and user pins), so they're fine. New auto-pin sites in subclass passes (CollectNormalizationOffenders, validate hooks, anything that walks the post-construction rule graph) need the explicit user-pin gate, because `_idAssigned` alone can't distinguish "ctor pinned" from "user pinned".
    - Adjacent shape worth noting: anonymous Id assignment also overrides ctor rune-pins for multi-rune tokens (the ctor only rune-pins single-rune tokens, so multi-rune `Token("é")` arrives at Compile with `_idAssigned == false`). That's by design: the multi-rune ctor doesn't auto-pin, and AssignAnonymousIds gives the rule a custom-range Id. The post-normalization re-pin in `GraphemeRule` then OVERRIDES that anon Id with the rune value, which is desired (`Token("é").Compile(FormC)` should match `Token('é')`'s leaf-id of 0xE9). The fix has to preserve this case while skipping the user-pin case, which is what the `IsUserSymbolIdPinned` flag distinguishes.
