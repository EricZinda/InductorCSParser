- Shared format helper hardcodes a separator that only makes sense for a non-empty body
  - Pattern: a helper that combines two pieces with a literal space (or other separator) using `$"{a} {b}"` works for every caller until one of them passes an empty `a`. The leading space then leaks into the result, and when a downstream writer adds its own separator before the result the user sees a double space (or a tab+space, etc.).
  - Concrete example: `Rule.AppendErrorMessage(body)` returned `$"{body} \"{_errorMessage}\""`. Every rule's failure trace passed a non-empty body (`"symbol #N"`, `"count= N"`, `"found '<EOF>'"`, etc.) except OrRule, which passes `$""` because there's no per-child detail to surface after all alternatives failed. `Lexer.WriteTraceLine` then writes `<label>: <message>`, so the empty body produced `Or:  "..."` with a double space between the colon and the quote.
  - Why this slips through: the helper doesn't spell out whether the body can be empty, and every other rule's trace body happens to be non-empty, so the bug only fires for the one outlier. The trace cases that ARE tested (TracingTests' Token-with-WithError, every other rule's success/failure traces) all hit the non-empty path and look fine.
  - Where to look: any "compose two strings with a literal separator" helper that's called by code paths that legitimately produce an empty piece. Candidates: trace-line builders, error-message formatters, anything that builds `"a: b"` / `"a (b)"` / `"a [b]"` shapes. Search for `$"{x} {y}"` / `$"{x}: {y}"` / `$"{x} ({y})"` patterns whose body is supplied by a caller.
  - How to fix without breaking the common case: branch on `body.Length > 0` and skip the separator when empty, or have callers stop passing empty bodies. The first is local to the helper and doesn't require auditing every call. The second is more honest about what the helper expects but requires per-caller changes.
