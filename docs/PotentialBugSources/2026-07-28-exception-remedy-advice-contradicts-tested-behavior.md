- Exception messages that recommend a replacement code pattern can contradict the library's own tested behavior
    - The shape: a validation exception (set-once, sealed, conflict) helpfully tells the user what to write instead. That advice is prose inside a string literal. No compiler checks it, no test executes it, so it can recommend a pattern that another part of the library deliberately makes a no-op. The message and the behavior each look correct in isolation and only conflict when you follow the advice end to end.
    - Concrete instance (fixed 2026-07-28): Rule.WithError's set-once exception said to wrap the rule with a plain Alias(...).WithError("second"). The exception only fires when the rule already has a message, and precisely then the error-ranking model makes the advice dead: the alias anchors its failure at the same depth as the inner's, the exact-depth tie goes to the first writer, and the inner records first, so the alias's message never surfaces. docs/ErrorArchitecture.md documents that tie-break on purpose, and AliasRuleTests.Alias_plain_WithError_does_not_override_an_inner_WithError asserts it. The user who follows the advice ships a message that silently never appears.
    - What makes this class easy to miss: the advice usually describes a pattern that works in the *general* case (per-use aliases over a message-free shared rule do give per-use messages). The exception's precondition is what breaks it. The advice has to work under the exact state that made the exception fire, not in the fresh-rule case the author was picturing.
    - Review checklist: for every exception message that names concrete replacement code ("call X instead", "wrap it with Y"), reproduce the state that triggers the exception, apply the advice verbatim, and check the promised outcome happens. If a test already proves the recommended pattern is a no-op in that state, the message is wrong, not the behavior.
