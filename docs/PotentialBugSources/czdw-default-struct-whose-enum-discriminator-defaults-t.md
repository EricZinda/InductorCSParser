- Default struct whose enum discriminator defaults to a meaningful "positive" state
    - A `public readonly struct` with an enum (or int) status field reports whatever the enum's zero value names on its `default`. When the zero value is a meaningful good outcome (`Success`, `Ok`, `Valid`, `Found`, `Enabled`), `default(T)` silently claims that good outcome even though no code ever produced it. Unlike the reference-field-on-a-default-struct case (which crashes with NullReferenceException, so it gets noticed), this one returns a wrong-but-non-crashing value, so it slips through every test that only exercises factory-built instances.
    - The shape: `enum Outcome { Success, Failure, ... }` puts `Success == 0`. A struct field `public Outcome Outcome { get; }` defaults to `Success`. A convenience accessor `public bool Ok => Outcome == Outcome.Success` then returns `true` for `default(T)`. Every real instance comes from a factory that sets a real outcome, so 99.9% of coverage exercises non-default values and the false-positive default goes undetected. It only surfaces when a real caller gets a default through an everyday path: an unassigned field, a `new T[n]` element, `List<T>.FirstOrDefault()` on an empty list, `Dictionary<K,T>` lookup miss, `dict.GetValueOrDefault(k)`. See the `ParseResult.Success` instance (fixed 2026-06-03): `default(ParseResult).Success` returned `true` with a null `Tree` and empty `Symbols`, so the idiomatic `if (result.Success) Use(result.Tree)` treated a never-run parse as a successful one.
    - Watch for: any `bool`/status accessor on a public-default struct that's defined purely as `Discriminator == SomePositiveValue` where `SomePositiveValue` is the enum's zero member. Also the manual form a caller writes themselves: `if (result.Outcome == Outcome.Success)`. Both read `true` on the default.
    - Two fixes, pick by blast radius. (1) Check a "was this constructed" signal in the accessor: a reference-typed field that every factory stamps and only the default leaves null, e.g. `Success => _grammar != null && Outcome == Success`. Minimal and non-breaking, but only fixes the accessor, not a caller's hand-written `Outcome == Success` check. (2) Give the enum a non-committal zero member (`None`/`Unset`/`NotRun = 0`) so the default discriminator isn't a positive state at all. This fixes both the accessor and the hand-written comparison, but shifts every other enum value by one (a breaking change for anyone who persisted the int values). The `ParseResult` fix took (1) because `ParseResult.Success` is the documented-recommended check and the enum's numeric values weren't worth shifting.
    - Reviewer mental model: when adding (or reviewing) a public-default struct with a status enum, ask "does `default(T)` claim a good outcome?" If the enum's zero value is `Success`/`Ok`/`Valid`/`Found`, the answer is yes and the convenience accessor needs the construction check (or the enum needs a neutral zero). Don't trust "every factory sets the real outcome", since `default(T)` skips every factory. This is the silent-false-positive cousin of [[public-default-struct-with-non-coalesced-reference-field]] (which crashes instead of lying).
