- Polarity drop in a wrapping or composing helper preserves the original set, leaving a fail-set under MustBeIn semantics
    - The first-set algebra (see `RuleStartRequirements`) carries an invariant: `Polarity.MustNotBeIn` (where the set is a fail-set, peek IS in here means the rule definitely fails) requires `Advance.Always` (the shortcut needs the rule to commit to consuming on success). When a wrapping operation downgrades `Advance` to `Sometimes` or `Never`, the polarity has to drop to `MustBeIn` to keep the invariant. The trap is that the SET also has to change, because the original fail-set under MustBeIn would now mean "tokens this rule might consume first," which is exactly the opposite of what the rule does. Falling back to the original set is silently wrong. Falling back to `TokenSet.Empty` is also wrong (it claims the rule definitely won't consume). The correct fallback is `TokenSet.Universe` (the noncommittal "I don't know what this rule consumes first," which keeps parent composition sound).
    - User-visible consequence: a wrapping rule like `Optional(NoneOf(...))` or `ZeroOrMore(NoneOf(...))` ends up publishing the fail-set under MustBeIn. When that triple gets composed into a parent `And` whose later sibling is Always, the parent's union ends up with the fail-set treated as a consume-set, and the parent's published filter excludes peeks the inner rule could actually consume. Inside an `Or`, the parent And gets shortcut-skipped on a peek the And could match, the Or commits to a later alternative that consumes less, and the parse fails on trailing input the And would have eaten. See backlog `pflk` for the worked `Or(And(Optional(NoneOf("xy")), OneOf("abc")), Token('z')).Parse("zb")` reproduction.
    - The fix shape is consistent across all three sites in `RuleStartRequirements.cs`: `WithAdvance` (when forcing MustNotBeIn → MustBeIn because newAdvance != Always), `MatchesAnyOf` fallback (when the running polarity composes to MustNotBeIn but the running advance dropped below Always), and `MatchesAllOf` fallback (same shape). All three return `(TokenSet.Universe, advance, Polarity.MustBeIn)` in the polarity-drop branch.
    - Reviewer mental model: any helper that produces a `(set, advance, polarity)` triple has to keep set and polarity in lockstep semantically. The same set under MustBeIn and MustNotBeIn means opposite things ("might consume" vs. "fails on"). When a constraint forces polarity to drop, the set has to be re-derived from the new polarity's semantics. Universe is the safe noncommittal fallback that never wrongly filters; the original set is the wrong-direction inversion; Empty is the "this rule definitely won't consume" claim, which is also wrong for a rule that actually CAN consume.
    - Sibling pattern (`complement-derived-firstconsumedtokens-on-negation-rules.md`) is the same fail-set-as-consume-set inversion but caused by hand-derived complement on a specific rule (NoneOf publishing `~_set` under MustBeIn). Both patterns share the lesson: don't try to express MustNotBeIn semantics by translating the set into a MustBeIn shape unless the translation is provably equivalent. For rune-only sets the complement is sometimes expressible; for cluster-aware sets and for non-Always rules it isn't, and the conservative `Universe` (or keeping the rule under MustNotBeIn-Always) is the only sound choice. <!-- style-lint-ok -->
    - When adding a new helper that operates on `RuleStartRequirements` and changes `Advance` or `Polarity`, ask: does the resulting triple still mean what the original meant? If polarity flipped without re-deriving the set, the answer is no, and the fix is `Universe` under MustBeIn, not the original set.
    - State-machine engine consumes the same compiled `Rule.FirstConsumedTokens` / `Rule.Polarity` fields via `Lowerer.CanSkipUnreachableAlt`. A fix in the `RuleStartRequirements` helpers flows through to both engines automatically; an SM-side workaround would need to mirror the same Universe fallback, which is more code for the same effect.
