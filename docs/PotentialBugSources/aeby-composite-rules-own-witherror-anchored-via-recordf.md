- Composite rule's own .WithError anchored via RecordFailure instead of RecordCompositeFailure, missing the subtree-extent Math.Max-merge
    - How this works: when a rule runs a sub-rule via `child.TryParse(...)` and that sub-rule fails, the sub-rule's outer transaction Math.Max-merges its `_subtreeDeepestFailure` into the parent's window via `Transaction.Dispose` before rolling the lexer position back. The parent's lexer.Position retreats to where the child started, but the parent's subtree-extent now reflects the deepest position the child's inner failures reached. The parent's own .WithError has to land at `Math.Max(_subtreeDeepestFailure, lexer.Position)` (i.e. `RecordCompositeFailure`), not at `lexer.Position` alone (`RecordFailure`). Otherwise a deeper Mechanical failure inside the child's subtree pushes MechanicalPosition past the Named slot's position, and the deepest-wins resolution drops the parent's .WithError. The user sees the generic "Parse failed at offset N: unexpected 'x'." template instead.
    - The shape AndRule / OrRule / AliasRule / BetweenInclusiveRule already follow on their failure paths is `lexer.RecordCompositeFailure(lexer.Position, ErrorMessage, ErrorForced)`. Any rule that drives a sub-rule via `TryParse` and then records its own .WithError on a child-failure path should match it. ScanUntilRule's two escape-end-failure branches (the rule-form escape-start path and the single-rune fast-path escape-start path) had been using plain `RecordFailure(lexer.Position, ...)`. Both were fixed by switching to `RecordCompositeFailure`. See backlog hunt `2026-05-20-scanuntil-escape-end-anchored-too-shallow.md`.
    - Distinct from `shallower-witherror-vs-deeper-orphan-deepest.md`. That pattern is about LOOKAHEAD rules (Peek, Not) where the sub-rule runs inside `BeginProbe` and the inner failures get rolled back, but failures recorded OUTSIDE the probe (by a sibling Or alternative that ran earlier) can still be deeper. The fix there is the `forced` flag on `.WithError("msg", forced: true)` to bypass the deepest-wins comparison entirely. This pattern is about NON-LOOKAHEAD composite rules where the sub-rule runs via `TryParse` (not Probe), the inner failures survive (Math.Max-merge), and the fix is to anchor at the deeper of subtree-extent and lexer.Position via RecordCompositeFailure.
    - When reviewing a rule that drives a sub-rule via `TryParse`, audit every `lexer.RecordFailure(lexer.Position, ...)` site reached after the child returned null. Ask: could the child's subtree have recorded a Mechanical or Named failure at a position deeper than lexer.Position (after the child's transaction rolled back)? If yes, the parent's own .WithError is silently dropped unless the anchor is RecordCompositeFailure. A rule whose only "fail after a sub-rule failed" path uses RecordFailure should be flagged.
    - Exception: a strict-EOF branch where the rule ran out of input (`lexer.Position == input.Length` or `_endPosition`) is safe with plain RecordFailure, because no sub-rule's subtree extent can exceed the lexer's readable range. ScanUntilRule's strict-unterminated branch is in this category. The fix only applies to branches where lexer.Position is genuinely shallower than where the sub-rule's subtree could have reached.
