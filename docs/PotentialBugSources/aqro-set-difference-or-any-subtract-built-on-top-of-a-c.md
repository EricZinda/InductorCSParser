- Set difference (or any "subtract") built on top of a complement that intentionally narrows the universe

  - TokenSet's `operator ~` is deliberately not a true complement: it complements over Unicode scalar values only and strips surrogate code units (U+D800..U+DFFF), because the surrogate-free result keeps `OneOf(~set)` from quietly matching a lone surrogate under `Compile(null)`. That narrowing is correct for `~` and locked in by tests (`Complement_never_fabricates_surrogates`, `Double_complement_of_Surrogates_is_Empty`).
  - The trap: implementing `a - b` (set difference) as `a & ~b` inherits that narrowing. `~b` is surrogate-free, so `a & ~b` can never retain a surrogate that lives in `a`. The minuend's surrogate members vanish, even when `b` contains none of them. `Surrogates - Empty` came out `[]`, violating both `X - Empty == X` and the operator's "every member of a that isn't a member of b" claim.
  - Why it slips through review: for rune-only, surrogate-free inputs `a - b` and `a & ~b` are genuinely equal, and the tests that shipped with the operator only exercised that case (ASCII letters/whitespace, the CRLF cluster). The divergence only shows on the one input class the narrowed complement was built to exclude.
  - The fix shape: when an operation's documented universe is *the operands* (difference complements against the bounded `b`, not against any fixed universe), compute it directly against the operands instead of borrowing a universe-narrowing helper. Here that meant a direct interval subtraction (`SubtractRuneIntervals`) that walks `a`'s and `b`'s intervals and keeps `a`'s code points not covered by `b`, surrogates included.
  - When reviewing any `X minus Y` / "remove these" / "everything in A but not B" helper, ask: is it implemented via a complement or negation primitive that clamps, normalizes, or excludes some part of the universe? If so, the subtraction silently drops whatever that primitive excludes from the left operand.
