- Pattern: a doc (or comment) claims `tree.ToString()` / `Symbol.ToString()` gives back the original input verbatim, when the verbatim accessor is `Symbol.SourceText`.
    - Why it's wrong: `ToString()` rebuilds text only from the nodes that survived into the tree. Delete rules contribute nothing, and `Token` / `Literal` / `LiteralIgnoreAsciiCase` default to `Delete`, so any grammar with delimiters, keywords, or whitespace-skipping loses that text in `ToString()`. Under a normalizing form the characters `ToString()` does keep come back in the normalized form, not the caller's original. `SourceText` is the accessor that returns the verbatim original section a rule matched, and it does so under every normalization form because it translates the match span back to original-input coordinates. Symbol.cs's own ToString XML doc states this ("To get the exact input verbatim, ... read SourceText").
    - What Compile(null) actually buys: it makes the tree's leaf text (and therefore `ToString()` on a grammar that preserves the content it matches) carry the original characters instead of the normalized ones. It doesn't make `ToString()` verbatim, because Delete content is still dropped regardless of form.
    - Where to look: any prose or comment that equates "round-trip" / "get the input back" / "character-exact" with `ToString()`. Grep docs and XML comments for `ToString()` near "original" / "round-trip" / "verbatim" / "character for character".
    - How to catch it: write the doc's claim as a test against a grammar that uses a Delete-default rule (a delimiter or keyword). If the claim is "ToString() == original", it fails the moment any matched text is Delete. The fix is to point at `SourceText` (verbatim, any form) and describe `ToString()` accurately (tree leaves only, normalized under a normalizing form).
