- Rune-scoped compiled lookahead fields republished as cluster-scoped by a sub-lexer wrapper
    - The lexer hands out one token per grapheme cluster. `WithinToken` is the one rule that changes that unit: it builds a sub-lexer in one-rune-per-token mode and runs an inner rule against the runes inside a single outer cluster. The compiled lookahead fields a rule publishes (`FirstConsumedTokens`, `Advance`, `Polarity`, produced by `ComputeRuleStart`) are always expressed in the tokenization unit the rule runs under. So an inner rule's `FirstConsumedTokens` is a set of *runes*, while the same field on an ordinary (non-WithinToken) rule is a set of *grapheme clusters*.
    - The trap: a wrapper rule that runs a sub-rule under one unit and then republishes that sub-rule's `(set, advance, polarity)` triple as its own is silently mixing units. The enclosing `Or` / `BetweenInclusive` lookahead shortcut peeks a whole grapheme cluster and interprets the wrapper's published set as cluster-scoped. Whether the mix is harmless depends on which membership question `Rule.CannotMatchLookahead` asks for that polarity:
        - `MustBeIn`: the shortcut tests the peek cluster's *first rune* against the set (`FirstConsumedTokens.Contains(peekFirstRune)`), then falls back to a whole-cluster `ContainsToken`. The first-rune test happens to be exactly the rune the inner rule reads first, so a rune-scoped set republished as cluster-scoped still gives the right answer. Harmless by luck, not by design.
        - `MustNotBeIn`: the shortcut tests *only* the whole peek cluster against the fail-set (`FirstConsumedTokens.ContainsToken(peekToken)`). There is no first-rune check. A multi-rune grapheme that is a member of the rune-scoped fail-set makes the shortcut skip the wrapper — but the inner rule, walking that cluster rune by rune, never sees the cluster as a unit and can match every rune (none of which is in the fail-set on its own). The shortcut skips a rule that would have matched.
    - User-visible consequence: the lookahead shortcut is a pure optimization and must never change a parse result. Here it does. A grammar like `Or(WithinToken(OneOrMore(NoneOf(clusterSet))), other)` fails on input that the `WithinToken` branch matches when parsed standalone, whenever `clusterSet` contains a multi-rune grapheme and that grapheme is the next token. No diagnostic — the branch is simply never attempted. Both the recursive and state-machine engines are affected, since both read the same compiled `Rule.FirstConsumedTokens` / `Rule.Polarity` fields.
    - The fix shape: when republishing a sub-rule's fields across a tokenization-unit boundary, project the set into the outer unit before publishing, or drop to the noncommittal fallback. For a `MustNotBeIn` fail-set the sound projection is `TokenSet.RunesOnlyPart` (drop the multi-rune entries): a rune-only set can only `ContainsToken`-match a single-rune peek cluster, and there the cluster's one rune is the rune the inner rule checks first. A subset of a `MustNotBeIn` fail-set is always sound (`RuleStartRequirements`: "a subset of actual fail-tokens is safe, just skips fewer than possible"). For a `MustBeIn` set no projection is needed because the shortcut's first-rune check already bridges the units.
    - Sibling pattern (`polarity-drop-preserves-fail-set-as-consume-set.md`) is the related failure where a fail-set is kept under the wrong *polarity*. This one keeps the right polarity but the wrong *unit*. Both share the lesson: a `(set, advance, polarity)` triple is only meaningful relative to the tokenization unit and the membership question it will be tested with — copying a triple from one context to another without checking both is where the shortcut loses soundness. <!-- style-lint-ok -->
    - Reviewer mental model during a sweep: find every place a rule's compiled lookahead fields cross a boundary that the sub-rule didn't itself control — a sub-lexer with a different `oneRunePerToken` setting, a transparent proxy that forwards a target's triple, a composite that unions children's triples. Ask "is the inner triple in the same unit, and tested with the same membership question, as the outer rule's consumer expects?" If a `MustNotBeIn` set with multi-rune entries can reach a consumer that only does whole-cluster `ContainsToken`, that's the bug surface.
