- Allow-list tables verified only against the author's understanding, not against the authoritative spec at the same version
    - A hand-curated allow-table (a TokenSet of permitted code points, a set of valid keywords, a whitelist of accepted values) can fail in two ways. It can MISS a value that belongs (false negative) or ADMIT a value that doesn't (false positive). Tests for these tables tend to cover the first kind ("X is accepted") and skip the second ("Y is rejected, for the right reason"), so over-admission slips in silently because nothing tests the boundary from outside.
    - This is the over-admission twin of the version-drift pattern in [[hand-curated-unicode-property-tables-fall-out-of-sync]]. That one is about a value going MISSING from the table over time. This one is about a value that was never supposed to be in the table getting typed in at the start, from the wrong source property or a stale spec reading, and never getting caught because the tests only check membership.
    - Concrete instance: TokenSet.Xid.cs XidStartAdds and XidContinueAdds both listed U+309B and U+309C. They're in Other_ID_Start, so they're in ID_Start, but XID_Start is ID_Start closed under NFKx and U+309B / U+309C K-decompose to SPACE + a combining mark. That means XID_Start drops them. The table's source property was Other_ID_Start, its target property is XID_Start. The commit that added them ("Bug: add U+309B..309C") read Other_ID_Start and stopped one step early. The four regression tests that commit added then pinned the buggy behavior in place. The bug was found by cross-checking the table against the actual DerivedCoreProperties.txt file at the spec version the table claims to track (Unicode 17.0). 309B..309C is listed under ID_Start / ID_Continue but the XID sections skip the range entirely.
    - The verification technique: an implementation of XID (Python's str.isidentifier, the .NET BCL's Char.IsLetter, etc.) is only as current as the Unicode version it ships with. Python 3.13 is on Unicode 15.0 while the parser tracks 17.0, and several characters (U+200C, U+200D, U+30FB, U+FF65) were added to XID_Continue in Unicode 16.0. Verifying the table against an older implementation will report false-positive bugs that aren't real. The check has to be done against DerivedCoreProperties.txt / PropList.txt at the same Unicode version the table claims to track, not against whatever Unicode version the local Python or runtime is on.
    - When reviewing an allow-table or its tests, ask: is there a test that picks a plausible-but-invalid neighbor and asserts it's rejected? For a Unicode property table, "plausible-but-invalid" means a code point that's IN the source property (e.g. Other_ID_Start) but NOT in the target property (XID_Start), or a code point in a related category. For a keyword whitelist, it means a near-match (lookalike, substring, case variant). An allow-table with zero rejection tests is untested on half its surface.
