- A recursive tree/graph traversal built with `yield return` over child iterators is O(nodes x depth), quadratic on deep structures

  - Shape: an `IEnumerable<T>` method walks a recursive structure by yielding itself and then `foreach (var x in child.Walk()) yield return x;` for each child. It reads as the obvious, clean way to flatten a tree, and on shallow trees it's fine. The trap is how C# iterators compose: a value yielded by a leaf iterator is re-yielded by its parent iterator, then its grandparent, and so on up to the root. A node at depth D is pulled through D `MoveNext` calls before the consumer sees it, so enumerating an N-node tree costs O(sum of node depths) MoveNext calls, which is O(N x depth). It also allocates one iterator state machine object per node. For a balanced tree that's ~O(N log N) with N allocations. For a deep, chain-shaped tree it degrades to O(N^2).
  - Concrete instance (2026-06-04): `Symbol.Walk()`, `Symbol.FindAll(SymbolId)`, and `ParseResult.FindAll(SymbolId)` all used the recursive-yield pattern. Deep parse trees are normal: an expression grammar with precedence levels (expr -> term -> factor -> primary) or nested parentheses produces a tree whose depth grows with the input. Measured on a chain-shaped tree (one Preserve child per node) built via the public Symbol constructor: a single `Walk().Count()` over 16,001 nodes took ~1,295 ms, and doubling the depth multiplied the time by 4.18x (quadratic). Fix: an explicit Stack<Symbol> pre-order traversal (pop a node, yield it, push children in reverse so they pop left-to-right) is O(N) total with one allocation and the same yield order.
  - Why it hides: it's not a correctness bug, output order and contents are identical, so every functional test passes. It hides on the shallow / wide trees unit grammars produce (a `OneOrMore(leaf)` makes a depth-2 tree where the penalty is invisible). It only bites a consumer that enumerates a deep real-world tree, which the short-input test suite never builds. The recursive form also reads as idiomatic and correct, because it is correct. Only the cost is wrong.
  - Where else to look: any `IEnumerable<T>` that recurses with `yield return` over a child collection and can be handed a deep instance. Tree/graph walkers, `Descendants()` / `Flatten()` helpers, visitor-style enumerators. The tell is `foreach (var x in child.SomeEnumerable()) yield return x;` inside the same method. The single-result, early-returning recursive form (`Find` returning the first match) is fine, it's not an iterator, returns on the first hit, and is O(depth) per call. Only the `IEnumerable` yield-based walks have the re-yield cost. .NET has no `yield foreach` that would flatten the nesting, so the fix is always an explicit worklist (Stack for pre-order DFS, Queue for BFS) rather than a cleaner yield.
  - Test that catches it: an equivalence test that the rewritten iterative traversal yields the same nodes in the same order as a reference recursive walk, over a wide-shallow tree, a deep chain, and a mixed tree, for each affected method. The size of the win is best shown with a one-off measurement of the depth-doubling ratio (near 2x = linear, near 4x = quadratic) on a chain tree. Don't assert timings, lean on the order-equivalence test as the permanent regression check.
