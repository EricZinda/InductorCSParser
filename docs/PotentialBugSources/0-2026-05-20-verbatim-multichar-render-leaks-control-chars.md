- Rendering a multi-character value verbatim into a single-line string leaks embedded control characters
    - When a renderer builds a one-line user-facing string (a trace line, an error message, a debugger view) and appends a value that can be more than one character verbatim, any control character inside that value goes straight into the line. A raw carriage return / line feed turns one logical line into several physical lines and corrupts whatever consumes the trace.
    - The trap is that the single-element path usually already escapes controls, so the code looks safe. `TokenSet.ToString` rendered single-rune entries through `RenderCodepoint` (printable ASCII verbatim, everything else `U+XXXX`), but the multi-rune grapheme entries were appended with a bare `sb.Append(grapheme)`. The CRLF cluster that lives in `LineTerminators` and `Ascii.AnyWhitespace` (U+000D U+000A) then leaked a raw CR/LF, while the single-rune line terminators in the same set rendered correctly as `U+000A` etc. The two paths disagreed on the same kind of character.
    - Fix shape: route the multi-character append through a helper that escapes per element to `U+XXXX` when the char's Unicode General_Category is line-breaking or non-printing (Control / Cc, LineSeparator / Zl, ParagraphSeparator / Zp), otherwise verbatim, so printable content (emoji, ZWJ families, regional-indicator flags, accented clusters) still shows through but line-breakers can't split the line. Read the category from the BCL tables (`CharUnicodeInfo.GetUnicodeCategory`) rather than a hand-kept code-point list so it tracks new Unicode versions. A `char.IsControl`-only check is Cc only and misses U+2028 / U+2029. Leave Format (Cf) chars like ZWJ verbatim, since they're the invisible glue inside emoji clusters and don't break the line. The shared helper lives in `DisplayEscape` (`AppendEscaped(StringBuilder, ReadOnlySpan<char>)` for accumulating callers, `Escape(string, offset, length)` for return-a-string callers, `IsControlOrLineSeparator(char)` as the predicate).
    - Higher-leverage fix when the render site is a `$"..."` interpolation feeding a one-line display: do the escape inside the interpolation handler itself, not at each caller. The 2026-05-28 fix moved `DisplayEscape.AppendEscaped` into `TraceInterpolatedStringHandler.AppendFormatted`, so every dynamic value spliced into a trace body is escaped automatically and "one trace event renders as one physical line" becomes an invariant the handler enforces. That avoids the per-caller approach that let the 2026-05-27 `Lexer.Read` fix close three sites and miss the eight rule-layer ones. Applies when there's a single handler / formatter every render site funnels through. Doesn't apply to direct-StringBuilder render paths (`TokenSet.ToString`, `SymbolExtensions.PrintTree`), which still call `DisplayEscape` explicitly.
    - Where else to look: anywhere a multi-char token, literal, grapheme, or matched span is spliced verbatim into a one-line display string that doesn't go through `TraceInterpolatedStringHandler`. Closed candidates: the rule-layer trace bodies that quote `lexer.Input.Substring(token.Offset, token.Length)` for the matched token, `Rule.ExpectedText` / `_expected` literal renderings, and the WithinToken `AsSpan` success-trace splice are all closed by the 2026-05-28 handler fix (any `$"..."` going through `TraceInterpolatedStringHandler` is auto-escaped now). The user-supplied `.WithError("...")` text appended by `Rule.AppendErrorMessage` after the handler runs is closed by the 2026-05-28 follow-up: `AppendErrorMessage` escapes the message through `DisplayEscape.Escape` for the trace render while the stored `_errorMessage` keeps the user's exact text for `ParseResult.ErrorMessage`. The trace *label* (the `"{Name}:{ruleClassName}"` string from `Rule.BuildTraceLabel`, whose `Name` half is the user's `.As("...")` value) is closed by the 2026-05-29 fix: `Lexer.WriteTraceLine` now writes `DisplayEscape.Escape(label, ...)`. The label was the last un-escaped splice in the trace path because it arrives as a plain `string` argument to `WriteTraceLine`, not as a `$"..."` hole the handler could reach, and `.As(string)` never validates the name's content. Open candidates: any `ToString` on a type that can hold a multi-char member and feeds a one-line display without the handler in between. The `{character}` placeholder work (pattern `c000`) is the sibling concern about showing the right unit. This one is about a correctly-chosen unit still carrying a line-breaking control char.
    - 2026-05-28 new instance (now closed): the `{character}` placeholder in `Rule.BuildErrorMessage` spliced `StringInfo.GetNextTextElement(input, failurePos)` straight into the default `PositionalErrorTemplate` ("Parse failed at offset N: unexpected '{character}'."), so a parse that failed at a bare LF / U+2028 / any Cc/Zl/Zp char put a raw line-breaker into `ParseResult.ErrorMessage` and split it across two physical lines. This is the user-facing error message, not a trace, so it doesn't pass through `TraceInterpolatedStringHandler` and wasn't covered by the 2026-05-28 handler fix. It was the open `{character}` candidate called out above. Fix: route the placeholder value through `DisplayEscape.Escape(element, 0, element.Length)` inside the `("character", () => ...)` provider in `BuildErrorMessage`. Printable graphemes (fullwidth, ligatures, supplementary-plane runes, emoji clusters) still render verbatim, so the "show the user-typed character" intent (pattern `c000`) is preserved. Only line-breaking controls now escape to `U+XXXX`. The user-supplied `.WithError` message still surfaces verbatim in `ParseResult.ErrorMessage` (it's the caller's own text, and the `customMessage` branch returns before the `{character}` path). Reachable under any normalization form, including the default FormC, since the failing input character is read from the original input.
    - Distinct from `c000-char-unit-rendering-in-user-facing-strings`: that pattern is "show a grapheme, not a UTF-16 code unit." This pattern is "even the right multi-char unit needs its control characters escaped before it goes on a one-line string."
