- "Can I skip this rule?" shortcut gates that ask only about the rule's own ErrorMessage instead of its subtree
    - Three shortcut sites have decisions of the form "skip Inner.TryParse / skip this child if the lookahead proves it can't match" and each used to gate on `ErrorMessage == null`. The intent is "if the rule itself carries a friendly message, run it so the message can claim the deepest-failure slot." The bug is that the gate only consults the rule's OWN `ErrorMessage`, not its descendants'. A composite (Or, And, BetweenInclusive) whose own ErrorMessage is null but whose subtree contains a `.WithError` leaf gets shortcut-skipped, every `RecordFailure` call inside the subtree is silently bypassed, and the user sees the generic positional template. See backlog `lkah` for the worked examples and the fix shape.
    - The three sites:
        1. `BetweenInclusiveRule.TryParseRule`'s outer shortcut — both success-path (AtLeast == 0, commits empty) and failure-path (records and returns null) drop descendant messages.
        2. `OrRule.TryParseRule`'s per-child shortcut — skips a child whose first set doesn't include the peek.
        3. `Lowerer.CanSkipUnreachableAlt` in the state-machine engine — emits a `CheckPeekedRuneInSet` opcode ahead of an alternative's PushBacktrack so the lowered program routes past the alternative without ever opening its frame. The SM mirror of OrRule's runtime per-child shortcut.
    - Three concrete shapes that bite the user: `OneOrMore(Or(... .WithError(...) ...))` on input that misses the first lookahead (BetweenInclusive failure-path shortcut fires, the Or never runs), `And(ZeroOrMore(Or(... .WithError(...) ...)), required)` on input that misses the ZeroOrMore's lookahead (success-path shortcut commits empty, the descendant never records), and `Or(Or(... .WithError(...) ...), other)` on input that misses every child's lookahead (per-child shortcut skips the inner Or — fires identically in the recursive engine and the SM engine).
    - The fix consults a compile-time `HasErrorMessageInSubtree` flag on `Rule` (populated by Compile in a post-order walk that ORs each rule's own `_errorMessage != null` with every descendant's value). The shortcut gate becomes `!Inner.HasErrorMessageInSubtree` / `!child.HasErrorMessageInSubtree`. Truly anonymous rules (no ErrorMessage anywhere in the subtree) keep the optimization. Any subtree with a `.WithError` somewhere disables it. Same flag for both engines; the SM Lowerer reads it directly because it has Rule access at lowering time.
    - Scanner-skip cousin: `BetweenInclusiveRule.TryCreateScannerSkip` has the same gate shape on `alternative.ErrorMessage != null`, but the bug doesn't manifest because the scanner-skip only fast-forwards the lexer to the next candidate or EOF, where the regular Inner.TryParse runs anyway. With the OrRule per-child fix in place, the per-child shortcut at the landing position correctly tries the composite child and the descendant's RecordFailure runs. A regression test pins the combined behavior so a future change to either site that breaks the interaction surfaces immediately. Documenting it because the gate-shape similarity is what makes the scanner-skip site a tempting place to introduce a regression in the future.
    - Reviewer mental model: any gate that decides "skip this rule because it has nothing to say on failure" needs to ask the SUBTREE question, not the immediate-rule one. A rule's apparent absence of an error message says nothing about its children. When adding a new shortcut, ask: would skipping this rule lose any `RecordFailure` call its subtree would have made? If the answer involves "yes, but only if a descendant has WithError," consult `HasErrorMessageInSubtree`, not `ErrorMessage`.
    - Watch out for the same shape in any future shortcut site that decides whether to bypass a child rule's `TryParse` based on whether "the child has a friendly message." Specifically: any future composite that tries to leverage `CannotMatchLookahead` to skip a child outright, and any SM lowering pass that emits a peek-skip opcode ahead of an alternative. The gate must consult `HasErrorMessageInSubtree`, not `ErrorMessage`.
    - State-machine sibling for the leaf-emit shortcut: the SM engine's `Stepper.Step_EmitLeafOneOf` opcode reads from `SymbolMetadata`, which doesn't carry a `HasErrorMessageInSubtree` field yet. Same metadata-extension follow-up that the `IsUserSymbolIdPinned` change (backlog `p1nd`) tracks. Adding a fixture for the relevant grammar shape should come with the metadata extension.
