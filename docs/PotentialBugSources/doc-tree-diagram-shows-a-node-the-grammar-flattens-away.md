- A hand-drawn parse-tree diagram in the docs shows a node whose rule is `Flatten`'d (or `Delete`'d), so the parser never produces it
    - Docs illustrate a grammar's output with an ASCII tree (the `- [pair]` / `- [key] colors` style in InductorParserReference.md, the `name: "text"` PrintTree style elsewhere). These diagrams are hand-written, never generated, so they drift from what the grammar actually produces the same way uncompiled code examples do, except a tree diagram isn't even a code reference a grep for a renamed API would catch. The drift hides because the surrounding *prose* and the *executable* example beside it stay correct.
    - Canonical case: InductorParserReference.md "A Bigger Example: Nested Rules" drew the `retries = 3` value as `- [integerExpression] 3`. The grammar names no rule `integerExpression`, and the integer alternative is `Integer().Flatten(FlattenType.Flatten)` inside `valueAtom`, so the integer contributes no named or preserved node at all. The parser renders `3` as a bare rune leaf directly under `values`, identical to the `hard` value's `h a r d` leaves. The diagram's sibling atoms (`red`, `green`, `blue`, `hard`) carried no label. Only the integer got a fabricated one, which tells a reader that `Integer()` is findable or that integers are tagged differently from other value atoms. Neither is true.
    - Why it's an easy mistake to make: when an author writes a value-list grammar they think in domain terms ("this value is an integer"), and the diagram inherits that mental model even though the grammar was deliberately flattened so the tree carries only the leaves. The `FlattenType.Flatten` on the value atom is precisely the instruction "don't keep a node for me", so any diagram that draws a node for it is self-contradicting against its own grammar.
    - Where to look: for every tree diagram in a doc, walk the grammar that precedes it and ask, for each drawn node, "does that rule reach the tree?" A node reaches the tree only if its effective `FlattenType` is `Preserve` (named via `.As(...)`, or `.Preserve()`, or a Preserve-by-default leaf like `OneOf`/`ScanUntil`). Any node drawn for a rule that is `Flatten` (every `And`/`Or`/count rule by default, or one explicitly `.Flatten(FlattenType.Flatten)`'d) or `Delete` (`Token`/`Literal`/`Eof`/`Not`/`Peek`, whitespace factories) is a phantom unless `ParseOptions.PreserveAllSymbols` is stated. Also check that a labeled node's label is a real rule name in the grammar, not an invented domain word.
    - Fix shape: redraw the diagram to match what the grammar produces (print `result.PrintTree()` on the documented input and reconcile), and lock it in with a test on the *real* tree. A diagram can't be compiled, so the regression test pins the structural claim instead: assert no symbol's `DisplayName` equals the phantom label, and that the node in question flattens to the leaves the corrected diagram shows. Asserting the diagram's original claim (the phantom node exists) is the test-first failing form. Related but distinct from `doc-prose-and-comments-naming-a-renamed-or-removed-api.md`: that pattern is a wrong *name* for a real thing. This one is a *node that can't exist* given the grammar's own flatten policy.
