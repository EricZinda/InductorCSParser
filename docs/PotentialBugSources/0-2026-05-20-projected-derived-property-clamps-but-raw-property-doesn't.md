- A raw property has a documented in-range invariant, but a public construction path doesn't enforce it. A derived projection of the same value clamps internally, so the two disagree on bad input
    - Shape: a result-bearing struct exposes both a raw scalar (e.g. `ErrorCharIndex`) and a derived projection of that scalar through a helper (`ErrorPosition` → `SourcePosition.From(input, ErrorCharIndex)`). The helper clamps its input as a defensive measure (positive offsets capped at `input.Length`, negatives floored at 0). The raw scalar is an auto-property that's whatever the constructor stored, with no enforcement. Built-in callers happen to feed in-range values, so the two views agree in practice. A public factory (or a future construction path that produces an out-of-range raw value) breaks the agreement.
    - Why it bites: a caller reading the doc on the raw property writes `input.Substring(result.ErrorCharIndex)`. The first time the raw property holds an out-of-range value, that caller throws. The same caller reading `result.ErrorPosition.Value.CharIndex` would have gotten the in-range value and worked. Two values that name the same point disagreeing is the failure shape, and silent disagreement is worse than a loud failure at the construction point.
    - How to spot it: look for a `readonly struct` with a numeric property whose doc declares an invariant ("always in [0, X]", "capped to Y") but whose constructor just assigns the parameter. Then look for a derived property on the same struct that re-computes the same number through a helper that DOES clamp. If both paths exist, they're meant to agree. The construction point is where to enforce: throw on out-of-range so the caller bug surfaces at the construction call rather than as a silent inconsistency downstream. (Clamping at construction also closes the gap but hides driver bugs.)
    - Other places this might apply (worth a sweep next time): any other "ErrorXxx" property family (ErrorTokenIndex, ErrorLine, ErrorColumn) where the conversion helper clamps but the raw input doesn't. Currently those are all derived from the same already-enforced (post-fix) ErrorCharIndex, so they inherit the invariant. But a future change that adds a new raw position property without enforcement would re-open the gap. Audit any new "char index" type properties at construction.
