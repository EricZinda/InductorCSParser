- A rule run as lookahead must discard the probe's failures, not just roll the position back
    - The pattern: a rule runs another rule purely to *look ahead*. It wants the yes/no answer but never commits the position. The idiom is `using var peek = lexer.BeginTransaction(); var match = inner.TryParse(...);` and then *not* calling `Commit`, so the `using` rolls the lexer position back.
    - The trap: a transaction rolls back the **position**, not the **failure tracker**. `Lexer.Transaction` documents this directly: "Commit does nothing to the failure tracker. Failures survive both commit and rollback." So every `RecordFailure` the probed rule made (and every `_subtreeDeepestFailure` high-water bump) is still there after the `using` disposes.
    - Why it matters: a lookahead probe is off the real parse path. Its failures are not near-misses, they're the parser asking a question, not trying to consume input. Keeping them lets a probe's deep excursion outrank the real parse's failures, so `ParseResult.ErrorCharIndex` (and the line/column derived from it) points at a stray position the probe reached rather than where the parse actually went wrong. The damage is worst when the probed rule is multi-token: it can record a failure *past* where the lookahead's own anchor sits.
    - The correct shape (what `PeekRule` and `NotRule` do): snapshot the failure state before the probe, and after it restore the snapshot and discard the subtree extent:
        - `var snapshot = lexer.SaveFailureState();`
        - run the probe
        - `lexer.RestoreFailureState(snapshot);`
        - `lexer.DiscardSubtreeExtent();`
      `DiscardSubtreeExtent` (which zeroes the mark) is only safe when the probe owns the whole `_subtreeDeepestFailure` window, i.e. when the probe runs directly inside a `BeginTransaction` scope, which zeroed the window on entry and merges the saved extent back with `Math.Max` on dispose. A probe that is *not* wrapped in its own transaction, one that shares a transaction window with the rule's real (consumed) scanning, must instead snapshot `lexer.SubtreeDeepestFailure` before the probe and restore it with `lexer.RestoreSubtreeExtent(snapshot)` afterward, so it undoes only the probe's contribution and leaves a committed sibling's legitimate extent intact. Zeroing in that situation would wrongly drop the sibling's mark.
    - Known instances: `PeekRule` / `NotRule` do it correctly. `ScanUntilRule` had the gap in two places, its rule-valued stopper probe and its rule-valued escape-start probe, both fixed 2026-05-18 (see `BugSearchLog/2026-05-18-scanuntil-rule-stopper-probe-leaks-failures.md`). The stopper probe uses the `BeginTransaction` + `DiscardSubtreeExtent` form. The escape-start probe, which can't roll back on a match, uses the snapshot + `RestoreSubtreeExtent` form.
    - Reviewer mental model: any time a rule calls `inner.TryParse` inside an uncommitted transaction (or any transaction it intends to roll back regardless of the inner outcome), ask "does this also discard the inner's failures?" If it only rolls the position back, the failure tracker is leaking. The TokenSet / int / span fast-path equivalents of these checks don't have the problem (they never call `RecordFailure`), so the leak is specific to the *rule-valued* probe paths.
