- Mutate-in-place fluent methods without set-once guards
    - The `Rule` fluent API encourages chains like `OneOrMore(OneOf(TokenSet.Digits)).As("digits").Preserve().WithError("expected digits")`. Reading top-to-bottom that looks like it's building a new rule at each `.` , the way LINQ chains do. The actual semantics are different: every modifier method mutates the receiver `Rule` instance in place and returns the same reference for chaining. That's a deliberate choice (rule graphs need shared subrules — `term` referenced from `sum` and from another `term` has to be the same instance), but the price is that calling the same modifier twice against the same instance overwrites the previous value with no error.
    - Four documented sites of this trap, all under the same shape (modifier writes a field; second call overwrites it; the bug only surfaces when a consumer tries to dispatch on which call's value won):
        1. `Rule.As(string)` once let a second call replace `Name`. The SemVer sample chained `.As("major")` / `.As("minor")` / `.As("patch")` across three references to a shared `OneOrMore(OneOf(digits))` instance. All three references ended up named "patch" (last call wins). `Tree.Find(major)` returned the same node as `Tree.Find(patch)` and the consumer got the same digit string for all three. Fixed in commit 6daadb1 — now throws on the second call.
        2. `Rule.As(SymbolId)` had the same shape against `Id` (`_idUserPinned` gate). Same fix shape in 6daadb1: throws on the second call.
        3. `Rule.WithError(string)` had the same shape against `_errorMessage`. Same fix in 6daadb1.
        4. `LateBoundRule.Bind(target)` had the same shape against `_target`: a second `Bind` before `Compile` silently replaced the first target via `_target = target; SetChildren(target);`. Fixed (z0bh): throws on the second call when `_target` is already set, with the same error-message shape as the other set-once methods.
    - The `.As(string)` + `.As(SymbolId)` composition is special: those write different fields (`Name` and `Id`), so a `.As(name).As(id)` chain isn't a same-overload repeat and stays legal. Only same-overload repeats are bugs, since those overwrite the field the previous call set. `Bind` is single-overload, so the gate is unconditional.
    - When reviewing a new fluent-style modifier on `Rule` (or a Rule subclass) that mutates a field on the receiver and returns it, ask: is the field set-once? If yes, the method should throw on a second call against the same instance, not silently overwrite. The error message should:
        - name the method that's set-once (`.As(string)` / `.As(SymbolId)` / `.WithError(...)` / `.Bind(...)`),
        - quote the existing value (so the user can see what they're about to overwrite),
        - point at the factory-function workaround for the legitimate "reuse this rule shape with a different value" use case.
    - The trap is easy to miss because fluent-style chains read as if they're producing fresh objects, and the test suite generally builds each grammar once per fixture. Reusing a shared rule reference across positions (the legitimate use case the immutable-graph design enables) is the path that triggers the bug. New modifier methods that follow the same `ThrowIfSealed(); _field = value; return this;` shape need the same `if (_field != null) throw` guard between those two lines.
