- Constructor-time auto-pinned Id survives a later `.As(string)` and silently steals the assignment
    - A `Rule` subclass that pins its `Id` in its constructor (via `SetIdInternal`) sets `_idAssigned = true` but leaves `_idUserPinned = false`. The `Compile` pipeline keys most of its id-collision detection on `_idUserPinned`, so an auto-pin slides past `CollectPinnedIds`'s conflict gate. A later `.As(string)` writes `Name` but doesn't reset `_idAssigned`, so `AssignNamedIds` skips the rule and the auto-pinned `Id` stays. The user-perceived effect: the rule has a name but its `Id` is still the constructor's auto-pinned value, and two such rules in the same grammar silently share that `Id`.
    - The only auto-pinning subclass today is `GraphemeRule` ([src/InductorParser/GraphemeRule.cs:58](../../src/InductorParser/GraphemeRule.cs#L58)), which pins a single-rune `Token` to its rune's code point so anonymous `Token('a')` leaves render as `SymbolId(0x61)` and tree walkers can dispatch on `leaf.Id == 'a'` without going through a synthetic per-rule id. The auto-pin is the right default for anonymous Tokens, but it has to step out of the way when the user identifies the rule. The asymmetric `.As(SymbolId)` overload already handles this: it overwrites `Id` regardless of `_idAssigned` (and sets `_idUserPinned = true`). The `.As(string)` overload didn't, so naming a single-rune Token left the rune-id in place and `Tree.Find(firstNamed) / Tree.Find(secondNamed)` returned the same leaf when both rules used the same rune.
    - Fix shape (applied in `tknm`): in `Rule.As(string)`, after writing `Name`, clear `_idAssigned` when `!_idUserPinned`. `AssignNamedIds` then gives the rule a fresh name-hashed custom-range id. The companion site in `GraphemeRule.CollectNormalizationOffenders`'s post-normalization rune re-pin also has to skip the re-pin when `Name != null`, otherwise the custom-range id from `AssignNamedIds` gets clobbered when normalization changes the expected rune (e.g., U+2126 → U+03A9 under FormC).
    - General lesson: if a rule subclass auto-assigns an Id in its constructor, the identification surface (`.As(string)`, `.As(SymbolId)`) is the layer responsible for inviting the user's intent in. The auto-pin path lives below the user's API and shouldn't outlast a user identification call. Watch for any new constructor that calls `SetIdInternal` directly (currently only `GraphemeRule`). The same trap would apply to a hypothetical user-defined `Rule` subclass that wanted to pin its Id at construction; the subclass-author contract on `SetIdInternal` should call out that identification methods now correctly override auto-pins, but only for `.As(string)` if the user-id-pinning fallthrough is intact.
    - The polarity-aware sites in `CollectPinnedIds` show what the framework does when it CAN see the auto-pin: it adds the auto-pinned value to `usedIds` so later passes don't reuse the slot, but it doesn't enter the rule into `pinnedRules` (the dictionary keyed for the `_idUserPinned` conflict check). That's correct: the auto-pin is allowed to collide with other auto-pins (two anonymous `Token('a')` rules legitimately share `SymbolId(0x61)`). The bug was that `.As(string)` should have invalidated the auto-pin instead of leaving it untouched.
    - When reviewing identification-related code: ask whether the rule's `_idAssigned == true && _idUserPinned == false` state can survive an identification call. If yes, the identification call is the wrong shape — it's writing `Name` (or a `Id` pin) without actually replacing the Id used at lookup time. The two consumers that care are `Tree.Find` / `Tree.Is` (compare `Symbol.Id == rule.Id`) and `NameOf(symbol.Id)` (looks up the user-supplied name from the rule index keyed on `Id`). Both fail silently when two rules end up sharing an Id by way of auto-pin.
