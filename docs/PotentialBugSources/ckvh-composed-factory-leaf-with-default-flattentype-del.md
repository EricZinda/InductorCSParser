- Composed factory leaf with default FlattenType.Delete silently erases its text from the tree
    - Companion to `composed-public-factories-inherit-inner-factorys-optional-clauses.md`. That one is about a composed factory inheriting a *clause* the docstring didn't promise (Float silently accepting `[+-]?` in the fractional position). This one is about a composed factory keeping the clause it promised but having the matched text disappear from the *tree* it builds, because the leaf carrying that text has `FlattenType.Delete` by default.
    - The shape: a public factory in `Rules.cs` describes its output semantically ("Match a signed integer", "Match a CRLF terminator", "Match a token-bounded comment body"). The author wires the characters that carry that semantic in via `Token('+')` / `Token('\n')` / `Literal("--")`. Those leaf rules have `FlattenType.Delete` by default, which is the right answer for "throw away the syntactic punctuation in the consuming grammar" (you don't want every comma to show up in the parse tree) but the wrong answer when the *content* of the leaf is what the docstring promises. The match succeeds and consumes the characters, the leaf produces a `Symbol.Discarded` rather than a real `Symbol`, and the parent rule's flattened child list never sees it. `result.ToString()` and `result.Find(rule).ToString()` walk the surviving leaves and miss the dropped one.
    - The asymmetry between `Symbol.ToString()` (rebuilds the text from surviving leaves) and `Symbol.SourceText` (slices the original input by the recorded match span) is the key tell. The composite's span covers the full match including the dropped leaf, so `SourceText` returns the user-typed text. `ToString()` returns text without the dropped leaf's characters. A test that only checks success / failure (the shape `FloatRuleTests.cs` used pre-`fl0a`, and the shape my new `IntegerRuleTests.cs` started from) never sees the divergence. A user who reads `ToString()` to recover the numeric / textual value the factory promised sees a silently truncated answer.
    - When reviewing a composed factory in `Rules.cs`, ask: does the docstring promise that a specific character or substring is part of the output (`"a signed integer"`, `"an end-of-line"`, `"a quoted body"`)? If yes, walk the leaves that carry that character and check their default `FlattenType`. The fix is `Token('+').Flatten(FlattenType.Flatten)` or `OneOf("+-").Flatten(FlattenType.Flatten)` (whichever shape fits) so the leaf bubbles up into the parent's child list. `Rules.Float()` (`fl0a`) and `Rules.Integer()` (`i1nt`) are the canonical cases. The composed factories that intentionally drop punctuation (`EndOfLine` discards the newline char on purpose, `InlineWhitespace` discards the whitespace on purpose) stay as-is because their docstrings don't promise the dropped text is in the output.
    - Reviewer mental model: the leaf's default `FlattenType` is a choice about the *consuming grammar*'s tree shape, not a choice about the factory's output. When a factory composes a leaf to encode part of its *own* output, override the default explicitly. `Float()` and `Integer()` both override the sign leaf to `Flatten(Flatten)` for exactly this reason. New composed factories should follow that shape unless the docstring explicitly says the leaf's text is excluded from the output.
