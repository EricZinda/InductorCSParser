- NoneOf-shaped admit-by-non-membership rules need conservative `FirstConsumedTokens`
    - Sibling pattern of "Static analysis on a TokenSet that ignores its multi-rune entries", but inverted. `OneOfRule` admits a token iff its chars ARE in the set, so `LookaheadFirstRunes` (rune-only ∪ first-rune-of-each-multi-rune-entry) is a tight superset of "what a OneOf-admitted token can start with." `NoneOfRule` admits a token iff its chars are NOT in the set, so its admit set includes every multi-rune cluster whose chars don't match a (necessarily finite) multi-rune-entry list, and a multi-rune cluster can start with any base rune.
    - That makes `NoneOfRule.FirstConsumedTokens` fundamentally Universe whenever the rule can match: even a rune R that's in `_set.RunesOnlyPart` (single-rune R is rejected) can be the first rune of an admitted multi-rune cluster like "R<combining mark>". The previous `~_set.RunesOnlyPart` answer was correct for the single-rune-admit case but ignored the cluster-admit case, so the recursive engine's `CannotMatchLookahead` shortcut and the SM lowerer's alternative-skip optimization both wrongly skipped NoneOf when the peeked rune was in the rune-only part. See backlog n7mh.
    - When reviewing a new `ComputeRuleStart` for a rule whose admit criterion is "NOT in some finite set," ask: can the rule admit a multi-rune cluster? If yes, the first rune of that cluster could be anything, so `FirstConsumedTokens = Universe` is the soundest answer and any tighter bound has to enumerate ALL multi-rune clusters that could match (impossible in general, since multi-rune clusters are unbounded). The optimization tradeoff: tight first-rune bounds work for OneOf-shaped rules (admit by membership against a finite set, so the admit set's first runes are also finite). They don't work for NoneOf-shaped rules (admit by non-membership, so the admit set is the complement of a finite set, which is infinite and includes clusters starting with any rune).
