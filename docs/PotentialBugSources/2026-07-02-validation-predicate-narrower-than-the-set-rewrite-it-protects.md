- A Compile-time validation whose qualifying predicate is narrower than the set rewrite it protects lets unchecked data into the sets the compiled rule matches against
    - The shape: a Compile pass has two legs that walk the same entries. The validation leg decides which entries need checking ("does this entry have a multi-rune conversion?") and throws on offenders. The rewrite leg decides which entries contribute to the compiled rule's sets ("is this entry non-form-stable?") and adds their converted runes. When the validation predicate is narrower than the rewrite predicate, every entry in the gap gets added without ever being checked. Nothing fails at Compile, nothing fails at parse, the rule just silently accepts input it was supposed to reject.
    - The worked case: IdentifierRule's three extras checks all funneled through `CompatibilityPiecesIn`, whose first line returned "passes" when `TryGetMultiRuneConversion` reported no multi-rune conversion. But `AddProjectedRunes` (the rewrite leg) normalizes every non-form-stable entry and adds the converted rune. An extra whose NFKx is a SINGLE rune sits exactly in the gap: `Identifier(extraStartRunes: TokenSet.Single(0x00A0))` compiled under FormKC put a bare SPACE in the identifier-start set (U+00A0 converts to SPACE), so `Parse(" x")` matched a space-led identifier with no opt-in from the caller. The comment justifying the skip claimed the single-rune conversion "is its own head, which the caller already listed", which conflated the entry (U+00A0, what the caller listed) with its conversion (U+0020, what the rewrite adds to the set).
    - Why it's easy to introduce: the checks are usually written while fixing a bug whose repro happens to be multi-rune (U+00A8's SPACE + combining mark, U+FDFA's eighteen-rune phrase), so "multi-rune" looks like the defining property of the problem when the defining property is actually "changes under the form". Four consecutive fixes in the same series (9ff872e, cb26fe2, 8752f81, b60a5bd, 2026-06-03..06) each keyed off multi-rune-ness and each left the single-rune gap open.
    - The reviewer mental model: find the rewrite leg and the validation leg, and diff their entry predicates. They should be the same predicate, ideally the same function. If the validation helper and the rewrite helper each reimplement "does this entry matter", the two will drift. The fix here made the validation's `TryGetConversion` deliberately mirror `AddProjectedRunes`: every conversion the rewrite would add is one the checks examine.
    - Sites to recheck when adding a Compile-time expansion: IdentifierRule's `ValidateNormalization` (now aligned), OneOfRule/NoneOfRule's `NormalizeAndValidate` (validation and rewrite are the same walk there, so they can't drift structurally, which is the shape to prefer), ScanUntilRule's escape-start handling (a rune-not-in-a-set rewrite with its own offender report), and any future rule that both validates user data under a form and rewrites its sets from that data in separate passes.
    - Distinct from `earlier-check-shadows-a-later-one-when-the-two-inputs-overlap.md` (two checks racing on the same input) and from `runtime-accept-wider-than-compile-time-lookahead-set.md` (runtime accepting more than a published set claims). Here both legs run at Compile time and the divergence is in which entries qualify, not in what happens to a qualifying entry.
