- A hot-path lookup linear-scans a sorted structure that's big enough to warrant binary search (and the comment may already claim it does)

  - Shape: a data structure maintains a sorted, non-overlapping invariant (intervals, ranges, a sorted array) precisely so lookups can be sub-linear, but the lookup is a plain linear scan. With a small structure that's fine, even faster than binary search. The cost only shows up once the structure grows large *and* the queried key tends to land late in the order. A linear scan with an early-out on "key is below this entry, and entries are sorted, so it's not here" makes the best case (low keys) O(1), which hides the worst case (high keys) behind a benchmark that only ever queries low keys. ASCII-heavy test inputs are exactly that misleading benchmark.
  - Concrete instance (2026-06-04): `TokenSet.ContainsRune(int)` linear-scanned `_ranges` (built sorted, non-overlapping, non-adjacent by `Normalize`). For small hand-built sets it was cheap, and for ASCII letters the first interval matched in one or two comparisons. But `TokenSet.Letters` is 659 intervals and `XidContinue` 775, and this is the per-token membership test for `OneOf` / `NoneOf` / `ScanWhile` / `ScanUntil` and the `AdvanceWhile*` lexer loops. A CJK / Cyrillic / Arabic / Hangul rune, or any miss past the Latin block, walked hundreds of intervals per character: ~135-170x slower than an ASCII letter (measured: 25 ms for `'A'` vs 3368 ms for U+4E00 and 4274 ms for a high miss, over 20M calls). Fix was a short linear prefix (so ASCII and small sets pay nothing) plus a binary search of the tail.
  - Why it hides: it's not a correctness bug, so no test fails and no error surfaces. Functional tests spot-check a handful of members and pass identically before and after. Unit-test and example grammars are overwhelmingly ASCII, which is the linear scan's best case, so even a timing benchmark looks fine unless it's fed non-Latin input. The header comment here actually *claimed* "binary search of intervals," so the code read as already-optimized while it wasn't. A comment asserting an algorithm is a thing to verify against the code, not trust.
  - Where else to look: any per-token / per-character / per-node lookup over a structure that carries a sortedness or ordering invariant. Interval/range membership (`TokenSet`), sorted-array `IndexOf`, a "find the rule/symbol whose range covers this position" scan, prefix tables. The tell is a `for` loop over an array whose construction goes through a `Sort` / `Normalize` / merge step, especially when the loop's only early-out depends on the key being small.
  - Test that catches it: a correctness-equivalence sweep that exercises keys across the whole ordered space (not just the cheap front) checks the lookup against an independent oracle and catches an off-by-one in the binary-search handoff. The performance itself is best shown with a one-off measurement comparing a front-of-range key against a late / past-the-end key on a large instance, since wall-clock thresholds in CI are flaky. Don't assert timings. Measure once, record the ratio, and lean on the equivalence sweep as the permanent regression test.
