- A comment that asserts "X can never be a member of this set" is a latent bug whenever an opt-in API exists that puts X into the set
    - Shape: a hot-loop comment justifies skipping (or being allowed to skip) a membership check by claiming a whole category of token can't be in the set. The canonical example: `ScanUntilRule`'s scan loop said a lone-surrogate token "can't be in any TokenSet (entries are valid Unicode scalars)," so "the stopper check correctly says no match" and the surrogate always flows through as body. That's only true for the common stopper set (one with no surrogate code units). `TokenSet.Surrogates` / `TokenSet.SurrogateRange` are the documented opt-in that puts surrogate code units into a set, and `TokenSet.ContainsToken` has a lone-surrogate branch so they match, so a surrogate-bearing stopper actually stops the scan.
    - Why it's dangerous even when the code is correct: the code that the comment describes was correct (it called `ContainsToken`, which handles the opt-in). The hazard is the comment itself. It reads as a license to optimize: "RuneValue == -1 means it can't match, so skip `ContainsToken` for this token." Acting on that license reintroduces exactly the fast-path-membership-drops-lone-surrogates bug that already bit `AdvanceWhileRuneIn`, `AdvanceUntilRuneIn`, and `TokenSet.Contains(string)`. A wrong "can't happen" comment is a primed regression, not just stale prose. See [[2026-05-15-fast-path-membership-drops-lone-surrogates]].
    - It also signals a coverage gap. If the comment says a case can't occur, there's usually no test exercising it. Here every ScanUntil surrogate test used a non-surrogate ('|') stopper, so the surrogate-bearing-stopper path was untested and nothing contradicted the comment. The fix added that test. The gap and the wrong comment travel together.
    - How to spot more: grep code comments for universal-impossibility phrasing about set / category membership ("can't be in any TokenSet", "never a member", "isn't a valid X so the check always fails", "RuneValue == -1 so it can't match"). For each, ask: is there a public factory or operator that constructs the excluded case anyway? In this codebase the surrogate opt-ins are `TokenSet.Surrogates` and `TokenSet.SurrogateRange`. Anything that says "surrogates can't be in a set" is simply wrong, those factories exist to put them there. Confirm the code actually routes through the shared membership primitive (`ContainsToken`) rather than a decode-first shortcut, and that a test pins the opt-in case.
