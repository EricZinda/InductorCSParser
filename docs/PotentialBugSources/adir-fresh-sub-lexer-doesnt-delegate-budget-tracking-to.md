- Fresh sub-lexer doesn't delegate budget tracking to the outer
    - Shape: a rule (canonically `WithinTokenRule`) constructs a new `Lexer` to run an inner rule over a sub-range of the outer input, but never wires the new lexer's budget bookkeeping back to the outer. The sub-lexer's `_ruleCountLimit / _maxDepth / _timeout / _cancellation` stay at the field-init defaults (zero / null), which the periodic budget check treats as "disabled". The outer parse's `EnterRule` increments depth and rule counts on the OUTER lexer only. Once execution crosses into the inner rule via the sub-lexer's `Rule.TryParse`, those counters are a fresh zero and the caller's budgets are effectively turned off.
    - Why it hurts: the caller's `MaxDepth` is documented as a stack-overflow defense. A recursive inner rule on a grapheme cluster crafted with many combining marks (a base char plus N copies of U+0301 is one UAX #29 cluster of N+1 runes) recurses N+1 levels deep with no depth cap. .NET can't catch the resulting `StackOverflowException`, so a "parser DoS" turns into a process crash. The cancellation / timeout shape is the same: a `Cancel()` fired during the inner run isn't observed until control returns to the outer.
    - Subtle variant that the obvious fix misses: copying the LIMITS onto the sub-lexer while leaving the sub-lexer's own `_ruleDepth / _ruleInvocations` separate still leaks a fresh `MaxDepth` worth of inner recursion on top of the outer's depth. A grammar where the outer rules already put the parser at depth K when WithinToken fires gets an inner allowed up to MaxDepth more frames, for a total of K + MaxDepth. The correct fix is to DELEGATE: `EnterRule / ExitRule / TickPeriodicBudget` on the sub-lexer forward to the outer, so the inner's recursion stacks on the outer's counter and MaxDepth covers the combined depth.
    - Where to look: any code path that constructs a `new Lexer(...)` outside `Rule.ParseRecursive`. The fix is `Lexer.InheritBudgetsFrom(Lexer source)` (added 2026-05-19): sets a `_budgetParent` pointer on the sub-lexer, and the four bookkeeping methods short-circuit to the parent's implementation when it's non-null. Sub-lexers can nest (WithinToken inside WithinToken) and delegation chains through.
    - Adjacent traps: `PreserveAllSymbols` is intentionally not propagated into the WithinToken sub-lexer because inner Symbols are discarded by design. The `TraceSink` is intentionally not propagated because inner traces would interleave confusingly with the outer trace. Those choices are correct for those flags. The bug was only about the four budget knobs that exist for safety. When adding a new sub-lexer site, ask separately for each ParseOptions field "is this for diagnostics (probably stays outer-only) or for safety (must delegate)?"
