- Using the rune value as a default in name-or-id lookups without gating on whether the user named the rule
    - Two places in the parser pre-fix had this shape: the leaf-Id assignment in `OneOfRule` / `AnyTokenRule` / `NoneOfRule` / `WithinTokenRule` (`leafId = runeValue >= 0 ? new SymbolId(runeValue) : Id`), and `Rule.NameOf`'s character-range short-circuit (which returned the rune's text for any id in `0..0x10FFFF` before consulting the name index). Both were documented optimizations for *unnamed* rules: tree consumers can switch on `Tree.Id == 'a'` without a synthesized per-rule id, and `PrintTree` renders character leaves as `'c'` instead of the noisy `c: "c"`. Without a `Name`-based gate, both branches fire even when the user explicitly named the rule via `.As("...")`, silently breaking `Tree.Find(rule)`, `Tree.Is(rule)`, `NameOf(leaf.Id)`, and `PrintTree` whenever the rule's Id (or the matched token's rune) lands in the character range. See backlog w1th.
    - The fix is the same shape in both places: gate the rune-as-default branch on "user did not name the rule," preserving the optimization for unnamed rules and honoring the user's name when set. All four leaf-emitting rules now share `leafId = (Name == null && runeValue >= 0) ? new SymbolId(runeValue) : Id`. `Rule.NameOf` consults a name index that tracks whether each entry is user-supplied; a user-supplied name wins over the rune-text default. `PrintTree` falls through to the long `<name>: "<text>"` form when a character leaf's `NameOf` differs from its rune text.
    - When adding a new leaf-emitting rule or any new path that surfaces a name from a SymbolId, ask: does this branch on whether the rule was user-named? If a rune-based default fires unconditionally, named uses of the rule are silently broken. The reference shapes are `LiteralRule` (always uses `Id` for the leaf, so it doesn't hit either default) and the post-fix `OneOfRule` / `NameOf` (gated on `Name == null` / `IsUserSupplied`).
