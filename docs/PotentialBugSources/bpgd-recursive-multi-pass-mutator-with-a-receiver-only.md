- Recursive multi-pass mutator with a receiver-only "already done" check
    - Shape: a class-level operation (here `Rule.Compile`) walks a graph and mutates per-node state across several passes (id assignment, FirstConsumedTokens, projected literal text, error-message inheritance, sealed flag, normalization form). The entry point checks `if (this._sealed) ...` and treats the early-return as both idempotency and safety. The check only looks at the receiver. The recursive passes do *not* re-check `_sealed` per node. They assume "nothing else is mutating these nodes right now," which only holds if every reachable node is unsealed. A second call to the same operation from a different receiver walks straight past the receiver check and lets the recursive passes re-mutate the sealed nodes, corrupting state that a previous caller is still relying on.
    - Why it's wrong: sealing is per-node, but the identity check that decides whether to commit to mutation is treated as a property of the *call*. When two roots share a sub-graph, the sub-graph is part of both grammars' identity. A second compile under a different identity (different normalization form, different surrounding id space) has to either reject the conflict for the whole reachable sub-graph or build a parallel sub-graph. Silently rewriting the existing one is the bug.
    - Where it was found: `Rule.Compile(NormalizationForm?)`. The receiver-only `_sealed` check missed the case where a sibling root reached a sealed subrule. `CollectNormalizationOffendersAll` then rewrote `Literal._expected`, `OneOf._set`, etc. into the new form, and `StampNormalizationForm` overwrote `_normalizationForm` on the shared nodes. The first root's parses started failing on input it had previously accepted. The id-assignment passes also re-used the sealed nodes' previously-assigned ids without checking for collisions across distinct sealed rule instances landing on the same custom-range slot. Find / Is / NameOf then dispatched two different rules through one SymbolId.
    - Fix landed: a recursive `CheckNoSealedReachableRules` pre-walk at the top of `Compile` (after the idempotent-receiver early return). If any reachable rule is already sealed, throw with a clear message naming the offender and pointing the user at the workaround (compile the parent grammar first, or expose shared rule shapes via factory functions that return a fresh instance per call). One walk replaces three narrower checks (id-collision, form-conflict, construction-time fresh-child) that earlier iterations of the fix experimented with.
    - Trade-off: the "library of shared static sub-rules across multiple grammars" pattern no longer works once any sub-rule has been individually `.Parse(...)`'d. Grammar files that expose multiple test-target top-level rules sharing sub-rules now have to seal them in a single eager Compile pass at type init (one static constructor that calls `RootRule.Compile()`, or an aggregate `Or(rootA, rootB, ...).Compile()` for unrelated test-target roots that share private sub-rules). The four HtmlGrammar / CssGrammar / BacklogGrammar / PrologGrammar fixtures in the test corpus needed one static constructor each.
    - Reviewer mental model: any class-level operation with the shape `void Foo(...) { if (this._sealed) return this; /* walk graph, mutate per-node */ }` is suspect. Ask "what happens when this walks into a node another caller already sealed?" If the recursive passes don't re-check the sealed state and treat per-node fields as theirs to overwrite, the receiver-only check is insufficient. The fix is a single recursive pre-walk that verifies no reachable node is already in the committed state, *or* a per-node sealed check inside each recursive pass. Pick one based on whether legitimate same-graph re-entry is required.
    - Related: `[[xpid-compile-time-auto-pin-overriding-user-supplied-pins]]` is a kindred shape: compile-time auto-assignment overwriting data the user committed. Same root cause (Compile mutates per-node state under the assumption nothing else relies on it), different trigger (one root, one user pin) vs (two roots, shared sealed subnode).
    - Grep target: every `if (this._sealed)` (or similar receiver-only commit-state check) in code that subsequently walks a graph via `Children` / sub-references and calls a mutating per-node hook. If the per-node hook doesn't itself check sealed state, the operation has the same shape.
