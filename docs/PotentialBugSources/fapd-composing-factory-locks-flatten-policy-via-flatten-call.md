- Composing factory locks the flatten policy via `.Flatten(...)`, blocking later `.As(name)`
    - The shape: a public factory in `Rules.cs` returns a composite `Or(...)` / `OneOrMore(...)` / `And(...)` and wants a non-default FlattenType. The natural way to write that is `Or(alternatives).Flatten(FlattenType.Delete)` — the same syntax a grammar author uses to override a flatten policy on a leaf. The factory's caller has no clue that's happening, since the factory's return value is just `Rule`.
    - The trap: `Rule.Flatten(type)` doesn't just set the field. It also sets the private `_flattenPolicyExplicitlySet` flag, which means "the user explicitly chose this; don't silently override it later." `Rule.As(name)` consults the same flag in `ApplyIdentificationFlattenPolicy` and throws on it, because `.As(name)`-with-an-explicit-non-Preserve-policy is a real user contradiction worth flagging. From the user's side, `factory().As("name")` then throws with a message that says "your flatten policy was explicitly set to FlattenType.Delete" even though the user never wrote `.Delete()` / `.Flatten(...)`. The factory body did.
    - User-visible consequence: a Tree.Find-by-name call against a composing factory's rule silently fails to compile (well, throws at grammar-construction time). The workaround (`factory().Preserve().As("name")`) is undocumented and asymmetric to every other factory in `Rules.cs` (Token / Literal / Integer / Float / Identifier all support `factory().As("name")`).
    - `Rules.EndOfLine`, `Rules.InlineWhitespace`, and `Rules.AnyWhitespace` had this shape. `Rules.Identifier` is the same pattern but chains `.Flatten(FlattenType.Preserve)`, which is safe because `.As(name)`'s auto-flip target IS Preserve — the `_flattenPolicyExplicitlySet` check is in the path that triggers only when the explicit policy is non-Preserve.
    - When reviewing any composing factory — built-in or user-written — ask: does it chain `.Flatten(FlattenType.X)` where X is non-Preserve? If yes, the factory locks the policy and a later `.As(name)` on the returned rule throws. The fix is `Rule.FlattenByDefault(...)`, a public method that mirrors `.Flatten(...)` minus the `_flattenPolicyExplicitlySet` assignment. It's public, not internal: external users write composing factories too, and they hit the identical trap, so the escape hatch has to be reachable from grammar code.
    - FlattenType is the only configurable property that needs this. It's the only one with a *class default* a composing factory has to override (`Or` / `And` / `OneOrMore` default to `Flatten`). The other "user did something" flags — `Name` (`.As(string)`), the pinned `Id` (`.As(SymbolId)`), `_errorMessage` (`.WithError`) — all start unset, so a factory that doesn't touch them leaves them overridable already. A blanket "reset everything the user-or-factory configured" method (an `AsFactory()`-style escape hatch) is the wrong shape: it would also unlock `Name` / `Id` / `_errorMessage`, whose set-once throws exist specifically to catch the silent double-`.As` / double-`.WithError` last-wins footgun. The right fix is property-specific, not a blanket reset.
    - Companion to `00000-composed-factory-leaf-flattentype-delete-erases-tree-text.md`. That one is about a *child* leaf's default FlattenType erasing the leaf from the composite's tree; this one is about the *outer composite*'s factory-applied FlattenType locking the user out of identifying the composite by name. Both surface the same theme: a factory's FlattenType choice is a default for the consuming grammar, not a binding decision, and the factory has to use a non-locking mechanism to apply it.
