- Cached static analysis vs. mutated Compile-time rule data
    - `Rule.Compile` runs several passes on the rule graph: id assignment, validation, `ComputeRuleStartAll`, normalization-form projection, sealing, form-stamping. The order matters when one pass MUTATES per-rule data (e.g. `_set` / `_expected`) and another pass CACHES a derived value (e.g. `FirstConsumedTokens`) computed from that data. If the cache pass runs before the mutation pass, the cached value drifts away from the rule's actual matchable runes the moment normalization rewrites the source data.
    - The shape that bit `Rule.Compile(NormalizationForm?)`: `ComputeRuleStartAll` ran BEFORE `CollectNormalizationOffendersAll`. The first pass cached each rule's `FirstConsumedTokens` against the user-supplied set / expected text. The second pass form-projected those fields in place: `GraphemeRule._expected` rewritten (U+212B → U+00C5 under FormC), `OneOfRule._set` projected to its post-normalization entries, `LiteralRule._expected` overwritten, etc. The cached `FirstConsumedTokens` then disagreed with the rule's actual matchable first runes, and `BetweenInclusiveRule` / `FirstOfRule`'s lookahead shortcut skipped the rule on input the lexer-normalized form would have matched. See backlog nrmf and search log a000.
    - Symptom: the rule appears to "silently never match" for one specific input shape (the canonical-singleton substitution case, NFD-decomposed first runes, set entries that project across runes), even though calling the inner rule directly with the same input matches. The lookahead-skip path is what hides the working inner rule from the outer scan. Disabling `Compile(null)` or the outer composite makes the bug vanish.
    - When reviewing any new Compile-time pass that mutates per-rule data, ask: is there a cached value derived from this data already populated by an earlier pass? If yes, either move the mutating pass earlier (so the cache reflects post-mutation state) or invalidate the cache after the mutation. The Compile pipeline gives ordering guarantees for free; downstream computeStart / computeRequiredLiteral / similar caches don't.
