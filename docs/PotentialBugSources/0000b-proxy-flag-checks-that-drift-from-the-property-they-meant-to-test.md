- Proxy-flag checks that drift from the property they were meant to test
    - A check written as `!_sealed` to mean "this rule was user-pinned, not pre-compiled" silently breaks once a rule can be both user-pinned AND pre-compiled. `Rule._sealed` answers "has Compile finished sealing this rule?" and `Rule._idUserPinned` answers "did the user call `.As(SymbolId)` on this rule?" The two were nearly equivalent in the original lifecycle (a freshly built rule pinned by `.As(SymbolId)` is unsealed; sealing happened only inside Compile, after the pinned-ids check ran), so `!_sealed` worked as a proxy for `_idUserPinned`. The proxy fails the moment a sub-rule is pre-compiled by one consumer (gets sealed with its user pin still set) and then composed into a larger grammar by another consumer (the larger Compile sees `_sealed=true` on a rule that is genuinely user-pinned). See backlog z2pn for the pin-conflict miss this caused in `CollectPinnedIds`.
    - The fix is to consult the precise property: `_idUserPinned` (set only by `.As(SymbolId)`, persists through sealing) for "did the user pin this id," and `_sealed` only for "is mutation now disallowed." The combined gate `_idUserPinned && idValue >= CustomRangeStart` keeps the original exclusions (rune-range pre-pins from Token's constructor still pass through, since they leave `_idUserPinned=false`; anonymous custom-range ids stamped by a previous Compile still pass through, since the anonymous-pass writes `_idAssigned=true` but never `_idUserPinned=true`) while letting pre-compiled user pins participate.
    - When reviewing a new check on a `Rule`'s lifecycle state, ask: does the check consult the property it actually cares about, or a proxy that's "currently equivalent"? Today's proxy can drift tomorrow when the rule lifecycle stretches: a rule that's compiled standalone first and then re-reached, a rule recombined into multiple parent grammars, a rule re-decorated between compiles. The exact properties to read from `Rule` are `_idAssigned` (has any id been written), `_idUserPinned` (was the id from `.As(SymbolId)`), `Name` (was a name from `.As(string)`), `_sealed` (is mutation locked out). Mixing these — using `!_sealed` to mean `_idUserPinned`, or `Name == null` to mean "anonymous" while ignoring the pinned-id case (the `p1nd` shape) — is the same family of bug.
    - State-machine equivalent: any lifecycle-state proxy in `ExperimentalSrc/InductorParser/StateMachine/` that reads from a denormalized snapshot (`SymbolMetadata`, the lowering pass's compile-time visible flags) needs the same audit. The metadata structs only project a subset of `Rule`'s state; if the SM uses a proxy field as a stand-in for the precise lifecycle property, the proxy is liable to the same drift. The fix shape there is to widen the metadata to carry the precise flag, the same way `xpid` widened it for `IsUserSymbolIdPinned` so the SM's leaf-id gate could match the recursive engine's.
