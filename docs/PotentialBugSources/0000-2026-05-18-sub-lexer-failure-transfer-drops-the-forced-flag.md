- Transferring a sub-lexer's failure onto the outer lexer with a flat forced argument drops the inner rule's forced flag
    - A rule that runs an inner rule on a *separate* `Lexer` instance (a sub-lexer) can't let the inner's failures reach the outer parse on their own. They live on the sub-lexer's `FailureStateSnapshot`, not the outer's. The boundary rule has to re-record them on the outer lexer. `WithinTokenRule` is the one rule that does this today: it builds a sub-lexer over one token's runes, runs the inner rule there, and on failure copies the inner's deepest failure onto the outer lexer.
    - The bug shape: the transfer reads `subLexer.DeepestFailureMessage` (just the string) and calls `outerLexer.RecordFailure(pos, message, forced)` with the *boundary rule's own* forced flag. `RecordFailure`'s `forced` argument decides which slot the failure lands in, the forced slot or the non-forced (named) slot. Passing the boundary rule's flag puts a forced inner `.WithError` into the non-forced slot whenever the boundary rule isn't itself forced. `docs/ErrorArchitecture.md` ranks depth-first with one exception, rule 1: "Forced wins. If any forced failure exists, it is reported." That rule only sees the forced slot. A forced failure demoted into the named slot loses rule 1's protection, so a shallower forced `.WithError` elsewhere outranks it, and a deeper non-forced failure shadows it.
    - The mirror half of the same conflation: writing `subLexer.DeepestFailureMessage ?? boundaryRule.ErrorMessage` makes the boundary rule's own `.WithError` a fallback used only when the inner has no message. It can never compete with an inner one, so a `forced` `.WithError` on the boundary rule itself can't dominate an inner message the way it does on every same-lexer composite.
    - The fix shape: transfer `subLexer.DeepestFailureMessage` with the *inner's* forced flag, not the boundary rule's, then record the boundary rule's own message as a separate failure and let ranking pick. `subLexer.DeepestFailureMessage` already returns the forced message when one exists, so the inner's forced flag is exactly `subLexer.SaveFailureState().ForcedMessage != null`:
        ```csharp
        var innerState = subLexer.SaveFailureState();
        string? innerMessage = subLexer.DeepestFailureMessage;
        if (innerMessage != null)
            outerLexer.RecordFailure(pos, innerMessage, forced: innerState.ForcedMessage != null);
        outerLexer.RecordFailure(pos, ErrorMessage, ErrorForced);
        ```
        Write the inner record first (it ran first), so a same-slot same-position tie goes to the inner, the order `And` and `Alias` produce naturally because their inner runs on the same lexer and records before the composite does.
    - Why a same-lexer composite doesn't have this bug: `Alias`, `And`, `Or`, `BetweenInclusive`, `Peek`, `Not` all run their children on the *outer* lexer. A child's `.WithError` calls `RecordFailure` on that same lexer directly, with its own forced flag, at its own position. The composite never re-records the child's message, it only adds its own. Ranking then works untouched. `docs/ErrorArchitecture.md` states this for `Alias`: "ranking picks the winner between the inner's failures and the alias's exactly as it would with no alias in the picture." A sub-lexer breaks that invariant because the inner's failures are quarantined on a different `Lexer`, and any re-recording step that passes a flat `forced` argument silently rewrites which slot the failure occupies.
    - Reviewer mental model: any time code reads one `Lexer`'s `DeepestFailureMessage` and re-records it on another `Lexer`, the `forced` argument has to be the *message's own* forced status, never the recording rule's. `DeepestFailureMessage` collapses the forced and named slots into one string for the final report. On a *transfer* that feeds back into ranking, the slot has to be recovered separately (`SaveFailureState().ForcedMessage != null`) and preserved. The forced flag belongs to the `.WithError` that produced the message, not to whatever rule happens to be doing the recording.
    - Adjacent shapes worth watching:
        - Any future rule that, like `WithinToken`, spins up a sub-lexer (a rule parsing a captured delimiter, a nested-language island, an isolated re-scan) and surfaces its failure. The same forced-flag-preserving transfer applies.
        - Any engine path (state machine, alternative evaluator) that lowers `WithinToken` into native opcodes rather than bridging to the recursive evaluator. Today the SM bridges `WithinToken` to the recursive `WithinTokenRule.TryParseRule`, so it inherits the fix. A native lowering would have to replicate the forced-flag-preserving transfer.
        - `RecordFailure(pos, message, forced)` callers generally: passing a `forced` value that isn't the one the message's own rule chose is the root mistake.
