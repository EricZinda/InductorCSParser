- A contiguous code-point range used as a category proxy includes the non-members the block interleaves
    - Shape: code (or a doc recipe) wants "all the letters in some block" and uses a single `Range(blockLow, blockHigh)`, assuming the block is solidly one category. Unicode blocks aren't contiguous by category: they interleave the odd symbol or punctuation mark between letter runs, so the range silently admits members the author didn't intend. Found in the "Homoglyph Confusables" recipe in UnicodeGotchas.md (mirrored in UnicodeGotchasExamples.cs and UnexpectedUnicodeTests.cs): `TokenSet.Range(0x00C0, 0x00FF)`, commented "Latin-1 Supplement letters," admits U+00D7 MULTIPLICATION SIGN and U+00F7 DIVISION SIGN (both Sm), the two non-letters Unicode parked between the accented-letter runs. A "Latin script only" identifier built on it accepts `a×b` and `a÷b`.
    - Why it happens: the Latin-1 Supplement is the textbook case (À..Ö, then × at U+00D7, then Ø..ö, then ÷ at U+00F7, then ø..ÿ), but the same trap is everywhere: Greek has U+03A2 (a reserved gap) between the uppercase letters, the General Punctuation block mixes spaces and dashes, and most "looks like all letters" ranges have a stray symbol or two. Writing one `Range(low, high)` reads as obviously correct and the common-case test (rejects Cyrillic а, accepts "apple") passes, because the test never feeds the interleaved non-member.
    - How to catch it: when a range stands in for a category, either intersect it with the real category set (`Range(low, high) & TokenSet.Letters`) so the category does the filtering, or split the range at the known non-members and add a test that feeds one of those non-members and asserts it's rejected. The recipe test only checked a member (Latin a) and a confusable from another block (Cyrillic а). It never checked a non-letter from inside the block itself. A set "tested for members but not for the non-members it should exclude" is the allow-table-tested-for-members-not-for-non-members pattern applied to ranges.
    - Second live instance (2026-06-04): the `Greek` set right below `LatinLetters` in the same "Homoglyph Confusables" recipe was still the naive `TokenSet.Range(0x0370, 0x03FF)`, "Greek and Coptic block only." It admits U+037E GREEK QUESTION MARK and U+0387 GREEK ANO TELEIA (both Po, and both punctuation confusables resembling a semicolon and a middle dot, the exact thing this security-framed section promises to keep out), the symbols U+0375/U+0384/U+0385, and several unassigned code points. The block has too many holes to hand-split cleanly, so the fix used the intersect form `Range(0x0370, 0x03FF) & TokenSet.Letters`. The Latin block was fixed but its Greek neighbor wasn't, exactly the "fix one instance, miss the sibling" tail this entry warned about. Follow-up: the intersect form isn't block-specific, so the Latin recipe was then switched from its hand-split sub-ranges to the same `(Ascii.Letters | Range(0x00C0, 0x00FF)) & TokenSet.Letters` shape, making both recipes use one pattern. Note the limit of that pattern: `block & Letters` drops the block's non-letter holes but is still not a script filter (a script spans many blocks, a block mixes scripts), so it stays a coarse approximation, true per-script work needs Script_Extensions data.
