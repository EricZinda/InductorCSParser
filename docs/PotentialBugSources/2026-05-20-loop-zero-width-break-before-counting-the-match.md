- A loop-style composite's no-progress break that runs before counting the match leaves the match out of the lower-bound check
    - A greedy repetition rule (`BetweenInclusiveRule`, and the `OneOrMore` / `ZeroOrMore` / `Optional` / `AtLeast` / `AtMost` / `Exactly` factories over it) needs a no-progress break so a nullable inner doesn't spin forever. If the inner succeeds without advancing the cursor, the loop must stop instead of matching the same empty span again. The natural place is `if (lexer.Position == before) break;` right after the inner returns. The trap is the *order* of that break relative to the iteration counter. A zero-width match is still a successful match (the inner's `TryParse` returned non-null), so if the break runs before the `count++`, that successful match is silently dropped from the count and the lower-bound check (`count < AtLeast`) sees one fewer match than actually happened.
    - User-visible consequence: `OneOrMore` / `AtLeast(n>=1)` / `Exactly(n>=1)` of a rule that can match empty (Optional, ZeroOrMore, Peek, Not, or any composite whose first-set is nullable) wrongly fails on input the inner can only match with a zero-width success, most cleanly empty input. `OneOrMore(Optional(X)).Parse("")` fails while `ZeroOrMore(Optional(X)).Parse("")` succeeds, even though the two differ only in the lower bound and the inner matched once either way. This contradicts the documented behavior ("OneOrMore fails if the first attempt fails", "BetweenInclusive fails if it can't reach atLeast") and standard PEG `e+ = e e*` semantics, where a nullable `e` makes `e+` match empty.
    - The fix is to count the match before applying the break: `count++;` then `if (zeroWidthMatch) break;`. The break still terminates the loop (one zero-width iteration, then stop), but the AtLeast check now sees the match that really happened. For `AtLeast >= 2` a single zero-width match still can't manufacture multiple empty matches, which is correct (you can't satisfy "two or more" from one empty span), but `AtLeast == 1` (the OneOrMore case) is satisfied.
    - Sibling pattern: `loop-composite-break-before-add-drops-preserve-zero-width-inner.md`. That one is the same break-on-no-progress site mishandling the matched child's Symbol (breaking before adding it to outputSymbols dropped a Preserve'd zero-width Symbol from the tree). This one is the break mishandling the match count. Reviewer mental model for any "break out if no progress" check in a loop composite: a zero-width match is a real, successful match. Everything a normal iteration does with a match (add its Symbol to the output, count it toward the bound, advance any per-iteration bookkeeping) has to happen for the zero-width one too before the break runs. The break only suppresses the next iteration, never the accounting for the match that already succeeded.
    - Cross-engine note (`recursive-vs.-state-machine-engine-divergence.md`): the state-machine engine's `Step_PopIterationCheck` already does `between.Counter++` before its `!advanced` check, so it counted the zero-width match all along. The recursive engine's break-before-count was the outlier. When the two engines disagree on a corner case and there's no cross-engine compare test exercising it, the bug can sit undetected in whichever engine is wrong. The recursive engine is the production default, so its divergence is the one that bites users.
