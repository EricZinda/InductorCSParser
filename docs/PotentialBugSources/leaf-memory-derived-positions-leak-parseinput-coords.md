- Position APIs derived from leaf memory must translate parseInput coordinates back to original-input coordinates
    - The parser normalizes input before lexing (`input.Normalize(form)` in `Rule.ParseRecursive`, mirrored in `StateMachineParser.Parse`). Every leaf Symbol carries a `ReadOnlyMemory<char>` constructed from `lexer.Input.AsMemory(...)` or `token.Memory`, both of which point into `parseInput`, not the caller's original `input`. Position APIs that recover offsets from leaf memory via `MemoryMarshal.TryGetString` get parseInput back, NOT the user's input.
    - Sibling pattern to [docs/PotentialBugSources/normalized-input-leaks-into-user-facing-strings.md](normalized-input-leaks-into-user-facing-strings.md). The sibling entry is about CONTENT strings (the user-facing text of the input, like the `{character}` placeholder); this entry is about POSITION values (offsets, line / column / token indices). Both leak the parseInput vs original-input distinction; the fix shape is opposite: content strings have to be re-read from the original (the matched span of `input` is the one the user typed), but positions have to be translated back from parseInput coordinates to original coordinates via `NormalizedPositionMap.TranslateToOriginal`. <!-- style-lint-ok -->
    - The trap only manifests when normalization actually rewrites the input — `String.Normalize` returns the same string reference when the input is already in the target form, and identity coincides with no translation needed. The default FormC + already-NFC input case (essentially all typed and web-sourced text) hits the identity path and looks fine, which is why every existing `SymbolPositionTests` case was either ASCII-only (FormC is a no-op) or compiled with `Compile(null)` (no normalization). Bugs in this pattern hide behind the identity case until someone parses non-NFC input through a normalized grammar.
    - The architectural fix: position translation lives where the original input lives. `ParseResult` already holds the caller's `_input` plus `_grammar.NormalizationForm`, so position-translating APIs go on ParseResult, not Symbol. Symbol exposes an internal `TryGetCharSpan` helper that recovers parseInput offsets from leaf memory; `ParseResult.SourceRangeOf(Symbol)` consumes that span and routes both endpoints through `NormalizedPositionMap.TranslateToOriginal` when parseInput differs from `_input` by reference. Identity case skips the translation entirely. Backlog ysrc shipped this for SourceRange; the same pattern applies to any future API in the same shape (a hypothetical `Symbol.OriginalInput` accessor, a span-tracking matcher result type, etc.) — they belong on ParseResult, not on Symbol.
    - When reviewing any new public API that returns positions derived from leaf memory, ask: is this position going to land in front of a user, in editor diagnostics, in a hand-built UI, or anywhere else that compares against the caller's original input? If yes, route it through ParseResult so the API has access to `_input` + `_grammar.NormalizationForm`, and translate via `NormalizedPositionMap.TranslateToOriginal`. Don't trust `MemoryMarshal.TryGetString`'s recovered string to be the original.
    - FormKC / FormKD make the translation lossy at per-grapheme granularity: a single original cluster (like a ligature `ﬁ`) can expand to multiple parseInput clusters (`f` + `i`), so two leaves can translate back into the same original-cluster span. The per-grapheme walker in `NormalizedPositionMap` gives the first leaf a zero-width range inside the cluster and the second leaf the full cluster span. That's the right answer for the user's "where in my input is this?" question, but a caller expecting per-leaf granularity has to know the API can produce zero-width or overlapping ranges in compatibility-form expansion cases.
