- Doc prose, code examples, and comments naming an API that was renamed or removed in a refactor
    - When a public API is renamed or moved during a refactor, the compiler updates every caller and every test, so the build stays green and the change looks complete. What the compiler can't see is the API's name spelled out in places that aren't compiled: markdown code blocks (docs/*.md, sample READMEs), prose ("call `result.SourceRangeOf(symbol)`"), and `//` comments. Those keep naming the old API and silently rot.
    - The canonical case: `ParseResult.SourceRangeOf(Symbol)` was the position-translating API for a while (see BugSearchLog z007), then the per-Symbol `ParseContext` landed and the accessor moved to `Symbol.SourceRange`, dropping `SourceRangeOf`. The code and the compiled tests followed. The prose lagged: `docs/Recipes.md`, `E2ESamples/SemVer/README.md`, a `FilterTests.cs` comment, a backlog workaround bullet, and a `PotentialBugSources` architectural prescription all kept naming `result.SourceRangeOf(...)`. A user copy-pasting the Recipes.md example got CS1061.
    - Why it hides: a code example only compile-checks if there's a test that runs it. The Recipes.md "validate after parsing" snippet was the one recipe with no test in `RecipesExamples.cs`, so it drifted while its tested siblings stayed correct. This is the same gap backlog item `ozpb` ("make sure all doc examples have tests that map back") is about: an untested example is an unverified claim.
    - Worse than a stale code snippet: prose that asserts a *reason* the old API exists can become a false factual claim. The SemVer README said positions "are not exposed on `Symbol` directly", which was true before the `ParseContext` change and false after. A future hunter reading the `ztax` pattern doc's "position APIs belong on ParseResult, not on Symbol" could "fix" the perfectly-correct `Symbol.SourceRange` by moving it, reintroducing the bug.
    - Where to look: grep the whole tree (not just `src/`) for any public type / method / property name that a recent refactor renamed or removed, and check every hit outside compiled code. `docs/*.md` code fences and prose, `E2ESamples/**/README.md`, sample and test `//` comments, backlog items, and other `PotentialBugSources` entries are all uncompiled and all drift. For each public API a refactor touches, the grep for its old name should come back empty everywhere except historical BugSearchLog entries (which record what was true on their date and shouldn't be rewritten).
    - Second instance (2026-06-03): primer2.md "Walking the tree with LINQ" ended with `result.Tree!.FlattenInto().OfType<Symbol>()`. `Symbol.FlattenInto` takes a `List<Symbol>` and returns `void` (no parameterless overload), so the line gives CS7036 + CS0023. The list-returning method is `Symbol.Flatten()`. Same root cause: it was the only block in primer2's tree-walking section with no `Primer2Examples.cs` test, so it drifted while the FindSetting / FindAll snippets beside it stayed correct. A method that mutates an out-param list (`FooInto(list)`) and a sibling that returns a fresh list (`Foo()`) are an especially easy pair to confuse in prose.
    - Third instance (2026-06-03): InductorParserReference.md's Symbol-tree section had THREE nonexistent-API references clustered together, none tested. (a) The API-surface code block declared `IReadOnlyList<Symbol> FlattenInto()` as a "convenience overload", but that overload is named `Flatten()` (the only real `FlattenInto` returns void and takes a `List<Symbol>`). (b) The LINQ example then used `symbol.FlattenInto().OfType<Symbol>()` (the same CS7036+CS0023 line as the second-instance primer2 find, in a doc the primer2 pass didn't touch). (c) The walk example used `symbol.Walk().Where(s => s.Id == BuiltinSymbols.Integer)`, but `BuiltinSymbols` exists nowhere in the tree. Two lessons. First, when you fix a renamed/removed-API reference in one doc, grep the *whole* `docs/` tree for the same broken spelling in the same pass, because it tends to appear in more than one doc, and an incorrect declaration in an API-surface listing (a) is what seeds the wrong call in the example (b). Second, a `Type.Member` reference (`BuiltinSymbols.Integer`) reads as a real static API and rots invisibly, where a lowercase placeholder rule variable (`someRule`, `settingName`) reads as illustrative, so prefer the placeholder form in example snippets. Fixed to `Flatten()` / `symbol.Flatten()` / `s.Id == integerRule.Id` with a new `Linq_on_the_symbol_tree_entry_points` regression test covering all four entry points.
    - Fix shape: point the doc / comment at the current API, and if the example is user-facing (a Recipes.md snippet, a primer), add a regression test that runs it so the next rename surfaces as a failing build instead of a silently-wrong copy-paste. Leave historical BugSearchLog entries alone.
