- An earlier check shadows a later one when the two checks' accept sets overlap
    - Several rules decide what to do with the current token by running an ordered series of checks and acting on the first that matches: ScanUntil checks "is this an escape start?" and "is this a stopper?"; Or tries its alternatives left to right; ScanUntil's escape path checks "stopper, then escape start." When two of those checks can both accept the same input, the order is load-bearing — whichever runs first wins, and the other becomes unreachable for that input.
    - The trap is writing the ordered checks as if the inputs were disjoint when they aren't. `ScanUntilRule.TryParseRule` ran the stopper check before the escape-start check. That is fine as long as the escape-start rune is never in the stopper set. But the natural way to write a string-body grammar puts them in the same place: a JSON body author thinks "the body stops at `"` and is special at `\`" and writes both into the `stopAt` set, and a shell-interpolation author wants `${...}` consumed as an escape while a bare `$` stops. In both cases the escape-start and a stopper share a prefix, the stopper check runs first, and the escape is dead code. The rule still compiles and still parses — it just silently terminates the body at the escape character. See backlog `0001` for the concrete case.
    - User-visible consequence: no exception, no diagnostic, just a parser that quietly does the wrong thing. The body leaf comes back shorter than expected (truncated at the first escape character), and the failure usually surfaces one rule later, when the outer grammar's closing delimiter doesn't match because the cursor is parked on the escape character instead.
    - The fix is almost always "check the more specific / higher-priority action first, the broad terminator last." An escape is the more specific, keep-scanning action; a stopper is the generic terminate. Checking the escape first costs nothing when the inputs are disjoint (the escape-start fails to match and the scan falls through to the stopper exactly as before), and it makes the overlap case work. Reordering this way is strictly more expressive: no grammar that kept the two checks disjoint changes behavior.
    - Sweep checklist for this shape: find every rule that runs check A then check B in a loop and acts on the first hit (`ScanUntilRule` escape-vs-stopper, `ScanUntilRule` escape-start-rule-vs-single-rune, the order of `Or` alternatives, `EndOfLine`'s `Literal("\r\n")`-before-`OneOf(LineTerminators)`). For each pair, ask: can the same token satisfy both? If yes, is the first-checked one the one the caller would want to win? If a reasonable, documented grammar would put overlapping inputs into both checks, the order is a latent bug. Pin the intended order with a test whose input lands in the overlap, not just inputs that hit one check cleanly.
