- Periodic / interval-gated polls never observe state that was already set before the first interval fires
    - The pattern: a hot-path counter is incremented on every iteration and a deeper "check" runs only when the counter crosses an interval boundary (`(counter & MASK) == 0` after `counter++`, every N iterations, every Nth tick). The interval is picked to make the deeper check cheap on average. The shape works fine for state that develops during the run (the elapsed time grows, the user clicks Cancel at the 7-second mark, the counter approaches its limit). It quietly fails for state that was *already true* at parse start: if the run ends before the first interval fires, the deeper check never runs at all and the pre-set state is silently ignored.
    - Why it recurs: when you look at the check site by itself, the gate looks correct ("every 1024 invocations, poll the cancellation flag"). The bug only surfaces when the run length is shorter than the interval *and* the state being polled was set externally before the run started. The two existing tests for the polled state ("pre-canceled signal aborts" / "pre-elapsed timeout aborts") naturally choose long inputs to exercise the deeper check fires at all, which masks the gap.
    - Concrete example in this repo: `Lexer.CheckPeriodicBudgets` polls `_cancellation.IsCanceled` (and `_stopwatch.Elapsed >= _timeout`) every 1024 rule invocations (`BudgetCheckInterval`). EnterRule does `_ruleInvocations++` and then `if ((_ruleInvocations & BudgetCheckMask) == 0) CheckPeriodicBudgets()`. The first call has `_ruleInvocations` go from 0 to 1, the mask check is 1 & 1023 = 1, and CheckPeriodicBudgets is not called. The first check fires when `_ruleInvocations` reaches 1024. A parse that uses fewer than 1024 rule invocations (a small grammar against a small input) never reaches the check and an externally pre-set ParseCancellation is silently dropped. See `docs/BugSearchLog/0-2026-05-19-pre-canceled-signal-ignored-on-tiny-parses.md`.
    - Two flavors of "pre-set state" the pattern can drop:
        - External flag set before the run starts (ParseCancellation pre-canceled, an HTTP request cancellation token already tripped). Highest-impact because the user explicitly asked to stop and was ignored.
        - Time-based state that's already past the deadline at run start (a Timeout small enough that the wall-clock check at the very first tick would already trip). Lower-impact because real-world deadlines are usually well above the run's own time-to-first-check, but the same shape applies.
    - Where else this shape can hide: any interval-gated poll on parser-internal state that was set up before parsing started, including a flag injected via ParseOptions, a static / process-wide kill switch, or an externally-supplied callback the parser is supposed to consult periodically. Counter-style budgets that grow with iterations (RuleCountLimit, MaxDepth on a deepening stack) don't have this gap because their state can't legitimately be "already exceeded" at iteration 0.
    - How to fix it generically: do an explicit one-time check at the start of the run, *before* the interval-gated loop begins. Either at the public entry point (cheap null-check, returns the same abort shape the loop would have produced) or inside the configure-then-check sequence that sets up the periodic check itself. The fix in this codebase is at the public `Rule.Parse(string, ParseOptions)` dispatcher: pre-flight the cancellation flag, short-circuit to `ParseResult.Aborted(ParseOutcome.Canceled, ...)`, and only then dispatch to the recursive or state-machine engine. Both engines inherit the fix because they both route through that one dispatcher. The direct experimental entry points (`StateMachineParser.Parse` and friends) bypass that dispatcher and still need their own pre-flight check if they're meant to be a supported public surface.
    - How to audit: for each interval-gated poll in the code (`(counter & MASK) == 0`, `if (counter % N == 0)`, every-Nth tickers, watchdog-style timers that fire on a schedule), ask: "is any of the state this poll inspects allowed to be pre-set by a caller before the loop starts? if so, is there an initial check that runs *before* the first iteration completes?" If the answer to the first is yes and the second is no, the bug is reachable as soon as a caller short-circuits the loop before the first interval boundary.
