- A rule's WithError is silently suppressed when its RecordFailure is shallower than orphan deepest records left behind by its inner subtree
    - The "deepest failure wins" policy in `Lexer.RecordFailure` updates the deepest position only when strictly deeper, and claims the message slot at an existing deepest only when both the new message is non-null and the existing slot is empty. That policy works fine for rules that record at their own actual failure position. It breaks for rules whose failure position is the START of a lookahead (or any zero-width point) when their inner subtree advanced the lexer and recorded one or more failures past that start. The lexer's `_position` rolls back via the inner's transaction, but `_deepestFailure` is a high-water mark and doesn't rewind. The outer rule then calls RecordFailure at its own (shallower) position, the deepest-wins rule ignores it, and the user-supplied `WithError` evaporates. See backlog `ympk` for the worked Peek and Not examples.
    - The two shapes that bite today (both fixed):
        1. `PeekRule` failing because inner failed: inner is allowed to read multiple tokens before it gives up. `Literal("ab")` on `"ax"` reads 'a' (advance to 1), reads 'x' at 1, mismatches against 'b', RecordFailure(1, null), rolls back. Peek's RecordFailure at offset 0 is shallower, so Peek's `WithError` never claims the message slot and the reported position points at the 'x' past where the lookahead was anchored.
        2. `NotRule` failing because inner succeeded: inner's run could explore non-taken `Or` alternatives that consumed input before failing, leaving orphan deepest records past Not's start position. The user sees the orphan position with the generic template, not Not's `WithError` at Not's anchor.
    - The fix shape: extend `Lexer.RecordFailure` with a `bool force = false` parameter that, when true, bypasses the deepest-wins comparison and unconditionally replaces both `_deepestFailure` and `_deepestFailureMessage`. Failing lookaheads pass `force: ErrorMessage != null` so a user-supplied `WithError` lands at the lookahead anchor, regardless of how far inner ran or what it recorded. The `ErrorMessage != null` gate matters: forcing a null message would actively overwrite any inner WithError that did manage to claim the slot (e.g. `Peek(Token('a').WithError("foo"))` with no own WithError on the Peek — inner's "foo" should still surface). Gating force on a non-null message preserves that.
    - Considered alternative: snapshot `DeepestFailure` / `DeepestFailureMessage` before inner runs and roll them back via a new internal Lexer method. That preserves an outside-the-lookahead deeper record (a sibling Or alternative that reached past the lookahead's anchor before failing) while the force-flag approach lets a Peek/Not with WithError overwrite that earlier record. The force-flag wins on simplicity (one parameter on an existing API vs. a new method plus snapshot bookkeeping at every call site), and the trade-off matches user intent: a grammar author who wrote `.WithError` on a Peek/Not is explicitly asking for their message to surface, so letting it dominate even an outside-the-lookahead deeper record is the desired behavior. Recorded so a future reader knows the snapshot/rollback shape was considered and consciously declined.
    - Reviewer mental model: any rule whose intended failure position is shallower than the lexer might reach during its inner subtree's run has to think about whether the deepest marker moved. If yes, and the rule has a user-supplied WithError, it should pass `force: true` so the equal-depth message-claim rule isn't needed (and isn't gated on shallower-than-deepest). The pattern applies to any rule that opens a transaction, runs an inner rule, and rolls back regardless of inner's outcome — Peek (success path also rolls back, but only the failure path needs the fix because success doesn't RecordFailure), Not, and any future zero-width composite that wraps an inner.
    - Adjacent shapes worth keeping an eye on for the same pattern:
        - A custom user-defined `Rule` subclass that wraps an inner via `using var transaction = lexer.BeginTransaction();` and `Inner.TryParse(...)` and is intended to be a lookahead / negative-lookahead variant. The `Rule` base contract documents the transaction shape but doesn't currently call out the deepest-marker-survives-rollback gotcha.
        - Any future engine path (state machine, alternative evaluator) that emits the equivalent of "RecordFailure at lookahead start" needs the same `force: true` logic. The SM currently bridges Peek and Not to the recursive engine for both, so the recursive fix is the only site needed today; if the SM ever lowers them natively, this is something the lowerer has to replicate.
    - Distinct from the `HasErrorMessageInSubtree` shortcut-bypass pattern (`0000a-shortcut-bypass-suppresses-descendant-witherror.md`). That one is about RUNTIME bypass of a rule entirely so its RecordFailure never fires. This one is about a rule whose RecordFailure DID fire but at a shallower position than the deepest-wins rule values. Both end with the user's `WithError` invisible, but the fixes are different: HasErrorMessageInSubtree changes the gate, the force flag changes how the position-comparison is done at record time.
