- A "does this need special handling?" predicate uses one granularity (graphemes), but the consuming context matches at a different granularity (runes), so cases that look uniform at the predicate's granularity but split at the consumer's granularity fall through silently
    - Shape: a helper computes some derived form (a normalization, a decomposition, a translation) and asks "is the result a single piece or multiple pieces?" to decide whether to take a special path. The predicate's "piece" definition is chosen for some natural-looking unit (e.g. grapheme clusters, the unit a TokenSet member is). The consuming caller then matches at a finer unit (e.g. runes, the unit a sub-lexer reads). Conversions that produce multiple pieces at the consumer's unit but only one piece at the predicate's unit (e.g. "SPACE + Extend" combining mark joins into ONE grapheme but stays TWO runes per UAX #29 GB9) silently skip the special path. The resulting entry stays in the set as a multi-piece-at-consumer-unit member that the consumer can never reach.
    - Concrete `InductorParser` instance: `Rules.Identifier(extraStartRunes: TokenSet.Single(0x309B)).Compile(FormKC).Parse("゛foo")` silently failed at offset 0 (before 2026-06-04 fix). U+309B KATAKANA-HIRAGANA VOICED SOUND MARK has NFKx = `" U+3099"` (SPACE + combining mark). UAX #29 GB9 joins them into ONE grapheme cluster (SPACE base + Extend), so `GraphemeHelpers.Count(normalized) == 1`. `TryGetMultiGraphemeConversion` returned false. `WithCompatibilityHeadRuneEquivalents` left U+309B in the start set as a single-rune entry. `OneOfRule.NormalizeAndValidate.NormalizedFor` then projected U+309B to the multi-rune grapheme `" U+3099"` in the OneOf's graphemes list. The OneOf lives inside `WithinToken`'s one-rune-per-token sub-lexer (the consumer), which reads runes one at a time and only consults the set's single-rune intervals. The multi-rune grapheme entry was unreachable. The user's `extraStartRunes` opt-in silently did nothing. Asymmetric with the multi-grapheme case (e.g. U+0E33 SARA AM, NFKx = NIKHAHIT + SARA AA splits into TWO clusters, which the predicate detects and head-expands).
    - Why it bites: the predicate's grapheme unit is the natural choice for the API's documented semantics (`TokenSet` members are graphemes). The consumer's rune unit is correct for its own context but not visible at the predicate site. The mismatch is invisible at code-review time because the predicate name and the consumer name don't reference the same unit. The fix has to pass the consumer's granularity into the predicate (a `splitByRunes` flag here) or split the predicate into two flavors.
    - How to spot it: when a helper takes a `TokenSet` and the result feeds into a consumer that matches at a finer unit than `TokenSet` members (a `WithinToken` sub-lexer reading runes is the canonical case), check what "multi" / "more than one piece" means in the helper vs. in the consumer. Any predicate that returns `false` for a multi-rune-but-single-grapheme input is suspect if the consumer is rune-scoped. The pattern shows up wherever a public API's natural unit (cluster, token, line, statement) is coarser than an internal context's matching unit.
