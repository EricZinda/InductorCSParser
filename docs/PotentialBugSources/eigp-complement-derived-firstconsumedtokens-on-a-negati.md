- Complement-derived `FirstConsumedTokens` on a negation rule that reads whole tokens
    - A rule whose semantics are "match if NOT in this set" (NoneOf, the body of ScanUntil) is tempting to give a `FirstConsumedTokens` that's just the complement of the rule's set. The shape "I match runes outside `_set`, so my first-consumed runes are `~_set`" reads natural and parallels OneOf / ScanWhile's positive derivation.
    - The trap: the rule reads a whole TOKEN (one user-visible character / grapheme cluster), not a single rune. A multi-rune cluster like `é`, a ZWJ family emoji, or a regional-indicator pair is one token whose first rune CAN be in the rune-only part of `_set` while the cluster as a whole IS NOT in `_set._multiRuneGraphemes`. The negation rule accepts that whole cluster because the membership test runs against the cluster, not against the cluster's first rune. So the cluster's first rune IS a possible first-consumed rune, even though `~_set.RunesOnlyPart` says otherwise.
    - User-visible consequence: when the rule sits inside a `Or` or `BetweenInclusive`, the shortcut peek-and-skip path consults `FirstConsumedTokens` and wrongly excludes the negation rule from being tried. The parse fails on input the rule would have matched, with a generic "unexpected '<character>'" error rather than consuming the cluster. Most likely under `Compile(null)` (no normalization preserves all multi-rune clusters) and on NFC-stable clusters that survive default normalization (skin-tone modifiers, ZWJ sequences, regional-indicator flags, Indic clusters with no precomposed equivalent).
    - `NoneOfRule.ComputeRuleStart` had this shape (see backlog n8no). `ScanUntilRule` already ducks the trap by publishing `Universe` with `Advance.Sometimes`, so the shortcut never fires for it. The lesson: complement derivation looks sound on rune-only sets and quietly stops being sound the moment multi-rune clusters enter the picture.
    - When reviewing a `ComputeRuleStart` on a negation rule, ask: does this rule read whole tokens, and could a multi-rune cluster pass it whose first rune is in the rule's "excluded" set? If yes, return `TokenSet.Universe`. The lookahead shortcut can't be made sound for that rule without enumerating every possible cluster, which the parser doesn't do.
