- An eager per-input cache is built in a shared init path, but one mode that runs that path never queries the cache, so it pays the build for nothing (per-token when the mode is a per-token sub-lexer)

  - Shape: a class lazily-conceived cache is actually allocated eagerly in a constructor or shared `Init` / `Bind` method so "it's ready when needed." That's fine when every caller needs it. It turns into a per-token cost when one of the callers is a short-lived sub-object created once per token / per cluster / per node that operates in a mode which never touches the cache. The build (object + backing array + any registry/`ConditionalWeakTable` insert) then runs once per token and is thrown away unread. ASCII-heavy inputs make it worse, not better: more, smaller sub-objects, each paying the full fixed build cost.
  - Concrete instance (2026-06-04): `Lexer.BindInput` eagerly built the input's `GraphemeClusterIndex` (`GraphemeClusterIndex.For(input)`, which allocates the index, a `bool[input.Length+1]`, and a `ConditionalWeakTable` entry). `WithinTokenRule` builds a fresh `oneRunePerToken` sub-lexer for every outer grapheme cluster, one per identifier character on the common `Rules.Identifier` path, each over a freshly-`Substring`'d token. But rune mode sizes tokens with `RuneHelpers` (`NextTokenLength` / `IsTokenBoundary` both branch away from `_graphemeIndex` when `_oneRunePerToken`), so the cluster index was never queried. Measured ~171 bytes/char of wasted allocation (~28% of identifier-parse allocation). Fix: resolve the field lazily through a property (`_graphemeIndex ??= GraphemeClusterIndex.For(_input)`) so the rune-mode sub-lexer never builds it and the grapheme-mode lexer builds it on first real query instead of at construction.
  - Why it hides: it's not a correctness bug, so no test fails. The cache is genuinely correct and genuinely used by the main (grapheme-mode) lexer, so unit tests of the cache and of grapheme tokenization all pass. The waste only shows up in an allocation profile of a parse that drives the per-token sub-lexer a lot, which is exactly the identifier-heavy real-grammar case the unit suite's short inputs don't stress. The eager build also reads as a deliberate "warm it up front" choice rather than an oversight.
  - Where else to look: any object created once-per-token / once-per-node that runs through a shared constructor or `Bind`/`Reset` path which unconditionally builds per-input state. Sub-lexers, sub-parsers, probe/lookahead scratch objects, pooled-then-rebound instances. The tell is a mode flag (`_oneRunePerToken` here, but any "lite mode" / "rune mode" / "probe mode" boolean) that later gates *reads* of a field the init path *wrote* unconditionally. If the read is gated by the flag, the write usually should be too, or the field should be lazy so the unused mode never pays. Check `BindInput`/`Reset` paths used by both a full and a reduced mode.
  - Test that catches it: assert the unused mode doesn't build the cache. Here that's a non-mutating peek into the registry (`GraphemeClusterIndex.HasCachedIndexFor`, a `ConditionalWeakTable.TryGetValue` that doesn't insert): walk a one-rune-per-token lexer to EOF over a fresh string and assert no index was cached for it, plus the positive control that a grapheme-mode lexer does cache one. Behavior is unchanged, so the permanent regression test is this build-skip assertion, not a parse-output check. The size of the win is best shown with a one-off `GC.GetAllocatedBytesForCurrentThread` measurement over a long identifier. Record the ratio rather than asserting a byte threshold (allocation sizes drift across runtimes).
