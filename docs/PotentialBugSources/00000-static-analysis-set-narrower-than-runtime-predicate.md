- `FirstConsumedTokens` that's narrower than the rule's runtime predicate
    - The lookahead shortcut (`Rule.CannotMatchLookahead`, consulted by `OrRule`, `BetweenInclusiveRule`, and the SM lowerer's alt-skip path) trusts `FirstConsumedTokens` to be a SUPERSET of every token the rule's runtime path would actually consume. A set that's narrower than the runtime predicate causes the shortcut to skip a rule that would have matched, and the failure is silent: the rule's body never runs, no failure is recorded, and the user just sees a parse failure at some unrelated downstream offset (or, when the rule was the only branch under `OneOrMore`, a "count=0" failure).
    - The risk lives wherever the rule's runtime compare admits more shapes than the static set spells out. Two patterns to watch for:
        - **Runtime-folded membership.** A rule that compares an input token against `_expected` via something more relaxed than `SequenceEqual` (`LiteralIgnoreAsciiCaseRule.AsciiCaseEquals` is the canonical example) admits inputs the strict cluster equality used by `TokenSet.ContainsToken` doesn't. The static set has to enumerate every variant the runtime predicate would fold to: both ASCII cases of the first letter for `LiteralIgnoreAsciiCase`, not just the spelling the grammar author typed.
        - **Multi-rune-cluster first graphemes after Compile-time normalization.** Compile's `CollectNormalizationOffenders` pass rewrites `_expected` in place before `ComputeRuleStartAll` runs. A literal whose first grapheme was a single precomposed rune (like 'é') in the source can become a multi-rune cluster (like "é" = e + combining acute) after FormD / FormKD decomposes it. Any `ComputeRuleStart` that only walks the original spelling, or that only handles `firstElement.Length == 1`, misses every input that lexes as the decomposed cluster.
    - Sound default when uncertain: widen, don't narrow. `RuleStartRequirements` notes that "a superset of actual first-consumed tokens is safe under MustBeIn (just slower). A subset would cause enclosing rules to wrongly skip a rule that could succeed." Specifically, adding the case-variant runes as single-rune entries to a `TokenSet` that also carries a multi-rune cluster never wrongly skips: `CannotMatchLookahead` returns false as soon as either the first-rune check or the cluster check matches.
    - When reviewing a new `ComputeRuleStart` for a literal-bearing rule whose runtime compare isn't bit-exact, ask: (1) what variant inputs does the runtime predicate accept on the FIRST token? (2) does the published `FirstConsumedTokens` admit a peek whose first rune is any of those variants? If the second answer is no, the shortcut will silently skip the rule on those variants. Mirror the runtime predicate's relaxation in the static set.
