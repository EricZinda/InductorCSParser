- A re-id (or re-projection) pass handles one branch of a normalization outcome but not the boundary-crossing branch
    - A Compile-time pass that mutates a rule's stored data under the chosen normalization form often has to update a derived value too (an Id, a cached first-set, a rendering). The trap: the conversion has several possible shapes and the update code only covers the shape the author was thinking about. Concrete InductorParser case: `GraphemeRule.ValidateNormalization` re-assigned the rule's character-range rune Id (via `SetLeafRuneId`) only when the converted text was *still a single rune* (`TrySingleRune` true, which covers the canonical-singleton case U+2126 OHM -> U+03A9). It silently skipped the case where a single rune *decomposes into a multi-rune cluster* (`Token('é')` U+00E9 -> "e + U+0301" under FormD), leaving the leaf with a character-range id (0xE9) that the `SymbolRanges` invariant says means "exactly one rune," even though the leaf is now two runes. A Token built multi-rune from the start gets a custom-range id, so the two paths produced different id shapes for identical matched content.
    - The conversion under a normalization form has at least four outcomes, and a correct re-id pass must decide each one. (1) unchanged. (2) single-rune to single-rune (re-point to the new rune). (3) single-rune to multi-rune-single-grapheme (drop the rune id, take a custom-range id). (4) single-rune to multi-grapheme (reject as an offender). The OHM test locked in (2), and (4) had an offender path, but (3) fell through the gap because it shares the "not a single rune" predicate with (4) while needing different handling. The fix added a `ClearLeafRuneId` counterpart to `SetLeafRuneId` for (3) and a re-run of `AssignAnonymousIds` after the normalization pass. The same enumeration applies to `ScanUntilRule`'s single-rune escape-start (`_escapeStartRune` vs `_escapeStartGrapheme`), which DOES handle all four, so use it as the reference shape when auditing any other single-rune-valued field a normalization pass can rewrite.
    - When auditing: for every Compile-time pass that rewrites rule data under a form, list the distinct *shapes* the rewrite can produce (not just "changed / unchanged") and confirm the derived-value update has a branch for each, especially the one that crosses a representational boundary (single rune to multi rune, BMP to supplementary, one grapheme to many). Decomposing forms (FormD / FormKD) are where the boundary-crossing shapes actually appear, so a test matrix that only exercises FormC will miss them, exactly how the prior xpid fix verified leaf-id consistency under FormC and left the FormD decomposition gap open.
    - Ordering footnote: when the fix is "drop the stale derived value and let an earlier assignment pass redo it," check the pass order. Here the id-assignment passes run *before* the normalization pass, so simply clearing the id wasn't enough. Compile had to re-run `AssignAnonymousIds` after normalization for the cleared rule to pick up a fresh id. Same shape as `a000` (cached static analysis vs. mutated Compile-time rule data): any consumer or assigner of the pre-mutation state may need to run again after the mutation.
