- Polyfill #if gate threshold doesn't match when the BCL type actually shipped
    - The pattern: every file in `src/InductorParser/Compatibility/` polyfills a BCL type that netstandard2.1 lacks, and wraps it in an `#if !<FRAMEWORK>_OR_GREATER` gate. The gate has exactly one job, which is to compile the polyfill in on frameworks where the BCL type is absent and leave it out on frameworks where the BCL provides it. For that to be correct, the framework symbol in the gate has to mark the *exact* version the BCL type was introduced. Get the threshold wrong and the gate silently does the wrong thing on the frameworks between the real introduction version and the version named in the gate.
    - Why it recurs: the gates look interchangeable (`#if !NET5_0_OR_GREATER`, `#if !NET6_0_OR_GREATER`) and get copy-pasted from one polyfill file to the next, but the types were introduced in different releases. `System.Text.Rune` shipped in .NET Core 3.0. `IsExternalInit` and `MemberNotNullAttribute` shipped in .NET 5. `InterpolatedStringHandlerAttribute` and `InterpolatedStringHandlerArgumentAttribute` shipped in .NET 6. A gate copy-pasted without re-checking the introduction version is a bug waiting for a target-framework change.
    - Two failure directions. Gate too narrow (names a later version than the real one, so the polyfill stays compiled in on frameworks that already have the BCL type): the polyfill type collides with the imported BCL type, giving `CS0436` or `CS0101` duplicate-definition diagnostics. Under `TreatWarningsAsErrors` even the "using the local one" `CS0436` warning fails the build. Gate too wide (names an earlier version): the polyfill is excluded on a framework that lacks the BCL type, and every use site fails with `CS0246` or `CS0103` "type not found".
    - It hides until the target set changes. The project today targets netstandard2.1 and net8.0. A wrong gate can still produce the right include/exclude decision for both of those (netstandard2.1 has none of these BCL types and gets every polyfill, while net8.0 has all of them and gets none), so the bug is invisible in CI. It surfaces the moment someone adds a target in the gap, for example a netcoreapp3.0 or netcoreapp3.1 target exposing a `Rune` gate that says `!NET5_0_OR_GREATER`.
    - Found and fixed here: `Compatibility/Rune.cs` was gated `#if !NET5_0_OR_GREATER` but `System.Text.Rune` shipped in .NET Core 3.0. Corrected to `#if !NETCOREAPP3_0_OR_GREATER`, which is defined for netcoreapp3.0, netcoreapp3.1, and all of net5.0+, exactly the frameworks that ship the BCL `Rune`. See `docs/BugSearchLog/2026-05-18-compatibility-folder-rune-polyfill-if-gate.md`.
    - How to audit: for each polyfill file, look up the precise framework version that first shipped the type, then confirm the gate names a symbol true for exactly that version onward. `NETCOREAPP3_0_OR_GREATER` is the right symbol for anything introduced in .NET Core 3.0, because the `NET5_0_OR_GREATER` family of symbols are each also `NETCOREAPP3_0_OR_GREATER`-true, but not the reverse. Don't assume two polyfills can share a gate just because they sit in the same folder.
