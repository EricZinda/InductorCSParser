- Fast-path membership tests that decode the rune first drop lone surrogates the general path matches
    - Shape: a "fast path" documented as equivalent to a general rule tests set membership by first decoding a rune (`Lexer.TryPeekRune`) and then doing `set.Contains(runeValue)`. `TryPeekRune` returns `false` for a lone surrogate (an unpaired high/low half — not a valid Unicode scalar). The fast path reads that `false` as "not a member" and stops, when it actually means "this token didn't decode as a rune."
    - Why it's wrong: the general path — `TokenSet.ContainsToken`, used by `OneOfRule` / `NoneOfRule` — has a deliberate lone-surrogate branch that matches a one-char surrogate token against the rune intervals by its UTF-16 code unit. The `ContainsToken` comment spells out the intent: "a user-typed Range that covers the surrogate range under an unnormalized Compile should still match it." `TokenSet.Range` validates only its endpoints, so `Range(0, 0x10FFFF)` (a plausible "any rune" set) covers the surrogate block as interior slots. Under `Compile(null)` the lexer surfaces a lone surrogate as a one-char token. So the general path matches it and the rune-decode fast path doesn't — the two diverge.
    - Where it was found: `Lexer.AdvanceWhileRuneIn` (the rune-only path `ScanWhileRule` uses) — fixed 2026-05-15. The sibling `AdvanceWhileTokenIn` was already correct because it falls back to `ContainsToken`.
    - Recurrence: `Lexer.AdvanceUntilRuneIn`'s slow per-cluster loop (the scanner-skip path `BetweenInclusiveRule` uses for `ZeroOrMore(Or(match, AnyToken().Delete()))`) had the identical `TryPeekRune(...) && Contains(...)` short-circuit. Fixed 2026-05-18. The 2026-05-15 fix swept the `ScanWhile` family but missed the `BetweenInclusive` scanner-skip family. Lesson: when fixing one fast-path membership site, grep every `AdvanceUntil*` / `AdvanceWhile*` sibling for the same `TryPeekRune` shape in the same pass.
    - Second lesson: don't copy the fix blindly across siblings. A consume scanner (`AdvanceWhileRuneIn`, the `ScanWhile` engine) gates its lone-surrogate branch on `tokenLength == 1`, because a run rule matches only single-rune tokens and rejects multi-rune clusters outright. A lookahead scanner (`AdvanceUntilRuneIn`, the scanner-skip) can't carry that gate: it stops on the leading rune of any cluster (its `TryPeekRune` branch has no length check), so its lone-surrogate branch tests the leading char with no length gate too. The first cut of the `AdvanceUntilRuneIn` fix copied the `tokenLength == 1` gate and thereby skipped multi-char clusters (lone surrogate plus glued combining mark, one cluster under UAX #29 GB9) that a `WithinToken` alternative would match. Match the gate to the scanner's role: consume or lookahead.
    - Reviewer mental model: any place that does `TryPeekRune(...)` and then `if (!ok) break;` / `if (!ok) return false;` to decide membership is suspect. A `false` from `TryPeekRune` is not "this token can't be in the set" — it's "this token isn't a single decodable rune." A one-char lone-surrogate token can still be a set member when the set's intervals were built with a `Range` that straddles `0xD800..0xDFFF`. The correct fast-path fallback for a `!TryPeekRune` token is `set.Contains((int)theSurrogateChar)` (one char only), which mirrors `ContainsToken`'s lone-surrogate branch. This only matters under `Compile(null)`, the documented opt-out for WTF-8 / unpaired-surrogate input — normalized compiles reject malformed UTF-16 before the lexer runs.
