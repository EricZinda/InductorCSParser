- Replacing a runtime shape check with a static rule-level property means every rule whose shape is conditional must report that property correctly
    - When a decision that used to read a runtime value (e.g. "is the Symbol the inner returned a leaf?", `innerSymbol.IsLeaf`) is refactored to read a declared rule-level property instead (e.g. `Rule.EmitsLeaf`), the property becomes the single source of truth for that rule's output shape. Every rule that can produce that shape now has to report it, including rules whose shape is conditional rather than fixed. A rule that hardcodes the base default for the property (because "this rule's own ctor doesn't emit that shape directly") diverges from what it actually produces at runtime, and any consumer that reads the property gets the wrong answer.
    - Concrete instance: `Rule.EmitsLeaf` (added 2026-05-28, bbb7d16) replaced AliasRule's `innerSymbol.IsLeaf` runtime check. Every fixed-shape rule got a correct constant (`emitsLeaf: true` for leaves like OneOf/Literal/ScanWhile, `false` for composites like And/Or/BetweenInclusive and zero-width predicates like Not/Peek/Eof). LateBoundRule correctly overrode EmitsLeaf to forward to its bound target. But AliasRule itself emits a leaf *conditionally* (only when it substitutes its identity onto a leaf inner) and it hardcoded `emitsLeaf: false`. So an alias that genuinely produces a leaf at runtime reported `EmitsLeaf=false`. The only consumer of the property is a *parent* AliasRule deciding whether to substitute, so aliasing an alias (`x.AliasedAs("a").AliasedAs("b")`) saw the inner alias claim "not a leaf," skipped substitution, and built an extra composite level that also leaked the inner alias's identity into the tree. The runtime check it replaced had handled this case, so it's a pure regression from the refactor.
    - The fix shape: a rule whose output shape is conditional must compute the property dynamically (an override), not seed a constant in the ctor. AliasRule's override mirrors its substitution gate (`_inner.EmitsLeaf && FlattenType == Preserve && _inner.FlattenType != Delete`), and TryParseRule now routes its gate through the same property so the "should I substitute?" decision and the "do I emit a leaf?" answer can't drift apart. LateBoundRule (forwards) and AliasRule (computes) are the two rules where the constant-in-ctor pattern is wrong. Any future rule whose emitted shape depends on its inner, its FlattenType, or runtime state needs an override too, and a new rule that hardcodes the base default for a shape-describing property is suspect whenever a sibling or parent rule reads that property.
    - Audit hook: when reviewing a new self-describing `Rule` property that another rule reads (EmitsLeaf today, the next "ask the rule its shape" property tomorrow), ask of every rule: is this value fixed for this rule, or does it depend on the inner / FlattenType / what the rule actually returns at parse time? If conditional, it needs an override, and there should be a test that exercises the rule both ways (here: aliasing a leaf directly vs aliasing an alias of a leaf). Closely related to `proxy-flag-checks-that-drift-from-the-property-they-meant-to-test`: that one is about reading the wrong property, this one is about a rule reporting the wrong value for the right property.
