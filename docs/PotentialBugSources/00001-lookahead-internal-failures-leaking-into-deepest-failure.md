- Lookahead-internal probe failures leaking into the lexer's deepest-failure slot
    - The lexer's transaction primitive rolls back the read cursor on the failure path but doesn't roll back `_deepestFailure` / `_deepestFailureMessage`. That's intentional and correct for Or alternatives: when alt1 reads three tokens and fails, alt1's high-water mark is the meaningful "how far did the parser get" hint and we want it to survive the rollback so alt2's success or the overall failure can reference it. The same primitive shape is wrong, however, for rules whose inner is a probe rather than a user-intended match. NotRule's inner is the canonical case: when inner fails (Not succeeds by design), inner's probe-position high-water mark is internal grammar machinery, not a place the user wanted the parser to be. Without a restore, that probe position outpoints any real later failure at a shallower position and silently drops the user's `.WithError("...")` on a real rule, making the parser report an error inside the lookahead with no custom message. See backlog `nlpd` for the worked NotRule case.
    - The fix is a `DeepestFailureSnapshot` struct + `SnapshotDeepestFailure()` / `RestoreDeepestFailure(snapshot)` helpers on `Lexer`. Probe-shaped rules snapshot before running the probe and restore on the path where the probe was supposed to fail. The transaction primitive itself stays unchanged because the Or-alternative case still wants the high-water mark to survive.
    - Reviewer mental model: any rule whose inner is documented as a "probe" or "lookahead" (the inner runs but its match outcome isn't part of the user's grammar match) needs to ask whether the inner's `RecordFailure` calls represent meaningful user-facing positions. If the inner fails on the path where the outer is supposed to succeed, the answer is no and the failure marks have to be undone. PEG semantics for negative lookahead specifically require this: `!X` succeeds when X fails, and X's failure is not a failure the user wants reported.
    - Sibling consumer case to watch: `PeekRule` has the symmetric shape. Peek's success path (inner matched) can leave alt-failures inside a successful inner Or in the deepest slot. Peek's failure path (inner failed) can have inner's probe position outpoint Peek's own startPosition + WithError, dropping a Peek-attached `.WithError("...")`. The same `Snapshot` / `Restore` primitive applies, but the failure-path policy decision (user's WithError on Peek vs. inner's probe position) is a separate tradeoff worth its own discussion.
    - State-machine engine has the same shape in `ExperimentalSrc/InductorParser/StateMachine/Lowerer.cs:LowerNot` and `LowerPeek`. The `FailRestore` opcode at the inner-failed-Not-succeeded exit pops the backtrack frame and restores lexer position / emit cursor / call-stack height, but doesn't carry a deepest-failure snapshot. Fixing requires extending `BacktrackFrame` or introducing a dedicated `RestoreDeepestFailureFrame` opcode for the not-succeeded path.
    - When adding a new rule type whose inner is a probe (a "soft" assertion, a "this should not match" gate, a try-this-and-recover composite), ask: does the inner's failure path become the outer's success path? If yes, snapshot the lexer's deepest-failure slot before running inner and restore it on that path. The transaction primitive does NOT carry this for you, by design.
