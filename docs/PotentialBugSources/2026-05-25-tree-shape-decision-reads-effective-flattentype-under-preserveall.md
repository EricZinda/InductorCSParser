- A tree-shape decision that reads the EFFECTIVE FlattenType breaks PreserveAllSymbols+Flatten symmetry
    - `PreserveAllSymbols` makes every rule's `effectiveFlattenType` Preserve at parse time (see `Rule.TryParse`). The b000 invariant says the captured tree, run through `Symbol.Flatten()`, must reproduce the default parse. A rule satisfies this as long as the node it emits under Preserve flattens back to what it would have emitted under its real FlattenType, which is automatic when it tags the emitted Symbol with its OWN FlattenType (a Flatten composite lifts away. A Flatten leaf bubbles up unchanged).
    - The trap is a rule that decides the *identity or shape* of the emitted node from `effectiveFlattenType` (or from whether a child returned `Symbol.Discarded` vs its own Symbol, which is the same thing one level down). PreserveAllSymbols flips that input, so the decision goes a different way than in the default parse, and post-hoc Flatten can't undo it. `AliasRule`'s leaf-rebadge was the instance: under `effectiveFlattenType == Preserve` it replaced the inner leaf with an alias-id leaf, so a transparent (Flatten) alias, or a Preserve alias over a Flatten inner leaf, rebadged under PreserveAllSymbols but not in the default parse. A Flatten *leaf* survives post-hoc Flatten (it is bubbled up, not lifted), so the alias's Id stuck where the default had the inner's. Fixed by reading the OWN FlattenType of the alias and its inner (`FlattenType == Preserve && _inner.FlattenType == Preserve`).
    - When reviewing any rule that builds a Symbol, ask: does any branch that affects the emitted node's Id, leaf-vs-composite shape, or whether a child's node is dropped/kept read `effectiveFlattenType` (or `lexer.PreserveAllSymbols`, or `innerSymbol == Discarded`) rather than the rule's / child's declared `FlattenType`? If so, parse it twice (default and PreserveAllSymbols+`Flatten()`) and compare the trees id-for-id, not just `ToString()`. `ToString()` (text) often agrees while the ids/shape diverge.
    - Distinct from `b000` (which is the general "the two flatten paths must agree" statement and its leaf-bubble case) and from `fapd` / the rebadge-lift-children entries: those are about a single path. This is specifically about a decision input (`effectiveFlattenType`) that only PreserveAllSymbols perturbs, so the bug is invisible to any test that parses one way only.
