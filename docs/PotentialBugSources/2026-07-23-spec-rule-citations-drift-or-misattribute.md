- Spec rule numbers, section anchors, and attributions in comments drift or misattribute
    - A comment that names a specific spec artifact (a UAX #29 rule number, a tr15 section anchor, "the spec's own example", a section number in the core standard) makes a claim no test verifies, and those claims go wrong in three recurring ways. The rule number can belong to a retired revision: "GB10" was the emoji-modifier rule until Unicode 11 reworked emoji properties, so citing GB10 for anything in a Unicode 15.0 codebase names a rule that no longer exists (the tag-sequence behavior it was credited with is plain GB9, since tag characters are GCB=Extend). The example can be attributed to the wrong document: the U+D4DB Hangul decomposition walkthrough is in The Unicode Standard's section 3.12, not UAX #15, even though UAX #15 is where a normalization implementer spends their time. And the anchor can point one section off: tr15's #Description_Norm (1.3) was cited for the "much text is already NFC" note that actually sits in 1.2 (#Norm_Forms).
    - The failure mode is quiet: the code is right, the tests pass, and the wrong citation sits there until a reader follows it, fails to find the claimed text, and burns time deciding whether the code or the comment is the broken half.
    - Review checklist: whenever a comment cites a numbered rule (GB*, WB*, SB*, LB*), check the number against the revision the codebase pins (rev 41 for this repo's UAX #29: GB1-GB5, GB6-GB8, GB9/GB9a/GB9b, GB11, GB12/GB13, GB999, and no GB10 or GB9c). Whenever it says a spec "uses this example" or "notes that", fetch the pinned revision and search for the example or the sentence, and check the anchor's section actually contains the claim. Where the claim is computable from the checked-in tables (a maximum chain depth, an expansion length, a count), turn it into a data test instead of prose, the way Decomposition_chains_are_at_most_three_levels_deep locks the chain-depth comment.
