    - Found and fixed (backlog `0000a`): `WithinTokenRule.ComputeRuleStart` forwarded the inner rule's `FirstConsumedTokens` / `Polarity` unchanged. The inner rule runs on a one-rune-per-token sub-lexer, so its set is rune-scoped, but the enclosing `Or` / `BetweenInclusive` shortcut peeks a whole grapheme cluster. For a `MustBeIn` inner this is sound (`CannotMatchLookahead`'s MustBeIn path does a first-rune check). For a `MustNotBeIn` inner whose fail-set holds a multi-rune grapheme it is not: `CannotMatchLookahead`'s MustNotBeIn path tests the whole peek cluster against the fail-set and skips the WithinToken when the cluster IS a member, even though the inner rule, walking that cluster rune by rune, matches every rune. `Or(WithinToken(OneOrMore(NoneOf(TokenSet.Graphemes("\r\n")))), ...)` failed to match `"\r\n"` though the WithinToken branch matched it standalone. Fix: project the fail-set to `RunesOnlyPart` (drop multi-rune entries) before publishing it under MustNotBeIn — a rune-only set only skips single-rune peeks, where the cluster's one rune is the rune the inner checks first; a subset of a MustNotBeIn fail-set is sound. Also swapped the method's `_innerRule.ComputeRuleStart()` re-invocation for `RuleStartRequirements.PassesThroughTo(_innerRule)` (reads the post-order-populated compiled fields, like `BetweenInclusiveRule` does) and dropped the stale comment claiming those fields aren't populated yet.
    - One regression test in `WithinTokenRuleTests.cs`: `Or_WithinToken_does_not_skip_when_inner_negative_rule_walks_a_multi_rune_cluster` (standalone-matches control + Or-still-matches assertion). Verified against both engines.
    - Pattern doc `0000-2026-05-15-rune-scoped-rule-fields-published-as-cluster-scoped.md` added: any rule that runs a sub-rule under a different tokenization unit (rune vs. grapheme cluster) and then republishes that sub-rule's compiled lookahead fields has to reconcile the units, and the MustNotBeIn whole-cluster membership test is where the gap bites.
    - AndRule / OrRule themselves: read closely for output-list rollback, transaction balance, and matchLength math — no bug found, both looked correct. The shortcut soundness gap was one layer down, in how WithinToken feeds the shortcut.
