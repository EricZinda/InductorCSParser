- 2026-06-26: localization sweep, English a non-English app surfaces to its end users and can't replace
    - Theme (not a random-start file pick): hunt every spot where an app whose grammar and UI are in another language ends up showing hardcoded English to its END USERS (the people typing the input being parsed), with no override. The grammar author reads English fine, so construction / Compile-time errors (the InvalidOperationException / ArgumentException family for `.As()` twice, name collisions, normalization-form conflicts, surrogate literals, etc.) are out of scope by design. The two exception types (`InductorParserBugException` vs `InvalidOperationException`) are both developer-facing and stay English.
    - Reviewed: `Rule.cs` (Parse / ParseRecursive / BuildErrorMessage / BuildBudgetMessage / FormatTemplate / PositionPlaceholders / NameOf / UserNameOf / DeriveRuleTraceName), `ParseOptions.cs` (the six message templates), `ParseResult.cs` (ErrorMessage, ToString, ToDebugString, PrintTree, DisplayNameOf), `ParseOutcome.cs`, `SyntaxTree/Symbol.cs` (DisplayName / Is), `SyntaxTree/SymbolExtensions.cs` (PrintTree label fallback), `Tracing/DisplayEscape.cs`, `TokenSet.cs` (ToString), `Lexing/NormalizedPositionMap.cs`, `Lexing/Lexer*.cs`, the per-rule `TraceFailure` strings, and `Core/UnexpectedUnicodeTests.cs`.
    - Good news first: the main parse-failure path is thoroughly localizable. Every GrammarMismatch and every budget abort routes through one of six overridable `ParseOptions` templates (`PositionalErrorTemplate`, `EndOfInputErrorTemplate`, `TimeoutAbortTemplate`, `RuleCountLimitAbortTemplate`, `DepthLimitAbortTemplate`, `CancellationAbortTemplate`). Placeholder substitution is language-neutral (numbers, plus `{character}` rendered through `DisplayEscape` as the user's own text or `U+XXXX`). Built-in rule factories (`Integer`, `Float`, `Identifier`, ...) don't bake in English `.WithError` text, so they produce mechanical failures that go through the template. `.WithError` messages are author-supplied, so those are already in the author's language.
    - Found (filed as backlog `lcgp`): four spots where English still leaks past the template system, ranked by how reachable they are.
        1. `Symbol.DisplayName` (Symbol.cs:197) / `Rule.NameOf(SymbolId)` (Rule.cs:894) / `ParseResult.DisplayNameOf` fall back to the class-derived trace label ("And", "Or", "OneOrMore", "BetweenInclusive[1..3]", "Eof", ...) for any rule the author didn't `.As(...)`-name. NameOf's own XML doc recommends it "for error-message rendering that wants to quote a rule's name", so a non-English app that follows that guidance and walks the tree generically surfaces English keywords. Override exists but is per-rule: you must `.As("localized")` every rule that could surface. No neutral or global default. This is the headline finding, the one that best matches "other user facing messages in english".
        2. Parsing end-user input that is ill-formed UTF-16 (lone surrogate, reversed pair) or contains U+FFFE throws a raw `System.ArgumentException` from `string.Normalize` at Rule.cs:1092 under the DEFAULT FormC. Verified message: "Invalid Unicode code point found at index N." Unlike every other parse failure (which returns a localizable `ParseResult`), this is an exception with a BCL English message and no template. By design (UnexpectedUnicodeTests pins the throw, e.g. line 157), and the app CAN catch it, but catching loses the structured error position and the message itself is unreplaceable. It's the one parse-time failure mode outside the localization story.
        3. `BuildBudgetMessage` `default:` returns hardcoded "Parse aborted." (Rule.cs:1193) with no template. Effectively unreachable today (all five ParseOutcome values are handled), purely defensive, but it's the single abort message with no override if the enum ever grows.
        4. `TokenSet.ToString()` emits the English word "more" in its truncation suffix (`,...+5 more`, TokenSet.cs:866). Primarily a debug / trace rendering, not on the default end-user error path, but it's public and an app could surface a character-set constraint string to users. No override.
    - Verified non-findings (so the next hunter doesn't re-chase them):
        - `NormalizedPositionMap.cs:130` (`chunk.Normalize(form)` in the per-grapheme FormKC/FormKD walker) doesn't throw on ill-formed input. It only runs after the whole input already passed `input.Normalize(form)` at Rule.cs:1092, so by then the string has no lone surrogates, and chunking on grapheme boundaries never splits a surrogate pair. An initial sweep flagged it as a second throw site, but it isn't reachable with ill-formed input.
        - Per-rule `TraceFailure` strings ("found", "wanted", "<EOF>", "wanted one of", "case-insensitive") in AnyTokenRule / LiteralRule / LiteralIgnoreAsciiCaseRule / OneOfRule / NoneOfRule / IdentifierRule are TraceSink debug output, off by default and documented as grammar-debugging aid, not end-user error text. Out of scope.
        - `ParseResult.ToDebugString()` ("Success:", "Success (no symbols)") and `ParseOutcome.ToString()` (enum names) are documented debug aids whose layout "may change between versions". The doc tells callers to read `Outcome` / `Tree` / `ErrorMessage` directly. Not localization targets.
    - Pattern: not a correctness bug, an inconsistency in an otherwise-complete localization design. The fix shape for each is in the `lcgp` backlog item.
    - Follow-up (same session): fixed finding 2. `Parse` now catches the `string.Normalize` ArgumentException and returns a `ParseResult` with the new `ParseOutcome.MalformedInput`, positioned at the offending character, message from the new `ParseOptions.MalformedInputTemplate`. So ill-formed input is now a localizable, structured-position failure like every other rejection instead of a thrown BCL exception.
