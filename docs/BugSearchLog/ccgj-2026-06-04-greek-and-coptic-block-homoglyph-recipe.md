- 2026-06-04: "Greek and Coptic block" homoglyph recipe admits non-letter punctuation/symbols
    - Approach: random starting area landed on `IdentifierRule.cs` (picked 7, list of 29 non-dir source files under `src/InductorParser/`, 7 mod 29 = 7). Read it side by side with its Unicode siblings: `GraphemeRule.cs`, `LiteralIgnoreAsciiCaseRule.cs`, `TokenSet.cs` (Single/Range/Runes/Graphemes, the category/whitespace builders, the surrogate-gap run-closing), `TokenSet.Xid.cs` (the hand-typed Other_ID_*/NFKx-closure tables, all UCD-test-verified), `Lexing/GraphemeHelpers.cs`, `Lexing/RuneHelpers.cs`, `Lexing/GraphemeClusterIndex.cs`, `Lexing/Lexer.Scanning.cs` (AdvanceWhileRuneIn/TokenIn), `AnyTokenRule.cs`, `ScanWhileRule.cs`, and `SyntaxTree/SourcePositionConverter.cs` (CRLF line counting). All of the production code came back clean and heavily defended. Followed the thread instead into the doc recipes, which have been a live vein lately (the latin1 ×÷ fix the day before).
    - Found and fixed: the "Homoglyph Confusables" section in `docs/UnicodeGotchas.md` had its `Greek` set as the naive `TokenSet.Range(0x0370, 0x03FF)`, commented "Greek and Coptic block only," sitting right under the carefully hand-split `LatinLetters` set that the previous day's hunt fixed to skip ×÷. The Greek and Coptic block is riddled with non-letters: U+037E GREEK QUESTION MARK and U+0387 GREEK ANO TELEIA (both Po, and both confusables resembling a semicolon and a middle dot respectively, the exact threat this security-framed section promises to keep out), U+0375/U+0384/U+0385 (Sk symbols), plus several unassigned code points. A confusable-resistant Greek identifier built on the naive range accepts the GREEK QUESTION MARK as an identifier character. Same bug class as the latin1 ×÷ one. The Latin neighbor was fixed, but its Greek sibling was missed.
    - Fix: changed the recipe to `TokenSet.Range(0x0370, 0x03FF) & TokenSet.Letters` (the block has too many holes to hand-split, so intersecting with the real category set keeps only letters and tracks the BCL's Unicode version). Updated the doc and added the mirrored doc-example test. Follow-up in the same pass: per a review question ("why not use the intersect form for every script?"), the answer is that it works for any block, so the Latin recipe was switched from its three hand-split sub-ranges to the same `(Ascii.Letters | Range(0x00C0, 0x00FF)) & TokenSet.Letters` form, and both mirrored Latin tests (`UnicodeGotchasExamples`, `UnexpectedUnicodeTests`) updated to match. The block-isn't-a-script caveat (the recipe is still a coarse approximation, true script filtering needs Script_Extensions) is already called out at the bottom of that doc section.
    - Verify: new test `DocExamples/UnicodeGotchasExamples.Homoglyph_Greek_set_rejects_non_letters` was red against the naive range (parsed U+037E as Success at the rejection assertion) and green after the `& TokenSet.Letters` fix. Non-letter inputs built from `new Rune(0x037E).ToString()` / `new Rune(0x0387).ToString()` so no editor can swap in an ASCII lookalike (the Canary meta-test caught an initial attempt that used a literal ASCII semicolon). Full `UnicodeGotchasExamples` fixture green (16/16). Command: `dotnet test --filter "FullyQualifiedName~UnicodeGotchasExamples"`.
    - Pattern: a second live instance of the existing `docs/PotentialBugSources/2026-06-04-contiguous-range-used-as-a-category-proxy-includes-interleaved-non-members.md`, which even named the Greek block as a candidate. Appended an instance note there rather than duplicating.
