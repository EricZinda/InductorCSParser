- 2026-05-18: ScanUntil's rule-valued stopper lookahead probe leaks failures
    - Start area: swept the rule folder (`src/InductorParser/`) broadly. Picked a random index that landed on `OrRule.cs` / `PeekRule.cs` (both already heavily swept per the `z000` / `0000b` entries), then followed the lookahead-probe thread out to the scan rules, which is where the bug turned up.
    - Files reviewed: `ScanUntilRule.cs`, `ScanWhileRule.cs`, `OrRule.cs`, `AndRule.cs`, `PeekRule.cs`, `NotRule.cs`, `AnyTokenRule.cs`, `EofRule.cs`, `OneOfRule.cs`, `NoneOfRule.cs`, `GraphemeRule.cs`, `LiteralRule.cs`, `LiteralIgnoreAsciiCaseRule.cs`, `WithinTokenRule.cs`, `AliasRule.cs`, `LateBoundRule.cs`, `BetweenInclusiveRule.cs`, `RuleStartRequirements.cs`, `Rules.cs`, the `Compile` / `CannotMatchLookahead` / `ResolveLeafId` sections of `Rule.cs`, `Lexing/Lexer.cs`, `Lexing/Lexer.FastPaths.cs`, `Lexing/Token.cs`, `SyntaxTree/Symbol.cs`, `SyntaxTree/SourcePositionConverter.cs`, plus `TokenSet.cs`'s `Contains` / `ContainsToken`.
    - Categories: lookahead-shortcut soundness (MustBeIn / MustNotBeIn polarity, the FIRST-set algebra in `MatchesAnyOf` / `MatchesAllOf` / `Combine`), lookahead-probe failure-state discipline, the transaction-windowed `_subtreeDeepestFailure` save/zero/Math.Max-merge, three-slot DeepestFailure resolution, zero-width-match handling in BetweenInclusive, scanner-skip soundness vs the unoptimized path, fast-path-vs-general-path divergence, lone-surrogate handling.
    - Found and fixed: `ScanUntilRule.TryParseRule` runs a rule-valued stopper as pure lookahead. A peek transaction always rolls the position back so the stopper is never consumed. But a transaction rolls back the *position*, not the failure tracker (`Lexer.Transaction` even documents "Failures survive both commit and rollback"). The in-loop stopper probe (and the post-loop EOF stopper probe) called `_stopperRule.TryParse` without the `SaveFailureState` / `RestoreFailureState` / `DiscardSubtreeExtent` discard that `PeekRule` and `NotRule` use. A multi-token stopper rule (`Literal("-->")`, `Literal("]]>")`, `Literal("\"\"\"")`) scanning a body that shares the stopper's prefix can match several tokens before failing, recording a mechanical failure *past* where the body ends. After `ScanUntil` succeeds, that stray mark is the deepest failure in the tracker, so an enclosing rule that fails at a shallower position reports `ParseResult.ErrorCharIndex` at the stray spot. Repro: `And(ScanUntil(Literal("-->")), Eof()).Parse("----->")` reported offset 4 instead of 3. Fix wraps both rule-stopper peeks with `SaveFailureState` + `RestoreFailureState` + `DiscardSubtreeExtent` inside the existing `using` peek scope (safe: `BeginTransaction` zeroed the subtree window, dispose merges the saved extent back with `Math.Max`). Regression test `ScanUntil_rule_stopper_probe_does_not_leak_a_failure_past_the_body` in `ScanUntilRuleTests`.
    - Found and fixed (second instance, same pattern): the rule-valued *escape-start* probe (`_escapeStartRule.TryParse`, used only by the `ScanUntil(stopAt, Rule escapeStart, escapeEnd)` overload) leaks the same way on its non-match path. A multi-token escape-start that matches a few tokens before failing leaves a stray deepest-failure mark. Repro: `And(ScanUntil(TokenSet.Runes("x"), Literal("xy"), AnyToken()), Eof()).Parse("abxz")` reported offset 3 instead of 2. Unlike the stopper probe it is not wrapped in a ScanUntil-level transaction, so it can't use `DiscardSubtreeExtent` (which would zero a committed escape-end's legitimate near-misses earlier in the same window). Fixed by snapshotting `_failureState` and `_subtreeDeepestFailure` before the probe and restoring both on the non-match path. The match path keeps the escape-start's failures (consumed content). Added a new `Lexer.RestoreSubtreeExtent(int)` (the precise counterpart of `DiscardSubtreeExtent`, which is `RestoreSubtreeExtent(0)`). Regression test `ScanUntil_rule_escape_start_probe_does_not_leak_a_failure_past_the_body`. The single-rune escape-start fast path (`_escapeStartRune`, the common backslash case) is an int compare and records nothing, so it is unaffected. The TokenSet-stopper path is also unaffected (no rule, no `RecordFailure`).
    - Cleared: the lookahead-shortcut FIRST-set algebra (`MatchesAnyOf` / `MatchesAllOf` / `Combine`, including the mixed-polarity `N \ P` case) was traced and is sound. The `_subtreeDeepestFailure` save/zero/merge machinery and the Peek/Not discard are sound. Scanner-skip end-position / tree-shape equivalence with the unoptimized path checks out.
    - Full suite re-run: 5730 passed / 2 skipped (the 2 pre-existing timing skips) with both fixes and both regression tests in place. The E2E sample grammars (Pep508, Newsboat, Toml) also stay green.
