    - Found and fixed: `ScanUntilRule.TryParseRule`'s per-token loop ran the stopper check before the escape-start check. When the escape-start rune (single-rune fast path) or the first rune of a rule-valued escape start is also a member of the stopper set, the stopper always wins and the escape is dead code — the scan terminates at the escape character. This is exactly the shape of both `Rules.cs` XML-doc `ScanUntil`-with-escape examples (`TokenSet.Runes("\"\\")` with escape `\`, and `TokenSet.Runes("\"$")` with escape `Literal("${")`). A user copying the documented JSON-string-body grammar gets a body that terminates at the first backslash. Fix: moved the `if (_hasEscape) { ... }` block ahead of the stopper block, hoisted `int tokenLen = lexer.PeekTokenLength(pos)` above both, and corrected the file-header order comment. Escape-first is strictly more expressive: escape-start doesn't match cleanly falls through to the stopper, so grammars that keep the two disjoint (every existing test + E2E grammar) are unaffected.
