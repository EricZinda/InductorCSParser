    - Found and fixed (psk0):
        1. `BetweenInclusiveRule.TryCreateScannerSkip` (recursive engine) unions every non-fallback Or-alternative's `FirstConsumedTokens.LookaheadFirstRunes` directly into `candidates` without checking `alternative.Polarity`.
        2. `Lowerer.TryLowerBetweenScanner` (state-machine engine) has the EXACT SAME pattern in the parallel scanner-skip lowering path.
       For a `MustNotBeIn` alternative like `NoneOf(stopSet)`, `FirstConsumedTokens` is the rule's FAIL-set, so `candidates` ends up being the set of runes where the rule will FAIL. `ZeroOrMore(Or(NoneOf(TokenSet.Runes("xy")), AnyToken().Flatten(FlattenType.Delete))).Parse("abxcyd")` scanner-skips straight to the 'x' (where NoneOf FAILS), the AnyToken-Delete fallback consumes it, scanner-skips to 'y', consumes, then runs off the end. The 'a' / 'b' / 'c' / 'd' positions are skipped past entirely. Slow path produces `["a","b","c","d"]` Preserve leaves; scanner-skip path produces `[]`. Confirmed bug on both engines by temporarily reverting each fix and watching the corresponding test fail with `Expected: "abcd" But was: <string.Empty>`. Fix shape (both sites): bail out of the scanner-skip builder when any non-fallback alternative has `Polarity != MustBeIn`. The scanner-skip can't be made sound for a `MustNotBeIn` alternative without enumerating the complement of the fail-set, which under grapheme tokenization is unbounded.
