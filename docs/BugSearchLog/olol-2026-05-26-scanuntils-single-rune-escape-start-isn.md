- 2026-05-26: ScanUntil's single-rune escape start isn't projected under Compile's normalization form, so a non-form-stable escape rune silently never fires
    - Random start: picked 17, 17 mod 30 = 17 over the 30-file `src/InductorParser/` top-level listing, mapping to `PeekRule.cs`. Read it side by side with the sibling lookahead-shape rules (`NotRule.cs`, `AndRule.cs`, `OrRule.cs`, `AnyTokenRule.cs`, `EofRule.cs`), then followed threads out into `OneOfRule.cs`, `NoneOfRule.cs`, `LiteralRule.cs`, `LiteralIgnoreAsciiCaseRule.cs`, `GraphemeRule.cs`, `WithinTokenRule.cs`, `ScanWhileRule.cs`, `ScanUntilRule.cs`, `BetweenInclusiveRule.cs`, `AliasRule.cs`, `LateBoundRule.cs`, `Rule.cs` (Compile orchestration, the `CollectNormalizationOffenders` hook, the `TryConvertToForm` helper, `ResolveLeafId`), `Lexing/Lexer.cs`, `Lexing/Lexer.FastPaths.cs`, `Lexing/Token.cs`, `Lexing/NormalizedPositionMap.cs`, `TokenSet.cs` (`NormalizedFor` / `AddProjectedEntry`), `SyntaxTree/Symbol.cs` / `SourceRange.cs` / `SourcePosition.cs` / `SourcePositionConverter.cs` / `SymbolExtensions.cs` / `SymbolId.cs`.
    - Categories checked. Zero-width-success handling in lookahead Preserve symbols (PeekRule / NotRule / EofRule build `lexer.Input.AsMemory(startPosition, 0)` for the Preserve branch, which reaches `Symbol.SourceRange` correctly via the leaf-memory → MemoryMarshal.TryGetString path and ParseContext's normalization mapping). Multi-rune escape-start handling in ScanUntil (the bug, below). Sub-lexer Symbol context: WithinTokenRule's leaf Symbol uses `outerLexer.Context` so SourceRange maps correctly even when the inner rule itself is a WithinToken nested inside. The inner sub-lexer's symbols are all discarded so a null inner context never reaches a real Symbol. AndRule / OrRule zero-children edge: Rules.And / Rules.Or both throw on empty children at the factory, so the constructors are unreachable with empty. AliasRule rebadge under all three FlattenType combinations (Preserve, Flatten, Delete) and across leaf vs composite inner shapes. AdvanceWhileTokenIn's lone-surrogate handling: the multi-rune-set path's `else` branch goes through `set.ContainsToken(span)` which handles lone surrogates via its own length-1 + `char.IsSurrogate` branch, so the lone-surrogate path stays sound when the set has multi-rune entries.
    - Found and fixed: `ScanUntilRule._escapeStartRune` (the `Rune escapeStart` constructor overload's single-rune fast path) was held as a plain `int` and never re-projected during Compile's normalization-form pass. `CollectNormalizationOffenders` only walked `_stopperSet`. So a user-typed precomposed escape rune (e.g. `new Rune('é')` = U+00E9) compiled under FormD silently never fired on the decomposed cluster the lexer produced (`"e + U+0301"`, one grapheme, two runes). The fast-path check `tokenLen == runeLen && runeValue == _escapeStartRune` saw `tokenLen=2`, `runeLen=1`, and bailed every cluster. The body fell through to the stopper check, the cluster was consumed as body, the escape sequence's `_escapeStartRule`-free path was effectively dead under FormD, and the parse silently produced wrong output (escape semantics quietly stripped). OneOf and ScanUntil's `_stopperSet` already got the projection via `OneOfRule.NormalizeAndValidate`. `_escapeStartRune` was the matching gap called out in `tokenset-bearing-rules-that-skip-form-projection.md` as "not currently form-projected, future grammar that uses a non-ASCII rune there would hit the same shape." The shape is real and a test triggers it.
    - Fix in `src/InductorParser/ScanUntilRule.cs`: dropped `readonly` from `_escapeStartRune`, added a `_escapeStartGrapheme` field (string? null until Compile projects the rune to a multi-rune-single-grapheme form), extended `CollectNormalizationOffenders` to convert the rune via `TryConvertToForm` and dispatch on the four outcomes (unchanged → no-op, single-rune-changed → re-point `_escapeStartRune`, multi-rune-single-grapheme → set `_escapeStartGrapheme`, multi-grapheme → report as offender). Modified the fast path in `TryParseRule` to span-equal against `_escapeStartGrapheme` when set, falling back to the existing int-compare otherwise. Local-only `CountGraphemes` mirrors GraphemeRule's same-shape helper.
    - Tests: two in `src/InductorParser.Tests/Rules/ScanUntilRuleTests.cs`. `ScanUntil_with_precomposed_escape_start_rune_fires_on_decomposed_input_under_FormD` is the failure-side test (under-the-bug parse succeeds with the escape silently swallowed. With the fix the escape fires, escape-end Token('x') fails on 'Y' and the rule fails). `ScanUntil_with_precomposed_escape_start_rune_consumes_escape_on_decomposed_input_under_FormD` is the happy-path sibling, asserting via the trace sink that `Token('x')` actually runs as escape-end (without the fix the escape is silently skipped and no `Token: found 'x'` trace line exists). Full suite: 6896 pass / 0 fail / 2 pre-existing skips.
    - Sibling-rule check: `LiteralIgnoreAsciiCaseRule`'s ASCII-only constructor restriction means its `_expected` is always form-stable (ASCII is invariant under all four normalization forms), so the same shape can't trigger there even though `tn8m`'s pattern doc grouped them together. The four other TokenSet / single-rune-int leaves all project correctly: OneOf, NoneOf, and ScanWhile via `OneOfRule.NormalizeAndValidate`, ScanUntil's `_stopperSet` via the existing override, and GraphemeRule / LiteralRule via `TryConvertToForm`. After this fix, the only remaining "rule holds caller-supplied user text that isn't form-projected" gap from `tn8m` is the `LiteralIgnoreAsciiCase` ASCII-only theoretical case, which the constructor blocks.
    - State-machine engine: `ScanUntilRule.LoweringEscapeStartRune` still exposes the post-projection `_escapeStartRune` value (canonical singleton substitutions like U+212A → 'K' still flow through correctly). The SM engine doesn't yet read `_escapeStartGrapheme`, so SM parses of the multi-rune-cluster escape-start case will still hit the original silent-skip behavior. That gap is tracked as a follow-up rather than blocking this fix because (a) the recursive engine is the default, (b) the SM engine is in `ExperimentalSrc/`, and (c) wiring `LoweringEscapeStartGrapheme` through the lowerer and state-machine opcodes is a larger change that isn't critical for the released parser. Adding a SM-side accessor and matching opcode is the natural next step if the SM engine moves out of experimental.
    - Pattern doc: this is the first concrete instance of the "single-rune-int caller-supplied state not form-projected" branch of `tn8m`. Rather than write a new pattern doc, this entry extends `tn8m`'s coverage. The existing pattern doc already names the shape and the open gap. A new pattern doc would duplicate without adding to the catalog.
