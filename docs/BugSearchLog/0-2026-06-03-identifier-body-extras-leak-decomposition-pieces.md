- 2026-06-03: `Rules.Identifier` body-side mirror gap of [the 2026-06-02 head-only fix](0000000000---2026-06-02-identifier-compat-start-continuation-piece.md): `extraBodyRunes` are still run through `body.WithCompatibilityEquivalents` after the union, so a body extra whose NFKx contains a non-XidContinue rune (the SPACE separators inside U+FDFA's Arabic-phrase NFKC are the canonical case) silently leaks that rune into the body set
    - Focus: "compatibility form bugs" (user-directed). Re-read [Rules.Identifier.cs](../../src/InductorParser/Rules.Identifier.cs) (the new dedicated file from the 2026-06-02 fix) alongside the new `WithCompatibilityHeadRuneEquivalents` / `AllCompatibilityTailRunesIn` helpers in [TokenSet.cs](../../src/InductorParser/TokenSet.cs) and the regression tests `Compatibility_identifier_does_not_promote_continuation_piece_to_start`, `XidStart_compatibility_continuations_are_all_in_XidContinue`, and `Identifier_rejects_start_extra_whose_decomposition_tail_is_not_a_body_character` in [XidIdentifierTests.cs](../../src/InductorParser.Tests/Core/XidIdentifierTests.cs).
    - Found and fixed: the prior fix split the start side into "head-only expansion + tail validation" so extras with continue-only tail pieces are rejected by name (`Identifier_rejects_start_extra_whose_decomposition_tail_is_not_a_body_character`). The body side didn't get a mirror. It still runs `body = (TokenSet.XidContinue | extraBodyRunes).WithCompatibilityEquivalents(form)` after the union. XidContinue is NFKx-closed (so the closure-safe expansion stays inside the identifier base), but the caller's extras carry no such guarantee. Any extra whose NFKx is multi-grapheme with a piece outside XidContinue silently injects that piece into the body set. Concrete repro: `Identifier(form: FormKC, extraBodyRunes: TokenSet.Single(0xFDFA))` (U+FDFA ARABIC LIGATURE SALLALLAHOU ALAYHE WASALLAM, NFKC = an 18-char Arabic phrase with three U+0020 SPACE separators) compiles silently and `Parse("abc def").Success` returns `True` because the SPACE separators landed in body. Fix in two pieces. (1) A new `AllCompatibilityPiecesIn(form, allowedRunes, ...)` helper in [TokenSet.cs](../../src/InductorParser/TokenSet.cs) that mirrors `AllCompatibilityTailRunesIn` but checks every NFKx piece (head included), since body matches against every code point after the first. (2) A follow-up validation in [Rules.Identifier.cs](../../src/InductorParser/Rules.Identifier.cs) that calls it on `extraBodyRunes` against `(TokenSet.XidContinue | extraBodyRunes)` and throws `InvalidOperationException` naming the offending entry, its conversion, and the missing piece. The allowed-set choice (XidContinue plus the caller's body extras themselves) is the body-side mirror of the start-side check against the expanded `body`: a piece passes if it's a spec body rune OR if the caller already opted it into body explicitly. Extras whose decomposition stays inside XidContinue (the ligature ﬁ → "fi" case) still pass automatically.
    - Regression test: `Identifier_rejects_body_extra_whose_decomposition_piece_is_not_a_body_character` in [XidIdentifierTests.cs](../../src/InductorParser.Tests/Core/XidIdentifierTests.cs), parameterized on FormKC / FormKD. Asserts the throw shape and message contents for U+FDFA, asserts the ligature ﬁ (whose pieces are both XidContinue) builds cleanly, and asserts the opt-in lane (passing U+FDFA together with explicit SPACE in `extraBodyRunes`) builds cleanly too. Fails before the fix (the rule compiles and `Parse("abc def")` returns success). Full suite: 7126 pass, 2 skipped (`[Test, Explicit]` UCD-fetch checks), 0 fail.
    - Pattern: same shape as the existing [2026-06-03-set-extender-applies-union-before-form-projection-on-closed-builtin.md](../PotentialBugSources/2026-06-03-set-extender-applies-union-before-form-projection-on-closed-builtin.md) entry from earlier today, but a sharper variant. The API had the closure-aware split applied for start extras and a second validation method added to enforce the invariant. The fix just didn't mirror over to the body side. When a closure-aware refactor adds a side-specific helper (`WithCompatibilityHeadRuneEquivalents`) and a side-specific validator (`AllCompatibilityTailRunesIn`), the other side may need its own helper and validator too. Updated the pattern doc to call out the head/tail/body symmetry as a thing to check next time.
