- 2026-05-20: GraphemeClusterIndex's shared mutable state races under concurrent parses of the same input string
    - Random pick: skipped the random index this round because the user asked for a security-related bug. Walked the budget-propagation and shared-state surface: `ParseOptions.cs`, `ParseCancellation.cs`, `Rule.cs` (Parse / ParseRecursive / TryParse / EnterRule), `Lexer.cs` (ConfigureBudgets / EnterRuleBudgetChecks / ExitRuleBudgetChecks / CheckPeriodicBudgets / Probe / Transaction), `WithinTokenRule.cs` (the recent sub-lexer budget-propagation fix), `Lexer.FastPaths.cs` (the unchecked scan loops), `ScanWhileRule.cs` / `ScanUntilRule.cs` (leaf scanners that don't tick budget per iteration), `NotRule.cs` / `PeekRule.cs` (lookahead probes), `NormalizedPositionMap.cs`, `Symbol.cs` (SourceText substring math), `SymbolExtensions.cs` (PrintTree recursion), `SymbolId.cs`, then the GraphemeClusterIndex cache.
    - Categories checked: stack-overflow via MaxDepth bypass (recent WithinToken fix already plugged the only sub-lexer site), unbounded scan loops past Timeout / RuleCountLimit (`AdvanceWhileRuneIn` / `AdvanceWhileTokenIn` / `AdvanceUntilRuneIn` / `AdvanceUntilLiteralCandidateIn` don't tick the periodic check, but documented as intentional leaf-scope work), error-template placeholder injection via the {character} substitution (substitution order rules it out), pre-elapsed-Timeout / pre-cancellation parses too small to hit the periodic check (cancellation path fixed at 73aa1df, pre-elapsed-Timeout explicitly left unfixed), thread safety of shared mutable state under "concurrent parses of the compiled grammar need no synchronization" (LateBoundRule's documented claim).
    - Found and fixed: `GraphemeClusterIndex.For` caches by string instance via a `ConditionalWeakTable<string, GraphemeClusterIndex>`, so two threads parsing the same input string share one index. The instance has mutable state (`TextElementEnumerator`, `bool[] _isStart`, `_exhausted` flag) that `EnsureWalkedTo` writes during the lazy walk. `TextElementEnumerator.MoveNext` is not thread-safe (the BCL doesn't claim otherwise, and the racy update on the internal index lets `ElementIndex` surface mid-cluster positions). The race writes `_isStart[idx] = true` for an idx that ISN'T a cluster start (the bug surfaced as `IsClusterStart(119)` returning true on a `"a\r\n"`-tiled input where 119 is mid-CRLF), which then trips the next `LengthAt` invariant check. An application that parses an interned literal or a cached config string from two threads can crash with `InvalidOperationException("Internal lexer invariant violated")`, an exception the caller has no warning to catch. Fix in `src/InductorParser/Lexing/GraphemeClusterIndex.cs`: per-instance `_walkLock` around the walk in `EnsureWalkedTo`, with a `volatile bool _exhausted` and `volatile int _walkedTo` fast-path that skips the lock once the walk has reached the requested target. Lock is per-instance so concurrent parses of different inputs never contend. The steady-state cost on a long parse is a pair of volatile reads per Read. Test added to `GraphemeClusterIndexTests.cs` (`Concurrent_walks_of_same_input_dont_corrupt_index`) runs a trial loop of 20 fresh strings with `2 * Environment.ProcessorCount` threads each walking the whole index, and pre-fix fails on the first trial (every run hits the race within ms).
    - Pattern: docs/PotentialBugSources/0-2026-05-20-shared-mutable-state-cached-per-input.md (the broader category, "a static cache that's keyed on a per-parse value but stores mutable state mutated during parse"). LateBoundRule's `_resolvedFlattenType` is the same shape done right: written once during single-threaded Compile, then read-only at parse time.
    - Cleared: scan-loop budget skipping is documented and intentional. Error-template placeholder injection is blocked by the positional-then-extra substitution order. Probe restores position / failure tracker / subtree extent but NOT budget counters (correct: a lookahead probe's work counts toward the parse). InheritBudgetsFrom chains through `_budgetParent` correctly under nested sub-lexers (each EnterRuleBudgetChecks call walks the chain to the root that owns the counters). SourcePositionConverter.ToLineColumn's CR / CRLF handling is correct at the EOF boundary. The `??=` lazy initialization of `_enumerator` is now inside the lock so two threads can't allocate parallel enumerators.
    - Not a bug, considered: `bool[] _isStart` writes are atomic in .NET, so a race that only set `_isStart[idx] = true` from two threads with the SAME idx is idempotent and harmless. The race that matters is the one inside `TextElementEnumerator.MoveNext` whose racy update produces a wrong idx, and that's what the fix targets. CountClustersUpTo's O(charIndex) walk on every {tokenIndex} placeholder substitution is a perf concern (a megabyte-scale input with a custom template that always renders {tokenIndex} pays for it on every parse failure) but not a correctness or DoS bug.
