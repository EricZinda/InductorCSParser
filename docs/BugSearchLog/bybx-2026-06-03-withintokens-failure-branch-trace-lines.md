- 2026-06-03: WithinToken's failure-branch trace lines print UTF-16 char counts but label them rune counts/offsets
    - Starting area: not randomized this pass. User directed the hunt to focus exclusively on `WithinTokenRule.cs`, so the random-start step was skipped deliberately.
    - Reviewed: `WithinTokenRule.cs` (full: constructor, the EOF branch, the sub-lexer substring + budget inheritance, the inner-failed branch, the prefix-consume branch, the leaf-emit tail), cross-checked against `OneOfRule.cs` (the shared leaf-emit shape), `Rule.cs` (`TryParse` transaction/rollback, `ParseChild`, `ResolveLeafId`, `OpensTransaction`), `Lexing/Lexer.cs` (`Read` / `NextTokenLength` / `IsEof` / `Position` semantics in `oneRunePerToken` mode), `Lexing/Token.cs` (`RuneValue`), and `Lexing/RuneHelpers.cs` (renamed from `SurrogateHelpers.cs` as part of this change).
    - Categories checked: leaf-id rune-vs-multi-rune selection, SourceRange/SourceText for multi-rune and astral matches, failure position snap-back to the outer cluster start, transaction rollback of the outer `Read()` on failure, forced/named inner `.WithError` surfacing, char-vs-rune unit confusion across the sub-lexer boundary, and trace-line correctness. All sound EXCEPT the last.
    - Found and fixed: both of `WithinTokenRule.TryParseRule`'s failure-branch trace lines read `subLexer.Position` / `DeepestFailurePosition`, which are 0-based UTF-16 char offsets into the substring, and printed them as if they were rune offsets/counts. The in-code comments asserted this directly ("subLexer.Position ... is the consumed rune count directly") and the rule's own model is rune-per-token, so the values diverge for supplementary-plane runes: one astral rune is two UTF-16 chars. On a two-rune `👍🏽` cluster (U+1F44D + U+1F3FD, four chars) where the inner consumed one rune, the prefix-consume line read `inner rule consumed only 2/4 of the token` (should be `1/2`) and the inner-failed line read `failed at token rune offset 2` (should be `1`). Position recording itself was already correct (snapped to the outer cluster start), so this is a diagnostic-only defect, but the trace is what a grammar author reads to debug an emoji / jamo / CJK-extension WithinToken grammar, and it actively contradicts the rule's documented rune model. Fix: added `RuneHelpers.RuneCount(ReadOnlySpan<char>)`, which counts runes with the lexer's own model (a surrogate pair is one rune, a stray surrogate is one rune, matching the sibling `EnumerateRuneValues`), converted both trace lines through it (passing a span over just the range each line reports on), and corrected the two stale "Position is the rune count" comments. The helper went on the rune-layer helper class rather than as a private method on the rule because it's a general UTF-16/rune primitive. That class was named `SurrogateHelpers`, but it already held `EnumerateRuneValues` and now `RuneCount` (rune-decoding, not just surrogate detection), so this change also renamed it to `RuneHelpers` (file `Lexing/RuneHelpers.cs`) to describe what it does. It stays separate from `GraphemeHelpers` (the grapheme-cluster layer, itself renamed from `GraphemeClusters` in the same pass for parallelism) since the two sit at different Unicode layers and have different visibility (internal vs public) and perf profiles.
    - Two regression tests in `WithinTokenRuleTests.cs` (`[RecursiveEngineOnly]`, verbatim trace assertions over a `👍🏽` cluster): `Prefix_consume_trace_reports_rune_counts_not_char_counts_for_supplementary_plane_cluster` and `Inner_failed_trace_reports_rune_offset_not_char_offset_for_supplementary_plane_cluster`. Both fail on a clean checkout (`2/4` and `offset 2`) and pass with the fix (`1/2` and `offset 1`). BMP multi-rune clusters (decomposed `é`, two chars/two runes) are unaffected since char count equals rune count there, so the existing WithinToken tests stay green. Also added `RuneHelpersTests.cs` covering `RuneCount` directly (empty, all-BMP, surrogate-pair-as-one-rune, mixed, lone trailing high surrogate, prefix range).
