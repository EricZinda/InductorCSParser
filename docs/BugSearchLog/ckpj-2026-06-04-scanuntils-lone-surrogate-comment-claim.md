    - Bug filed + fixed: `ScanUntilRule.TryParseRule`'s header comment said the lexer's one-char lone-surrogate token "can't be in any TokenSet (entries are valid Unicode scalars)" and therefore "the stopper and escape-start checks both correctly say no match" so the surrogate always "flows through as body." The first clause is false: `TokenSet.Surrogates` and `TokenSet.SurrogateRange` build sets whose entries are surrogate code units, and `TokenSet.ContainsToken` has a lone-surrogate branch (the same one OneOf / NoneOf use) precisely so they match. So `ScanUntil(stopAt: TokenSet.Surrogates)` STOPS at a lone surrogate rather than consuming it as body. The same wrong claim was mirrored in a comment in `ScanUntilRuleTests.cs` above the `StopOnPipe`-based surrogate tests (those use a '|' stopper, which genuinely has no surrogates, so the tests were right but the comment over-generalized). User-visible consequence is a maintainer hazard, not a current misbehavior: anyone "optimizing" the scan loop on the comment's word (skip `ContainsToken` for a RuneValue == -1 token because "it can't match") would silently break the documented WTF-8 / unpaired-surrogate boundary scan. This is the same fast-path-membership-drops-lone-surrogates shape that already bit `AdvanceWhileRuneIn` (2026-05-15), `AdvanceUntilRuneIn` (2026-05-18), and `TokenSet.Contains(string)` (2026-05-19).

    - Note for the next hunter. The big trap on this surface is that `Parse` requires consuming all input by default (`ParseOptions.AllowTrailingInput == false`), and ScanUntil never consumes its stopper. A surrogate-detection oracle that doesn't set `AllowTrailingInput = true` (or append the stopper) will see spurious failures whenever the stopper is left unconsumed, which looks like a ScanUntil-surrogate bug but isn't.
