- 2026-05-28: User's `.WithError` text in trace lines splices raw control characters after the handler runs
    - Not a fresh random-walk sweep. Followed the explicit "One adjacent gap left open and noted in the search log" bullet at the bottom of [--2026-05-28-rule-match-trace-lines-leak-raw-control-chars.md](--2026-05-28-rule-match-trace-lines-leak-raw-control-chars.md). That fix routed every `$"..."` interpolation hole in a trace body through `DisplayEscape.AppendEscaped` via `TraceInterpolatedStringHandler.AppendFormatted`, but the user's `.WithError("...")` text is appended to the FAIL line by `Rule.AppendErrorMessage` *after* the handler has already finished, so the auto-escape doesn't reach it.
    - Reviewed: [Rule.cs:187-193](../../src/InductorParser/Rule.cs#L187-L193) (`AppendErrorMessage`), [Rule.cs:211-220](../../src/InductorParser/Rule.cs#L211-L220) (`TraceFailure` overloads that call `AppendErrorMessage`), [TraceInterpolatedStringHandler.cs](../../src/InductorParser/Tracing/TraceInterpolatedStringHandler.cs) (the handler that escapes interpolation holes, to confirm `AppendErrorMessage` runs outside its reach), [Lexer.Tracing.cs](../../src/InductorParser/Lexing/Lexer.Tracing.cs) (`WriteTraceLine`, the sink writer that takes `AppendErrorMessage`'s output verbatim), [WithErrorTests.cs](../../src/InductorParser.Tests/Core/WithErrorTests.cs) and [UnicodeAsAndWithErrorTests.cs](../../src/InductorParser.Tests/Core/UnicodeAsAndWithErrorTests.cs) (existing WithError trace tests, none covered control chars). Cross-checked [DisplayEscape.cs](../../src/InductorParser/Tracing/DisplayEscape.cs) for the `Escape(string, offset, length)` companion to `AppendEscaped`, which was kept as a return-a-string helper when the 2026-05-28 handler fix removed its only production caller.
    - Categories swept: post-handler trace splice of user-supplied text (the bug), the symmetric path on a success line (no `_errorMessage` is appended on success, so the trace handler's auto-escape covers the success-line interpolation body alone), `ParseResult.ErrorMessage` vs trace render (the stored `_errorMessage` field has to keep the user's exact text for the API surface, so escaping in the field would over-reach).
    - Found and fixed: `Token('a').WithError("line1\nline2").Parse("x")` with a `TraceSink` set drives `Rule.TraceFailure` → `lexer.WriteTraceLine(label, Failure, AppendErrorMessage(formatted))`. `formatted` came out of the handler already-escaped (so `found 'x', wanted 'a'` is one line), but `AppendErrorMessage` then did `$"{body} \"{_errorMessage}\""` with `_errorMessage = "line1\nline2"`, so the FAIL line went into the sink as `   FAIL | Token: found 'x', wanted 'a' "line1<LF>line2"` and the embedded LF split the one-event-per-line layout that every other trace assertion in the suite relies on.
    - Fix at [Rule.cs:187-205](../../src/InductorParser/Rule.cs#L187-L205): route `_errorMessage` through `DisplayEscape.Escape(_errorMessage, 0, _errorMessage.Length)` before interpolating into the trace body. The stored `_errorMessage` field is unchanged, so `ParseResult.ErrorMessage` still surfaces the user's exact multi-line text to API callers who want it verbatim. The escape only affects the trace-display path, where the one-line invariant is the property we're protecting. `DisplayEscape.Escape`'s no-control-char fast path (one scan + Substring) means the common printable WithError pays nothing past the existing string allocation. Updated the method-level comment to point at the handler-runs-first reason the escape has to be here rather than upstream.
    - Tests: one regression test in [TracingTests.cs](../../src/InductorParser.Tests/Core/TracingTests.cs) `WithError_message_in_trace_escapes_control_chars`, slotted directly above the existing `WithError_message_appears_in_quotes_after_trace_body_on_failure` test that locks in the verbatim render of an all-printable WithError ("expected an A"). The new test drives `WithError("line1\nline2")` and asserts the FAIL line shows `"line1U+000Aline2"`. Verified the test catches the bug: reverted [Rule.cs:187-205](../../src/InductorParser/Rule.cs) to the raw `_errorMessage` splice, re-ran the test, it failed with the expected diff (`"line1U+000Aline2"` vs `"line1\nline2"`). Restored the fix and re-ran to confirm green.
