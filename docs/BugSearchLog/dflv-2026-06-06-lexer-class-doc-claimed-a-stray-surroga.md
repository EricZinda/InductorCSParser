    - Found and fixed (comment bug, code was correct): the `Lexer` class-doc malformed-UTF-16 paragraph (`Lexing/Lexer.cs`) said stray surrogates "are walked one char at a time in both modes" and that in grapheme mode StringInfo "treats unpaired surrogates as 1-char text elements," so "Read produces a one-char token over the stray." That's only true for a stray with nothing after it. When a combining mark (or any Extend) follows, UAX #29 GB9 fuses them: StringInfo decodes the stray to U+FFFD (GCB = Other, a base) and won't break before the following Extend, so `"\uD800" + U+0301` is ONE two-char cluster. The method comment in `Lexer.Scanning.cs` (AdvanceWhileRuneIn's `tokenLength == 1` check) already described this fusion correctly, so the two comments flatly contradicted each other. The class doc was the wrong one. Empirically confirmed via `StringInfo.GetTextElementEnumerator` and through the real lexer: `new Lexer("\uD800" + combining-acute).PeekTokenLength(0) == 2`. User-visible consequence is a maintainer hazard, not a current misbehavior. Anyone "simplifying" grapheme-mode tokenization to force every stray to a 1-char token (trusting the old prose) would silently break the fused-cluster boundary. Fix: rewrote the class-doc paragraph to state the bare-stray vs stray+Extend split and the GB9 reason, and (from the same review) corrected two more stale claims in the same paragraph block, that the rune sub-lexer mode is "selected by an internal constructor and used only by WithinTokenRule" (it's the public `Lexer(string, bool)` overload, which is why WithinTokenRule self-links into the no-IVT ExternalContractTests), and added a note that a normalizing Compile rejects lone surrogates up front via `string.Normalize` before the lexer runs.
