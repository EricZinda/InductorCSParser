- 2026-05-18: Compatibility/ folder sweep, Rune polyfill #if gate fixed (NET5_0_OR_GREATER to NETCOREAPP3_0_OR_GREATER)
    - Not a random-walk start. The hunter was directed to sweep `src/InductorParser/Compatibility/` specifically, the folder the find-a-bug random-start procedure normally skips, so it had never been swept before. All five files reviewed: `Rune.cs`, `IsExternalInit.cs`, `MemberNotNullAttribute.cs`, `InterpolatedStringHandlerAttribute.cs`, `InterpolatedStringHandlerArgumentAttribute.cs`.
    - Categories swept on the `Rune` polyfill: every member compared against BCL `System.Text.Rune` behavior. Constructors (`char`, `char`+`char`, `int`, `uint`), `IsValid`, `Value`, `IsAscii`, `IsBmp`, `ReplacementChar`, the three `TryCreate` overloads, `GetUnicodeCategory` (BMP and supplementary paths), `Equals`/`GetHashCode`/`CompareTo`, `ToString`, and the comparison operators are all behaviorally faithful to the BCL type. Cross-checked against actual parser usage: the parser only ever exercises `new Rune(int)`, `Rune.IsValid(int)`, `.Value`, and `.ToString()` (everything else is public-surface-only, unused internally), and all of those are correct. The netstandard2.1 build compiles clean, so no BCL member the parser needs is missing from the minimal polyfill.
    - Categories swept on the four attribute polyfills: `AttributeUsage` targets, `Inherited`, `AllowMultiple`, and constructor signatures all match the BCL types exactly. `IsExternalInit` is `internal` (the recommended polyfill practice) and is safe here because the only `init`-bearing types (the `record struct`s `ScannerSkip`, `Interval`, `RuleStartRequirements`) are all `private`/`internal`, so no public API surface forces an external consumer to resolve the modreq.
    - The bug (fixed): `Rune.cs` gated the polyfill with `#if !NET5_0_OR_GREATER`, but `System.Text.Rune` shipped in .NET Core 3.0, not .NET 5. The file's own line-3 comment says so, and line 13 contradicted it. `NET5_0_OR_GREATER` is undefined for netcoreapp3.0 and netcoreapp3.1, so a build for either of those frameworks compiled the `public` polyfill `System.Text.Rune` in alongside the BCL one. Demonstrated: `dotnet build -p:TargetFrameworks=netcoreapp3.1` produced 53 `CS0436` type-conflict diagnostics (errors, because `TreatWarningsAsErrors` is on). Latent for the current target set of netstandard2.1 and net8.0, since both of those evaluate the wrong gate to the right answer. Fix: changed the gate to `#if !NETCOREAPP3_0_OR_GREATER` (defined for exactly the frameworks that ship the BCL `Rune`) and corrected the line-13 comment. The change is a strict no-op for netstandard2.1 and net8.0 (both evaluate the new gate identically to the old), verified by clean builds of all three frameworks. The net8.0 test run reported one failure (`WithinTokenRuleTests.WithinToken_WithError_surfaces_over_deeper_orphan_from_abandoned_Or_alternative`), pre-existing on this branch and unrelated, confirmed by stashing the gate change and seeing it fail identically on the clean baseline. The four sibling attribute polyfills already have correct gates (`!NET5` and `!NET6`, matching when those types actually shipped) and were left alone.
