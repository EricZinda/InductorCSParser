    - Found and fixed: `Rule.BuildErrorMessage`'s `{character}` placeholder (the default `PositionalErrorTemplate` "Parse failed at offset N: unexpected '{character}'.") substituted `StringInfo.GetNextTextElement(input, failurePos)` verbatim. When the parse fails at a control / line-separator character (a bare LF, U+2028, U+2029, NUL, etc.) the raw char goes straight into `ParseResult.ErrorMessage`, splitting the one-line message across two physical lines in a log or terminal. This is the user-facing error message, not a trace, so it bypasses the 2026-05-28 `TraceInterpolatedStringHandler` auto-escape that closed the rule-layer trace sites. It was the open `{character}` candidate the pattern doc called out. Every other render site (`TokenSet.ToString`, `SymbolExtensions.PrintTree` short + long form, `Lexer.Read` trace) already routes user-bearing text through `DisplayEscape`. Fix: wrap the placeholder value in `DisplayEscape.Escape(element, 0, element.Length)`. Printable graphemes (fullwidth, ligatures, supplementary-plane runes, emoji clusters) still render verbatim, so the "show the user-typed character" intent is preserved. Only Cc/Zl/Zp escape to `U+XXXX`. The `customMessage` (user `.WithError`) branch returns earlier, so user error text is untouched.
