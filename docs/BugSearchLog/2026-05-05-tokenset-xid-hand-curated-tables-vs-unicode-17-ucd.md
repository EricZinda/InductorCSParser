- 2026-05-05: TokenSet.Xid hand-curated tables vs. Unicode 17.0 UCD
    - Reviewed: `TokenSet.Xid.cs` (`XidStartAdds`, `XidStartExclusions`, `XidContinueAdds`, `XidContinueExclusions`, `BuildXidStart`, `BuildXidContinue`), `Rules.Identifier`, `TokenSet.cs` (set-algebra operators consumed by the build), `Compatibility/Rune.cs` (polyfill, not exercised on net8.0 test target).
    - Cross-checked against UAX #31 derivation rules and `PropList.txt` `Other_ID_Start` ranges.
    - Categories: missing or extra ranges in the hand-curated add / exclude tables, miscategorization of code points the BCL reports differently than UCD, off-by-one range endpoints.
    - Found and fixed (k309, commit 8d1a4f9): `XidStartAdds` was missing the `(0x309B, 0x309C)` range (KATAKANA-HIRAGANA VOICED / SEMI-VOICED SOUND MARK, GC=Sk, in `Other_ID_Start` since Unicode 5.1 and unchanged in Unicode 17.0). Same gap in `XidContinueAdds`. Before the fix, `Rules.Identifier().Parse("゛")` and `Parse("゜")` failed at offset 0 with `unexpected '゛'` / `unexpected '゜'`, contradicting the parser's documented UAX #31 R1 compliance.
    - The fix adds the range to both Adds tables, mirroring the existing pattern for U+2118 / U+212E (similarly outside the L+Nl base, listed in both Adds tables with cross-reference comments). Four regression tests in `XidIdentifierTests` cover both endpoints (309B and 309C) in both start and continue position, so a future fat-fingered range like `(0x309B, 0x309B)` would also fail.
    - Cross-checked the rest of the hand-curated tables against Unicode 17.0 PropList.txt and DerivedCoreProperties.txt; the remaining add / exclude ranges line up. Added the "Hand-curated Unicode property tables..." pattern bullet to `docs/PotentialBugSources/`.
