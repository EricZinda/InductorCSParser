- 2026-05-05: NoneOf FirstConsumedTokens vs. multi-rune clusters whose first rune is in the rune-only part
    - Reviewed: `NoneOfRule.cs` (especially `ComputeRuleStart` and the `TryParseRule` membership check), `OneOfRule.cs` for the parallel `LookaheadFirstRunes` helper, `ScanWhileRule.cs` and `ScanUntilRule.cs` for sibling scan rules that publish `FirstConsumedTokens`, `FirstOfRule.cs` and `BetweenInclusiveRule.cs` to confirm where `CannotMatchLookahead` actually fires, plus `Rule.CannotMatchLookahead` and `Lexer.TryPeekRune`.
    - Categories: lookahead-shortcut soundness for negation rules, multi-rune-cluster vs. rune-only set interaction, parallel between OneOf's positive `LookaheadFirstRunes` and NoneOf's complement-style derivation, EOF / lone-surrogate handling on the FirstOf shortcut path.
    - Found and fixed (n8no): `NoneOfRule.ComputeRuleStart` returned `~_set` (or `~_set.RunesOnlyPart`) as `FirstConsumedTokens`, but the existing comment only justified the multi-rune-entry-head case and missed the inverse: a rune r that IS in `_set.RunesOnlyPart` can still be the first rune of a multi-rune cluster the set doesn't list, and NoneOf reads a whole token, so that cluster passes. With the buggy formula, `FirstOfRule`'s peek-and-skip shortcut wrongly excluded NoneOf branches when the next input was a multi-rune cluster (e + combining acute, ZWJ family emoji whose head rune was in the set, regional-indicator pair starting with a listed rune). Most likely to bite grammars compiled with `Compile(null)` (no normalization), but also any grammar where `_set.RunesOnlyPart` overlaps with the first runes of NFC-stable multi-rune clusters. Fix: return `TokenSet.Universe`, since the parser can't enumerate every cluster that could start with r and pass NoneOf. Disables the FirstOfRule lookahead shortcut for NoneOf branches, restoring pre-shortcut "always try" behavior. Regression test in `NoneOfRuleTests.NoneOf_in_FirstOf_matches_multi_rune_grapheme_starting_with_excluded_rune`. Full suite: 1868 / 1870 pass (2 pre-existing skips), state-machine tests 94 / 94.
    - Sibling-rule check: `ScanWhileRule` and `OneOfRule` use `LookaheadFirstRunes(_set)` which adds first runes of multi-rune entries to the rune intervals, sound because OneOf / ScanWhile only match tokens IN the set. `ScanUntilRule`'s stop-set has the inverse semantics (scan WHILE NOT in stop set) but already publishes `Universe` for its FirstConsumedTokens via the rule defaults, so it isn't affected. The bug was specific to NoneOf's negation-style derivation.
