    - Categories: cross-grammar shared-subrule corruption, form-conflict detection scope, Compile re-entry into sealed subgraphs, anonymous-id collisions across independent compiles, idempotency of Compile, surrogate handling in `TokenSet.Contains(string)` (already fixed in master per the user note that closed the 2026-05-19 attempt), XID exception-table coverage vs Unicode 17 UCD (already pinned in `2026-05-05`).
    - Initial finding: `Rule.Compile(NormalizationForm?)`'s `if (_sealed)` early return only checks the receiver. A new compile from a different root that reaches an already-sealed subrule walks straight past it and into `CollectNormalizationOffendersAll`, which rewrites `Literal._expected` / `OneOf._set` / etc. into the new form. The first root's parses then break on input they previously accepted. Worked through three rounds of fixes:
        - Round 1 (rejected). Added `CheckSubtreeFormConflict` to reject form mismatches. Not enough: catches form drift but not the wider problem of two distinct rules sharing a custom-range SymbolId after independent compiles.
        - Round 2 (rejected). Widened `CollectExplicitIds`'s duplicate-id check to fire for any `_idAssigned` rule, not just `_idUserExplicit`. Broke 8 E2E grammar tests that exhibited the exact pattern (HtmlGrammar.Comment.Parse + HtmlGrammar.Attribute.Parse colliding at the same anonymous slot).
        - Round 3 (rejected). Added a construction-time fresh-child check on `Rule(...)` and `SetChildren`. Catches the explicit `Or(compiledRule1, compiledRule2)` misuse, but misses the static-grammar pattern where the composite was built before any sub-rule was independently `.Parse(...)`'d.
        - Round 4 (landed). Strict "fresh-tree" invariant: `Compile` walks the graph and rejects if *any* reachable rule is already sealed. One walk replaces all three earlier checks (form-conflict, id-collision, construction-time fresh-child). The trade-off is that the "library of shared static sub-rules across multiple grammars" pattern stops working once any of the sub-rules has been individually `.Parse(...)`'d. Grammar files that want to expose multiple test-target rules sharing sub-rules now compile them in a single eager pass at type init.
    - Fix at `Rule.cs`: added `CheckNoSealedReachableRules` recursive walk and called it at the top of `Compile` after the idempotent-`_sealed` early return. Updated `Pre_compiled_sub_rule_cannot_be_used_in_a_new_grammar` in `IdAssignmentTests.cs` (renamed and pointed at `doc.Compile()` instead of the `And(...)` constructor) plus two new regression tests in `NormalizationTests.cs` (`Compile_a_second_root_with_a_different_form_on_a_shared_subrule_throws`, `Compile_a_second_root_does_not_silently_change_a_shared_subrule`). Updated grammar fixtures to satisfy the strict invariant: `HtmlGrammar`, `CssGrammar`, and `BacklogGrammar` each got a static constructor that calls `RootRule.Compile()` once at type-init time. `PrologGrammar` got a static constructor that wraps `Standard.Document` / `Htn.Document` / `Standard.Query` / `Htn.Query` in an aggregate `Or(...)` and compiles that, so every shared sub-rule across both grammar bundles is sealed in one pass. Two CssGrammar test cases (`Hex_color_requires_3_or_6_digits`, `Identifier_rejects_leading_digit`) and one Prolog test (`Cpp_optional_whitespace_corpus_parses`) dropped a redundant `And(rule, Eof())` wrap in favor of direct `.Parse(...)` (default `AllowTrailingInput = false` already enforces full-consumption).
