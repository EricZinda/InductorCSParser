- 2026-05-05: WithinToken sub-lexer made transparent
    - Reviewed: `WithinTokenRule.cs`, `Lexing/Lexer.cs`, `ScanUntilRule.cs`, `OrRule.cs`, `BetweenInclusiveRule.cs`, plus every other rule that touches `lexer.Input` / `lexer.Position`. The audit was looking for the same `Input.Length`-vs-`_endPosition` pattern that 9scu's loop-condition fix patched at one site.
    - Reworked the sub-lexer to own a substring of just the outer token's runes instead of sharing the outer string and bounding via `_endPosition`. `lexer.Input`, `lexer.Position`, `lexer.IsEof`, `lexer.DeepestFailure`, and `Read()`/Token offsets are all now expressed in coordinates of that substring. The previously-tacit "use IsEof, not Input.Length" convention is now impossible to violate: rules can use either form and stay correct, and any user-defined `Rule` subclass following the same pattern is safe by default. WithinToken translates sub-lexer positions back to outer-input coordinates via `+ token.Offset` for the outer parse's deepest-failure tracking.
    - Cost: one short substring allocation per WithinToken match (typically 1-4 chars per cluster). WithinToken fires at one-cluster granularity, not in a tight inner loop.
    - Side-effect fix: `OrRule` and `BetweenInclusiveRule` peek with `if (pos < input.Length) { Lexer.TryPeekRune(input, pos, ...); }`. Pre-change, in a sub-lexer at IsEof that condition could be true (because `input.Length` was the FULL outer length) so the peek read content from past the sub-lexer's bound. Harmless for parse outcomes (the inner rule failed at IsEof either way) but incorrect in principle. With the substring approach, `input.Length` is the readable bound, so the check is meaningful.
    - Verified by reverting the 9scu loop-condition fix temporarily and confirming the regression tests still pass against the substring-only change, then restoring the IsEof form (both correct, IsEof reads cleaner). Full suite: 1833 / 1835 pass.
