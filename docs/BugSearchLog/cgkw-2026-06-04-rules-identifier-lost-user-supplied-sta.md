    - Adjacent fix in the same pass: while reviewing `TryGetMultiPieceConversion`, noticed a pre-existing leak in the public `WithCompatibilityEquivalents` API. When a source entry is NON-form-stable but its NFKx is a SINGLE piece (e.g. U+212B ANGSTROM SIGN -> U+00C5, a 1-rune-to-1-rune compatibility singleton, or "e + combining acute" -> precomposed U+00E9 under FormC), the old loop returned false from the multi-piece predicate and fell through to `newIntervals.Add(rune)` / `newGraphemes.Add(entry)`, keeping the un-normalized original verbatim. The form-equivalent rune was never added, so `TokenSet.Single(0x212B).WithCompatibilityEquivalents(FormC).ContainsRune(0x00C5)` returned false. Masked in practice because `OneOfRule.NormalizeAndValidate.NormalizedFor` re-projects every entry at OneOf compile time, and for `IdentifierRule` the source sets carry no multi-rune grapheme entries (RejectMultiRuneGraphemes in Rules.Identifier blocks them). But the public API was visibly wrong for any external caller that inspected the returned `TokenSet` directly. Fix: replaced the multi-piece-only predicate at the WithCompatibilityEquivalents callers with `TryGetNormalizedConversion` (returns true for any non-form-stable entry) plus a new `AddProjectedConversion` helper that routes multi-piece results through `AddPieces` (split) and single-piece results to the right bucket (single rune to intervals, single-grapheme multi-rune cluster to graphemes). Regression test: `WithCompatibilityEquivalents_projects_single_piece_non_form_stable_entries` in [NormalizationTests.cs](../../src/InductorParser.Tests/Core/NormalizationTests.cs). Full suite: 7147 pass, 2 skipped (`[Test, Explicit]` UCD-fetch checks), 0 fail.
