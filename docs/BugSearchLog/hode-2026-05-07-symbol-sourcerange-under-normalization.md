- 2026-05-07: Symbol.SourceRange under normalization
    - Reviewed: `SyntaxTree/Symbol.cs` (the `SourceRange` getter, `FindFirstLeaf` / `FindLastLeaf`, the `MemoryMarshal.TryGetString` extraction), `SyntaxTree/SourcePosition.cs`, `SyntaxTree/SourcePositionConverter.cs`, `Lexing/NormalizedPositionMap.cs` (already used by `Rule.ParseRecursive`'s failure path but not by `Symbol.SourceRange` pre-fix), `Rule.ParseRecursive` (where `input` and `parseInput` diverge), `ExperimentalSrc/InductorParser/StateMachine/StateMachineParser.cs` (parallel normalization path for the SM engine), `ParseResult.cs` (which already holds the caller's `_input` and the grammar's NormalizationForm), and the leaf-construction sites in `GraphemeRule.cs` / `LiteralRule.cs` / `LiteralIgnoreAsciiCaseRule.cs` / `OneOfRule.cs` / `NoneOfRule.cs` / `AnyTokenRule.cs` / `WithinTokenRule.cs` / `ScanWhileRule.cs` / `ScanUntilRule.cs` (all build leaf memory from `lexer.Input.AsMemory(...)` or `token.Memory`, both pointing at parseInput).
    - Cross-checked the existing `SymbolPositionTests.cs` and `NormalizationTests.cs` to confirm the shape was uncovered: SymbolPositionTests never compiled with a non-default form or fed a non-NFC input, NormalizationTests only verified `ParseResult.ErrorCharIndex` translation. The systematic `NormalizationExamples` matrix landed before this hunt; we leveraged it for the regression coverage instead of hand-rolling per-grapheme cases.
    - Categories: original-input vs. parseInput coordinate confusion in tree-position APIs, asymmetry between `ParseResult.ErrorCharIndex` (translated) and `Symbol.SourceRange` (pre-fix untranslated), FormKC / FormKD per-grapheme expansion (ligature `ﬁ` → "f" + "i") as a multi-leaf-shares-one-original-cluster edge.
    - Found and fixed (ysrc): `Symbol.SourceRange` built positions against the underlying string of the leaf memory, which is parseInput. When parseInput differed by reference from the caller's input (decomposed input under FormC, precomposed input under FormD, ligature input under FormKC, Vietnamese non-canonical-order input, Devanagari composition exclusions, etc.), the returned CharIndex / TokenIndex / Line / Column were all in parseInput coordinates and disagreed with `ParseResult.ErrorCharIndex`. The XML doc on `Symbol.SourceRange` claimed "the span in the original input string". The existing `normalized-input-leaks-into-user-facing-strings.md` pattern doc explicitly extended that claim to `Symbol.SourceRange`. Both were aspirational pre-fix.
    - Fix: moved the position-translation responsibility off Symbol and onto ParseResult, where the caller's `_input` and the grammar's `NormalizationForm` already live. `Symbol.SourceRange` removed entirely; `Symbol` exposes an internal `TryGetCharSpan(out string parseInput, out int start, out int endExclusive)` helper that walks to the leftmost / rightmost leaf and recovers the parseInput-relative bounds via `MemoryMarshal.TryGetString`. New public `ParseResult.SourceRangeOf(Symbol)` consumes that span and routes both endpoints through `NormalizedPositionMap.TranslateToOriginal` when parseInput differs from `_input` by reference; identity case (Normalize returned the same string) and default-constructed ParseResult both fall through to using parseInput coords directly. Considered but rejected: a `ConditionalWeakTable<string, ParseInputMap>` keyed on parseInput (works but introduces global state and a theoretical reference-reuse pitfall if a future runtime intern Normalize results), and a per-Symbol `ParseInputMap` reference field (~8 bytes per Symbol on million-leaf trees, plus plumbing through 9 leaf-emitting rules + the SM engine + WithinToken's sub-lexer). The ParseResult-method approach has zero per-Symbol cost, no global state, and naturally mirrors how `ParseResult.ErrorCharIndex` already centralizes the position-translation responsibility for failures.
    - Migration cost: ~40 call sites replaced `symbol.SourceRange` with `result.SourceRangeOf(symbol)`. All in `SymbolPositionTests.cs` and one in `Primer2Examples.cs`. No leaf-construction sites in any rule changed, no Lexer plumbing, no state-machine changes beyond removing the brief ParseInputMap.Register call that an earlier draft of the fix added.
    - Regression coverage: 12 new test methods in `SymbolPositionTests.cs`, expanding via `[TestCaseSource]` from `NormalizationExamples.RowFormPairs` to 297 new cases. Three matrix-driven tests (Token / OneOf / Literal targets, 25 rows × 4 forms each = 100 each, of which ~30 exercise non-identity translation per fixture). Six per-rule one-shot tests at the canonical FormC + decomposed-café case (NoneOf, AnyToken, LiteralIgnoreAsciiCase, ScanWhile, ScanUntil, WithinToken). Composite-range stitching test (both endpoints translate). Column-position-unit test. FormKC ligature multi-grapheme expansion test (two leaves spawn from one source cluster, both map inside the cluster span; X afterward gets the right TokenIndex). Full SymbolPosition fixture: 329 / 329 pass under both recursive and state-machine engines. Full suite: 2683 / 2685 (2 pre-existing skips for the LoneSurrogateNotNormalizable matrix-table self-check). State-machine `.Tests` fixture: 96 / 96.
    - Adjacent shape (not pursued): `Symbol.ToString()` and `Symbol.GetUtf8ByteCount()` return the parseInput substring / byte count, not the original-input substring / byte count. That's deliberate — the leaf compared against parseInput, so its captured text is what the parser saw — and matches how `ParseResult.ErrorMessage`'s `{character}` placeholder pulls from the original while position values translate. A docstring on `ParseResult.SourceRangeOf` calls out the FormKC per-leaf-translation quirk (when one source cluster spawns multiple parseInput leaves, the per-grapheme walker gives the first leaf a zero-width range inside the cluster and the second leaf the full cluster span — quirky but defensible).
