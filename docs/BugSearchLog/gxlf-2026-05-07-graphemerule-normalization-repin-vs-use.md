- 2026-05-07: GraphemeRule normalization-repin vs. user .As(SymbolId) pin
    - Reviewed: `GraphemeRule.cs` (`CollectNormalizationOffenders`, `TrySingleRuneValue`, ctor), `Rule.cs` (`As(SymbolId)`, `As(string)`, `SetIdInternal`, `CollectPinnedIds`, `AssignNamedIds`, `AssignAnonymousIds`, `Compile(NormalizationForm?)`, the ctor's `_idAssigned` flag), `LiteralRule.cs` and `LiteralIgnoreAsciiCaseRule.cs` (their CollectNormalizationOffenders for comparison; neither touches Id), `OneOfRule.cs` and `NoneOfRule.cs` (set-projection-only, no Id touch), and the leaf-id assignment branch in every leaf-emitting rule (already covered by the z003 parse-tree-leaf-id sweep, but re-checked because this bug interacts with the rule's Id rather than the leaf's).
    - Categories: opportunistic Id assignment in a Compile-time pass that overwrites a user-supplied .As(SymbolId) pin, canonical-singleton normalization (U+212B → U+00C5 ANGSTROM, U+2126 → U+03A9 OHM, U+2329 → U+3008, U+212A → U+004B KELVIN, U+1E9E → U+00DF eszett, ...), interaction between the constructor's rune auto-pin and user-supplied .As pins, distinguishing user-pinned-custom-range ids from anon-assigned-custom-range ids and from named-hash-custom-range ids.
    - Found and fixed (xpid): `GraphemeRule.CollectNormalizationOffenders` unconditionally called `SetIdInternal(new SymbolId(runeValue))` whenever post-normalization `_expected` was single-rune. For the unnamed Token case (`Token('Ω').Compile()`) this is the documented and desired behavior: leaf ids stay consistent between `Token('Ω')` and `Token('Ω').Compile(FormC)` (covered by the existing `Token_with_singleton_decomposable_rune_repins_id` test). But for the user-pinned case (`Token('Ω').As(new SymbolId(0x200100)).Compile()`), the same code path silently overrode the user's pin: `rule.Id.Value` came back as `0x03A9` (post-normalization OMEGA rune) instead of `0x200100`. The user's `.As(SymbolId)` docstring promises "stable numbering across versions, useful when serializing parse trees"; the re-pin breaks that promise on every single-rune Token whose character is a canonical singleton. Backlog `xpid` has the write-up.
    - The fix adds an `_idUserPinned` flag to `Rule`, set by `As(SymbolId)` (not by `SetIdInternal`), and gates the GraphemeRule re-pin on `!IsUserSymbolIdPinned`. The flag preserves the existing rune-pin behavior in three cases that need it (unnamed single-rune Token, anonymous multi-rune Token, named-via-`As(string)` multi-rune Token) so leaf-id consistency between `Token('é')` and `Token("é").Compile(FormC)` still holds. One regression test in `NormalizationTests.cs` next to the existing `Token_with_singleton_decomposable_rune_repins_id` locks in the user-pinned case. Full suite: 1903 / 1905 (2 pre-existing timing skips) before the test, 1904 / 1906 after the fix.
    - Sibling check: `LiteralRule.CollectNormalizationOffenders` and `LiteralIgnoreAsciiCaseRule.CollectNormalizationOffenders` only update `_expected`, never touch Id. `OneOfRule.NormalizeAndValidate` only projects `_set`, never touches Id. So the bug surface is GraphemeRule-only.
    - Cross-cutting note: this is the same shape as bug `a000` ("Cached static analysis vs. mutated Compile-time rule data"), but on a different field (`Id` rather than `FirstConsumedTokens`). When a Compile pass mutates rule data based on normalization, every downstream consumer of the pre-mutation state needs a check for the user-override case. Added a "Compile-time auto-pin overriding user-supplied pins" pattern bullet to `docs/PotentialBugSources/` for future sweeps that touch any opportunistic Id-assignment path.
