- 2026-06-04 Position-mapping / post-parse hot paths sweep (focus: performance issues that hit real grammars)

  - Start: directed perf sweep per request ("focus on potential performance issues, things that hit real grammars"), not a random file pick. Began at the rule hot paths, then followed the trail out to the post-parse position-mapping code that every `Symbol.SourceRange` / `Symbol.SourceText` / error-position read goes through.
  - Reviewed source for redundant per-parse / per-token / per-access work: `OneOfRule`, `NoneOfRule`, `ScanWhileRule`, `ScanUntilRule`, `AndRule`, `OrRule`, `BetweenInclusiveRule`, `IdentifierRule`, `WithinTokenRule`, `LiteralRule`, `LiteralIgnoreAsciiCaseRule`, `GraphemeRule`, `AnyTokenRule`, `PeekRule`, `Token.cs`, `TokenSet.ContainsRune`/`ContainsToken`, `Lexer.cs` + `Lexer.Scanning.cs`, `GraphemeClusterIndex.cs`, `Rule.TryParse`/`ParseChild` dispatch, `SourcePosition.cs`, `SourcePositionConverter.cs`, `NormalizedPositionMap.cs`, `Symbol.SourceRange`/`SourceText`.
  - Categories checked. Per-parse recomputation of values that are pure functions of the grammar (TokenSet projections, complement / first-rune sets, rendered set strings), all computed once at construction or in `ValidateNormalization` at Compile time, clean. Per-token allocation on the matching hot path, where leaf rules collapse to the shared `Symbol.Discarded` on the Delete default and only allocate a Symbol when the tree actually keeps the node, clean. The `ReferenceEquals(original, normalized)` fast path: confirmed `string.Normalize(FormC)` returns the same instance for ASCII and for already-NFC input on .NET 5+, so ASCII grammars never hit the translation walker. O(n^2) / re-scan-from-zero patterns in the post-parse position mapping.
  - Fixed: `NormalizedPositionMap.TranslateViaLockstep` (the canonical FormC/FormD position-translation walker that every non-ASCII `SourceRange` / `SourceText` / failure-position read runs) stepped both strings with `StringInfo.GetNextTextElement(...).Length`, which allocates a substring per grapheme purely to read its length. The parser already keeps a zero-allocation per-input grapheme-boundary cache (`GraphemeClusterIndex`, whose whole stated reason for existing is to replace exactly this `GetNextTextElement` call), and the normalized side's index is already built by the lexer during the parse. Switched the walker to `GraphemeClusterIndex.For(...).LengthAt(...)` on both sides. A single deep-position translate dropped from ~1.1 MB allocated (one substring per grapheme walked) to essentially zero. Test `TranslateToOriginal_does_not_allocate_per_grapheme_walking_to_a_deep_position` in `NormalizationTests.cs` verifies it via `GC.GetAllocatedBytesForCurrentThread`.
  - Scope note: this removes the per-grapheme *allocation* on the default FormC/FormD path. The walk is still O(offset) *time* (it steps cluster-by-cluster from 0), so reading positions on every node of a large tree remains O(n^2) time overall. That deeper "cache the whole translation" lever is left for later. The compatibility-form walker `TranslateViaPerGraphemeNormalize` (FormKC/FormKD only) still allocates per grapheme, but there the `original[..].Normalize(form)` chunk call dominates and is algorithmically required, so the cached-index swap wouldn't remove its allocation. Left as-is.
  - Not bugs (verified solid, recorded so the next hunter can skip): the rule matching hot paths (no per-parse recompute, leaf allocation is gated on the tree actually keeping the node), `TokenSet.ContainsRune` linear-prefix-then-binary-search, `GraphemeClusterIndex.LengthAt` / `EnsureWalkedTo` monotonic walk, the ASCII / already-NFC `ReferenceEquals` fast path, `Token` zero-copy spans. `SourcePositionConverter.ToLineColumn` and `GraphemeClusterIndex.CountClustersUpTo` are O(charIndex) per call but allocation-free. The O(n^2)-on-a-tree-walk time cost they share with the (now allocation-free) lockstep walker is a real but bigger-scope time issue, noted above, not fixed here.
  - Unrelated pre-existing failure observed (not introduced by this change, present at HEAD): `UnicodeLiteralCanaryTests.AllNonAsciiStringLiteralsAreWrappedInCanary` fails on two raw U+309B (゛) char literals in `XidIdentifierTests.cs:687,690` that aren't wrapped in `Canary(...)`. Left alone, different domain, not this bug.
