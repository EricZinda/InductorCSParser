- 2026-05-28: TokenSet-bearing rules cached pre-projection set rendering, so the trace shows entries the rule no longer matches
    - Not a fresh random-walk sweep. Followed the explicit "Out of scope and worth a follow-up" bullet at the bottom of [tn8m-2026-05-07-scan-rules-tokenset-not-projected-under-form.md](tn8m-2026-05-07-scan-rules-tokenset-not-projected-under-form.md): the tn8m fix routed `OneOfRule.NormalizeAndValidate` through `ScanWhileRule` and `ScanUntilRule` so the runtime set actually projects under Compile's normalization form, but left the `_setRendered = set.ToString()` cache that each rule splices into its trace lines. After projection, the cache no longer reflects what the rule matches.
    - Reviewed: [OneOfRule.cs](../../src/InductorParser/OneOfRule.cs), [NoneOfRule.cs](../../src/InductorParser/NoneOfRule.cs), [ScanWhileRule.cs](../../src/InductorParser/ScanWhileRule.cs), [ScanUntilRule.cs](../../src/InductorParser/ScanUntilRule.cs) (full files for each, with focus on the constructor cache write, the CollectNormalizationOffenders override, and every TraceSuccess/TraceFailure call that splices `_setRendered`). Cross-checked [TokenSet.NormalizedFor](../../src/InductorParser/TokenSet.cs) (the projection mutation, with canonical singletons U+212A→U+004B, U+212B→U+00C5, U+2126→U+03A9 under FormC, and precomposed→decomposed multi-rune clusters under FormD), the existing `NormalizationTests.cs` coverage for the canonical-singleton trio, and [UnicodeExamples.KelvinGrapheme](../../src/InductorParser.Tests/UnicodeExamples.cs) (the Canary-wrapped U+212A constant the tests use so an editor can't silently swap it for ASCII 'K').
    - Categories swept: cached static analysis vs mutated compile-time rule data (the a000 pattern), trace-only correctness, normalization-form rule projection consistency between runtime matching and display. The recursive engine is the only consumer of `_setRendered` (the SM engine builds its own opcode-side display, doesn't read these caches).
    - Found and fixed: each of the four rules stores `_setRendered = set.ToString()` (or `_stopperRendered = stopAt.ToString()` for ScanUntil's TokenSet stopper) at construction with the `readonly` modifier. The CollectNormalizationOffenders override calls `OneOfRule.NormalizeAndValidate(this, ref _set, form, offenders)` which rewrites the `_set` field, then returns without touching the rendered string. A grammar like `OneOf(KelvinGrapheme)` (U+212A) compiled under the default FormC has `_set = {0x004B}` after Compile but the trace still reports `wanted one of '[U+212A]'`, telling a grammar author looking for a normalization mismatch the rule is matching one thing while it's actually matching another. ScanUntil's TokenSet-mode stopper (the most common shape, three of five constructors) had the same staleness in its success and unterminated-body trace lines. ScanUntil's rule-mode stopper renders as `rule <name>` and doesn't need refreshing (the inner Rule handles its own normalization through the walker's recursion into Children).
    - Fix: drop the `readonly` modifier from `_setRendered` / `_stopperRendered` in each of the four rules, and re-assign after `NormalizeAndValidate` mutates the set. One line each in the four `CollectNormalizationOffenders` overrides ([OneOfRule.cs:43-51](../../src/InductorParser/OneOfRule.cs), [NoneOfRule.cs:32-42](../../src/InductorParser/NoneOfRule.cs), [ScanWhileRule.cs:52-64](../../src/InductorParser/ScanWhileRule.cs), [ScanUntilRule.cs:236-303](../../src/InductorParser/ScanUntilRule.cs)). The rendered string lives outside the hot path (it's only read on a traced match), so re-running `set.ToString()` once per Compile pays nothing at parse time. The field-level docs were updated to call out that the cache is now refreshed by `CollectNormalizationOffenders`.
    - Tests: four parallel regression tests, one per affected rule, each driving the rule with `KelvinGrapheme` (U+212A) and asserting the trace shows `[K]` (the post-FormC projection). `OneOf_trace_set_rendering_refreshes_after_Compile_projects_the_set` exercises the SUCC path, `NoneOf_trace_set_rendering_refreshes_after_Compile_projects_the_set` exercises the FAIL path (since NoneOf fails when the token IS in the set), `ScanWhile_trace_set_rendering_refreshes_after_Compile_projects_the_set` exercises the SUCC path with a single AdvanceWhileRuneIn step, `ScanUntil_trace_stopper_rendering_refreshes_after_Compile_projects_the_set` exercises the success trace's stopper splice. Each test uses `Does.Contain('[K]')` / exact-output `Lines(...)` depending on what the rule's trace shape supports. Verified all four catch the bug: reverted the NoneOf fix to the bare `NormalizeAndValidate` call, re-ran the NoneOf test, it failed with `wanted one not in '[U+212A]'` (the stale cache) vs expected `[K]`. Restored the fix, re-ran to confirm green.
    - Full `InductorParser.Tests` suite: 6926 / 6928 pass with the two long-standing skips (timing / Unicode UCD probes), no other regressions. The new tests added 4 to the recursive-engine count.
    - Pattern reference: this is a fresh instance of the `a000-cached-static-analysis-vs-mutated-compile-time-rule-data.md` pattern. That pattern doc already names the rule-level data caches that get rewritten by Compile and the static-analysis fields that read them. The addition is that trace-display caches sit in the same shape and need the same invalidation discipline. No new pattern doc, since the existing one covers the shape directly.
