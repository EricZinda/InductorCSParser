    - Bug filed + fixed (doc bug): the "Zero-Width and Invisible Format Characters" section lumped the joiners in with genuinely-breaking format chars and said all of them "come through as their own tokens." Empirically, StringInfo.GetTextElementEnumerator splits "a‍b" into TWO clusters [a+ZWJ][b], and "a‌b" into [a+ZWNJ][b], because ZWJ has Grapheme_Cluster_Break = ZWJ and ZWNJ has GCB = Extend, both covered by GB9, which keeps Extend and ZWJ attached to the preceding character. Only ZWSP (U+200B) and the soft hyphen (U+00AD), which have GCB = Other, actually break and lex as their own single-rune token. A joiner stands alone only at the very start of input, where nothing precedes it ("‍a" is [ZWJ][a]). User-visible consequence is a maintainer/reader hazard: someone trusting the claim would expect a trailing ZWNJ on "café‌" to be a filterable standalone token, when it's actually glued into the last grapheme, so Literal("café") fails for a different reason than the doc implies. The rune-level strip recipe below the claim still works (it filters by rune value, not by token), so no code changed.
