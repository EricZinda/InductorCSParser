- 2026-05-08: CollectPinnedIds pin-conflict detection vs. pre-compiled rules
    - Started in `LateBoundRule.cs` (random number 7 mod 27 = LateBoundRule). Sibling sweep: `NotRule.cs`, `PeekRule.cs`, `AnyTokenRule.cs`, `WithinTokenRule.cs`, `EofRule.cs`. None of those landed a bug after re-reading their TryParse / ComputeRuleStart shapes against the existing pattern docs. Followed a thread out into `Rule.cs`'s id-assignment passes (`CollectPinnedIds`, `AssignNamedIds`, `AssignAnonymousIds`) since `IdAssignmentTests.cs` was the last `wnfw-...` backlog item and pinned-id-conflict-detection wasn't covered against pre-compiled sub-rules. Cross-checked existing tests in `IdAssignmentTests.cs`, `NameOfTests.cs`, `NormalizationTests.cs`, `CompileTests.cs`. The "two reachable rules pinned to the same SymbolId fail" check existed for the all-unsealed shape but had no pre-compiled-sub-rule variant.
    - Categories: pin / id-assignment integrity, two-step Compile (sub-rule first, larger grammar second), proxy-flag check (`!_sealed`) drifting from the actual property it was meant to test (`_idUserPinned`).
    - Found and fixed (z2pn): `CollectPinnedIds` used `!r._sealed && idValue >= CustomRangeStart` to gate the conflict check on whether the rule is "user pinned." The `!_sealed` half conflated "rule wasn't pre-compiled" with "rule wasn't user-pinned." A sub-rule that the user pinned via `.As(SymbolId.Custom(N))` and then pre-compiled standalone (sealed) silently dropped out of the conflict-detection map, so a second rule in the larger grammar with the same pin won the slot uncontested. The conflict went undetected and `Tree.Find` against either rule returned the same nodes regardless of which rule actually matched. Fix: gate on `r._idUserPinned` (set only by `.As(SymbolId)`, persists through sealing) instead of `!r._sealed`. Pre-compiled anonymous rules still don't participate (their `_idUserPinned` is false), and rune-range pre-pins (Token('a').Id == 0x61 from the constructor) still don't participate either way (the `>= CustomRangeStart` half of the gate stays). Added the regression test `Pre_compiled_sub_rule_pin_collides_with_unsealed_sibling_pin` in `IdAssignmentTests.cs`.
    - Adjacent shape (not pursued): the same "what does `_sealed` actually mean here" confusion could exist in other Compile-pass gates. `AssignNamedIds` and `AssignAnonymousIds` only check `_idAssigned`, so they're immune. `ComputeRuleStartAll` writes the rule's start fields without an `IsSealed` check, so a pre-compiled sub-rule's start fields get re-written each time the larger grammar is compiled — but the value computed is the same as last time (post-order walk, child fields already populated, no incoming state matters), so this is a wasted-write rather than a soundness issue. Worth a follow-up if benchmark traces show repeated Compiles dominating, otherwise leave alone.
