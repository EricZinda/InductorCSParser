- 2026-06-03: UnicodeGotchas.md "Python 3 identifiers" and "Rust identifiers" recipes throw `InvalidOperationException` at Compile time because the doc passes the normalization form to `Compile` but not to `Identifier`
    - Starting area: user-directed focus on `docs/`. Walked every code-fence in every doc that has examples (`primer1`, `primer2`, `Primer3`, `Primer4`, `Recipes`, `tutorial-peek`, `InductorParserReference`, `UnicodeGotchas`, `InductorParserDesignDecisions`). Cross-referenced each runnable snippet against the matching test file under `src/InductorParser.Tests/DocExamples/`. Tests for snippets that take an `extraStartRunes` parameter look at `Rules.Identifier` and the existing `UnicodeGotchasExamples.Python3_identifier_recipe` test caught my eye because the test calls `Identifier(NormalizationForm.FormKC, ...)` while the doc snippet calls `Identifier(extraStartRunes: ...)` (no form). A test that silently corrects what the doc says is a classic doc-drift indicator.
    - Found and fixed (doc bug, not engine): UnicodeGotchas.md "Matching specific languages" gives a Python 3 recipe and a Rust recipe (same profile, same shape). Both are written as:
      ```csharp
      var python = Identifier(extraStartRunes: TokenSet.Runes("_"))
          .Compile(NormalizationForm.FormKC);
      ```
      `Rules.Identifier` (signature `Identifier(NormalizationForm? form = NormalizationForm.FormC, TokenSet extraStartRunes = default, TokenSet extraBodyRunes = default)`) uses its `form` parameter to pre-expand XidStart and XidContinue: under FormKC, those sets contain entries (ligatures like U+0132 IJ -> "IJ", U+0133 ij -> "ij", fullwidth Latin, math-bold) whose NFKC conversion is a multi-grapheme sequence that a OneOf rule can't match as a single token. The function's own internal comment ends with "Pass the same form to Compile afterward." The doc snippet doesn't: it lets `form` default to FormC and then calls `Compile(FormKC)`. The Compile-time form check then finds every unexpanded entry, throws `InvalidOperationException`, and reports "Compile failed: 1549 rules have expected text that isn't in FormKC" with a per-entry list of how to fix it. Probed in a scratch test against the live library: the doc-as-written form throws immediately at `.Compile(FormKC)` before any input is ever parsed.
    - Why it hid: the test for this recipe ([UnicodeGotchasExamples.Python3_identifier_recipe](../../src/InductorParser.Tests/DocExamples/UnicodeGotchasExamples.cs)) reads `Identifier(NormalizationForm.FormKC, extraStartRunes: TokenSet.Runes("_"))`, which silently corrects the doc by passing FormKC positionally. The test passes. The doc doesn't. That's the gap an automated "code in doc must compile" check would catch but no human reviewer has: a test that doesn't match its own doc string is invisible if both pass on their own terms. The Rust recipe sits right next to the Python one in the same doc with the same wrong shape, but had no test of its own.
    - Fix: [UnicodeGotchas.md](../UnicodeGotchas.md) now reads:
      ```csharp
      var python = Identifier(form: NormalizationForm.FormKC,
                              extraStartRunes: TokenSet.Runes("_"))
          .Compile(NormalizationForm.FormKC);
      ```
      (and the same for Rust). The named-arg form keeps the snippet readable. The FormKC repetition is intentional because Identifier and Compile each need it for different reasons (pre-expand the sets vs. validate / normalize at parse time), and the doc now has a paragraph between the Python and Rust blocks explaining that. Three test changes in [UnicodeGotchasExamples.cs](../../src/InductorParser.Tests/DocExamples/UnicodeGotchasExamples.cs). (1) The existing `Python3_identifier_recipe` test now uses the named-arg form too, so the test and the doc snippet are character-for-character identical except for variable name. (2) New `Rust_identifier_recipe` covering the second snippet for the same reason. (3) New `Identifier_default_form_with_FormKC_compile_throws` that asserts the doc-as-was form (`Identifier(extraStartRunes: ...).Compile(FormKC)`) throws `InvalidOperationException`, locking in the requirement so a future "let's simplify the snippets" attempt that removes the `form:` line surfaces as a failing assertion explaining why. `dotnet test --filter FullyQualifiedName~DocExamples` => 61/61 pass (59 prior + 2 new).
