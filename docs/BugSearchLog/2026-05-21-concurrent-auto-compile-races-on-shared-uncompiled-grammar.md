- 2026-05-21: thread-safety sweep, plus the auto-compile-on-first-parse race (resolved as by-design + docs)
    - User asked for a multithreading bug. Skipped the random-file pick and swept the shared-mutable-state surface that survives a parse: `Rule.cs` (Parse / ParseRecursive / Compile and all its passes, TryParse, ParseChild, the lazy `_nameIndex` / `_idByNameIndex`), `Symbol.cs` (SourceRange / SourceText / DisplayName / Is recompute every call, no cache), `ParseContext.cs` / `ParseResult.cs` (immutable, error positions recompute, no cache), `ParseOptions.cs` / `ParseCancellation.cs` (per-call, ParseCancellation flag is volatile), `Lexer.cs` (per-parse or pooled-per-thread, re-bound via ResetForReuse), `TokenSet.cs` (immutable readonly struct, with `_normalizedCache` / `_categoryCache` ConcurrentDictionary and the Xid / Letters / Digits builders Lazy in the thread-safe default mode), `SourcePositionConverter.cs` / `NormalizedPositionMap.cs` (stateless statics), and `GraphemeClusterIndex.cs` (the 2026-05-20 per-instance-lock fix, re-read end-to-end, with the volatile `_walkedTo` / `_exhausted` handshake correct).
    - Conclusion on the documented guarantee: a *compiled* grammar is genuinely thread-safe for concurrent parsing. Nothing in TryParse writes shared rule state (every `_field =` in the rule subclasses is in a constructor or a Compile pass, never in TryParse), each Parse builds its own Lexer / Symbol tree / ParseResult, the lazy name indexes are benign (each thread builds a complete local Dictionary, only the final reference publish is shared), and the per-input grapheme cache is internally locked. So the "build once, parse many times across threads" model holds for the compiled grammar.
    - Found, then resolved as by-design: `Rule.ParseRecursive` (and `NameOf` / `IdOf`) auto-compile with a bare `if (!_sealed) Compile();`. Compile mutates per-node state across many passes and the passes don't re-check the seal flag mid-walk, so two threads sharing an *uncompiled* grammar both run the mutating passes at once. The visible symptom is a spurious `InvalidOperationException` out of `CheckNoSealedReachableRules` ("...has already been compiled and can't be reused in another grammar"), plus rarer result divergence. Reproduced reliably with a barrier-synchronized stress test (threw at trial 7 of 200). An initial fix serialized the auto-compile behind a per-root lock with a volatile seal flag, but on review (with the maintainer) the decision was that compilation is a single-threaded build step and doesn't need to be thread-safe: the caller compiles once, then shares the compiled grammar. Making Compile thread-safe would put a volatile read and a gate allocation on the parse path for a case that's really caller misuse, so the lock fix was reverted.
    - What landed instead: (1) a "Thread Safety" section in `docs/InductorParserReference.md` spelling out the rules. Compile once single-threaded, then parse from any number of threads with no synchronization. Sharing an uncompiled grammar across threads races the auto-compile and isn't supported, so compile up front via `.Compile()` or one warm-up parse. The section also covers the shared per-input grapheme cache, ParseCancellation, ParseOptions, and TraceSink. (2) A short design-note comment at the top of `Rule.Compile` so a future hunter doesn't re-add the lock. (3) A regression test `Core/CompileTests.cs` `Concurrent_parsing_of_a_compiled_grammar_is_thread_safe` that compiles up front, then hammers the same input from many barrier-released threads and asserts every result matches the single-threaded baseline with no exceptions, which catches a future parse-time shared-state regression. Full suite green (6884 tests).
    - Pattern: docs/PotentialBugSources/2026-05-21-lazy-one-time-init-auto-triggered-from-a-shared-path.md (the broader category, "a lazy one-time multi-pass initialization auto-triggered from a hot/shared path"), reframed to capture the real lesson: the fix is sometimes a lock and sometimes a documented single-threaded responsibility, so weigh which before adding synchronization.
    - Cleared (re-confirmed safe, not bugs): the lazy `_nameIndex` / `_idByNameIndex` build (benign double-build, complete-then-publish). TokenSet's value-based caches (ConcurrentDictionary GetOrAdd / TryAdd, value-equal results). GraphemeClusterIndex's lock + volatile handshake. The pooled-Lexer reuse (per-thread, reset via ResetForReuse). The deterministic, idempotent nature of the Compile passes themselves (id assignment is DFS-order / FNV-hash stable, so concurrent compiles wouldn't produce *different* ids, which is why the corruption surfaces as a thrown exception far more often than as a divergent result).
