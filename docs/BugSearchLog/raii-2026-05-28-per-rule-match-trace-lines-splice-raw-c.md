    - Categories swept: LateBoundRule / AliasRule transparency and flatten-forwarding correctness (clean), And/Or/Not/Peek Preserve-vs-Flatten child plumbing (clean), and trace-line layout when matched token text or stored expected text holds a control / line-separator rune (the bug).
    - Found and fixed: every rule's own `found '...'` / `wanted '...'` / `token '...'` trace body splices the matched input text (`lexer.Input.Substring(token.Offset, token.Length)`, or `AsSpan` in WithinToken) or the rule's stored `_expected` literal verbatim. For a token / literal holding a Control (Cc), LineSeparator (Zl), or ParagraphSeparator (Zp) char (a `Token('\n').Preserve()` match, an LF / CR captured by `OneOf(LineTerminators)`, a CRLF cluster, a `LiteralIgnoreAsciiCase("a\nb")` whose ASCII-only pattern still allows C0 controls), the splice dumps a raw CR / LF into the middle of the SUCC / FAIL line and the one-event-per-line layout downstream trace assertions rely on breaks into pieces. This is the exact follow-up the 2026-05-27 `Lexer.Read` fix named but left undone: that fix escaped `Lexer.Read`'s line and built the shared `DisplayEscape` helper, but the per-rule lines still quoted raw text. `Lexer.Read` and the rule line both fire for the same token, so the leak survived at the rule layer.
    - Fix (root-cause, not per-caller): the escaping moved into `TraceInterpolatedStringHandler` itself. Its three `AppendFormatted` overloads (generic `<T>`, `string`, `ReadOnlySpan<char>`) now route every interpolation hole through `DisplayEscape.AppendEscaped`, so any dynamic value spliced into a `$"..."` trace body, matched token text, a stored `_expected`, a set rendering, a count, gets Cc/Zl/Zp chars rewritten to U+XXXX automatically. `AppendLiteral` (the author-written scaffolding between holes) stays verbatim. This makes "one trace event renders as one physical line" an invariant the handler enforces rather than a rule every trace caller has to remember, which is exactly the gap that let the 2026-05-27 fix close three sites and miss the eight rule-layer ones. Escaping is idempotent and `AppendEscaped` writes straight into the builder with no intermediate allocation, and it only runs on the tracing-on path (the handler's `shouldAppend` gate), so a tracing-off parse still pays nothing. Existing trace assertions over printable text (`wanted 'a'`, `found 'maj'`) are byte-for-byte unchanged.
    - Because the handler does it, the per-caller escaping was removed: the 8 rule files keep their original raw `lexer.Input.Substring(...)` / `_expected` / `AsSpan` splices (reverted to HEAD), and `Lexer.Read`'s explicit `DisplayEscape.Escape(...)` call from the 2026-05-27 fix was reverted to a raw substring too (the handler now covers it). `SymbolExtensions.PrintTree` and `TokenSet.ToString` keep their explicit `DisplayEscape` calls: they build display strings directly, not through the trace handler, so the handler can't reach them. `DisplayEscape.Escape(string, offset, length)` now has no production caller (Lexer.Read was its only one) but is kept as the return-a-string companion to `AppendEscaped`, still covered by `DisplayEscapeTests`.

The first three fail on a clean checkout (the diff shows a raw `\n` spliced into the line, e.g. `found '\n'` instead of `found 'U+000A'`). All four pass with the fix. The handler's own `Off_path_does_not_evaluate_interpolated_arguments` / `On_path_evaluates_interpolated_arguments_exactly_once` deferral tests still pass (the escape runs after the hole is evaluated, so it doesn't disturb evaluation timing or count).
