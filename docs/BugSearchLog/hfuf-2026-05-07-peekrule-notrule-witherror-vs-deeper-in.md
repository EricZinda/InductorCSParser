- 2026-05-07: PeekRule / NotRule WithError vs deeper inner-recorded failures
    - Random starting point: picked file index 18 from the `src/InductorParser/` listing (alphabetical, excluding subdirectory contents) which lands on `PeekRule.cs`. Read its sibling lookahead rule `NotRule.cs` side-by-side because they share the "lookahead transaction, throw away inner's symbols, succeed iff inner's outcome matches" shape. The deepest-failure interaction below applies symmetrically to both.
    - Reviewed: `PeekRule.cs`, `NotRule.cs`, `Rule.TryParse` and `Rule.ParseChild` (the outputSymbols rollback and `effectiveFlattenType` normalization), `Lexer.RecordFailure` (the deepest-wins / equal-depth-claim policy on lines 428-443), `Lexer.BeginTransaction` and the `Transaction.Dispose` rollback, `BuildErrorMessage` (the customMessage / EOF / positional-template fallback path that decides what `ParseResult.ErrorMessage` ends up showing), the existing `WithErrorTests` (deepest-failure-wins baselines), `PeekRuleTests` and `NotRuleTests` (existing WithError assertions that only cover the equal-depth case where inner is a single-token rule). Cross-checked the `EofRule.cs` failure path for the same shape (it doesn't open a transaction so it records at `lexer.Position` directly; equivalent to PeekRule's start when inner is also zero-width-equivalent).
    - Categories: WithError-message suppression by deeper inner-recorded failures, lookahead-rule failure-position policy (start-of-lookahead vs deepest-during-inner), Or-alternative orphan deepest records surviving past the alternative's rollback, equal-depth-message-claim rule's reliance on the rule's own RecordFailure landing AT the deepest position, recursive engine vs SM engine parallelism (SM mirrors the same RecordFailure semantics so the same fix shape applies if the SM ever lowers Peek / Not — currently it bridges to recursive for both, so no SM change here).
    - Found and fixed (ympk): both `PeekRule.TryParseRule` (lines 25-40) and `NotRule.TryParseRule` (lines 33-52) called `lexer.RecordFailure(transaction.StartPosition, ErrorMessage)` on the failure path. When inner is a multi-token rule (`Literal("ab")`) or a composite that explores non-taken paths (`Or(...)` whose first alternative consumes some input before failing), inner's own RecordFailure at the deeper position survives the inner's rollback (DeepestFailure is a high-water mark, not transaction-rolled-back). The outer rule's RecordFailure at the start position is shallower than that orphan deepest, so the deepest-wins rule ignores it and the equal-depth-claim rule never fires. The user-supplied `WithError` is silently dropped and `ParseResult.ErrorMessage` falls back to the generic positional or end-of-input template. Repro: `Peek(Literal("ab")).WithError("expected 'ab' ahead").Parse("ax")` yields `Parse failed at offset 1: unexpected 'x'.` and `Not(Or(Literal("ab"), Literal("a"))).WithError("...").Parse("a")` yields `Unexpected end of input.`. The fix adds a `bool force = false` parameter to `Lexer.RecordFailure` that, when set, bypasses the deepest-wins comparison and unconditionally replaces both position and message slots. PeekRule and NotRule pass `force: ErrorMessage != null` on their failure paths so a user-supplied WithError lands at the lookahead anchor regardless of how far inner ran. The `ErrorMessage != null` gate matters: forcing a null message would overwrite any inner WithError that did manage to claim the slot, dropping inner's friendly message in the (Peek-without-its-own-WithError-wrapping-an-inner-with-WithError) case.
    - Considered the alternative shape of snapshotting `DeepestFailure` and `DeepestFailureMessage` before inner runs and rolling them back via an internal `RollbackDeepestFailureTo` Lexer method (the position-counterpart of the transaction's rollback). That preserves earlier-deeper records from outside the lookahead (a sibling Or alternative that reached past the lookahead's anchor), while the force-flag approach lets a Peek/Not with WithError overwrite that earlier record. The force-flag wins on simplicity (one parameter on an existing API vs. a new method plus snapshot bookkeeping at every call site), and the trade-off matches user intent: a grammar author who wrote `.WithError` on a Peek/Not is explicitly asking for their message to surface, so letting it dominate even an outside-the-lookahead deeper record is the desired behavior. Recorded here so a future reader knows the snapshot-rollback shape was considered and consciously declined.
    - Two regression tests in `PeekRuleTests` / `NotRuleTests` lock in the post-fix behavior: `Peek_WithError_surfaces_at_lookahead_anchor_when_inner_records_a_deeper_failure` (Peek + Literal("ab") on "ax", asserts both anchor position and WithError message), `Not_WithError_surfaces_at_lookahead_anchor_when_inner_Or_records_a_deeper_orphan_failure` (Not + Or(Literal("ab"), Literal("a")) on "a", same assertions). Existing `Peek_fails_when_inner_fails` and `Not_fails_when_inner_matches` still pass: in those grammars inner's failure happens AT the start position, so the force flag pins the deepest where the equal-depth claim rule was already putting it.
    - Pattern doc `shallower-witherror-vs-deeper-orphan-deepest.md` describes the broader pattern (any rule whose failure position is shallower than where its inner subtree records can have its WithError silently suppressed by orphan deeper records). Reviewer mental model: any rule that opens a transaction, runs an inner rule, and rolls back regardless of inner's outcome has to think about whether the deepest-failure marker moved during inner's run, because the marker survives the rollback.
