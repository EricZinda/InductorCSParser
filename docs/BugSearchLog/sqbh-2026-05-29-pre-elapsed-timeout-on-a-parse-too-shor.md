    - Behavior confirmed: the periodic budget check fires only on 1024-invocation boundaries, so a parse that completes in fewer invocations (e.g. `Token('a').Parse("a")`) never polls the clock and a one-tick `Timeout` on it returns Success rather than Timeout. Reproduced directly.
    - Outcome: this is by design, not a bug. `Timeout` is best-effort. The deadline is there to stop a long-running or runaway parse, which by definition runs long enough to hit a periodic check, so the budget reliably trips on the parses it's meant to catch. A parse that finishes before the first check is already fast, so completing it and returning the real result is the right call rather than retroactively failing finished work. The correct response is documentation, not code: re-polling the clock at parse end was considered and rejected. This is the opposite of the cancellation flavor (fixed 2026-05-19): there a caller explicitly called Cancel() before parsing and being ignored violates the ParseCancellation doc, here nobody set anything and the wall clock simply hadn't run out at the one point it gets checked.
