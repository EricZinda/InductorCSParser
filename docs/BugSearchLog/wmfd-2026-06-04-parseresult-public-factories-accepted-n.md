- 2026-06-04: `ParseResult` public factories accepted null required arguments, allowing contradictory custom-driver results
    - Random start: picked `707520`, so `707520 mod 29 = 7` over the 29 top-level `src/InductorParser/` files, landing on `INormalizationReporter.cs`. Read the normalization reporter/compile path (`INormalizationReporter`, `Rule.Compile`, `CompileNormalizationReporter`, `BuildNormalizationErrorMessage`, `GraphemeRule`, `LiteralRule`, `OneOf`/`NoneOf`/`ScanWhile`/`ScanUntil` normalization hooks) and confirmed the recent failed-compile poisoning and normalization-offender count fixes already covered the obvious mutation/reporting bugs. Followed the public-boundary path into custom-rule and custom-driver surfaces: `Rule.TryParse`/`ParseChild`, the external `LookbehindRule` tests, public lexer helpers, and `ParseResult` factories.
    - Found and fixed: `ParseResult.Succeeded`, `Failed`, and `Aborted` are public for custom parse drivers, but they didn't validate required null arguments. The sharpest case was `ParseResult.Succeeded(..., grammar: null!)`: the result carried `Outcome == Success` and caller-supplied symbols, while `Success` returned false because `_grammar == null` is the default-struct check. `Succeeded(null!, ...)` similarly reported success while `Symbols` silently collapsed to empty. `Failed`/`Aborted` accepted null `message`, `input`, or `grammar`, leaving later derived properties to degrade against an empty fallback instead of rejecting the bad factory call. Fix: `Succeeded` now rejects null `symbols`, and the shared constructor rejects null `errorMessage`, `input`, and `grammar` before applying the existing `ErrorCharIndex` range check and abort-outcome validation.
    - Verification-time fix: running the `InductorParser.ExternalContractTests` project surfaced a separate public-surface regression: the no-IVT linked copy of `WithinTokenRule.cs` failed to compile because trace-only messages called internal `RuneHelpers.RuneCount`. That breaks what `InductorParser.ExternalContractTests` is for: linked built-in rules should compile against only public + protected APIs. Fix: made `RuneHelpers` public so the existing helper methods are available to linked built-in rules and external rule authors without duplicating rune-count logic.
    - Regression: added `ParseResultFactoryTests.Factories_reject_null_required_arguments`, alongside the existing `ParseResult` factory validation checks moved out of `ErrorPositionTests`. Verified it failed before the fix (`Assert.Throws<ArgumentNullException>` caught null on the first missing check), then passed after. Also ran the full `ErrorPositionTests` fixture.
