- 2026-05-28: Lexer.AdvanceWhileTokenIn skipped a lone-surrogate token that a rune-only set covers
    - Not a fresh random-walk sweep. Picked seed `date +%s` 1780008104 mod 27 = 2 → AnyTokenRule.cs (recently swept), followed the runbook's "follow a thread out to a less-covered area" guidance into the public Lexer scanning API at [Lexer.Scanning.cs](../../src/InductorParser/Lexing/Lexer.Scanning.cs). The 2026-05-18 sweep [000-2026-05-18-advanceuntilrunein-slow-path-drops-lone-surrogate.md](000-2026-05-18-advanceuntilrunein-slow-path-drops-lone-surrogate.md) cleared "AdvanceWhileTokenIn lone-surrogate handling" while fixing the sibling AdvanceUntilRuneIn site. The clear was correct for the in-library caller ScanWhileRule (which branches on `set.HasMultiRuneGraphemes` to pick AdvanceWhileRuneIn for rune-only sets, so the bug path doesn't fire). The clear was wrong for direct callers of the public method, whose documented behavior still has to hold.
    - Reviewed: [Lexer.Scanning.cs](../../src/InductorParser/Lexing/Lexer.Scanning.cs) (both AdvanceWhileRuneIn and AdvanceWhileTokenIn), [TokenSet.cs](../../src/InductorParser/TokenSet.cs) (ContainsToken span overload, the length-1 lone-surrogate branch), [ScanWhileRule.cs](../../src/InductorParser/ScanWhileRule.cs) (the in-library caller that branches before dispatch), [SurrogateHelpers.cs](../../src/InductorParser/Lexing/SurrogateHelpers.cs) (the IsSurrogatePairAt the rune-decode path uses), the 2026-05-15 [0000-2026-05-15-scanwhile-rune-fast-path-vs-lone-surrogate.md](0000-2026-05-15-scanwhile-rune-fast-path-vs-lone-surrogate.md) (the original AdvanceWhileRuneIn fix that handled the lone surrogate by code unit), and the 2026-05-18 cross-method audit entry.
    - Categories swept: fast-path-vs-slow-path equivalence between AdvanceWhileRuneIn and AdvanceWhileTokenIn (the bug), public Lexer API behavior vs in-library use, lone-surrogate handling parallels with the AdvanceUntilRuneIn fix the 2026-05-18 sweep landed.
    - Found and fixed: `AdvanceWhileTokenIn`'s `else` branch (the path that runs when `TryPeekRune` returns false on a lone surrogate, or when the token is a multi-rune cluster) gated the membership check on `set.HasMultiRuneGraphemes`. For a rune-only set with the surrogate's code unit as a rune-interval entry, the gate short-circuited to false and the loop bailed even though `TokenSet.ContainsToken`'s length-1-surrogate branch routes through `ContainsRune` and would have matched. `AdvanceWhileRuneIn`'s rune-only path already handles this (the 2026-05-15 fix), so the two methods disagreed on rune-only sets containing surrogate values. A custom `Rule` subclass calling `AdvanceWhileTokenIn` directly (the documented "either rune or multi-rune grapheme entries" rule) silently skipped a surrogate the set accepts. ScanWhileRule's branch shields the in-library caller from the bug, which is why the 2026-05-18 audit cleared it.
    - Fix: drop the `set.HasMultiRuneGraphemes &&` short-circuit in the `else` branch and call `ContainsToken` unconditionally. `ContainsToken` handles all three token shapes: length-1 surrogate → `ContainsRune` of the code unit, single rune (BMP or surrogate-paired) → `ContainsRune` of the value, multi-rune cluster → binary search the `_multiRuneGraphemes` array (returns false fast when the array is null or empty). The perf change is negligible: the `else` branch only fires for unusual tokens (lone surrogates, multi-rune clusters), and `ContainsToken`'s single-rune-via-TrySingleRune path on a rune-only set with a 2+ char cluster does one extra check before the multi-rune array short-circuit returns false. Comment updated to call out why the `else` branch can't take the short-circuit.
    - Tests: two regression tests in a new [Core/LexerScanningTests.cs](../../src/InductorParser.Tests/Core/LexerScanningTests.cs). `AdvanceWhileTokenIn_consumes_lone_surrogate_a_rune_only_set_covers` constructs a Lexer over `UnicodeExamples.HighSurrogateMinText` (Canary-wrapped U+D800), builds `TokenSet.SurrogateRange(0xD800, 0xD800)` (rune-only, no multi-rune entries), and asserts AdvanceWhileTokenIn returns count 1 and advances the lexer past the surrogate. `AdvanceWhileTokenIn_and_AdvanceWhileRuneIn_agree_on_rune_only_set_with_surrogate` drives both methods on the same input and set, asserts the counts and final positions match. Both red before the fix (count 0 vs expected 1), both green after.
    - Full `InductorParser.Tests` suite: 6928 / 6930 pass with the two long-standing skips, no other regressions. The new tests add 2 to the recursive-engine count.
    - Pattern reference: this fits [0000-2026-05-15-fast-path-membership-drops-lone-surrogates.md](../PotentialBugSources/0000-2026-05-15-fast-path-membership-drops-lone-surrogates.md), the pattern doc the 2026-05-15 ScanWhile fix established for "fast-path membership probes drop lone surrogates because TryPeekRune returns false." This is the same pattern in a different gating shape: AdvanceWhileTokenIn's gate was on `HasMultiRuneGraphemes` rather than on `TryPeekRune` directly, but the consequence was identical, so existing pattern doc covers it.
