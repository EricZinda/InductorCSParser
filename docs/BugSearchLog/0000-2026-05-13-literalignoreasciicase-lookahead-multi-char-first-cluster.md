    - Categories: ASCII case folding × multi-rune-cluster lookahead, `FirstConsumedTokens` shape mismatch between runtime match and compile-time filter, Or / BetweenInclusive lookahead-shortcut soundness when a rule's runtime accept-set is wider than its publish-set, decomposed-form (FormD / FormKD) and Compile(null) leaving base+combining-mark clusters multi-char in `_expected`, design-question whether a rule named "IgnoreAsciiCase" should accept non-ASCII patterns at all, recursive engine vs SM engine parallel (both read the same compiled `FirstConsumedTokens` / `Polarity` fields so both engines suppress the rule identically).
    - Found and (initially) fixed at the publish-set level: `LiteralIgnoreAsciiCaseRule.ComputeRuleStart` admitted both ASCII letter cases only inside the `firstElement.Length == 1` branch. A multi-char first grapheme starting with an ASCII letter (e.g. `LiteralIgnoreAsciiCase("e" + U+0301)` under Compile(FormD) or Compile(null), and equivalently the FormD-projected `LiteralIgnoreAsciiCase("é")`) fell through to `FirstTokenMustBeFirstGraphemeOf(_expected)`, which only seeds the multi-rune cluster as written. The Or-lookahead peeked the case-swapped input cluster, found it isn't in the published set, and the rule never ran, even though `AsciiCaseEquals` would have folded the leading letter and matched at runtime. Repro: `Or(LiteralIgnoreAsciiCase("e" + U+0301).Preserve().As("literalBranch"), AnyToken().As("fallback")).Compile(FormD).Parse("E" + U+0301)` parsed with the `AnyToken` fallback (`Find(literalBranch)` returned null) instead of the `LiteralIgnoreAsciiCase` branch. The first-cut fix widened the publish-set to admit the case-swapped multi-rune cluster.
    - Followed up at the design level: a non-ASCII char in a rule named `LiteralIgnoreAsciiCase` is itself the trap. ASCII case-folding can't reach U+00DF / U+0301 / any non-ASCII code point, so a non-ASCII char in the pattern silently behaves as a bit-exact compare and mismatches the rule's name. The existing `mdmd` backlog stub flagged the same concern. Final fix: validate the pattern at construction time (throw `ArgumentException` for any char outside 0x00..0x7F), which makes the case-fold lookahead bug structurally unconstructable. `ComputeRuleStart` simplifies back to the single-char ASCII-letter branch plus the standard `FirstTokenMustBeFirstGraphemeOf` fallback (the only ASCII multi-char cluster is CRLF, which starts with '\r' rather than an ASCII letter and goes through the fallback uniformly). `StringInfo.GetNextTextElement` can't throw on ASCII-only input, so the `catch (ArgumentException)` surrogate-fallback is removed too. Backlogs `mdmd` and `liac` (the publish-set-widening bug report I'd opened earlier the same day) are deleted as resolved.
    - Test fixtures rewritten: `LiteralIgnoreAsciiCaseRuleTests` matrix tests now branch per row on `IsAsciiOnly(row.Source)`: ASCII rows parse and assert success; non-ASCII rows assert construction throws. Three new construction-throws tests cover a non-ASCII letter ("straße"), an ASCII base + combining mark ("a" + U+0301), and a lone high surrogate ("\uD800X"). One accepts-control-chars test pins that 0x00..0x1F and 0x7F stay legal. `LiteralRuleTests.LiteralIgnoreAsciiCase_rejects_non_ascii_case_variant` is rewritten as `..._rejects_non_ascii_pattern_at_construction`. `NormalizationTests.Compile_LiteralIgnoreAsciiCase_auto_converts_non_ASCII` is rewritten as `..._rejects_non_ASCII_pattern_at_construction`. `UnexpectedUnicodeTests.LiteralIgnoreAsciiCase_with_*_surrogate_*` tests are rewritten as construction-throws tests; the `Multiple_surrogate_literals_under_default_Compile_aggregate_inner_exceptions` test drops the LiteralIgnoreAsciiCase term and expects two inner exceptions (Token + Literal) instead of three.
    - Considered keeping the publish-set widening as a precision-only improvement (admitting both case-swapped clusters at lookahead time for any future relaxation that adds back multi-char patterns). Rejected: the construction-time restriction is a hard guarantee that prevents the whole class of "runtime accept wider than publish-set" bugs from existing here, and the publish-set code path becomes dead weight that drifts out of sync. Better to lean on the type system / validation gate.
    - Pattern doc `0000-runtime-accept-wider-than-compile-time-lookahead-set.md` describes the broader pattern (any rule whose runtime accept-set is wider than its publish-set has the same soundness risk). The LiteralIgnoreAsciiCase case is now mitigated by restricting the input domain at construction, but the pattern still applies to future rules that add equivalence relations on top of stored literal data.
