- 2026-05-06: BuildErrorMessage character-placeholder vs normalization sweep
    - Reviewed: `Rule.cs` (`BuildErrorMessage`, `PositionPlaceholders`, `FormatTemplate`, `ApplyPlaceholders`, `BuildBudgetMessage`, `ParseRecursive`'s three failure-reporting branches), `ParseOptions.cs` (template defaults and the `{character}` placeholder doc), `Lexing/NormalizedPositionMap.cs` (lockstep + per-grapheme translators), `SyntaxTree/SourcePositionConverter.cs`, `EofRule.cs`, `OneOfRule.cs`, `LiteralRule.cs`, `LiteralIgnoreAsciiCaseRule.cs`, `GraphemeRule.cs`, `WithinTokenRule.cs` (looking for other user-facing strings rendered from `parseInput`).
    - Categories: original-vs-normalized coordinate mismatches in user-facing strings, placeholder rendering when normalization changes character shapes (FormKC fullwidth → ASCII, ligature → letters, math letters → ASCII), drift between the position-family ({charIndex}/{tokenIndex}/{line}/{column}) and the content-family ({character}).
    - Found and fixed: `BuildErrorMessage` rendered `{character}` via `StringInfo.GetNextTextElement(parseInput, posInParseInput)`, where `parseInput` is the post-normalization input. Every other placeholder in the same template uses `(failurePos, input)` (original-input coordinates and the original string). Under FormKC the message says `unexpected '1'` for input `'１'` (fullwidth digit folded to ASCII), `unexpected 'f'` for input `'ﬁ'` (ligature folded to letters). The position is right; the quoted character is what the parser saw internally rather than what the user typed.
    - The fix swaps the substitution to `StringInfo.GetNextTextElement(input, failurePos)`, matching the position-family. Two regression tests in `ErrorMessageTemplateTests.cs` lock in the FormKC fullwidth-digit and ligature shapes.
    - Cross-checked the rest of `BuildErrorMessage`'s call sites (the trailing-input branch in `ParseRecursive` passes `customMessage: null` and the same `pos / parseInput / failurePos / input` quadruple, so the fix carries to it) and `BuildBudgetMessage` (no `{character}` placeholder in budget templates, no equivalent issue).
    - Trace lines that quote the current token (`OneOfRule`, `LiteralRule`, `EofRule`, etc.) all read from `lexer.Input` directly. Under normalization `lexer.Input == parseInput`, so trace output legitimately reflects what the lexer saw and isn't affected by this fix; trace is a debug surface, not a user-facing one.
    - Added a "Normalized input leaks into user-facing strings" entry to `docs/PotentialBugSources/` noting the broader pattern: anywhere a user-facing string quotes content from `parseInput`, the source string should be `input` instead (and the offset should be in original coordinates).
