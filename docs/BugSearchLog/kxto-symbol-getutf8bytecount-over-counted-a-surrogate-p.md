- Symbol.GetUtf8ByteCount over-counted a surrogate pair split across two leaves
    - Start area: directed at the SyntaxTree folder (not random). Read every file under `src/InductorParser/SyntaxTree/`: Symbol.cs, SymbolId.cs, SymbolRanges.cs, SymbolExtensions.cs, SourcePosition.cs, SourcePositionConverter.cs, SourceRange.cs, ParseContext.cs, FlattenType.cs.
    - Files reviewed: the nine SyntaxTree files above, cross-checked against the existing fixtures SymbolPositionTests, RawSourceTextTests, SymbolExtensionsTests, SymbolDisplayNameAndIdOfTests, the SourceRange / SourceText matrix helpers, and `Lexing/NormalizedPositionMap.cs` (consumed by Symbol.SourceRange). Read `Core/UnexpectedUnicodeTests.cs` to confirm lone surrogates are a supported, tested input under Compile(null). Traced the one non-test caller, `ExperimentalSrc/BenchMarks/Rebar/BenchmarkPlan.cs`.
    - Categories checked: off-by-one in SourcePositionConverter.ToLineColumn (CRLF, lone CR, lookahead-past-limit) and ToTokenIndex, SourceRange / SourceText parseInput-to-original translation under FormC / FormD / FormKC / FormKD and the ReferenceEquals identity shortcut, FlattenInto Delete / Flatten / Preserve branches and the SameChildren rebuild fast path, TryGetCharSpan recovery from empty / zero-width / default `_leafChars`, Find / FindAll / Walk traversal, Is(Rule) / Is(string) / DisplayName name resolution, PrintTree character-leaf vs composite rendering, SymbolId range arithmetic, the default-struct `SourcePosition.Input` nullability gotcha, ToString / GetUtf8ByteCount consistency.
    - Found: `Symbol.GetUtf8ByteCount` summed `Encoding.UTF8.GetByteCount` over each leaf span independently. That is correct for well-formed text (UTF-8 is context-free per code point), but when one leaf ends with a high surrogate and the next leaf begins with the matching low surrogate, `ToString()` concatenates them into one four-byte supplementary code point while the per-leaf sum counted each half as an unpaired surrogate (U+FFFD, three bytes), over-counting the boundary by two bytes. The doc promised "the UTF-8 byte length of this symbol's rendered text". For that shape it returned more than `Encoding.UTF8.GetByteCount(ToString())`. Reachable from a real parse: a grammar that Preserve-captures a lone high surrogate and a lone low surrogate with a Delete-flattened char dropped between them (lone surrogates are a documented Compile(null) input, used for WTF-8 / JSON unpaired-surrogate round-tripping). Demonstrated with a failing test (the method returned 6 where the rendered text was 4 bytes). `GetUtf8ByteCount` had zero test coverage.
    - Fixed: the method was removed, with no replacement accessor on Symbol. Investigating its only caller, the Rebar benchmark's `SumMatchBytes`, showed it wanted the byte size of each match's contiguous input region, which is `SourceText` semantics (one run of input), not `ToString()` semantics (surviving leaves, normalized, Delete content dropped). The two coincided only because the Rebar grammar has no Delete content and no normalization. A self-contained `Symbol.GetSourceTextUtf8ByteCount` was considered and prototyped, but a Symbol-level byte-count accessor isn't worth maintaining for a single benchmark caller, so it too was dropped. The benchmark now recovers each match's span from `Symbol.SourceRange` and counts `Encoding.UTF8.GetByteCount` over the contiguous input run. One contiguous run has no per-leaf boundary, so the surrogate-split over-count can't occur. (Trade-off accepted: `SourceRange` also derives line/column per endpoint, making `SumMatchBytes` for the recursive engine O(n^2), judged not worth a dedicated accessor.) No byte-count accessor remains on Symbol, so this bug has no public surface left to recur on, and there is no regression test to keep.
    - Cleared: SourcePositionConverter.ToLineColumn is sound for CRLF, lone CR, and the lookahead-past-`limit` case. SourceRange / SourceText translation and the FlattenInto rebuild were traced extensively and check out. The stateful-`Encoder.GetByteCount` route (an earlier candidate fix for the old method) was probed and rejected, since `Encoder.GetByteCount` doesn't carry a leftover high surrogate across calls.
    - Not a bug, considered: `default(SourcePosition).Input` is null despite the "Never null" doc, but no library API hands a consumer a default-constructed SourcePosition, so it isn't reachable. `Is(Rule)` throws on a null rule while `Is(string)` tolerates null, an API-consistency wart but not a demonstrable bug.
