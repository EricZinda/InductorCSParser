    - Found and fixed (doc bug, not engine): the one Recipes.md example with no backing test in `RecipesExamples.cs` had drifted. The "Numbers with no leading zeros, validate after parsing" recipe ([docs/Recipes.md](../Recipes.md)) showed `var range = result.SourceRangeOf(node)!;` and the prose said "`result.SourceRangeOf(node)` gives the column of the original text." `ParseResult` has no `SourceRangeOf` method (confirmed: zero matches under `src/InductorParser`, and the full `ParseResult` definition has only Find / FindAll / DisplayNameOf / DisplayName / PrintTree / ToString / ToDebugString plus the Error* properties). A user copy-pasting the recipe gets CS1061. The real API is `Symbol.SourceRange` (public, returns `SourceRange?`, translates parseInput offsets to original coordinates via the Symbol's `ParseContext`), which the working SemVer sample (`E2ESamples/SemVer/Rewrite/SemVerParser.cs`) already uses.
    - Root cause (history): [z007-2026-05-07-symbol-sourcerange-under-normalization.md](z007-2026-05-07-symbol-sourcerange-under-normalization.md) records a refactor that moved ~40 calls from `symbol.SourceRange` to `result.SourceRangeOf(symbol)` (positions belonged on ParseResult because Symbol didn't yet carry the original input). A later change gave every Symbol a `ParseContext` (OriginalInput, parseInput, form), which let the translating accessor move back onto `Symbol.SourceRange` and dropped the `SourceRangeOf` form. The code and the compiled tests followed. The prose and comments that named the API didn't. The example survived because it was the only recipe in Recipes.md without a regression test in `RecipesExamples.cs`, exactly the gap backlog item `ozpb` (doc examples must have tests) warns about.
