- XID_Start and XID_Continue over-admitted U+309B and U+309C, which NFKx closure removes
    - Found while adding two-direction coverage to TokenSet.Xid.cs's hand-curated tables. A "4 ranges in XidStartAdds, only 3 tests" count mismatch sent me to verify each entry against the authoritative DerivedCoreProperties.txt: 309B..309C appears under ID_Start and ID_Continue but the XID_Start and XID_Continue sections skip from 3041..3096 straight to 309D..309E, leaving the range out. Same story in Unicode 15.0, 16.0, and 17.0 (cross-checked all three so it's not a version-skew false alarm).
    - Root cause: U+309B / U+309C are in Other_ID_Start (so they're in ID_Start), but their NFKx decomposition is U+0020 SPACE + U+3099 / U+309A combining mark. The closure-under-NFKx step that turns ID_Start into XID_Start (and ID_Continue into XID_Continue) drops them because their normalized form can't start an identifier. The previous "Bug: add U+309B..309C to XidStartAdds and XidContinueAdds" commit conflated "in Other_ID_Start" with "in XID_Start" and read the wrong column of DerivedCoreProperties.txt. The four regression tests that commit added (Katakana_voiced_sound_mark_309B_is_in_xid_start and its three siblings) pinned the buggy behavior.
    - Why earlier tests missed it: the "spot-check additions, never verify the result against the spec" pattern documented in 0-allow-table-tested-for-members-not-for-non-members. The author cross-checked the table against PropList.txt's Other_ID_Start (the right list for ID_Start) but not against DerivedCoreProperties.txt's XID_Start (the post-NFKx-closure list that XidStartAdds is meant to feed).
    - Lesson from the same hunt: verifying these tables against an *implementation* of XID (Python's str.isidentifier, the .NET BCL, etc.) only works if the implementation's Unicode version matches the version the table claims to track. Python 3.13 is on Unicode 15.0 while the parser tracks 17.0. Several code points (U+200C, U+200D, U+30FB, U+FF65) were added to XID_Continue in Unicode 16.0, so checking the table against Python's older data flags them as bugs when they aren't. Cross-check against the actual UCD file at the table's claimed version instead.
    - Fix: removed (0x309B, 0x309C) from XidStartAdds and XidContinueAdds. Replaced the four old "is_in_xid_*" tests with one Katakana_voicing_marks_are_excluded_by_NFKC_closure test that asserts the correct behavior in both positions plus the Identifier()-level rejection. Added XidStart_includes_every_curated_addition covering U+1885..1886, 2118, 212E (the original count-mismatch gap that surfaced this).
    - Behavioral impact for grammars that relied on the old behavior: a Japanese-identifier grammar that used a bare 309B / 309C voicing mark mid-word now needs Compile(NormalizationForm.FormKC), which decomposes the mark to SPACE + the combining mark (where the combining mark is a normal continue char). That's the UAX #31-conformant way to handle it.
    - Full suite: 6884 pass, 0 fail, 2 skipped.
