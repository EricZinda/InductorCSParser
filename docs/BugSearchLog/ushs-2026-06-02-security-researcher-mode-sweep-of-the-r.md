    - Recurring patterns considered as attack-class probes:
        - Grapheme clustering hides delimiter runes from rule-set checks. `OneOf(TokenSet.Single('"'))` does NOT match a `"<combining mark>` cluster. This is documented in [Rules.cs](../../src/InductorParser/Rules.cs)'s `ScanUntil` docstring and in [SecurityByDefaultTests](../../src/InductorParser.Tests/Core/SecurityByDefaultTests.cs)'s `Invisible_character_inside_a_keyword_breaks_a_strict_literal`. By design, not a bug, and the [SecurityByDefaultTests](../../src/InductorParser.Tests/Core/SecurityByDefaultTests.cs) tests already lock the behavior in.
        - `LiteralIgnoreAsciiCase` accepts ASCII control chars (including NUL) in the pattern. The constructor only rejects `c > 0x7F`. This is intentional — the docs say "ASCII-only pattern," not "printable ASCII." A user-controlled pattern is grammar code anyway, not input data.
        - `Rules.Integer()` and `Rules.Float()` use `TokenSet.Digits` (Unicode decimal-digit category), so Arabic-Indic and other non-ASCII digits match. This is documented and consistent with `TokenSet.Letters`. A grammar that wants ASCII-only digits uses `TokenSet.Ascii.Digits`.
        - Forced `.WithError` competition under `WithinTokenRule` uses first-writer-wins ties: the inner's forced WithError lands at `startPosition` first, so the outer's own forced WithError at the same position is correctly skipped. Consistent with how `AndRule` / `OrRule` / `BetweenInclusiveRule` handle composite forced WithError ranking.
