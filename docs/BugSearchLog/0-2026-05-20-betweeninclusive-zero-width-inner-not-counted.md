    - Found and fixed: `BetweenInclusiveRule.TryParseRule`'s zero-width-match check ran `if (zeroWidthMatch) break;` before `count++`, so a successful inner match that consumed nothing was never counted. A nullable inner (Optional, ZeroOrMore, Peek, Not, or any composite that can match empty) on input it can't advance through therefore left `count` short of `AtLeast`, and `OneOrMore` / `AtLeast` / `Exactly` failed even though the inner did match the required number of times. `OneOrMore(Optional(OneOf("a"))).Parse("")` failed with "Unexpected end of input" while `ZeroOrMore(Optional(OneOf("a"))).Parse("")` succeeded, same nullable inner with only the lower bound differing. Contradicts the documented behavior. `OneOrMore` "Fails if the first attempt fails" (the attempt succeeded), and `BetweenInclusive` "fails if it can't reach atLeast" (a zero-width match is a match that should count). It also diverged from the state-machine engine, whose `Stepper.Step_PopIterationCheck` does `between.Counter++` before its `!advanced` check (`ExperimentalSrc/.../Stepper.cs:496`), i.e. the SM engine already counted the zero-width match. Fix in `src/InductorParser/BetweenInclusiveRule.cs`: move `count++` above the `if (zeroWidthMatch) break;` so a zero-width success counts toward the bound while the break still stops the loop (no infinite loop). The non-zero-width path is unchanged (count++ then loop condition re-checked).
