- 2026-06-04: `TokenSet.ContainsRune` linear-scanned hundreds of intervals per token on the scanning hot path (performance, not a correctness bug)
    - Focus this pass: the user asked for performance issues that hit real grammars rather than a correctness bug. Started from the recursive-engine hot path (`Rule.TryParse`, `OrRule`, `AndRule`, `BetweenInclusiveRule`) and followed the per-token work down into the membership test every scanning rule shares.
    - Reviewed: `Rule.cs` (`TryParse` / `ParseChild`), `OrRule.cs`, `AndRule.cs`, `BetweenInclusiveRule.cs`, `Lexer.Scanning.cs` (`AdvanceWhileRuneIn` / `AdvanceWhileTokenIn`), `OneOfRule.cs`, `NoneOfRule.cs`, `ScanUntilRule.cs`, `TokenSet.cs` (`ContainsRune`, `ContainsToken`, `Normalize`, the `Letters` / `Digits` / `Xid*` builders), and `TokenSetTests.cs`.
    - Categories checked: per-rule-invocation allocations, per-token membership cost, and the interval representation's search complexity versus the size of the built-in sets real grammars use (`Letters`, `Digits`, `XidStart`, `XidContinue`).
    - Found and fixed: `TokenSet.ContainsRune(int)` walked `_ranges` with a linear scan whose only early-out was `codepoint < ranges[index].Low`. That early-out fires fast for low (ASCII) code points but degrades to O(ranges) for anything deep in the list. `Letters` carries 659 intervals and `XidContinue` 775, so every CJK / Cyrillic / Arabic / Hangul rune (and every miss past the Latin block) scanned hundreds of intervals per token on the `OneOf` / `NoneOf` / `ScanWhile` / `ScanUntil` path. The file header even claimed the rune path was "binary search of intervals," which it wasn't. Fix: scan a short linear prefix (`LinearScanPrefix = 8`, keeps ASCII at one or two comparisons and leaves small / `Ascii.*` sets pure linear) then binary-search the tail. `Normalize` already guarantees `_ranges` is sorted, non-overlapping, non-adjacent, so the binary search is correct.
    - Measured (Release, 20,000,000 calls against `TokenSet.Letters`). Before: `'A'` (U+0041) 25 ms, CJK U+4E00 3368 ms, miss U+FFFF 4274 ms. After: `'A'` 43 ms, CJK U+4E00 298 ms (11x faster), miss U+FFFF 325 ms (13x faster). Non-ASCII membership drops from ~170 ns/call to ~15 ns/call, and ASCII stays ~2 ns/call (a pure binary search regressed ASCII to ~9 ns/call, which the prefix scan avoids).
    - Regression tests (`TokenSetTests`): `ContainsRune_matches_letter_category_oracle_across_the_scalar_space` (sweeps 0..0x10FFFF against the Unicode category oracle, exercising every code point in the binary-searched tail), `ContainsRune_binary_search_tail_hits_members_and_misses_gaps`, and `ContainsRune_checks_interval_endpoints_in_the_binary_searched_tail` (50 / 40 disjoint intervals well past the linear prefix, checking members, gaps, and interval endpoints through the binary-search branch).
    - Verification: this is a performance fix with identical semantics, so the new tests pass both before and after (they catch an off-by-one in the prefix-to-binary handoff, not a behavior change). `dotnet test src/InductorParser.Tests/InductorParser.Tests.csproj --filter "FullyQualifiedName~TokenSetTests"` (115 passed) and the full `dotnet test src/InductorParser.Tests/InductorParser.Tests.csproj` (7150 passed, 2 pre-skipped UCD tests) both green.
