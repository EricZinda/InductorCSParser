    - Found and fixed: `ScanUntilRule`'s rule-mode constructors set `_stopperRendered = $"rule {stopAt.Name ?? stopAt.GetType().Name}"` at construction. If a grammar author calls `.As("name")` on the inner rule AFTER the ScanUntil is built but before Compile, the cache keeps the typeof-name `OneOfRule` instead of the rule's actual name `name`. The static-init pattern hits this naturally (a stopper field initializer runs before the static ctor's `.As(...)` call), as does any refactor that names a shared rule later. The recent 2026-05-28 `setRendered` fix explicitly left rule-mode out, reasoning "the inner Rule handles its own normalization through the walker's recursion into Children". That reasoning covers normalization-form projection but misses post-construction Name changes. Trace now reads `FAIL | ScanUntil: unterminated body, expected stopper 'rule OneOfRule'` when the inner is actually named `stopX`.
    - Fix: add a `ValidateCompiled` override to ScanUntilRule that refreshes `_stopperRendered = $"rule {_stopperRule.Name ?? _stopperRule.GetType().Name}"` when `_stopperRule != null`. `ValidateCompiled` is called in Compile's pass 5 (`ValidateAll`), which runs on every reachable rule unconditionally, so the refresh covers both `Compile(form)` and `Compile(null)`. The TokenSet path keeps refreshing through `CollectNormalizationOffenders` (the projection that needs refreshing only runs there). Field-level comment updated to call out the two refresh sites and why each is in its own hook. Same root-cause shape as the 2026-05-28 sister fix. The difference is that the rule-mode rendering depends on Name (set by the user pre-Compile) rather than on a projection mutation (set by Compile itself), so the refresh hook has to be the one that runs after Name is locked in but before the rule is sealed.
