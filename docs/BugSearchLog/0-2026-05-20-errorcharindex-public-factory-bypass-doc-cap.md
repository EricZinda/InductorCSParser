    - Found and fixed: `ParseResult.ErrorCharIndex`'s XML doc promises the value is in range for the original input ("callers can index into the original input string without bounds-checking"). `ParseResult.ErrorPosition.CharIndex` is in range because it goes through `SourcePosition.From`, which clamps explicitly. But `ParseResult.ErrorCharIndex` is an auto-property that holds whatever the private constructor stored, with no enforcement. The public `Failed` and `Aborted` factories (documented as "Exposed as public so custom parse drivers can build a ParseResult with the same structure the built-in Parse produces") forwarded the caller's raw `errorCharIndex` into that auto-property. Result: a custom driver passing an out-of-range value would see `result.ErrorCharIndex` disagree with `result.ErrorPosition.CharIndex` and break its "Substring(ErrorCharIndex)" caller. Built-in `Rule.Parse` never trips it because `Math.Max(lexer.DeepestFailure, lexer.Position)` plus the position-map translate already lands inside `[0, input.Length]`, so this is a gap visible only through the public factory surface.
       Fix shape: enforce the invariant in `ParseResult`'s private constructor by throwing `ArgumentOutOfRangeException` when `errorCharIndex` falls outside `[0, input?.Length ?? 0]`. Surfaces custom-driver bugs immediately rather than silently clamping. The `input == null` case covers `default(ParseResult)` and exotic factory calls that pass null. Updated the `ErrorCharIndex` doc from "capped to the input length" (which suggested gracefully clamping) to "always in [0, input.Length] (enforced at construction)" to match. `Rule.Parse`'s in-range callers (the Aborted budget path, the Failed grammar-mismatch / trailing-input paths, and the pre-flight cancellation path that passes 0) are unaffected.
