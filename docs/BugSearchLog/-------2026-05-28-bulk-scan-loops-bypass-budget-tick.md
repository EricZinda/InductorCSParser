    - Found and fixed: `ScanWhileRule` / `ScanUntilRule` and the Lexer's `AdvanceWhileRuneIn` / `AdvanceWhileTokenIn` primitives all run tight `while`-loops that consume one token per iteration without calling `_budget.TickPeriodic`. Each whole scan is ONE `EnterRule` from the engine's view, so the periodic budget check (gated on the 1024-invocation mask) never fires between scan-open and scan-close. An attacker who points a hot scan rule at a long matching run (a JSON string body with no closing quote, a CSV field with no delimiter, an identifier of one million letters) pins the parser through the whole run with NO Timeout, Cancellation, or RuleCountLimit observation. Fix in [Lexer.Scanning.cs](../../src/InductorParser/Lexing/Lexer.Scanning.cs) (per-iteration `_budget.TickPeriodic()` inside both AdvanceWhile primitives) and [ScanUntilRule.cs](../../src/InductorParser/ScanUntilRule.cs) (per-iteration `lexer.Budget.TickPeriodic()` inside the body scan loop). The Budget's own 1024-mask amortizes the actual `Stopwatch.Elapsed` / `cancellation.IsCanceled` read, so the per-iteration cost is one int increment plus one mask compare. Updated the `ParseOptions.RuleCountLimit` doc comment to call out that bulk-scan iterations now count as work units (the doc previously said "every rule invocation increments a counter," which would mislead a reader trying to predict the trip point).
    - Regression tests: two new tests in [BudgetTests.cs](../../src/InductorParser.Tests/Core/BudgetTests.cs) (`ScanWhile_observes_Timeout_during_long_inner_scan`, `ScanUntil_observes_Timeout_during_long_inner_scan`), each parses a 1 M-char run through a bare scan rule with `Timeout = 1 tick` and asserts `ParseOutcome.Timeout`.
