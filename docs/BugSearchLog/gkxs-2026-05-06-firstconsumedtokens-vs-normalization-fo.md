- 2026-05-06: FirstConsumedTokens vs. normalization-form pass ordering
    - Reviewed: `Rule.cs` (`Compile(NormalizationForm?)` pass ordering), `GraphemeRule.CollectNormalizationOffenders` / `ComputeRuleStart`, `LiteralRule.CollectNormalizationOffenders` / `ComputeRuleStart`, `LiteralIgnoreAsciiCaseRule.CollectNormalizationOffenders` / `ComputeRuleStart`, `OneOfRule.NormalizeAndValidate` / `ComputeRuleStart`, `NoneOfRule.CollectNormalizationOffenders` / `ComputeRuleStart`, `TokenSet.NormalizedFor`, `BetweenInclusiveRule.TryParseRule` (the lookahead shortcut), `OrRule.TryParseRule` (the per-child shortcut).
    - Categories: cached static-analysis vs. mutated rule data, Compile-pass ordering, normalization-form interaction with the lookahead shortcut, canonical singletons (Angstrom / Ohm / Kelvin), NFD-decomposed first runes.
    - Found and fixed (nrmf): `Rule.Compile(NormalizationForm?)` ran `ComputeRuleStartAll` BEFORE `CollectNormalizationOffendersAll`, so each rule's `FirstConsumedTokens` was cached against the user-supplied `_set` / `_expected` while the normalization-form pass that runs immediately after rewrites those fields (canonical singletons like U+212B → U+00C5, NFD-decomposed first runes like 'Å' → "A"+combining ring, OneOf set entries that project to a different rune or to a multi-rune cluster). The cached set then disagreed with the rule's actual matchable runes, and `BetweenInclusiveRule` / `OrRule`'s lookahead shortcut consulted the stale cache and wrongly skipped the rule on input the normalized form would have made match. `OneOrMore(Token("Å")).Compile(FormC).Parse("Å")` failed at offset 0 with "unexpected 'Å'", even though the lexer-normalized input is exactly what the rule's post-projection text matches. Same shape for `OneOrMore(OneOf(TokenSet.Single(0x212B)))` and for `Literal(string)` whose first rune normalizes differently. Backlog nrmf has the full write-up.
    - The fix swaps the two passes in `Rule.Compile(NormalizationForm?)` so the normalization-form block runs first, then `ComputeRuleStartAll` walks the post-projection graph and caches the matchable runes the rule will actually see at parse time. Both passes already require `ValidateAll` to have run, so neither precondition shifted. Two regression tests in `OneOfRuleTests` and `GraphemeRuleTests` cover the OneOf and Token shapes (canonical-singleton substitution under FormC). Full suite: 1905 / 1907 (2 pre-existing timing skips) before and after.
    - Sibling-rule check: `LiteralRule.ComputeRuleStart` and `LiteralIgnoreAsciiCaseRule.ComputeRuleStart` also read `_expected` for their first-rune answer, and `NoneOfRule.ComputeRuleStart` returns `Universe` after the n7mh fix so it isn't affected by `_set` projection. The pass-ordering swap covers Token / Literal / LiteralIgnoreAsciiCase / OneOf uniformly because the fix is at the Compile orchestration level, not inside any individual rule.
    - Added a "Cached static-analysis vs. mutated Compile-time rule data" pattern bullet to `docs/PotentialBugSources/` for future sweeps that touch any per-rule field set during Compile passes.
