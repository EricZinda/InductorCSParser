- Claims audit over the built-in Unicode segmenter, normalizer, and host-globalization check: five wrong assertions fixed
    - Method: user-directed follow-up to the same-day GraphemeHelpers.Count hunt. Instead of hunting for behavior bugs, this pass extracted every checkable assertion about Unicode or about the code from the focus area's comments and docs and verified each one against the pinned spec editions (UAX #15 rev 53, UAX #29 rev 41, both fetched), the checked-in tables (scratch probes over the decomposition data), the pinned ICU 72.1 oracle, or the code itself.
    - Verified correct, no change needed: the UAX #29 rev 41 = Unicode 15.0 claim and its no-GB9c corollary, the GB9c skip set in GraphemeBreakConformanceTests (ran the fixture: 1180 pass, exactly the seven documented lines skip), dotnet/runtime#81429 really is the open GlobalizationMode API proposal, the GlobalizationMode switch-before-environment-variable reading order, the Hangul arithmetic constants and the 11,172 syllable count, the U+FDFA 18-character expansion and 941 composition-pair claims (already asserted by tests), the D-with-dots composite-shift example's UAX #15 attribution (that one really is in section 1.3), the U+0344 non-starter example, the U+180E category history (Cf, then whitespace, then Cf again), the Other_ID_Start claims for U+2118 and U+309B..309C, the halfwidth-jamo NFKC chains, the per-cluster grapheme counts on the Tamil / Tibetan / Hebrew / Devanagari samples, TUS section 5.18 as Case Mappings, and the whole Host Globalization Settings section of UnicodeGotchas.md.
    - Find 1: UnicodeNormalizationTests' Hangul round-trip test said U+D4DB is "the syllable the UAX #15 spec itself uses". UAX #15 rev 53 doesn't contain U+D4DB anywhere. The example is from The Unicode Standard's conjoining-jamo section (3.12), the section that defines the arithmetic. Fixed the attribution.
    - Find 2: the AppendDecomposition comment in UnicodeNormalization.cs said decomposition chains are "five levels at most". Computed the true maximum over every scalar from the checked-in tables: three, in both canonical and K-form modes (the deepest are polytonic Greek like U+1F82, which expands through U+1F02 and U+1F00). Fixed the comment and added Decomposition_chains_are_at_most_three_levels_deep to UnicodeNormalizationDataTests so a table regeneration that deepens a chain updates the comment instead of quietly outdating it.
    - Find 3: the eszett constant's comment in UnicodeExamples.cs said U+00DF's "Uppercase folds to SS under FormKC". All four normalization forms leave U+00DF unchanged (verified against ICU 72.1). The SS expansion is Unicode's full uppercase mapping from SpecialCasing.txt, a case mapping normalization never applies, and .NET's ToUpperInvariant doesn't apply it either (the probe shows the eszett coming back unchanged). Rewrote the comment.
    - Find 4: two comments cited UAX #29 "GB10" for the England-flag emoji tag sequence (UnicodeExamples.cs and UnexpectedUnicodeTests.cs). Revision 41 has no rule GB10 at all (the old GB10 was the emoji-modifier rule, retired when Unicode 11 reworked emoji properties). Tag characters are GCB=Extend, so plain GB9 is what keeps the sequence together, and the sequence itself is defined by UTS #51, not UAX #29. Also tightened the keycap constant's "GB9 / GB9a" to GB9 (VS16 and the enclosing keycap are Extend, and GB9a is the SpacingMark rule, which doesn't apply).
    - Find 5: the QuickCheck remark in UnicodeNormalization.cs cited tr15's #Description_Norm anchor for "much text is already NFC". That sentence lives in section 1.2 (anchor #Norm_Forms), and section 1.3 (#Description_Norm) doesn't say it. Fixed the anchor.
    - Also caught and corrected a wrong code claim in the same-day Count hunt's own log entry: it said no fixture reads NormalizationTest.txt, but NormalizationConformanceTests has been reading NormalizationTest-15.0.0.txt all along.
    - Correction for the record, old entry left as written: the 2026-05-07 graphemerule-normalization-repin entry lists "U+1E9E → U+00DF eszett" among canonical-singleton normalizations. U+1E9E LATIN CAPITAL LETTER SHARP S has no decomposition of any kind and every normalization form leaves it unchanged (verified against ICU 72.1). Its relationship to U+00DF is the lowercase case mapping. The other singletons that entry lists (U+212B, U+2126, U+2329, U+212A) are real.
