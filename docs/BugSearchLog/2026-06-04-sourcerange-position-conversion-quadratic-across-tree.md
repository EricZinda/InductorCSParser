- 2026-06-04 SourceRange position conversion walks from offset 0 on every node (quadratic across a tree)

  - Focus: performance issues that hit real grammars (per the hunt request), not correctness. Random start mapped into the hot-path leaf/loop rules, then followed the trail out to the post-parse position-reporting path, which the recent perf passes (linear-scan ContainsRune, lockstep position-map allocation, within-token eager grapheme index) hadn't touched.
  - Files reviewed: OrRule, TokenSet (ContainsRune / ContainsToken / NormalizedFor), Rule.cs (TryParse / ParseChild / dispatch / error templates), BetweenInclusiveRule (the loop OneOrMore/ZeroOrMore/Optional reduce to), OneOfRule, ScanWhileRule, LiteralRule, LiteralIgnoreAsciiCaseRule, Lexer.cs + Lexer.Scanning.cs (AdvanceWhileRuneIn / AdvanceWhileTokenIn / Read / NextTokenLength), Token, GraphemeClusterIndex, NormalizedPositionMap, Symbol.cs (SourceRange / SourceText / Flatten), SourcePosition, SourcePositionConverter.
  - Categories checked: per-token allocation, repeated per-call work that a cache could remove, O(n) scans on a structure with an ordering invariant, eager work a mode never uses, quadratic accumulation across a tree walk.
  - Found, filed as backlog item `0a00` (not fixed, deferred at the maintainer's request): `Symbol.SourceRange` builds two `SourcePosition.From` per node, and `SourcePosition.From` computes line/column (`SourcePositionConverter.ToLineColumn`, a char-by-char walk from 0) and token index (`GraphemeClusterIndex.CountClustersUpTo`, a bool-array scan from 1) both in O(charIndex). Reading positions across a parse tree (an LSP server's diagnostics, a typed-AST projection recording spans) reads a SourceRange per node, so a node at offset P costs O(P) and the whole tree is O(nodes x length), i.e. quadratic in document size. Even pure-ASCII grammars pay this cost: the ASCII / already-NFC `ReferenceEquals` fast path only skips the normalized-position translation, not the line/column/token walks. Proposed fix (prototyped 2026-06-04, then reverted): cache line starts per input in a new `LineStartIndex` (sorted array + binary search, O(log lines) per query) and back `CountClustersUpTo` with a build-once cumulative-count array (or the O(1) identity shortcut when the input has no multi-char cluster). Measured on a 16K-line word-per-line grammar reading SourceRange on every node under PreserveAllSymbols: 144K chars went from ~36,900 ms to ~186 ms (~198x), and the size-doubling ratio dropped from 3.85x (quadratic) to 1.60x (linear). The backlog item carries the runbook. The permanent regression checks (LineStartIndex equivalence sweep, GraphemeClusterIndex oracle) land with the fix, not now.
