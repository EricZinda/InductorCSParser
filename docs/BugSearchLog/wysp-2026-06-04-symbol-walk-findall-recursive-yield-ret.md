- 2026-06-04 Symbol.Walk / FindAll recursive yield-return is quadratic on deep trees

  - Continuation of the same performance-focused hunt that filed the SourceRange item. After confirming the per-rule engine machinery (ParseBudget, Transaction, Probe) allocates nothing per invocation and the lookahead rules (Peek/Not) are struct-based and clean, swept the post-parse tree-consumer API.
  - Files reviewed this pass: GraphemeRule, RuneHelpers, GraphemeHelpers, NoneOfRule, ScanUntilRule, Lexer.Failures.cs, Lexer.Probe.cs, Lexer.Transaction.cs, ParseBudget.cs, PeekRule, NotRule, AnyTokenRule, ParseResult.cs, Symbol.cs (Walk / Find / FindAll / FlattenInto), SymbolExtensions (PrintTree), IdentifierRule + Rules.Identifier, WithinTokenRule.
  - Dismissed as false positive: an Explore agent flagged the `lexer.Input.Substring(...)` calls inside the `$"..."` trace messages in OneOfRule / NoneOfRule / Literal* / GraphemeRule / AnyToken as per-token allocations. They are NOT: TraceSuccess/TraceFailure take a TraceInterpolatedStringHandler whose constructor reports shouldAppend=false when tracing is off, so the compiler skips the interpolation holes (the Substring is never evaluated). Proven by TracingTests.Off_path_does_not_evaluate_interpolated_arguments.
  - Found and FIXED (backlog item `0900`, since removed now that the fix landed): `Symbol.Walk()` and `Symbol.FindAll(SymbolId)` traversed with recursive `foreach (var x in child.Walk()) yield return x;`. A nested-iterator value is re-yielded through every enclosing iterator, so a node at depth D cost D MoveNext calls and the whole walk was O(N x D) plus one iterator allocation per node, quadratic on a deep chain-shaped tree. Deep trees are normal expression-grammar output (precedence chains, nested parens). Measured on a chain tree built via the public Symbol constructor: a single Walk().Count() over 16,001 nodes took ~1,295 ms and doubling the depth multiplied time by 4.18x (quadratic). Find / ParseResult.Find (plain recursion, early return) were unaffected, and ParseResult.FindAll only nests one level over the top-level Symbols so it needed no change once Symbol.FindAll went iterative. Fix: replaced both with an explicit Stack<Symbol> pre-order walk (push children in reverse so they pop left-to-right). That's O(N), one allocation, identical yield order. After: the depth-doubling ratio dropped from 4.18x to 2.00x (linear). Regression check: SymbolTraversalTests (src/InductorParser.Tests/Core/) asserts Walk/FindAll yield the same nodes in the same order as a reference recursive walk across wide-shallow, deep-chain, and mixed trees. Full suite green (7168 passed, 2 pre-existing skips).
