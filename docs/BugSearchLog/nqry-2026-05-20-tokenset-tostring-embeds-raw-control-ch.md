- 2026-05-20: TokenSet.ToString embeds raw control characters for multi-rune grapheme entries, corrupting one-line trace output
    - Starting area: user-directed ("do the find-a-bug item on TokenSet"), so no random pick. Read `TokenSet.cs` and `TokenSet.Xid.cs` end to end, side by side with the TokenSet-membership consumers `OneOfRule.cs`, `NoneOfRule.cs`, `ScanWhileRule.cs`, plus the scanner-skip / first-rune consumers `BetweenInclusiveRule.cs` (TryGetBmpChars caller), `Lexing/Lexer.FastPaths.cs` (AdvanceUntilRuneIn), and `RuleStartRequirements.cs` (the mixed-polarity `N \ P` Combine path). Surveyed existing coverage in `Core/TokenSetTests.cs`.
    - Categories swept: `Contains(int)` / `Contains(char)` / `Contains(string)` / `ContainsToken(span)` agreement (already reconciled by the 2026-05-19 lone-surrogate fix), `Equals` / `GetHashCode` consistency across the rune and multi-rune halves (consistent), `operator |` / `operator &` / `operator ~` interval and grapheme merges (the interval intersection's "result is already normalized" claim holds, with the adjacency argument checked by hand), the documented `a & ~b` set-difference idiom dropping `a`'s multi-rune entries when `b` is rune-only (confirmed by design, tested at `Complement_via_explicit_rune_only_mask_works_for_rune_only_sets`, the workaround is to union the multi-rune part back in), `Range` / `SurrogateRange` surrogate-block splitting and endpoint validation (correct), `TryGetBmpChars` ignoring multi-rune entries (consistent with its only caller, which feeds it a `LookaheadFirstRunes`-flattened rune-only set), `LookaheadFirstRunes` / `RunesOnlyPart` first-rune projection (correct), `NormalizedFor` / `WithCompatibilityEquivalents` projection + cache (heavily covered already), and finally ToString rendering.
    - Found and fixed: `TokenSet.ToString()` at [TokenSet.cs](../../src/InductorParser/TokenSet.cs) rendered single-rune entries through `RenderCodepoint` (printable ASCII verbatim, everything else `U+XXXX`, so control characters escape) but appended every multi-rune grapheme entry verbatim via `sb.Append(multi[index])`. The built-in `TokenSet.LineTerminators` and `TokenSet.Ascii.AnyWhitespace` carry the CRLF cluster (U+000D U+000A) as a multi-rune entry, so `LineTerminators.ToString()` returned `"[U+000A-U+000D,U+0085,U+2028-U+2029,<CR><LF>]"` with a literal carriage return and line feed in it. Rules cache `set.ToString()` into `_setRendered` and splice it into every `TraceSuccess` / `TraceFailure` line, so any grammar that traces a rule over a line-terminator set (`ScanUntil(LineTerminators)`, `OneOf(Ascii.AnyWhitespace)`, etc.) had one logical trace line break into three physical lines. Single-rune control characters in the same set rendered correctly as `U+000A` etc., so the rune and multi-rune paths disagreed.
    - Fix: added `AppendGraphemeForDisplay(StringBuilder, string)` next to `RenderCodepoint`, and call it from the multi-rune loop in `ToString`. It appends each char verbatim unless the char's Unicode General_Category is Control (Cc), LineSeparator (Zl), or ParagraphSeparator (Zp), in which case it emits `U+XXXX`. Reading the category from the BCL tables (`CharUnicodeInfo.GetUnicodeCategory`) instead of a hand-kept code-point list keeps the escape set tracking new Unicode versions, and it catches U+2028 / U+2029 that a `char.IsControl`-only check (Cc only) would miss. Format characters (Cf) like ZWJ are deliberately left verbatim so emoji ZWJ families still render. Printable multi-rune graphemes (emoji, regional-indicator flags) still render as themselves because their surrogate halves report as Surrogate, not a control/separator category, so only the embedded line-breaking/control chars escape. One new regression test `ToString_escapes_control_chars_in_multi_rune_grapheme_entries` in [TokenSetTests.cs](../../src/InductorParser.Tests/Core/TokenSetTests.cs) asserts `LineTerminators` / `Ascii.AnyWhitespace` render with no raw CR/LF and show `U+000D` / `U+000A`, and that a US-flag-bearing set still renders the flag verbatim. Full `InductorParser.Tests` suite 6880 pass / 2 pre-existing skips (the `LoneSurrogateNotNormalizable` rows `String.Normalize` rejects) on the recursive engine. `TokenSetTests` (108) also green under the state-machine engine.
    - Pattern doc: added [docs/PotentialBugSources/2026-05-20-verbatim-multichar-render-leaks-control-chars.md](../PotentialBugSources/2026-05-20-verbatim-multichar-render-leaks-control-chars.md). Distinct from the `c000` char-unit-rendering pattern (that one is about showing the right unit, a grapheme vs a surrogate half): this is about a multi-character value being appended verbatim into a single-line string, so an embedded control character leaks through and breaks the line, even where the single-element render path already escapes controls.
