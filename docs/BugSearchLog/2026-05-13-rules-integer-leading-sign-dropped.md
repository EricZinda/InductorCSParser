- 2026-05-13: Rules.Integer() vs Rules.Float() composition (sign-flatten asymmetry)
    - Random pick: 47 mapped into the source file list (28 files under `src/InductorParser/`, 47 mod 28 = 19), landed on `PeekRule.cs`. Read it side-by-side with `NotRule.cs` (the sibling lookahead). Both already covered by the `z007` (`Symbol.SourceRange under normalization`) and `2026-05-07` (`peek-not-witherror-vs-deeper-inner-deepest`) sweeps. Followed the WithError-and-flatten thread out into the leaf-emitting rules: `GraphemeRule.cs`, `LiteralRule.cs`, `LiteralIgnoreAsciiCaseRule.cs`, `OneOfRule.cs`, `NoneOfRule.cs`, `AnyTokenRule.cs`, `ScanWhileRule.cs`, `ScanUntilRule.cs`, `WithinTokenRule.cs`, then up into the composite factories in `Rules.cs` that wire those leaves into pre-built grammars: `Integer()`, `Float()`, `EndOfLine()`, `InlineWhitespace()`, `AnyWhitespace()`, `Identifier()`.
    - Categories: composed-factory tree-shape leaks (leaf `FlattenType.Delete` defaults erasing user-visible match text), docstring-vs-implementation drift on factory output, asymmetry between sibling factories that solve the same problem one way vs another.
    - Cross-checked the existing `FloatRuleTests.cs` (the `fl0a` regression suite from search log `2026-05-05`) for whether anything pinned the tree-rendering of the sign. The Float tests only assert `Success` / failure for various sign permutations, never `ToString()` content, so they didn't cover the tree-shape side. No `IntegerRuleTests.cs` existed.
    - Found and fixed (`i1nt`): `Rules.Integer()` was `And(Optional(Or(Token('+'), Token('-'))), OneOrMore(OneOf(TokenSet.Digits)))`. `Token` has the default `FlattenType.Delete`, so the sign leaf was dropped during the parse-time flatten step. `Integer().Parse("-5").ToString()` returned `"5"` instead of `"-5"`. The named form (`Integer().As("number")` then `result.Find(...).ToString()`) had the same shape. `Symbol.SourceText` still returned the full `"-5"` (the recorded match span covers the sign), so the two accessors disagreed silently. The sibling `Float()` factory had the same problem and was fixed in `fl0a` (search log `2026-05-05`) by switching to `OneOf("+-").Flatten(FlattenType.Flatten)`. `Integer()` was overlooked.
    - Fix: replaced `Optional(Or(Token('+'), Token('-')))` with `Optional(OneOf("+-").Flatten(FlattenType.Flatten))` in `src/InductorParser/Rules.cs:638`, matching Float's shape. The `Flatten(Flatten)` override makes the sign leaf bubble up into the parent's child list. The docstring picked up a remarks line explaining that the sign is in the tree. Six regression tests in a new `src/InductorParser.Tests/Rules/IntegerRuleTests.cs`: three sanity (unsigned / negative / positive match) and three tree-shape (`ToString()` returns the full text on `"-5"`, `"+5"`, and the named `Find(rule).ToString()` on `"-42"`).
    - Adjacent shape (not pursued): the other composed factories in `Rules.cs` use Token / Literal leaves whose default `FlattenType.Delete` is exactly what the user wants (`EndOfLine()` discards the actual newline char, `InlineWhitespace()` discards the whitespace, `Identifier()` works through `WithinToken` which builds its own leaf). The factory-vs-tree shape only mismatches when the docstring promises an "is signed" or "includes ___" semantic AND the leaf carrying that semantic defaults to Delete. Added the pattern to `docs/PotentialBugSources/` so future composed-factory work asks the question.
