- 2026-06-02: TokenSet.Ascii.AnyWhitespace was missing VT (U+000B) and FF (U+000C), the two ASCII line terminators the rest of the library counts
    - Focus: "unusual/unexpected/invalid Unicode." Started from the Unicode built-ins in `TokenSet.cs` (the whitespace / line-terminator factories), then swept outward through the matching, normalization, and position surfaces.
    - Reviewed for behavioral correctness (all clean): `NormalizedPositionMap` (lockstep + per-grapheme walkers), `Symbol.SourceRange`/`SourceText` translation under FormC/D/KC/KD, `SourcePositionConverter.ToLineColumn`, `GraphemeClusterIndex`, `SurrogateHelpers`, `TokenSet` set-algebra + `ContainsToken` (lone-surrogate and multi-rune paths), `OneOfRule`/`NoneOfRule`/`ScanWhileRule`/`ScanUntilRule` (incl. escape-start normalization), `WithinTokenRule`, `GraphemeRule`, `LiteralRule`/`LiteralIgnoreAsciiCaseRule`, `Rules.Identifier` (XID start/continue + FormKC `WithCompatibilityEquivalents`), `TokenSet.Xid.cs`, `DisplayEscape`, `AnyTokenRule`, `BetweenInclusiveRule`.
    - Empirical fuzz campaigns (all passed, confirming robustness): adjacent-leaf SourceRange has no gaps/overlaps across all 5 forms, ScanWhile/ScanUntil consume identical text to per-token OneOf/NoneOf, Identifier start/continue acceptance matches XidStart/XidContinue, Identifier(FormKC) matches a from-scratch reference over compatibility chars, OneOf/NoneOf are strict complements on any non-EOF token, Token/AnyToken SourceText round-trips under every form, and line counting matches `EndOfLine()` acceptance.
    - Found and fixed: `TokenSet.Ascii.AnyWhitespace` was `InlineWhitespace | Single('\r') | Single('\n') | Graphemes("\r\n")` = `{SPACE, TAB, CR, LF, CRLF}`. Its doc called it "ASCII whitespace including line terminators" yet omitted VT (U+000B) and FF (U+000C), which `TokenSet.LineTerminators` / `IsLineTerminator` (UAX #18) treat as line terminators, `Rules.EndOfLine()` consumes, `ToLineColumn` counts as a line break, and the full-Unicode `TokenSet.AnyWhitespace` includes. That also broke the `Ascii.X == X ∩ ASCII` relationship its sibling honors (`Ascii.InlineWhitespace` *is* exactly `InlineWhitespace ∩ ASCII`). User impact: a grammar skipping whitespace with `Ascii.AnyWhitespace` silently fails to skip a form feed (a real page-break char in plain-text/source files) where the full set would. Fix: added VT and FF (as `Single('\v')` / `Single('\f')`) and rewrote the doc, dropping the inaccurate "(the regex \s convention)" aside (`\s` includes `\v`/`\f`, which the set didn't).
    - Regression test: `TokenSetTests.Ascii_AnyWhitespace_is_the_ascii_restriction_of_full_AnyWhitespace` (fails before the fix at U+000B). Updated `Ascii_AnyWhitespace_contains_space_tab_cr_lf` -> `Ascii_AnyWhitespace_contains_every_ascii_whitespace_char` to assert VT/FF are now in. Full `InductorParser.Tests` suite: 6965 pass, 2 pre-existing explicit Unicode-conformance skips, 0 fail.
