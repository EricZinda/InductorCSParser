- 2026-06-04: WithinToken's one-rune-per-token sub-lexer built a `GraphemeClusterIndex` it never queries, once per grapheme cluster (performance, not a correctness bug)
    - Focus this pass: the user asked for performance issues that hit real grammars rather than a correctness bug, starting from where the previous pass left off (the just-landed `TokenSet.ContainsRune` binary-search fix). Picked the recursive-engine per-token hot path again, this time following the allocation cost rather than the comparison cost. Random-ish start: the membership rules were already swept, so the trail led from `OneOfRule` into `WithinTokenRule` and the `Lexer` sub-lexer construction it drives, which is the per-cluster machinery behind `Rules.Identifier`.
    - Reviewed: `WithinTokenRule.cs`, `Lexer.cs` (the constructors, `BindInput`, `NextTokenLength`, `IsTokenBoundary`, `Read`), `Lexer.Scanning.cs`, `Lexing/GraphemeClusterIndex.cs`, `IdentifierRule.cs`, `OneOfRule.cs` / `NoneOfRule.cs` (membership / `_setRendered` caching), `Lexer.Tracing.cs` (confirmed the `Substring` interpolations in trace lines are deferred by `TraceInterpolatedStringHandler`, so they cost nothing when tracing is off), `SyntaxTree/SourcePositionConverter.cs` and `SourcePosition.cs` (line/column re-walk), and `TokenSet.cs` (`NormalizedFor` cache vs the uncached `WithCompatibilityEquivalents` ~130K-rune walk under FormKC/FormKD).
    - Categories checked: per-token / per-cluster allocations on the parse hot path, work computed at parse time that could be cached or skipped, and whether a sub-mode of a shared init path pays for state it never uses.
    - Found and fixed: `Lexer.BindInput` eagerly built the input's `GraphemeClusterIndex` (`GraphemeClusterIndex.For(input)`), allocating the index object, its `bool[input.Length+1]`, and a `ConditionalWeakTable` entry. WithinToken creates a fresh sub-lexer in `oneRunePerToken` mode for every outer grapheme cluster (so once per identifier character on the common `Identifier` path), each over a freshly-allocated `Substring`, so each sub-lexer constructed a brand-new index. But rune mode never queries cluster boundaries: `NextTokenLength` and `IsTokenBoundary` both branch to `RuneHelpers` when `_oneRunePerToken`, so that index was pure waste. Fix: make `_graphemeIndex` lazily resolved through a `GraphemeIndex` property (`_graphemeIndex ??= GraphemeClusterIndex.For(_input)`) instead of eager in `BindInput`. Rune-mode sub-lexers never touch it and never build it. Grapheme-mode lexers resolve it on first `Read` instead of at construction, same shared CWT-cached instance, no behavior change. (Left the deliberate `Substring` copy in `WithinTokenRule` alone: its comment defends it as robustness for user-defined inner rules that might bound a loop on `Input.Length`, so that's a design choice, not a bug.)
    - Measured (`GC.GetAllocatedBytesForCurrentThread`, Debug, parsing a 2000-char ASCII identifier, 100 iterations averaged). Before: 1,239,520 bytes/parse (619.8 bytes/char). After: 897,536 bytes/parse (448.8 bytes/char). ~342 KB (~28%) less allocation per parse, ~171 bytes/char of the per-cluster grapheme-index churn removed, scaling with identifier length.
    - Regression test (`WithinTokenRuleTests.Rune_mode_sublexer_builds_no_grapheme_cluster_index`): walks a 16-char one-rune-per-token lexer to EOF and asserts `GraphemeClusterIndex.HasCachedIndexFor(input)` is false (it was true before the fix, one index per sub-lexer), then confirms a grapheme-mode lexer still resolves its index on first read. Added the internal `GraphemeClusterIndex.HasCachedIndexFor` peek (non-mutating `ConditionalWeakTable.TryGetValue`) so the test can observe the cache without populating it.
    - Verification: identical semantics, so all existing parse / Identifier / WithinToken / grapheme tests pass unchanged. `dotnet test src/InductorParser.Tests/InductorParser.Tests.csproj` green under both engines (recursive 7158 passed, statemachine 7158 passed, 2 pre-skipped UCD tests), and `InductorParser.StateMachine.Tests` (108 passed) covers the `IsGraphemeClusterStart` scanner-skip path that now resolves the index lazily.
