    - Found and fixed: the scanner-skip fast paths (`Lexer.AdvanceUntilRuneIn` BMP `IndexOfAny` path, `AdvanceUntilLiteralCandidateIn` single-literal and `bmpFirstRunes` paths) re-validate every byte-level `IndexOf`/`IndexOfAny` landing through `IsAtMidGraphemeCluster`, which only ever consulted `GraphemeClusterIndex` (grapheme-cluster boundaries). In the WithinTokenRule one-rune-per-token sub-lexer the token unit is the rune, not the grapheme cluster, so the gate wrongly reported a mid-cluster rune (a combining mark, the second rune of decomposed e-acute) as a non-token-boundary. The vectorized fast path then skipped past it to end-of-input while the per-token slow path (and the rest of the one-rune lexer, which walks `NextTokenLength`) correctly stopped on it. Concretely, a one-rune sub-lexer over "e + combining acute" scanning for U+0301 returned `Position == 2` (EOF) on the `IndexOfAny` path and `Position == 1` on the slow path. That is a fast/slow divergence, and it breaks the documented invariant in `Lexer.FastPaths.cs` that exactly one path runs over the full candidate set either way. Fix: renamed the gate to `IsAtMidToken` and made it mode-aware. In one-rune mode a position is interior only when it is the trailing half of a surrogate pair (the IndexOf/IndexOfAny candidates are BMP non-surrogates, so it effectively never skips), and grapheme mode is unchanged. Regression test in `WithinTokenRuleTests.cs` (`Scanner_skip_in_one_rune_sublexer_does_not_skip_mid_cluster_runes`) builds the one-rune sub-lexer directly and asserts the two paths agree.
    - Masking note (why no prior sweep caught it and why it is not user-observable today): the only one-rune-mode lexer is the WithinTokenRule sub-lexer, which (a) discards the inner parse tree entirely, exposing one leaf for the outer cluster, and (b) only reaches the scanner-skip via the `ZeroOrMore(Or(real, AnyToken.Delete()))` shape, which consumes to end-of-input regardless of where the scanner jumps (the deleted fallback catches everything the scanner skipped). So WithinToken still succeeds and emits the same leaf whether the inner scan stopped on the combining mark or ran off the end. The bug is a real fast/slow invariant break and a latent correctness hazard (it would surface if WithinToken ever exposed inner structure, if another caller used one-rune mode, or if the inner shape stopped consuming to EOF), but it has no current public-API-visible effect. Verified by parsing the WithinToken grammar with the scanner on (no trace) and off (`TraceSink` set) and confirming identical output.
