    - Categories: error-message helpfulness on surrogate-bearing literals during Compile, ASCII-letter cast truncation on supplementary-plane runes in the case-insensitive lookahead set, debug-output rendering of leaves containing quote / newline characters, `SourcePositionConverter.ToLineColumn` behavior on bare-CR and CRLF boundary positions, `GraphemeClusterIndex` cache behavior on empty input, propagation of mixed-case-sensitivity through `AllOfRule.ComputeConcatenableText`.
    - Found and filed (n4kp): `Rule.CollectNormalizationOffenders` calls `expected.Normalize(form)` on every literal-bearing rule's expected text without first checking for stray surrogates, so a grammar like `Token("\uD800")` or `Literal("\uD800X")` compiled with the default FormC gets .NET's runtime-generic `ArgumentException` (".NET 8: 'String contains invalid Unicode code points'") leaking out of Compile, instead of the multi-rule `BuildNormalizationErrorMessage` shape Compile uses for ordinary form mismatches. Reproduced with three failing tests; stack trace pointed at `Rule.cs:1106`. The grammar author has no way to tell that the issue is a stray surrogate or that `Compile(null)` is the documented path (called out for `Rules.Token(string)` and the existing `Literal_with_lone_surrogate_first_char_compiles_under_null_normalization` fixture).
    - Other findings deferred as not-real-bugs: `LiteralIgnoreAsciiCaseRule.ComputeRuleStart`'s `IsAsciiLetter((char)first)` truncates supplementary-plane runes (low 16 bits of U+10041 == 'A'), producing a SUPERSET FirstConsumedTokens that's documented as safe (perf only, no correctness impact since the parse-time `AsciiCaseEquals` does bit-exact compare on non-letter positions). `AllOfRule.ComputeConcatenableText` propagates `IgnoreCase |= ...` across mixed-case-sensitivity child runs (the prefilter literal becomes case-insensitive even though some of its parts are case-sensitive), but the prefilter is a SAFE OVERACCEPT (the real parse rejects mismatches), so it's perf only too.
