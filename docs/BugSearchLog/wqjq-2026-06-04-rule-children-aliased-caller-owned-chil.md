- 2026-06-04: `Rule.Children` aliased caller-owned child arrays, letting compiled grammars mutate after sealing
    - Random start: picked `228738`, so `228738 mod 29 = 15` over the 29 top-level `src/InductorParser/` files, landing on `OrRule.cs`. Read `OrRule` side-by-side with `AndRule`, `BetweenInclusiveRule`, the shared `Rule.TryParse` / `ParseChild` / `ValidateChildren` plumbing, `Rules.cs` factory forwarding, `Lexer.RecordCompositeFailure`, and the existing `OrRuleTests`, `AndRuleTests`, and `BetweenInclusiveRuleTests` coverage around child collection, rollback, source spans, and error anchoring.
    - Found and fixed: `Rule.ValidateChildren` validated the `Rule[]` but returned that same caller-owned array as the public `IReadOnlyList<Rule> Children`. A caller who wrote `var children = new[] { Token('a'), Token('b') }; var rule = Or(children); rule.Compile(); children[0] = Token('z');` could change the already-compiled grammar, bypassing every `ThrowIfSealed` mutation check. Fix: after validating the array, `ValidateChildren` now returns a defensive copy for non-empty child lists while keeping the shared `NoChildren` instance for empty leaf-rule lists.
    - Regression: added `OrRuleTests.Or_copies_children_array_so_compiled_rule_stays_immutable`. Verified it failed before the fix (`Parse failed at offset 0: unexpected 'a'`) and passed after.
