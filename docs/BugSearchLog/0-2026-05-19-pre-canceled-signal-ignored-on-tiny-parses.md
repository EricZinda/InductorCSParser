- 2026-05-19: Pre-canceled ParseCancellation ignored on parses too short to reach the periodic check
    - Directed start (not random): the backlog item asked to focus on the cancellation and budgets code. Read `src/InductorParser/ParseCancellation.cs`, `src/InductorParser/ParseOptions.cs`, `src/InductorParser/ParseOutcome.cs`, `src/InductorParser/Lexing/ParseBudgetExceeded.cs`, and the budget-bearing portions of `src/InductorParser/Lexing/Lexer.cs` (ConfigureBudgets / EnterRule / EnterRuleAtDepth / TickPeriodicBudget / CheckPeriodicBudgets) plus the parse-driver + catch handler in `src/InductorParser/Rule.cs` (ParseRecursive, BuildBudgetMessage, the public Parse dispatcher).     - Categories checked: pre-set / pre-elapsed budget state never visible to the periodic check, the 1024-invocation interval as an overshoot vs as a complete miss, the rolled-back-Position vs DeepestFailure choice in the catch path, ConfigureBudgets reset-vs-leak across pooled Lexer reuse, the null-Cancellation NRE check, the public Rule.Parse dispatcher vs the recursive ParseRecursive vs the StateMachineParser entry points (recursive engine, state machine engine, and Rule.Parse routing them).
    - Found and fixed: the periodic budget check fires only at 1024-invocation boundaries (`(_ruleInvocations & BudgetCheckMask) == 0` after the `_ruleInvocations++` in EnterRule). For a parse that completes in fewer invocations (e.g. `Token('a').Parse("a")`) the check never runs at all. With a pre-canceled ParseCancellation, that means the explicit cancel-before-parse signal is silently dropped and Parse returns Success, which contradicts ParseCancellation.cs's own doc claim ("On the next check after Cancel() fires, the parse aborts with ParseOutcome.Canceled"). Existing budget tests masked this because every cancellation / timeout test parses a 5000-char input chosen precisely to push past the first periodic check. Fix in `src/InductorParser/Rule.cs`: the public `Parse(string, ParseOptions)` dispatcher now does a pre-flight `options.Cancellation?.IsCanceled` check and returns `ParseResult.Aborted(ParseOutcome.Canceled, ...)` before dispatching to either engine. Both the recursive engine and the state machine engine inherit the fix because both go through the same public dispatcher. Test added to BudgetTests.cs (`Pre_canceled_signal_aborts_even_on_tiny_parses`) parsing `Token('a')` against `"a"` with a pre-canceled signal. Pre-fix it returned Success. Post-fix it returns Canceled with the templated cancellation message.
    - Pattern: docs/PotentialBugSources/0-2026-05-19-periodic-check-misses-initial-budget-state.md (the broader category, "a periodic / interval-gated poll never observes state set before the first interval fires").
    - Cleared: ParseCancellation.cs (no time-based API, correct volatile flag, correct null-check semantics inside CheckPeriodicBudgets). ConfigureBudgets / ResetForReuse pair cleanly zero out _ruleInvocations / _ruleDepth / _stopwatch / _cancellation so pooled lexers can't leak budget state between parses. EnterRule's depth check fires on every call (not gated by the 1024 mask), so MaxDepth doesn't have the same gap. The catch in ParseRecursive uses the `Math.Max(DeepestFailure, Position)` idiom correctly (Position is rolled back by transactions, DeepestFailure is the high-water mark). The 1024-invocation overshoot for RuleCountLimit is documented and intentional (predictable trip point + invocation-count determinism).
    - Not a bug, considered: a small RuleCountLimit (say 1) is also "ignored" on a 1-invocation parse, but a count-based limit can't trip below its own value, so there's no surprise. A pre-elapsed Timeout (`TimeSpan.FromTicks(1)` on a parse that finishes in nanoseconds) is the same shape as pre-cancellation but a much rarer real scenario: the Stopwatch starts at ConfigureBudgets and there's no externally-controlled "already elapsed" state, only a tiny window between ConfigureBudgets and the first invocation.
